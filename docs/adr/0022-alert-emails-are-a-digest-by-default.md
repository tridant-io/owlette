# Alert emails are a digest by default

From this change every site alert email (machines offline, asleep and awake, agent errors, reboot pending, process crashes, threshold breaches, display events and hoot escalations) reaches each person as one digest a day at 08:00 in their timezone, unless they choose an hourly or weekly digest or each alert as it happens (`users/{uid}.preferences.alertDelivery`, absent means `daily`, so there is no backfill). The owner asked for it because the volume came from repeats: an outage re-alerts every hour, a threshold rule may have no cooldown, and a Mac sends two emails per sleep. We chose one setting per person, which follows the ruling that built-in alerts are each person's own emails from every site, over a cadence per alert type, which is a matrix nobody asked for. We chose to queue each alert per recipient (`alert_digests/{uid}/digest_events`) over one log per site, because a site log still needs a due marker per person and a way to skip people already mailed. The cost is speed: an offline machine is reported the next morning unless the person switches to "as it happens", and the owner accepted that with no class kept immediate by default.

## Consequences

- Talon email outputs and API key expiry notices always arrive as they happen, and so does the `ADMIN_EMAIL` fallback, which has no person to hold a preference. Webhooks, talon taps and autonomous hoot are never delayed: they fire before or apart from email.
- Who may receive a queued alert is decided again at send time (`partitionRows`): an opt-out, a mute, a removal, a narrowed scope or a paused site drops it, and a recipient list that came from a failed read holds it for the next run.
- `GET /api/cron/alert-digest` must run every 15 minutes in each environment. Each period is claimed in a transaction, rendered once and stored on the claim, and sent under the Resend idempotency key `alert-digest/<uid>/<periodKey>`, which advances once anything may have gone out under it, so a double run, a load-balancer retry or a resumed dead run sends one email. A period that sent nothing keeps its key, so rows held by a failed recipient read retry on the next run.
- Senders queue only while the job is running (`global/alert_digest.lastRunAt` within 45 minutes); before its first run and after it stops, each alert is emailed as it happens. The `alert_delivery` status component degrades when a digest is queued and the job is stale or has never run. A queued row lives at most 14 days (a TTL on `digest_events.deleteAt`).
- Rolling back means reverting the send sites first, so nothing new queues, and leaving the job running a day so every queue drains.
- People learn of the change from a note in their first digest and the changelog, with no separate notice email. The unsubscribe page offers "weekly digest instead" beside turning alert emails off.
