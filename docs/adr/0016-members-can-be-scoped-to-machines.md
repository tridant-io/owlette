# A member can be limited to machines, and only whole-site members reach anything site-wide

Giving one person on another owlette account control of a single machine meant moving that machine to a site of its own, because a member row reached every machine of its site. From 4.1.29 a member row may carry `machineIds`, 1–30 machines of the site: its machine scope. With one, the person reaches only those machines, at their site role, with their swoop mode applying there and nowhere else, and reaches nothing site-wide whatever their role. Without one, the row is whole site, so every existing row is unchanged. Three layers enforce the scope, and each fails closed: the rules, where a block under one machine takes `canAccessMachine`, a block that spans machines takes `canAccessWholeSite`, and `isSiteAdmin` needs a whole-site row; the server, where `resolveSiteAccess`'s facts carry the scope, the one builder `siteStanding` puts it on every actor, the wrapper checks it before the `capability_enforcement` switch so turning enforcement off never widens a scope, the `_shared` gates refuse a scoped caller unless the route opts in, and `hasCapability` decides by the role matrix, then the swoop mode, then the scope; and the dashboard, which queries exactly the listed machines, because rules are not filters. Moving a machine between sites is out: fielded agents cannot follow a move made on the server, since their tokens carry one site.

## Consequences

- `canAccessSite` admits scoped members, so it is reserved for the site document, the swoop, display and hoot settings (`settings/{swoop,display,cortex}`), and the schedule and reboot presets. A new block written with it hands every scoped member the whole collection.
- A machine outside the scope answers 404 'machine not found or no access', as a machine that does not exist does. A site-wide route or capability answers a scoped caller 403, kill, kick and the site's swoop sessions list included.
- `[]` reaches nothing, and neither does a value that is not a list. Widening is `PATCH {machineIds: null}`, which deletes the field, never `[]`. An owner's row and your own row cannot be scoped.
- The 30-machine cap comes from Firestore's `in` limit: the dashboard lists a scope with one `documentId() in` query.
- Rollback order: remove the scoped members first, because code from before 4.1.29 ignores `machineIds` and widens them to the whole site; then the web; then the rules. While a scoped row exists, never redeploy an older Railway deployment or let the Vercel standby serve older code.
- Site logs are filtered by `machineId`. Autonomous hoot chats stay whole site. Alert emails reach a scoped member only for their machines.
- Removing a machine, or pairing a machine whose document had gone, drops its id from every member's scope, so a reused machine id never inherits an old grant.
- Narrowing someone's scope ends every swoop session they sit in on a machine it drops, as removing them or taking their swoop does: the whole session ends within about 2 s, and everyone else in it reconnects on their own and is decided again.
- Fielded agents are untouched: the agent terms in the rules are unchanged (ADR 0001).
