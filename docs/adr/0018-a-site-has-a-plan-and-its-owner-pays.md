# A site has a plan, and its owner pays

owlette's first plan gates (on dev since october 2026, dormant) read one plan per account: the site owner's, applied to every site they own. tridant id, which sells owlette, bills per site instead: each site is one line on its payer's monthly invoice, active machines times that site's tier price, and a site can be free, core or pro on its own. So from 4.2.0 the plan belongs to the site. The server reads it from tridant id per site (`GET /v1/sites/owlette:{siteId}/entitlements`), every gate asks about the site it acts on, and tridant id stays the only source of truth: owlette holds no Stripe key and keeps only a pointer on the site document for the UI. The payer is always the site's owner, and only the owner can change the site's billing, although tridant id would let any organization pay for any site; a payer who is not the owner is a case nobody has asked for, and it would need its own consent and transfer rules. What tridant id cannot count is owlette free, which is per account: an account's free sites are at most one, holding at most one machine between them, and owlette counts that itself from the sites the account owns. The 14-day trial is tridant id's, one per organization, and covers every site the owner has registered there.

## Consequences

- Anything that asks "is this allowed on this plan" takes a site id, never a user id. `resolveSitePlan` and `requireEntitlement` are the two ways in; a per-user plan check is a bug.
- A plan refusal is 402. It is never 401 or 403 on an agent route: fielded agents delete their tokens when a refresh is refused.
- When tridant id cannot be reached, or answers something unreadable, the site is unrestricted. A site tridant id does not know is free. An expired or wrong api key therefore turns every gate off quietly, which is why the client logs `rejected` and `Sunset` at error.
- A site in a trial or a paid period never counts toward the free limits, so a trial that ends can leave an account over them. Nothing is unpaired or deleted: new pairings and new sites are refused, and the machines beyond the first show the upgrade notice.
- Transferring a site stops its billing at the period end, and the new owner upgrades again. Deleting a site stops its billing first. Deleting an account unlinks it from its tridant organization.
- Usage is reported once a day, late in the UTC day, and tridant id bills what it holds when the month ends. A report that arrives after the 1st counts for nothing, so the last run of a month is the one that bills.
- `SITE_BILLING_MANAGE` is the owner's alone and is checked even while `capability_enforcement` is off: the switch fails toward availability, and letting a member put sites on the owner's card is not availability.
- An account whose email already has a tridant organization is never joined to it by email. The owner signs in to tridant id and the fresh ID token is the consent (`POST /v1/billing/link`).
- Everything stays behind `PLAN_ENFORCEMENT`. Rollback is turning it off; nothing a customer paid for is lost, because tridant id holds it.
