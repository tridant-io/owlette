# A hoot call that changes what a machine launches always asks a person

hoot's tier-2 tools could point a process at another program, schedule one to run as SYSTEM or set one to run when a service fails, with no approval card, on every path including unattended ones, so a prompt injection could get code run on a machine. The owner's ruling: approval is required, always. The check is on the server where tools are dispatched, not in the prompt or the UI, and it classifies by call rather than by tier, because one tool can both read and launch; a field or action nobody has classified needs a person. A script can't be read for what it launches, so the tools that run code always ask too. We chose per-call classification with a server-side record of each card over moving these tools to tier 3, because the site's tier-3 setting can turn tier 3 off and "always" has to mean always.

## Consequences

- **What asks:** any `update_process` field but `name`, `priority` and `visibility` (`time_delay`, `time_to_init` and `relaunch_attempts` decide when a crash relaunch happens and when it becomes a reboot); `add_process`, `delete_process`, `set_launch_mode`; `manage_scheduled_task` but `list`, `get_details`, `get_history`, `stop`; `manage_windows_service` `set_startup`, `set_recovery`; `manage_windows_feature` but `list`; `manage_windows_update` `set_scheduled_install`; `registry_operation` but `read`; a talon with a `command` output or `allowActions`, and arming one; `run_command`, `run_powershell`, `run_python`, `execute_script`, `write_file`, `deploy_software`; and any tool nobody has classified, with a test that holds every tool in `mcp-tools.ts` to a class.
- **What doesn't:** `start_process`, `restart_process` and `kill_process` run or stop what is already configured, and unattended recovery depends on them. A person chose that target, so they stay free. The site's tier-3 setting now governs only reboot, shutdown and file reads, and whether a public conversation may go to local hoot.
- **Where nobody can answer, it doesn't run.** A dashboard chat and a follow-up show a card; a talon, autonomous hoot and the public conversations API refuse. Autonomous hoot also refuses the tools that run code at any `maxTier`, and autonomous hoot, talons and follow-ups aren't offered `manage_scheduled_task`, `manage_windows_service`, `registry_operation` or the talon-writing tools at all, read actions included. A talon with let hoot act can no longer restart a Windows service.
- **An approval is the server's, exact, and spent once.** ai 7 honours `approval` on a tool part in any state, pairs answers to calls by approval id across parts, re-runs `needsApproval` on what a client sent, and resumes on input the browser sends back. So a card is a record: `chats/{chatId}/approvalRequests/{toolCallId}`, holding tool, machines and input hash, written only when the model's own call raises it, never for a call id that arrived in incoming messages. The runner strips `approval` from every incoming part except a boolean answer in `approval-responded` on a call with a record, and refuses shared call and approval ids. Dispatch runs an approved call only if it matches the record, the record is under 24 hours old, and this turn holds the one atomic claim in `chats/{chatId}/approvals`. The day covers coming back to a follow-up that fired overnight; a later answer just makes hoot ask again. The SDK's `experimental_toolApprovalSecret` isn't used: this record also binds the machines, and the signature would have to round-trip through the client.
- **An approved change that can't be recorded isn't made.** It writes a blocking `allow` row with old and new values first, as unattended calls already do, so a Firestore outage stops launch changes rather than losing the record of who approved them. Lists of secret shapes kept leaking, so only names and settings as single values, and bare paths, go in as they are; free-form values are a keyed hash and a length, keyed with `CORTEX_INTERNAL_SECRET` because site admins read these rows and a plain hash gives up a short value to a few thousand guesses. With no key, no hash is written; the row and the change still stand. A path followed by a bare secret with no flag would still read as a path.
- **The fielded half lives on the server.** A fielded agent can't be changed from here and is a client of whatever the server sends, so the gate, the refusal of Winlogon and service values, and the secret filter on registry reads all run on the web side. The registry rules also live on the agent, for the `/commands` route; both copies are tested on `agent/tests/fixtures/registry_refusals.json`. Both refuse a key path with anything outside printable ASCII, because JS `trim` and Python `strip` disagree on whitespace. Under a service's `Parameters` key, value names outside the denylist (`Cmd`, `Arguments`, `Run`, `Bin`, `Target`) still pass both copies, behind a card, unless their data looks like a program: no list of names can be complete for third-party services.
- **Local hoot has no approval flow, so it has no such tools** from 4.2.0, and the server sends a conversation only to an agent with `capabilities.localHootLaunchGate` on 4.2.0 or later. An older agent's own crash-event loop (`cortex.autonomousEnabled`) can't be gated from the server until it updates, though that setting can be turned off through its config document.
- This covers hoot only. The dashboard's own process editing and direct API calls are a person or a key acting deliberately, not a model. Two paths overlap, and both treat a launch change as tier 3. A tool call through the commands route needs a key with `maxToolTier` 3 or a person with an open step-up window. A sender's call (ADR 0017) needs a grant of tier 3, because an admin set that grant deliberately, as with a key; it also checks parameters before any tool runs.
