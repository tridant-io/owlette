# A machine moves to another site when its agent confirms

From 4.2.3 a superadmin, or anyone who is owner or admin of both sites, moves a paired machine to another site from the admin panel, with nobody at the machine. The server can't do it alone: a machine's site lives in its own `config.json` (`firebase.site_id`) and token store, which nothing remote rewrites, so a machine rebound on the server keeps writing to its old site, is refused on every write, and never unpairs; and cleaning the old site first makes removal detection (#326) see its config document vanish and unpair it. So the agent does the move and the server only cleans up after it: the request stores a pending move in `machine_moves/{sourceSiteId}:{machineId}` and queues a `site_move` command; the agent fetches the new site's tokens with the refresh token it holds for the old one (`POST /api/agent/auth/move`), ends hoot and its fleet session, writes the tokens and the move into `.tokens.enc` in one write and the site into `config.json`, reconnects on the new site and confirms from there (`POST /api/agent/auth/move/confirm`); only that confirm removes the old site's copy, exactly as remove machine does. We chose this over rebinding on the server, which strands every fielded agent, and over pairing it again at the machine with a pre-authorized phrase, which needs someone there. It amends ADR 0016's last sentence: a machine can move between sites when its agent can follow the move.

## Consequences

- Only an agent that says it can follow is moved: the request answers `409 agent_too_old` unless the heartbeat carries `capabilities.siteMove: 1` and `agent_version` is 4.2.3 or later. An older machine is updated first, or leaves and joins at the machine. There is no installer half: a move is refused while an update is queued, and the move lives in `.tokens.enc`, which the installer never touches.
- The move's record is server-only, never a field on the machine document, which the agent can write. Both channels to the agent, the command and `move` on `GET /api/agent/site`, carry only the move's ID; tokens come only from the agent route, for the refresh token of the old site and the same machine. A move that is not the caller's answers 404 there, never 401 or 403, because a fielded agent reads either on an auth route as a revoked token.
- The old site's refresh token stays valid until the confirm, so a move cut short leaves the machine where it was, and a client still bound to the old site does not unpair while its config names another. A pending move lapses after 7 days. A `switching` move never does, because the agent already holds the new site's tokens and expiring it would cut them off; removing the machine from the old site is the way out.
- hoot ends before the new tokens are written, so its last write on the old site's token can't put the machine back there after the cleanup.
- History doesn't move. The old site's copy goes as remove machine's does: member scopes and hoot mcp grants naming it are pruned, talons are left as remove leaves them.
- Refused as well: API keys (a key reaches one site, a move two), a same-ID machine on the new site, the new site's plan limit, and a machine with an install, uninstall, update or roost sync queued or a deployment in flight. No path raises a prompt on any platform (ADR 0005).
