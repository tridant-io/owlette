# The agent refuses reboots, shutdowns and deployments inside active hours

hoot knew nothing of a machine's active hours, and one machine rebooted on its own after hoot had agreed to stop that. A check in the web app or in hoot's prompt would miss the API, the CLI and every path added later, so the agent enforces it when it runs the command. On Windows, before `reboot_machine`, `shutdown_machine` or `install_software`, the agent reads the active hours in force from the registry and compares them with the machine's own clock. Inside the window it fails the command with `Error: active_hours: …`, naming the window and when it ends. Only an `activeHoursOverride` on the command lets it through, and only the server sets one. Clients cannot write commands, every server path that builds a command strips the override names from params a client or a model supplied, and the server adds the field only for a call a person approved: a dashboard confirm with a reason, an API call that sends an explicit override with a reason, or a dashboard hoot tool call on a single machine that went through the in-chat approval of tool tier 3, which an override forces even on a site that turned that approval off. Nothing that runs without a person can override: autonomous hoot, talons, follow-ups and the public conversations API can only defer a reboot to the end of the window, and local hoot has no reboot, shutdown or deployment tool at all. Rollouts and fleet updates are not guarded. A rollout's `sync_pull` restarts nothing, and each refusal would count toward its canary abort. A fleet update reboots no machine, and the old agent that runs it has no guard, so the first guarded release could not guard its own install (ADR 0006).

## Consequences

- Windows always has active hours: 8–17 when nobody set any. From the first guarded release, daytime API and CLI scripts that reboot, shut down or send a deployment are refused until they pass `active_hours_override` with a reason. That breaks API users, so the changelog and the docs call it out.
- A machine is protected only once it runs a guarded release. An old agent ignores the window and the override, so the dashboard keys its active-hours wording on `capabilities.activeHoursGuard`.
- Every override is logged with who approved it and why.
- The guard covers the dedicated commands, not the shell. hoot's `execute_script` and `run_powershell`, and local hoot's shell tools, can still run `shutdown /r` or an installer; only a prompt rule stands in the way: dashboard hoot's, and local hoot's in `agent/CLAUDE.md`.
- owlette's own crash-loop reboot inside the window waits for the window to end. The weekly reboot schedule is left alone, because a person chose its time.
- owlette never writes `NoAutoRebootWithLoggedOnUsers`. Microsoft lists it under legacy policies on Windows 11, field reports say it is ignored there, and while it is on, Windows ignores policy active hours.
- hoot stops Windows' own update restarts by limiting them to outside active hours (`limit_auto_restart`, the default: active hours by policy and no restart deadline). Only when someone explicitly asks for no update restarts at all does it turn off automatic installs (`disable_auto_install`), after saying that security updates then wait for a person.
