## 0. What this proves, and what it cannot

plan.md D2 puts the streamer in the console session as SYSTEM, spawned by the service over inherited
anonymous pipes. Six primitives hold that up. This spike exercises all six, but **three of them — (1) the
session retarget, (4) reaching `Winlogon`, (5) `SendSAS` — cannot even be attempted without SYSTEM, and that
is the point**, so the unelevated pass below is a floor, not an answer. Primitive (2)'s *mechanism* does not
depend on privilege; the child's identity does.

answer does not depend on who is running — see §5, which is the spike's headline finding.

## 2. How to run it as SYSTEM, non-destructively

The harness cannot elevate and must not. It is put into a SYSTEM context by a temporary scheduled task the
human registers from a console **they** elevated by clicking — the `owlette_service.py:5247-5313` pattern,
minus the recovery watchdog.

**Nothing in this procedure stops a service, writes into `C:\ProgramData\Owlette`, or puts a secret on a
command line.** The only argument is a subcommand and two paths.

### 2.1 Once, from an ordinary shell

```powershell
cd C:\Users\admin\Documents\Git-restored\Owlette\agent\swoop\spikes\securedesk
cargo build --release
mkdir C:\swoop03
```

`C:\swoop03` is a scratch directory of the human's choosing, outside the repo and outside the Owlette install
tree. Everything the SYSTEM run produces lands there, because a task running as SYSTEM has no console.

### 2.2 The runner script

A SYSTEM task has nowhere to print, and `schtasks /TR` quoting is its own kind of trap, so the command goes
in a one-line `.cmd` instead. Write `C:\swoop03\run.cmd`:

```bat
@echo off
set R=C:\Users\admin\Documents\Git-restored\Owlette
"%R%\agent\.venv\Scripts\python.exe" "%R%\agent\swoop\spikes\spawn-py\spawn_spike.py" %* 1>>C:\swoop03\out.txt 2>&1
```

### 2.3 Register, run, delete — from an elevated **cmd.exe**

One primitive per run, so a failure is attributable. This block is cmd syntax (`::` comments, `^`
continuation); in PowerShell drop the comments and put each `schtasks` on one line.

```bat
:: 1. register
schtasks /Create /TN Swoop03 /TR "C:\swoop03\run.cmd spawn --json C:\swoop03\spawn.json" ^
         /SC ONCE /ST 00:00 /RU SYSTEM /RL HIGHEST /F

:: 2. run, and watch C:\swoop03\out.txt from another window
schtasks /Run /TN Swoop03

:: 3. re-register with the next subcommand (/F overwrites) and run again
schtasks /Create /TN Swoop03 /TR "C:\swoop03\run.cmd leak    --json C:\swoop03\leak.json"    /SC ONCE /ST 00:00 /RU SYSTEM /RL HIGHEST /F
schtasks /Create /TN Swoop03 /TR "C:\swoop03\run.cmd job     --json C:\swoop03\job.json"     /SC ONCE /ST 00:00 /RU SYSTEM /RL HIGHEST /F
schtasks /Create /TN Swoop03 /TR "C:\swoop03\run.cmd inject  --json C:\swoop03\inject.json"  /SC ONCE /ST 00:00 /RU SYSTEM /RL HIGHEST /F
schtasks /Create /TN Swoop03 /TR "C:\swoop03\run.cmd desktop --seconds 180 --json C:\swoop03\desk.json" /SC ONCE /ST 00:00 /RU SYSTEM /RL HIGHEST /F
schtasks /Create /TN Swoop03 /TR "C:\swoop03\run.cmd sas     --json C:\swoop03\sas.json"     /SC ONCE /ST 00:00 /RU SYSTEM /RL HIGHEST /F

:: 4. when every run is done
schtasks /Delete /TN Swoop03 /F
schtasks /Query  /TN Swoop03
```

From a second window, live:

```powershell
Get-Content C:\swoop03\out.txt -Wait
```

### 2.4 What the human does during each run

- `spawn`, `leak`, `job` — nothing. They finish in under a second.
- `inject` — nothing, but **the pointer will jump 40 px and come back, and a left shift is pressed and
  released**. Have a text editor focused if you want to see that shift alone types nothing.
- `desktop --seconds 180` — this is the one that needs hands. Start it, then in order: **lock (Win+L)**,
  wait for a frame line, **unlock**, raise a **real UAC prompt** (right-click any installer → run as
  administrator, then *cancel* it), and let it finish. Each of the three is a separate `desk_switch` →
  `desk_lost` → `desk_rebuilt` → `desk_recovered` group in `out.txt`.
- **logon screen**: sign out (or reboot) with nobody logged in, then run `desktop` again from the elevated
  console *after* signing back in only if the task can be started remotely — otherwise register the task to
  run at startup for this one case and read `out.txt` afterwards.
- `sas` — **watch the screen.** A working `SendSAS(FALSE)` puts the Ctrl+Alt+Del security options screen up.
  Dismiss it with Escape.

## 4. Primitive (2a) — `CreateProcessAsUser`, `lpDesktop`, pipes, and the round trip

`CreateProcessAsUserW` with `lpDesktop = WinSta0\Default`, `bInheritHandles = TRUE`,
`STARTF_USESTDHANDLES`, `CREATE_SUSPENDED | CREATE_NO_WINDOW | CREATE_UNICODE_ENVIRONMENT |
EXTENDED_STARTUPINFO_PRESENT`, the child resumed only after it is in the job.

The wire is `PROTOCOL.md` §6's, kept deliberately: **stdin line 1 is the bundle**, one json object on one
line; stdout is json lines. The spike's bundle is `bundle-valid.json`'s shape with obviously fake values plus
one extra field, `spikeCanary` (§5). It is written once, wiped from the harness's buffer after the write, and
**never printed** — only its length is. The child reads exactly two fields out of it and reports the length
back, which is what says the whole line arrived.

## 5. Primitive (2b) — **the handle list. This is the finding.**

### 5.1 pywin32 cannot express `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, at all

`agent/src/swoop_spawn.py:441` does this:

```python
try:
    si.lpAttributeList = {'handle_list': list(child_handles)}
except Exception as e:
    logger.warning('swoop: handle list unavailable, relying on flags: %s', e)
```

and on this box logs *"handle list unavailable, relying on flags: 'PySTARTUPINFO' object has no attribute
'lpAttributeList'"* on every spawn. The comment above it guesses "older pywin32". **That guess is wrong, and
this is not a version problem.** Measured three ways:

1. `win32process.STARTUPINFO()` exposes exactly nine attributes — `dwFillAttribute`, `dwFlags`, `dwX`,
   `dwXCountChars`, `dwXSize`, `dwY`, `dwYCountChars`, `dwYSize`, `wShowWindow`. No `lpAttributeList`, and
   `PySTARTUPINFO` is a C type with a fixed member table, so the assignment cannot be made to stick.
2. A byte scan of every `.py`, `.pyd` and `.dll` under the agent venv's `site-packages` for
   `lpAttributeList`, `STARTUPINFOEX`, `ProcThreadAttribute` and `UpdateProcThreadAttribute` returns **zero
   hits in any file**. pywin32 312 does not bind the API anywhere, under any name.
3. `spawn_spike.py preflight` runs the probe live: `pywin32 312 … expressible: False — AttributeError:
   'PySTARTUPINFO' object has no attribute 'lpAttributeList'`.

So the `except` branch in `swoop_spawn.py` is not a fallback for old installs. **It is the only branch that
ever runs**, and the product's handle-list restriction is not in force today.

CPython's own `subprocess.STARTUPINFO` *does* take `lpAttributeList={'handle_list': …}` — but it reaches
`CreateProcessW`, not `CreateProcessAsUserW`, so it cannot be combined with a token and is no help here.

### 5.2 ctypes can, and does

`spawn-py/winapi.py` drives `InitializeProcThreadAttributeList` → `UpdateProcThreadAttribute` →
`CreateProcessAsUserW` with a real `STARTUPINFOEXW` and `EXTENDED_STARTUPINFO_PRESENT`. It works, first try,
unelevated. The one trap worth writing down: the `HANDLE` array must outlive the `CreateProcess*` call — the
attribute list stores a pointer to it, not a copy — which is why `AttributeList` is an object that owns the
array and not a function that builds one.

### 5.3 What the fallback actually leaks — measured, not argued

The child counts its own inherited handles. The discriminator is exact: `CreateProcess` copies
`HANDLE_FLAG_INHERIT` along with an inherited handle, and a handle the child opens for itself does not carry
it, so valid handle values with that flag set **are** what the parent handed over. A second check rides along
— the harness creates one extra inheritable, already-signalled event, deliberately leaves it *out* of the
list, and tells the child its numeric value in the bundle line (a handle value is not a secret).

| arm | handle list | inherited handles in the child | canary |
|---|---|---|---|
| `spawn` (n = 10) | **on**, 2 entries | **2**, in 10 of 10 | `absent` or `absent_value_reused` — not inherited |
| `leak` (n = 1) | **off** (`lpAttributeList = NULL`) | **25** of 117 handles held | **`inherited`** |

Handle values are per-process, so the canary's number is sometimes free in the child and sometimes already
taken by something the child opened itself: `absent` and `absent_value_reused` are both passes and the child
tells them apart by the inherit flag. Only `inherited` is a leak.

The 25, by kind: **14 file handles, 5 console/char handles, 3 pipes, 3 other kernel objects** (one of them
the canary event). Of those 25, exactly 2 were meant to cross.

Two things this says and one it does not:

- **It says the restriction works and the fallback does not.** Two versus twenty-five is the whole argument
  for doing primitive (2) through ctypes.
- **It says the count is a property of the parent, not of the child.** The 25 is what a python process with
  an open console and a handful of open files hands over; the service's number will differ. What does not
  differ is the shape: with `bInheritHandles = TRUE` and no list, the child gets *every* inheritable handle
  the parent holds **at the instant of the call**, which in a process with a 5-second loop and worker threads
  includes whatever another thread happened to open inheritably a microsecond earlier. That race is precisely
  what the attribute list exists to close, and it is not closable by "only making the right handles
  inheritable" in a multi-threaded parent.
- It does **not** say anything has been exploited. swoop is unreleased, this is a pre-release gap in a branch,
  and the fix is a code change in Task 2.1, not an incident.

`spawn_spike.py` also demonstrates that `EXTENDED_STARTUPINFO_PRESENT` with a NULL attribute list behaves
exactly like a plain `STARTUPINFO`, which is why the `leak` arm is a faithful model of today's product path
and not a strawman.

**[x] 5.2** as SYSTEM, `leak` arm: `handlesInherited` — **11** of 103 total , canary verdict — **inherited** , kinds — **4 char, 4 file, 2 pipe, 1 other**. This is what ships today, because pywin32 cannot express the handle list at any version.

## 7. Primitive (4) — capture and injection across Default ↔ Winlogon

### 7.1 Capture: follow the input desktop, rebuild after `DXGI_ERROR_ACCESS_LOST`

`securedesk/src/desk.rs` runs on a **dedicated thread** — `SetThreadDesktop` refuses a thread that owns a
window, a timer or a hook, and a desktop association belongs to the thread that made it. Loop:
`OpenInputDesktop` → compare the name → `SetThreadDesktop` only when it changed → drop the duplication →
rebuild the D3D11 device and `DuplicateOutput` → `AcquireNextFrame(8 ms)`.

The clock reported is **event → first frame carrying a picture**, not event → duplication created. A rebuilt
duplication hands back frames with `LastPresentTime == 0` while the new desktop has composed nothing, and a
viewer looking at those is looking at nothing. `desk_rebuilt.buildMs` and `desk_recovered.recoveredMs` are
both emitted so the API cost and the compositor's can be told apart, and `blankFrames` counts how many
empty frames came between.

**Unelevated, machine unlocked, no switch available (n = 2 runs):**

| | capture rights | inject rights |
|---|---|---|
| baseline attach to `Default` | ok, 0.007 ms | ok, 0.007 ms |
| cold `D3D11CreateDevice` + `DuplicateOutput` | **140.4 ms** | **157.6 ms** |
| content frames on an idle desktop | 9 in 12 s | 6 in 8 s |
| switches / losses / recoveries | 0 / 0 / 0 | 0 / 0 / 0 |

Two things this settles even without a lock: duplication succeeds through a desktop handle opened with
**either** mask (inject rights are a strict superset and do not break capture), and the cold rebuild is
~150 ms, which is the floor any recovery number below has to clear.

`OpenInputDesktop` failing is **not** proof the machine is locked — it is equally a switch in progress, or a
thread without rights to the desktop that is now current. Nothing in `desk.rs` concludes anything from it.

Two design notes for Task 6.1, both visible in the numbers above:

- **The capture loop attaches on its very first look**, to the desktop the thread is already on — the
  `desk_switch` from `-` to `Default` at 0.007 ms. That mirrors `capture::DesktopWatcher::follow()`, and it is
  harmless for a thread that only duplicates. It is **not** harmless for a thread that also injects (§7.2c),
  so capture and injection must stay on separate threads unless §7.2c comes back saying otherwise.
- **A lock produces two symptoms** — a `DXGI_ERROR_ACCESS_LOST` and an input-desktop name change — in either
  order. `desk.rs` starts one clock on whichever arrives first and names it in `desk_recovered.reason`, so
  `recoveredMs` measures the event rather than its second symptom. §7.1e is asking which one that is.

### 7.2 Injection: the three desktop-rights arms

Three arms, each on a **fresh thread** because `SetThreadDesktop` cannot be undone for the thread that called
it. Each reports two independent things per half, because the failure that matters does not show up in the
first one: what `SendInput` returned with its real last error, and whether the event **arrived**, read back
through `GetCursorPos` and `GetAsyncKeyState`.

**Unelevated, through the spawn path (n = 1 run, 3 arms):**

| arm | attached | `SendInput` mouse | err | mouse arrived | `SendInput` key | err | key arrived |
|---|---|---|---|---|---|---|---|
| `none` (no attach) | false | 1 | 0 | false | 1 | 0 | false |
| `capture` (`READOBJECTS\|WRITEOBJECTS`) | true | **0** | **5** | false | **0** | **5** | false |
| `inject` (+ `DESKTOP_JOURNALPLAYBACK`) | true | 1 | 0 | false | 1 | 0 | false |

**The `capture` row reproduces tonight's finding exactly**, now through the SYSTEM-shaped spawn path rather
than from a bare test: a desktop opened with capture's mask attaches fine and turns every `SendInput` into
`0 of 1, last error 5 (Access is denied.)`. `DESKTOP_JOURNALPLAYBACK` is the missing right. That is why
`agent/swoop/src/input` has its own `InputDesktop` and does not share `capture`'s `DesktopWatcher`.

**The arrival column is not measurable from the agent's shell and is `false` for the wrong reason.** A
control — plain `SendInput` from a bare python in that shell, no spawn, no attach, no token — returns 1 with
last error 0 and the pointer does not move. So the shell swallows synthetic input wholesale, and nothing in
the arrival column above is evidence about the spawn path. **Run `inject` from an ordinary elevated console
via §2, never from an agent shell.**

That leaves the second half of tonight's finding — a pre-emptive attach to the desktop a thread is *already*
on leaves the mouse working and silently kills the keyboard — **entirely unmeasured here**, because it lives
in exactly the column this shell destroys.

## 8. Primitive (5) — `SendSAS(FALSE)`

`securedesk/src/inject.rs` loads `sas.dll` at runtime (`LoadLibraryW` + `GetProcAddress`) rather than linking
it: a link-time import turns a missing dll into a process that will not start, and the whole point is that
the failure is legible. `SendSAS` returns void, so **nothing in-process can tell you the sequence was
raised** — what says so is the input desktop switching to `Winlogon`, which the child re-reads 250 ms after
the call and reports as `inputDesktopAfter`, and the human's eyes.

The policy is handled entirely by the harness, in python, so it is restored even if the child dies:
read → set 3 → run → restore, with the restore in a `finally`.

**Prior state on this box, read unelevated:**

```text
reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System" /v SoftwareSASGeneration
```

## 9. Primitive (6) — no path can raise a UAC prompt

Four independent pieces of evidence, three of them measured unelevated, one outstanding.

1. **No source in the spike asks to elevate.** `spawn_spike.py preflight` greps every `.py`, `.rs` and
   `.toml` in both spike directories for `runas`, `ShellExecute`, `requestedExecutionLevel`,
   `requireAdministrator`, `highestAvailable`, `Start-Process` and `AppInfo`. **8 hits — 6 in
   `spawn_spike.py`, 2 in `winapi.py`, none in any `.rs` file — and every one is prose or the scanner's own
   vocabulary**: the docstrings saying this never happens, the `ELEVATION_VERBS` tuple, and the
   manifest-check needle list. The scan prints every hit with its line so a
   reader judges rather than trusts; it is scoped to the two directories this spike owns, because the other
   spikes' vendored virtualenvs are full of the word and say nothing about this path.
2. **The child embeds no manifest asking for elevation.** A byte scan of the built `securedesk.exe` for
   `requestedExecutionLevel`, `requireAdministrator` and `highestAvailable`, in both ASCII and UTF-16, finds
   none. A Rust binary embeds no application manifest by default, so the child runs `asInvoker`. If that ever
   changes, `preflight` says so and this section has to be re-argued rather than repeated.
3. **`consent.exe` did not appear.** `spawn` snapshots every running process before and after the spawn
   window and reports any `consent.exe` that is new. Across **10 consecutive spawns** unelevated: **none**,
   and none already running. `consent.exe` is the UAC prompt; its absence is the observable half of the claim.
4. **The mechanism cannot reach the elevation path.** Every token in the harness is a `DuplicateTokenEx` of
   the one the process already holds. UAC elevation is entered through the AppInfo service, which is reached
   by `ShellExecuteEx` with the `runas` verb or by a manifest requesting elevation during `CreateProcess`.
   `CreateProcessAsUserW` with a duplicated primary token is neither. This is the same argument
   `agent/src/swoop_spawn.py`'s module docstring makes, and the same one research §11.3 makes —
   SYSTEM-in-console-session means swoop **never needs to elevate at runtime**, because the service already
   has the privilege.

## 10. Still unproven

Ordered by what it blocks.

1. **Everything that needs SYSTEM.** §3.1–3.4, §4.1–4.4, §5.1–5.3, §6.1–6.2, §9.2. The unelevated pass could
   not retarget the token (error 1314), so no measurement above was taken by a process that was actually
   SYSTEM-in-the-console-session. **Task 6.1 must not start on the strength of §5 and §7.1 alone.**
2. **Every desktop switch.** §7.1a–g. Nothing in-process can make Windows change the input desktop; the
   interesting cases are a human pressing Win+L, a real UAC prompt and the logon screen. No recovery time is
   measured, and whether the secure desktop is *visible* is not measured at all.
3. **Whether injection reaches `Winlogon`.** §7.2b, §7.2d. The `capture`-mask refusal reproduced; nothing
   about crossing to the secure desktop did.
4. **The pre-emptive-attach keyboard failure as SYSTEM.** §7.2c. It lives entirely in the arrival column,
   which the agent's shell destroys. `input/mod.rs`'s `InputDesktop` doc asks this question by name and its
   `poll` stays conditional until it is answered.
5. **`SendSAS` end to end.** §8.1–8.6. Unattempted; the policy write needs admin and the result needs eyes.
6. **The logon screen at all.** Needs a sign-out or a reboot with nobody logged in, and a task registered to
   run at startup.
7. **The real service as the parent.** Everything here has a python-in-a-scheduled-task parent, not
   `owlette_service.py`. The token, the session and the job are the same primitives, but the *set of
   inheritable handles* is not — which is exactly §5.3's caveat, and the reason Task 2.1's helper should not
   assume the 2 in §5 transfers.

## 11. Recommendation for Task 2.1's spawn-helper shape

**[ ] 11.1** *Provisional, and not to be acted on until §3, §4, §5 and §9 carry SYSTEM numbers.* The
unelevated pass already settles one of these outright; the rest are proposals with their evidence named.

1. **Drive `CreateProcessAsUser` through ctypes, not pywin32, for the `STARTUPINFOEX` alone.** §5.1 is not a
   version problem and will not be fixed by a pywin32 bump — the API is not bound anywhere in the package.
   The `except Exception` around `si.lpAttributeList` in the current `agent/src/swoop_spawn.py` should be
   deleted, not widened: it makes a permanent condition look like a transient one and logs a warning nobody
   will action. `spawn-py/winapi.py` is the working shape, at about 200 lines of declarations for the whole
   surface (tokens, pipes, attribute list, job, process), and it needs no new package.
   **Evidence: §5.1, §5.2, §5.3 — measured, and independent of privilege.**
2. **Keep everything else on pywin32.** The token duplication, `CreateEnvironmentBlock`, the job object and
   the pipes all work through pywin32 today and there is no reason to rewrite them; the only thing pywin32
   cannot do is the one thing above. A helper that is half ctypes is a smaller change than one that is all
   ctypes, and `owlette_service.py` already carries the `ctypes.windll.advapi32.SetTokenInformation` precedent
   for exactly this kind of gap.
3. **Put the stderr file in the handle list too, or stop inheriting it.** The current product path passes
   three child handles (stdin, stdout, stderr-file); the spike passes two by pointing `hStdError` at the
   stdout pipe. Either is fine — what is not fine is a list that omits one of the handles the child needs, so
   whichever Task 2.1 picks, the list and the `STARTUPINFO` std handles must be written from **one** list in
   the code, not two.
4. **Assign to the job before `ResumeThread`, and never `TerminateProcess`.** The spike resumes only after
   `AssignProcessToJobObject` returns, and `job` proves closing the job is sufficient (§6). Do not add
   `JOB_OBJECT_LIMIT_BREAKAWAY_OK` — the streamer launches nothing that should outlive it.
5. **Do not reuse `_launch_command_as_user`, and say why in the code.** It passes `bInheritHandles = 0`
   (`owlette_service.py:3028`), so the child would get no pipes at all. The current `swoop_spawn.py` docstring
   already says this; keep it.
6. **Keep the bundle off every surface but stdin.** The spike writes it, wipes its own buffer and reports only
   the length; the child reads two fields and echoes back a byte count. Task 2.1 should hold the same line.
