## 2. What each mode measures, and what it cannot

| mode | measures | blind to |
|---|---|---|
| `caps` | `VideoDecoder.isConfigSupported` over 11 codec strings × 3 `hardwareAcceleration` hints, `RTCRtpReceiver/Sender.getCapabilities`, `MediaCapabilities.decodingInfo`, and the presence of every api the client needs | whether any of it is true — support claims and real decode disagree, which is why `decode` exists |
| `decode` | a real paced decode of canned 1080p60 annex-b chunks, one access unit per frame period, with a centre-pixel readback per sampled frame | anything a longer or higher-motion stream would show; these are 60 frames |
| `stall` | the static-desktop stall, two arms: webcodecs (submit → output across a 3 s idle) and a loopback `RTCPeerConnection` rendered into a `<video>` (arm B's shape), each with and without a 2 Hz host floor | the loopback arm contains this browser's **own encoder** restarting, so its first-frame number is an upper bound on the decoder's share, and the split is not established here |
| `soak` | N windows each decoding 1080p60 for 30 s; sustained output rate, errors, black frames | it is a **WebCodecs** ceiling. Arm B decodes through the WebRTC decoder. They usually share the same hardware decoder, but that is an assumption this spike did not test |
| `fp` | `RTCCertificate.getFingerprints()`, the `a=fingerprint:` fallback, and whether the two agree | nothing — this one is complete on the browsers that ran it |
| `readback` | spike 0.1 §6's 24 readback configurations, re-run here because 0.1 §6 item 2 assigned Safari and Firefox to this task | — |
| `perms` | keyboard lock, pointer lock with `unadjustedMovement`, clipboard read/write: does the api resolve or reject | **whether a prompt appeared.** No api exposes that, so it is a human observation and stays one |

## 3. WebCodecs: what is claimed, and what really decodes

`VideoDecoder.isConfigSupported`, 11 codec strings × 3 `hardwareAcceleration` hints. `any` is
`no-preference`, `hw` is `prefer-hardware`, `sw` is `prefer-software`.

**Chrome 153.0.8010.48 / Windows 11 / RTX 2080 Ti** — n = 1 call per cell:

| codec string | any | hw | sw |
|---|---|---|---|
| `avc1.42E01E` h264 baseline 3.0 | yes | yes | yes |
| `avc1.4D401F` h264 main 3.1 | yes | yes | yes |
| `avc1.64002A` h264 high 4.2 | yes | yes | yes |
| `avc3.64002A` h264 high 4.2, avc3 | yes | yes | yes |
| `hev1.1.6.L123.B0` hevc main 8-bit 4.1 | yes | yes | **no** |
| `hvc1.1.6.L123.B0` same, hvc1 spelling | yes | yes | **no** |
| `hev1.1.6.L93.B0` hevc main 8-bit 3.1 | yes | yes | **no** |
| `hev1.2.4.L123.B0` hevc main10 4.1 | yes | yes | **no** |
| `vp8` | yes | **no** | yes |
| `vp09.00.10.08` | yes | yes | yes |
| `av01.0.04M.08` | yes | **no** | yes |

**HEVC has no software decoder on this browser, in either spelling and at either level.** That is the same
"hardware or nothing" shape the WebRTC intent-to-ship describes, measured here through WebCodecs.

**Edge 153.0.4234.32 / Windows 11, with `Microsoft.HEVCVideoExtension 2.4.109.0` installed**, n = 1 call per
cell: **identical to Chrome on all 33 cells** — every H.264 string yes in all three modes, every HEVC string
yes for `no-preference` and `prefer-hardware` and **no** for `prefer-software`, `vp8` and `av01` without a
hardware path, `vp09` with one.

That identity is the thing to be careful with. It says Edge-with-the-extension matches Chrome through the
WebCodecs surface. It says nothing about Edge without it, which is the configuration most of the fleet's
operators will actually have, and which §9.4 leaves as a protocol rather than a result.

### 3.1 The real decode — Chrome

60 canned annex-b access units per run, submitted one per 16.67 ms — paced, because dumping the file in at
once measures throughput and hides a DPB hold (spike 0.9 measured 208 ms against 8.3 ms that way). A centre
pixel is read back from every 10th decoded frame, so "it decoded" means pixels, not callbacks.

**Chrome 153 / Windows**, n = 60 access units per row, 6 pixel checks per row:

| stream | codec string | accel | claimed | frames out | held at eos | non-black | submit→output p50 | p95 |
|---|---|---|---|---|---|---|---|---|

| h264 1080p | `avc1.64002a` | hw | yes | 60/60 | 1 | 6/6 | 0.50 | 0.80 |
| h264 1080p | `avc1.64002a` | sw | yes | 60/60 | 1 | 6/6 | 2.60 | 10.10 |
| h264 1080p | `avc3.64002a` | any | yes | 60/60 | 1 | 6/6 | 0.60 | 0.70 |
| h264 1080p | `avc3.64002a` | hw | yes | 60/60 | 1 | 6/6 | 0.50 | 0.70 |
| h264 1080p | `avc3.64002a` | sw | yes | 60/60 | 1 | 6/6 | 2.60 | 3.20 |
| hevc 1080p | `hev1.1.6.L123.B0` | any | yes | 60/60 | 1 | 6/6 | 0.50 | 0.80 |
| hevc 1080p | `hev1.1.6.L123.B0` | hw | yes | 60/60 | 1 | 6/6 | 0.60 | 0.80 |

Milliseconds. Three things worth keeping:

1. **Claim and reality agreed on every one of the 12 rows here.** Where `isConfigSupported` said yes, 60 of 60
   access units decoded to non-black pixels; where it said no, `configure()` was accepted and the codec then
   closed itself, so `decode()` threw `InvalidStateError` on the first chunk. The disagreement this mode exists
   to catch did not appear on Chrome — which is a result about Chrome, not about the mode.

3. **One frame is still held at end of stream** with `optimizeForLatency: true` and a B-frame-free stream, in

   that counts frames must flush before it counts.

### 3.2 The real decode — Edge

Same 12 rows, same shape: **60/60 frames out and 6/6 non-black on every row `isConfigSupported` accepted**, and
0/60 on the two it refused, where the failure is the decoder's own `error` callback firing
`OperationError: Unsupported configuration. Check isConfigSupported() prior to calling configure().` before
`decode()` throws on a now-closed codec. Latencies are within noise of Chrome's (`prefer-hardware` p50 0.50–0.80
ms, `prefer-software` H.264 p50 2.5–2.6 ms), with one outlier worth naming because a test would trip on it:
the **first** HEVC row of the run (`hev1`, `no-preference`) had a p95 of **138.90 ms** against 1.30–1.70 ms on
the three HEVC rows that followed it. n = 1 occurrence; it reads like first-use initialisation of the hardware
HEVC path, and it is a reason to warm a decoder before timing one, not a finding about HEVC.

## 4. Arm B: what the WebRTC receiver advertises

This is the probe the product's capability negotiation actually uses (PROTOCOL.md §3: codec chosen per viewer
from the client probe ∩ host encoders).

**Chrome 153 / Windows** — `RTCRtpReceiver.getCapabilities('video')` distinct mime types:

```
video/VP8  video/rtx  video/VP9  video/H264  video/AV1  video/H265  video/red  video/ulpfec  video/flexfec-03
```

`RTCRtpSender.getCapabilities('video')` lists the same set minus `flexfec-03`, so this browser both sends and
receives H.265 — which is what makes the loopback arm in §5 possible at all.

Header extensions offered by the receiver include
`http://www.webrtc.org/experiments/rtp-hdrext/playout-delay`, so the extension PROTOCOL.md §3 requires
(`min = 0`, `max ∈ (0, 500]`) is negotiable on this browser. The full list is in the run file.

`MediaCapabilities.decodingInfo`, n = 1 call per row:

| type | contentType | supported | smooth | powerEfficient |
|---|---|---|---|---|
| webrtc | `video/H264;codecs=avc1.64002A` | true | true | **true** |
| webrtc | `video/H265;codecs=hev1.1.6.L123.B0` | true | true | **true** |
| webrtc | `video/VP8` | true | true | false |
| webrtc | `video/AV1` | true | true | false |
| file | `video/mp4;codecs="avc1.64002A"` | true | true | true |
| file | `video/mp4;codecs="hvc1.1.6.L123.B0"` | true | true | true |

`powerEfficient` is the field that separates a hardware path from a software one here: H.264 and H.265 report
true, VP8 and AV1 report false, and that matches §3's `prefer-hardware` column exactly. **`decodingInfo` with
`type: 'webrtc'` is therefore a usable hardware-decode probe for arm B**, and it is the only one that speaks
about the WebRTC decoder rather than the WebCodecs one.

### 4.1 Edge — the one place the two Chromium browsers diverge, and it is the one that matters

**Edge 153 does not offer H.265 in WebRTC at all**, on the same machine, the same GPU and the same driver where

| `RTCRtpSender.getCapabilities('video')` contains `video/H265` | **yes** | **no** |

The loopback arm in §5 confirms it from the other direction: forcing `video/H265` through
`setCodecPreferences` on Edge fails before any negotiation, with
`video/H265 is not in RTCRtpSender.getCapabilities('video')`, and the harness records **n = 0** for those two

`research/02-browser-client.md` §0 listed Edge's WebRTC H.265 receive as *unverified* and said "treat Edge as

## 5. The static-desktop stall, and whether a host floor frame rate clears it

Two arms, three seconds of a genuinely still source in each, five repeats per cell. The figure is
`first-after-idle`: from the moment the source starts moving again to the moment a frame comes out of the
decoder (WebCodecs arm) or is presented by the `<video>` (loopback arm).

The loopback arm's source is a canvas driven by `captureStream(0)` + `requestFrame()`. That detail is
load-bearing: `captureStream(60)` keeps emitting frames whether or not the canvas changed, and an earlier
iteration of this harness measured 171 "idle" frames in a three-second idle window because of it. With explicit
frames the idle window really is idle — `framesPresentedDuringIdle` is 1 or 2 at floor 0, and 7 or 8 at a 2 Hz
floor, which is what a floor of 2 Hz over 3 s should produce.

### 5.1 WebCodecs arm — no stall on either Windows browser

| browser | stream | floor | n | first-after-idle p50 | p95 | frames held through the idle window |
|---|---|---|---|---|---|---|
| Chrome | h264 | 0 Hz | 5 | 0.50 | 0.60 | 0, 0, 0, 0, 0 |
| Chrome | h264 | 2 Hz | 5 | 0.50 | 0.50 | 1, 1, 1, 1, 1 |
| Chrome | hevc | 0 Hz | 5 | 0.60 | 0.80 | 0, 0, 0, 0, 0 |
| Chrome | hevc | 2 Hz | 5 | 0.60 | 0.60 | 1, 1, 1, 1, 1 |
| Edge | h264 | 0 Hz | 5 | 0.50 | 0.70 | 0, 0, 0, 0, 0 |
| Edge | h264 | 2 Hz | 5 | 0.60 | 0.70 | 1, 1, 1, 1, 1 |
| Edge | hevc | 0 Hz | 5 | 0.80 | 1.10 | 0, 0, 0, 0, 0 |
| Edge | hevc | 2 Hz | 5 | 0.80 | 0.80 | 1, 1, 1, 1, 1 |

Milliseconds. Steady-state submit→output is 0.50–0.60 ms p50 in every row, so **the frame after a three-second
silence costs the same as any other frame**, and the decoder held nothing across the gap (the single held frame
in the 2 Hz rows is the floor frame still in flight when the window closed, not a stalled one). On Windows, in
WebCodecs, there is no stall to clear and the floor buys nothing.

### 5.2 Loopback arm — arm B's own shape

| browser | forced codec | floor | n | first-after-idle p50 | p95 | max | frames presented during idle |
|---|---|---|---|---|---|---|---|
| Chrome | H264 | 0 Hz | 5 | **47.60** | 63.00 | 63.00 | 1 |
| Chrome | H264 | 2 Hz | 5 | **51.80** | 54.50 | 54.50 | 7 |
| Chrome | H265 | 0 Hz | 5 | **42.80** | 45.60 | 45.60 | 2 |
| Chrome | H265 | 2 Hz | 5 | **53.10** | 58.40 | 58.40 | 7 |
| Edge | H264 | 0 Hz | 5 | **44.70** | 63.60 | 63.60 | 1 |
| Edge | H264 | 2 Hz | 5 | **51.60** | 60.00 | 60.00 | 8 |
| Edge | H265 | — | **0** | — | — | — | refused: `video/H265` is not in `RTCRtpSender.getCapabilities('video')` |

Milliseconds. `steadyFrameGapMs` p50 was **16.70 ms** in every completed row, which is the evidence that these
are 60 Hz client rows (spike 0.1 §2.4) and matches 0.1 §4.5's 16.70 ms exactly.

**The 2 Hz floor did not help, and the numbers lean slightly the other way** — 47.6 → 51.8 ms on Chrome H.264,
42.8 → 53.1 ms on Chrome H.265, 44.7 → 51.6 ms on Edge. At n = 5 per cell that difference is not something to
build on, but the direction is consistent across all three pairs and the honest summary is "no benefit
measured". `getStats` tells the same story from a third angle: `totalFreezesDuration` was **3.01–3.03 s** with
and without the floor in every row, while `freezeCount` went from **1** to **6** — the floor chopped one long
freeze into six short ones and removed none of it.

**What this row is not.** The loopback arm contains this browser's own encoder restarting after an idle source,
and `decoderImplementation` came back `null` from `getStats` on both browsers, so there is no measurement here
that splits the ~45–50 ms between sender and receiver. Read it as an upper bound on the receive side, and as a
statement about Windows: **plan.md D5's stall claim is a macOS claim, and §9.3 is the row that tests it.**

## 6. The multi-window ceiling — not reached at 8

Ten groups: 1, 2, 4, 6 and 8 simultaneous Chrome windows, each decoding its own 1080p60 stream for 30 s, once
with H.264 and once with HEVC. All the windows of a group live in one Chrome instance (one GPU process, as a
real operator with eight swoop windows would have), tiled so none is occluded, launched from the shell because
no browser lets one page open eight windows. Every window submits **1801 access units** at the stream's own
60 fps.

| group | windows | aggregate output | per-window output | submit→output p50 | p95 | black frames | decoder errors | hidden windows |
|---|---|---|---|---|---|---|---|---|
| h264 ×1 | 1 | 60.0 fps | 60.03 | 0.60 | 0.70 | 0 | 0 | 0 |
| h264 ×2 | 2 | 120.1 fps | 60.03 each | 0.50–0.60 | 0.70–0.80 | 0 | 0 | 0 |
| h264 ×4 | 4 | 240.1 fps | 60.03 each | 0.50 | 0.70–1.00 | 0 | 0 | 0 |
| h264 ×6 | 6 | 360.2 fps | 60.03 each | 0.50–0.60 | 0.70–0.90 | 0 | 0 | 0 |
| **h264 ×8** | 8 | **480.3 fps** | 60.03 each | 0.40–0.60 | 0.90–1.10 | 0 | 0 | 0 |
| hevc ×1 | 1 | 60.0 fps | 60.03 | 0.60 | 0.80 | 0 | 0 | 0 |
| hevc ×2 | 2 | 120.1 fps | 60.03 each | 0.50–0.60 | 0.80 | 0 | 0 | 0 |
| hevc ×4 | 4 | 240.1 fps | 60.03 each | 0.50–0.60 | 0.80–1.50 | 0 | 0 | 0 |
| hevc ×6 | 6 | 360.2 fps | 60.03 each | 0.50–0.60 | 0.80–1.30 | 0 | 0 | 0 |
| **hevc ×8** | 8 | **480.3 fps** | 60.03 each | 0.50–0.60 | 0.80–1.50 | 0 | 0 | 0 |

Milliseconds; ranges are min–max across the windows of the group. Every window in every group held real time,
every sampled frame was non-black (61 of 61 per window), no decoder errored and no window was ever hidden.

**No ceiling was found at 8 × 1080p60, in either codec, on an RTX 2080 Ti.** The failure mode
`research/02-browser-client.md` §9.1 predicted for HEVC — hardware-decoder exhaustion showing up as a black
stream rather than a slowdown, because HEVC has no software fallback — **did not occur at eight windows**.

Read the number for what it is. The submission is paced at 60 fps per window, so this measures *"can N windows
each hold real time"*, not the maximum throughput of the decoder; the aggregate 480 fps is a floor on capacity,
not a limit. And it is one GPU: this says nothing about an Intel iGPU, an AMD card, or a VM with no GPU at all,
all of which are in the fleet. The HEVC ×8 group is the one to re-run first on other hardware, because it is
the one whose failure is silent.

## 7. `fp` acquisition — the binding the whole viewer token hangs on

PROTOCOL.md §8 makes `fp` a mandatory viewer claim, and the api mints the token *before* the browser connects,
so the fingerprint has to exist at mint time. There are two ways to get one and this settles which exist.

| | Chrome 153 / Windows | Edge 153 / Windows |
|---|---|---|
| `RTCPeerConnection.generateCertificate` | yes | yes |
| `RTCCertificate.getFingerprints()` | **yes** | **yes** |
| algorithms returned | `sha-256` only | `sha-256` only |
| hex case from `getFingerprints()` | **lower** | **lower** |
| `a=fingerprint:` in `createOffer()` output | yes | yes |
| …needs `setLocalDescription()` first | **no** | **no** |
| hex case in the SDP line | **upper** | **upper** |
| the two agree (case-insensitively) | **yes** | **yes** |

**The finding that matters is the case.** `getFingerprints()` returns the value in lowercase hex; the SDP
`a=fingerprint:` line carries it in uppercase; PROTOCOL.md §9's canonical form is
`<hash-func> <HEX:WITH:COLONS>` with **hex uppercase**. So the browser must uppercase what `getFingerprints()`
gives it, and a naive `fp === sdpFingerprint` comparison anywhere in the stack fails on a value that is
correct.

No fingerprint value appears in any run file: the harness records the shape and the case, never the digits.

## 8a. Keyboard lock, pointer lock and clipboard

Driven through Playwright against the **installed** Chrome and Edge (not the bundled chromium), with
`clipboard-read` and `clipboard-write` granted by the harness, so this measures whether the api works when
permitted. n = 1 pass per browser.

| step | Chrome 153 / Windows | Edge 153 / Windows | prompt appeared? |
|---|---|---|---|
| `navigator.keyboard.lock()` after a JS-initiated fullscreen | **resolved**, fullscreen still held | **resolved**, fullscreen still held | not observable under automation |
| `requestPointerLock({unadjustedMovement: true})` | promise **resolved**, `pointerlockchange` fired, `document.pointerLockElement` set | same | not observable under automation |
| `navigator.clipboard.writeText` | resolved | resolved | not observable under automation |
| `navigator.clipboard.readText` | resolved, **read back exactly what was written** | same | not observable under automation |
| `permissions.query('clipboard-read'/'clipboard-write')` | `granted` / `granted` (set by the harness) | same | — |

The whole right-hand column is the limitation, and it is structural, not an oversight: a permission prompt is
what the browser shows when the permission state is *not* already decided, and automation decides it. The page
asks the operator instead, and `drive-perms.mjs` answers "unsure" so that no run file ever claims a prompt was
or was not seen. **Prompt behaviour is a [human] cell on every browser, including these two** — §9.1's `perms`
walkthrough is how it gets filled.

No movement delta was captured after the pointer lock (`first movement=null` in both runs) because nothing
moved the mouse; whether `unadjustedMovement` actually delivers *unaccelerated* deltas is a separate question
this spike did not answer, and it needs a physical mouse with pointer acceleration on.

## 9. PENDING [human] — the copy-paste protocol

Everything in this section is a protocol, not a result. It follows the shape of spike 0.2 §9: exact commands,
what to click, what each run produces, how it comes back.

### 9.0 Getting the harness onto the machine

The harness is three static files plus 1.2 MB of canned chunks, all inside
`agent/swoop/spikes/browser-matrix/`, and it has no build step and no dependencies. Either check the branch
out (`git checkout feat/swoop`) or copy that one directory across. Node 18+ is the only requirement, and only
for the page server.

```
cd agent/swoop/spikes/browser-matrix
node server.mjs                 # prints: page: http://127.0.0.1:17450/
```

Leave it running. Every run writes a JSON file into `runs/` on **that** machine. `runs/` is gitignored, so
when the runs are done, zip it and hand it back:

```
# macOS
zip -r swoop-2.12-runs-macos.zip runs
# windows powershell
Compress-Archive -Path runs -DestinationPath swoop-2.12-runs-windows.zip
```

The page also prints everything it measures into the right-hand pane, and echoes it to the server's stdout, so
a screenshot or a copy-paste of either is a usable fallback if the zip is awkward.

### 9.1 Safari on macOS — PENDING [human]

Safari has no clean-profile flag and no command-line switches. Run it as it is, and say in the hand-back
whether any extensions are enabled.

```
open -a Safari "http://127.0.0.1:17450/?mode=auto&label=safari-macos&autorun=1&reps=5"
```

Watch it for six minutes; **keep the window frontmost and visible the whole time** — a run whose window was
hidden writes `everHidden: true` and is void (spike 0.1 §2.3). The page says `done` in the header when it has
finished, and the last line of the pane names the file it wrote.

Then the two interactive modes:

```
open -a Safari "http://127.0.0.1:17450/?mode=perms&label=safari-macos"
```

Press **run**, then click the four buttons in order — `keyboard lock (fullscreen)`, `pointer lock
(unadjustedMovement)`, `clipboard write`, `clipboard read`. After each one the page asks *did a browser prompt
appear?* — answer it honestly: **that answer is the measurement**, and it is the only part of this spike no
script can take. (Expect at least one refusal: keyboard lock is not implemented outside Chromium, and the page
records `absent` for it rather than failing.)

Then the soak, which is four groups of windows. Safari will not let a page open its own windows, so each one
is an AppleScript line:

```bash
for n in 1 2 4 6 8; do
  for i in $(seq 0 $((n-1))); do
    osascript -e "tell application \"Safari\" to make new document with properties {URL:\"http://127.0.0.1:17450/?mode=soak&idx=$i&group=safari-macos-h264-$n&stream=h264-1080p&secs=30&label=safari-macos&autorun=1\"}"
    sleep 2
  done
  sleep 50            # 30 s of decoding plus its tail
  osascript -e 'tell application "Safari" to close every document'
  sleep 5
done
```

Repeat with `stream=hevc-1080p` and `group=safari-macos-hevc-$n`. **Make the windows small and tile them so
every one is visible** — an occluded or backgrounded window stops decoding and the row is void; `summarize.mjs`
prints `WINDOW WAS HIDDEN - void` for any that were. Then:

```
node summarize.mjs
```

and hand back what it prints along with the zip.

## 11. The rules Waves 3.11, 3.12, 4.6 and 8.7 inherit

Each of these is written so the task that inherits it can follow it without reading the raw results. Where a
rule rests on an unmeasured browser, it says so and says what closes it.

1. **Ask the WebRTC receiver, not WebCodecs, what arm B can decode.** The client capability probe that
   PROTOCOL.md §3 sends to the host is built from `RTCRtpReceiver.getCapabilities('video')` mime types plus
   `navigator.mediaCapabilities.decodingInfo({type:'webrtc', …})`. `VideoDecoder.isConfigSupported` describes a
   different decoder and must not stand in for it. (§4.)

2. **Treat `powerEfficient` from `decodingInfo({type:'webrtc'})` as the hardware-decode flag.** On the browser
   measured it separated H.264/H.265 (true) from VP8/AV1 (false) exactly as `prefer-hardware` did in WebCodecs.
   It is the only probe available for the WebRTC decoder. (§4.)

3. **Never offer HEVC to a viewer that has not reported hardware HEVC decode.** There is no software fallback:
   the WebCodecs probe refuses `prefer-software` for every HEVC string, and forcing it closes the codec. A
   viewer that negotiates HEVC and cannot decode it in hardware gets a black stream, not a slow one. (§3.)

4. **Codec strings: `avc1.<profile><constraints><level>` and `hev1.1.6.L<level>.B0`, annex-b, no
   `description`.** Both `avc1`/`avc3` and `hev1`/`hvc1` decoded identically on the browser measured, so pick
   one pair and keep it; the annex-b form (no `description`) is what PROTOCOL.md §4 puts on the wire. Derive
   the level from the bitstream, not from the encoder config. (§3.1.)

5. **Get `fp` from `RTCCertificate.getFingerprints()` and uppercase the hex.** `generateCertificate` +
   `getFingerprints()` returns `sha-256` with **lowercase** hex; PROTOCOL.md §9's canonical form is uppercase,
   and the SDP line is uppercase. Uppercase at the point of minting, and compare fingerprints
   case-insensitively everywhere. (§7.)

6. **The `a=fingerprint:` fallback is `createOffer()`, not `setLocalDescription()`.** On the browser measured
   the line is present in the offer `createOffer()` returns, before any local description is set, and agrees
   with the certificate. Implement it as the fallback for an engine with no `getFingerprints()`, and take the
   value from the offer rather than from `pc.localDescription`. (§7.)

7. **Present from the decoder output callback and read the renderer's own buffer.** Spike 0.1 §6's rule is
   unchanged and now has a second, independent confirmation on Chrome: the `desynchronized` canvas does not
   read back empty, it reads back *expensively* (0.00 ms synchronized against 1.5–3.5 ms). Keep
   `desynchronized` for presentation; never put a per-frame readback in the product's hot path. (§8.)

8. **A resolution change is a decoder reconfigure, and one frame is held at end of stream.** With
   `optimizeForLatency: true` and no B-frames, the last access unit only comes out on `flush()`. Anything that
   counts frames — a test, a stall detector, a "did the picture arrive" check — must flush first or it is
   always one short. (§3.1.)

9. **Do not build the host's floor frame rate for Windows clients; keep it behind a switch for macOS.** On
   Chrome and Edge on Windows there is no static-desktop stall to clear: the frame after a three-second
   silence costs 0.5–0.8 ms through WebCodecs, and through a real `<video>` a 2 Hz floor changed nothing it
   could be said to have improved (§5). The claim D5 records is a macOS claim; until §9.3 and §9.1 run, make
   the floor a bundle-controlled setting with a default of *off*, not an always-on behaviour, and measure it on
   macOS before turning it on for anyone.

10. **Plan the multi-window codec downgrade, but do not trigger it below 8 windows on the evidence here.**
    Eight simultaneous 1080p60 decodes held real time in both codecs with no errors and no black frames (§6),
    so the (N+1)-window HEVC→H.264 downgrade `research/02-browser-client.md` §9.1 proposes has no measured
    trigger point yet. Build the mechanism — a viewer that reports decode failure asks for H.264 — and drive
    it from the client's *observed* failure, not from a window count this spike cannot supply.

11. **Keyboard lock, pointer lock with `unadjustedMovement` and both clipboard directions all work on
    Chromium once permitted, so build the happy path against them — and build the refusal path too.** Every one
    resolved on Chrome and Edge (§8a). Keyboard lock is Chromium-only by specification and the page already
    records `absent` rather than failing when `navigator.keyboard.lock` does not exist; Task 4.6 must do the
    same rather than assuming the api. Whether a prompt interrupts the user is unmeasured everywhere, so do not
    design a flow that depends on there being no prompt.

12. **Task 8.7's e2e specs feed real H.264 chunks, not a stubbed decoder — and never HEVC.** Playwright
    1.63.0's bundled Chrome for Testing decodes H.264 to real pixels headless and headed (§8b), which is the
    opposite of what the task text assumed. HEVC works only headed, because headless has no GPU and HEVC has
    no software path, so an HEVC assertion would pass locally and fail in CI. Assert on decoded frames for
    H.264; assert nothing about `video/H265` in the receiver capabilities. Run `node playwright-codecs.mjs`
    once on the CI runner before relying on this, because it was measured on a Windows box with a GPU.

13. **Three design questions stay open, and each names the run that closes it.** (a) Does the macOS
    decoder stall on a static desktop, and does a host floor clear it — §9.3 and §9.1. (b) What does Edge do
    with HEVC on a machine without the Video Extension, and is the failure a refusal or a black stream — §9.4.
    (c) Does Safari or Firefox reproduce review-1 F7's empty readback — §9.1 and §9.2, which is the re-test
    spike 0.1 §6 item 2 assigned to this task and which this task could not run. **Until each returns, the
    matrix cell stays empty.** A task that needs one of these answers should treat the empty cell as a blocker
    on that path, not as permission to assume Chromium's behaviour.

## 12. What this spike did not measure

- **Safari, on any version of macOS or iOS.** Not available on this box. Every Safari cell is empty.
- **Firefox, on any OS.** Not installed on this box. Every Firefox cell is empty.
- **Chrome and Edge on macOS**, which is where the static-desktop decoder stall is claimed to live. §5's
  Windows rows say nothing about it.
- **Edge without the HEVC Video Extension.** `Microsoft.HEVCVideoExtension 2.4.109.0` is installed here and was
  not removed. §9.4 is the protocol.
- **Any GPU but this one.** Every hardware-decode answer above is an RTX 2080 Ti answer on driver 591.86. An
  Intel iGPU, an AMD card and a VM with no GPU will each answer differently, and the fleet contains all three.
- **iOS and Android.** Out of scope for v1 (plan.md defers touch/mobile viewers), and not run.
- **A ≥ 120 Hz client.** No such display on this box (spike 0.1 §2.4). Nothing here is refresh-rate sensitive
  except the loopback stall arm's frame gaps, which are reported at 60 Hz only.
- **Whether the WebRTC decoder and the WebCodecs decoder share one hardware budget.** §6's ceiling is a
  WebCodecs ceiling; arm B's decoder was not soaked.
- **Whether a permission prompt appears** for keyboard lock, pointer lock or clipboard. That is a human
  observation on every browser, including the two measured here (§8/§9.1).
- **Long-running decode.** The canned streams are 60 access units, and the soak replays them; a real session
  runs for hours and a drift or a leak over that horizon is invisible at this length.
- **HEVC over a real network.** The loopback arm never leaves the machine, and spike 0.2 §14 records that HEVC
  on the LAN is still unmeasured.
