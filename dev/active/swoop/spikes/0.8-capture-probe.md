## 2. Adapter / output enumeration, and what the Parsec virtual adapter does

`IDXGIFactory1::EnumAdapters1` returns **three** adapters; `Win32_PnPEntity` with `PNPClass='Display'`
returns **two** display devices.

| DXGI idx | description | vendor / device | LUID | flags | VRAM | outputs |
|---|---|---|---|---|---|---|
| 0 | NVIDIA GeForce RTX 2080 Ti | 0x10DE / 0x1E07 | `0x…0000F5CA` | 0x0 | 11027 MiB | **2** |
| 1 | NVIDIA GeForce RTX 2080 Ti | 0x10DE / 0x1E07 | `0x…0001746A` | 0x0 | 11027 MiB | **0** |
| 2 | Microsoft Basic Render Driver | 0x1414 / 0x008C | `0x…0001150E` | 0x2 (`SOFTWARE`) | 0 MiB | 0 |

Adapter 1 carries the *identical* `VendorId`, `DeviceId`, `SubSysId` (0x12A410DE), `Revision` (161) and
`DedicatedVideoMemory` as adapter 0, but a **different LUID** and **zero outputs**. Adapter 2 is WARP and is
not a PnP device. Two PnP display devices minus WARP leaves adapter 0 = the physical RTX 2080 Ti and
**adapter 1 = the Parsec Virtual Display Adapter**, which as an IddCx indirect display driver reports the
identity of the render adapter it is paired with. (The LUID/zero-output/PnP-count correlation is a
measurement; the "IddCx reports its paired render adapter's identity" explanation is inference.)

**What it does to enumeration:**

1. It adds a **phantom adapter that looks exactly like the real GPU** and would be picked by any selection
   rule based on description, vendor id or VRAM. With no Parsec virtual display created, it has **zero
   outputs**, so it is harmless if and only if the code enumerates *outputs*, not adapters.
2. It **does not** add a phantom output today, and it did **not** appear in either output list
   (n = 2 attached outputs, both on adapter 0).
3. It **does not** force a second capture device on this box. It would the moment Parsec created a virtual
   display on it, because of the cross-adapter rule measured next.

**Cross-adapter duplication matrix** — a D3D11 device on adapter A against every output (n = 6 pairs):

| device adapter | output | result |
|---|---|---|
| 0 (real GPU) | global 0 `\\.\DISPLAY1` | **OK** — `B8G8R8A8_UNORM` 1920x1080, rotation identity |
| 0 (real GPU) | global 1 `\\.\DISPLAY2` | **OK** — `B8G8R8A8_UNORM` 2160x3840, rotation rotate270 |
| 1 (Parsec VDD) | global 0 | **`0x80070057` E_INVALIDARG** "The parameter is incorrect." |
| 1 (Parsec VDD) | global 1 | **`0x80070057` E_INVALIDARG** |
| 2 (WARP) | global 0 | **`0x80070057` E_INVALIDARG** |
| 2 (WARP) | global 1 | **`0x80070057` E_INVALIDARG** |

The same-adapter rule from `research/03-windows-host-stack.md` §1.1 is confirmed, and the failure code is
**E_INVALIDARG, not `DXGI_ERROR_UNSUPPORTED`** — a recovery loop that only retries on the DXGI-namespace
errors will treat this as fatal.

`IDXGIOutput5::DuplicateOutput1` format negotiation, per attached output (n = 8 calls):

| requested list | negotiated |
|---|---|
| `[BGRA8]` | `B8G8R8A8_UNORM` |
| `[BGRA8, RGB10A2, RGBA16F]` | `B8G8R8A8_UNORM` |
| `[RGB10A2]` | `B8G8R8A8_UNORM` |
| `[RGBA16F]` | `B8G8R8A8_UNORM` |

All eight calls succeeded, including the two lists that do **not** contain BGRA8, and all eight returned
BGRA8. On an SDR desktop `DuplicateOutput1` therefore buys nothing over `DuplicateOutput` here. It did not
fail for DPI reasons — the probe sets `DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2` before any DXGI call.
HDR behaviour is **unmeasured** (no HDR display on this box; both outputs report `BitsPerColor = 8`,
`ColorSpace = 0` = `RGB_FULL_G22_NONE_P709`).

| adapter / output index | 0 / 0 | 0 / 1 |
| `DesktopCoordinates` | (0,0)-(1920,1080) | **(-2160,-1138)-(0,2702)** |
| desktop size | 1920x1080 | 2160x3840 |
| `DXGI_OUTPUT_DESC.Rotation` | identity | **rotate270** |
| `DXGI_OUTDUPL_DESC.ModeDesc` | 1920x1080 @ 59997/1000 | **2160x3840** @ 59997/1000 |
| **acquired `ID3D11Texture2D`** | 1920x1080 | **3840x2160** |
| format (both descs and texture) | `B8G8R8A8_UNORM` | `B8G8R8A8_UNORM` |
| `DesktopImageInSystemMemory` | false | false |
| effective DPI | 96x96 (100%) | **120x120 (125%)** |
| raw DPI | 92x92 | 185x185 |
| texture bind/misc flags | bind `0x28`, misc `0x2900`, 1 mip, 1 array, 1x sample | same |

**Virtual desktop: origin (-2160, -1138), extent 4080x3840 — negative in both axes** (review-3 F12's case is
live on this box, not hypothetical).

Three measured traps:

1. **`DXGI_OUTDUPL_DESC.ModeDesc` is in rotated desktop orientation; the texture is not.** Output 1 reports
   `ModeDesc` 2160x3840 and hands back a **3840x2160** texture. Sizing an encoder from `ModeDesc` on a
   rotated output produces a transposed surface.
2. **Dirty-rect coordinates are output-local, un-rotated texture coordinates.** Measured bounding box over
   the whole run: output 0 `(0,0)-(1920,1080)` (n = 878 frames), output 1 **`(0,0)-(3840,2160)`**
   (n = 721 frames). They are never virtual-desktop absolute (output 1 sits at x = -2160 and produced no
   negative rect), and on output 1 they reach x = 3840, which is impossible in the 2160-wide rotated desktop
   space. The desktop offset **and** the rotation are both the streamer's job.
3. **Per-monitor DPI changes what a DPI-unaware caller sees.** A DPI-unaware PowerShell reports output 1 as
   1728x3072 at (-2160,-1138); the per-monitor-v2 probe reports 2160x3840. Any process in the chain that is
   not per-monitor-v2 aware will compute injection coordinates 25% off on this monitor.

## 5. `GetFrameMoveRects` then `GetFrameDirtyRects`

All runs call move rects first, then dirty rects out of the same `TotalMetadataBufferSize` buffer, as the API
requires. Coverage is a true union area (overlaps counted once), as a percentage of the output.

| scene | n frames | move rects/frame | dirty rects/frame p50 / p99 / max | dirty coverage p50 | p95 | `RectsCoalesced` | metadata bytes p50 / max |
|---|---|---|---|---|---|---|---|
| static desktop, output 0 (background apps only) | 837 | **0.00** (max 0) | 1 / 4 / 6 | 3.60% | 38.01% | 0 | 16 / 96 |
| static desktop, output 1 (genuinely idle) | 151 | **0.00** (max 0) | 1 / 6 / 7 | 0.01% | 0.04% | 0 | 16 / 112 |
| dragged window (`SetWindowPos`, 1,689 moves) | 981 | **0.00** (max 0) | 1 / 4 / 5 | 33.51% | 36.77% | 0 | 16 / 80 |
| scrolling content (`ScrollWindowEx`, 1,811 scrolls) | 915 | **0.00** (max 0) | 1 / 3 / 4 | 33.06% | 33.06% | 0 | 16 / 64 |
| **real browser page scrolling** | 1,199 | **0.00** (max 0) | 1 / 1 / 1 | **91.65%** | 91.65% | 0 | 16 / 16 |
| flood repaint, output 0 | 958 | **0.00** (max 0) | 1 / 1 / 2 | 33.33% | 100.00% | 0 | 16 / 32 |
| flood repaint, output 1 (4K) | 940 | **0.00** (max 0) | 1 / 2 / 4 | 8.33% | 8.34% | 0 | 16 / 64 |

**`GetFrameMoveRects` returned zero move rects in every scene: 0 across n = 5,981 frames.** Not for a dragged
window, not for a `ScrollWindowEx` blit, not for a GPU-composited browser scroll. `RectsCoalesced` was never
set (0 of 5,981). The move-rect path therefore has no measured benefit on Windows 11 23H2 with driver 591.86,
and the streamer must not depend on it — but the call order and the "all moves before all dirties" buffer
split still have to be implemented correctly, because the API contract does not promise zero.

The dirty-rect win is real and large in the opposite direction: an idle output costs 0.01% coverage, an
application window costs 33%, and a full-window browser scroll costs 92% — i.e. dirty rects are worth having
for signage and kiosk content and are worth almost nothing during a scroll. `TotalMetadataBufferSize` p50 was
**16 bytes** (a single `RECT`) in every scene, so reading the metadata is free.

## 8. `DXGI_ERROR_ACCESS_LOST`

Forced with a temporary mode change on output 0 (`ChangeDisplaySettingsExW` with `CDS_FULLSCREEN`, so nothing
is written to the registry), 1920x1080@60 → 1680x1050@60 and back, three rounds = **six events**. The trigger
runs on its own thread so "trigger → detect" measures the duplication, not the blocking mode change. The
probe restored 1920x1080@60 after every round and again at the end; the final restore returned
`DISP_CHANGE_SUCCESSFUL` and the layout was verified back to (0,0)-(1920,1080).

**Blast radius: both outputs lost access in 6 of 6 events** (`outputs_lost=[1, 0]` every time — output 1, a
different physical monitor on the same adapter, lost access *first*). A mode change on one output kills every
duplication on the adapter.

| event | trigger → detect | detect → recreated | recreated → first `AcquireNextFrame` | that frame had `LastPresentTime==0` | recreated → first desktop image | detect → first desktop image | retries |
|---|---|---|---|---|---|---|---|
| 1 shrink | 445.9 ms | 115.9 ms | 23.3 ms | yes | 115.2 ms | 231.1 ms | 0 |
| 1 restore | 363.6 ms | 98.4 ms | 22.1 ms | yes | 109.6 ms | 207.9 ms | 0 |
| 2 shrink | 322.3 ms | 112.9 ms | 18.5 ms | yes | 91.6 ms | 204.5 ms | 0 |
| 2 restore | 298.6 ms | 98.3 ms | 115.0 ms | no | 115.0 ms | 213.3 ms | 0 |
| 3 shrink | 328.1 ms | 316.4 ms | 1.6 ms | yes | 10.2 ms | 326.6 ms | **1** (`0x80070005`) |
| 3 restore | 330.0 ms | 103.1 ms | 107.3 ms | no | 107.3 ms | 210.4 ms | 0 |

Aggregate (n = 6 on every row):

| stage | min | p50 | p95 | max | mean | sd |
|---|---|---|---|---|---|---|
| trigger → `DXGI_ERROR_ACCESS_LOST` | 298.6 | **328.1** | 446.0 | 446.0 | 348.1 | 47.7 |
| detect → duplication recreated | 98.3 | **103.1** | 316.4 | 316.4 | 140.8 | 78.8 |
| recreated → first `AcquireNextFrame` | 1.6 | 22.1 | 115.0 | 115.0 | 48.0 | 45.3 |
| recreated → first frame with a desktop image | 10.2 | **107.3** | 115.2 | 115.2 | 91.5 | 37.2 |
| **detect → first desktop image** | 204.5 | **210.4** | 326.6 | 326.6 | 232.3 | 43.0 |

Two failure modes that a naive recovery loop gets wrong:

- **`DuplicateOutput` returns `0x80070005` (E_ACCESSDENIED) during the transition**, in 1 of 6 events. It is
  transient and succeeded on the next attempt 50 ms later. Treating it as fatal would black-screen the
  session. (The earlier six-event run of the same probe hit it twice, same code — **3 of 12 events across
  both runs**.)
- **The first `AcquireNextFrame` after recreation carried `LastPresentTime == 0` in 4 of 6 events**, i.e. a
  pointer-only frame with no desktop image, at p50 22 ms; the first frame that actually carried an image came
  at p50 107 ms. Recovery must not treat "a frame arrived" as "the picture is back".

A first run of the same measurement (before the metric was refined) gave consistent numbers over its own
n = 6: trigger → detect p50 316 ms, detect → recreated p50 111 ms, detect → first image p50 210 ms (n = 5;
one event produced no desktop image within 10 s on a fully static screen — see the recommendation).

### Lock-screen trigger: **PENDING — owner action required**

Not measured. Locking the workstation from this agent would move the input desktop to `Winlogon`, which an
unelevated user process cannot open, so the probe could not recreate the duplication and the box would be
left locked awaiting a password nobody here can type. The mode-change path was measured instead, as the task
allows.

Exact steps for the owner (≈ 90 seconds, no build needed — the binary already exists):

```
cd agent/swoop/spikes/capture-probe
.\target\release\capture-probe.exe pacing --output 0 --timeout 8 --seconds 45
```

…then press **Win+L** within the first 10 seconds, wait ~5 s, unlock, and let the run finish. Read off
`access_lost=` (expected 1) and the `WAIT_TIMEOUT`/frame counts, then run:

```
.\target\release\capture-probe.exe accesslost --output 0 --repeats 1
```

from an **elevated** console *only if* the recreate-after-unlock timing is wanted, since recreating on the
secure desktop needs SYSTEM. The unelevated case is the one that matters for the memo: it should confirm that
a lock raises `DXGI_ERROR_ACCESS_LOST` and that an ordinary user token cannot re-duplicate until unlock —
which is exactly why D2 puts the streamer on a SYSTEM token in the console session with
`OpenInputDesktop`/`SetThreadDesktop`.

## 10. Recommendation for Task 3.6

**Pacing pattern to adopt: one blocking `AcquireNextFrame` per capture thread with a timeout of 8 ms, in a
dedicated thread per output, and no frame timer of our own.**

DDA is vsync-locked: 60.0–60.4 desktop frames/s with p50 interval 16.65–16.66 ms at every timeout tested
(n = 906 at 8 ms, n = 898 on a real browser scroll with sd 0.47 ms), while the content source was changing
~3,000 times a second. Timeout 0 buys 5 fps of duplicate near-zero-interval frames for 2.7 million syscalls
and a fully burnt core (99.94% `WAIT_TIMEOUT`); timeout 16 lets the call block a full frame period and adds
jitter (sd 2.65 vs 1.35 ms). **8 ms is the measured knee**: 61.3% of calls return `WAIT_TIMEOUT` cheaply,
call p50 is 7.98 ms, and the interval distribution is the tightest of the blocking options. Treat
`DXGI_ERROR_WAIT_TIMEOUT` as "no new frame" and loop; never sleep between calls. Do not add an encoder-side
frame timer — the compositor already paces us, and D5's static-desktop floor frame rate must be a *separate*
periodic IDR, not an attempt to pull frames faster.

Corollaries, each backed by a number above:

- **Use dirty rects, ignore move rects.** 0 move rects in 5,981 frames across six scenes. Implement the
  ordered two-call read (moves before dirties, out of one `TotalMetadataBufferSize` buffer) because the API
  demands it, but build no optimisation on move rects. Dirty rects are worth it: 0.01% coverage idle vs 92%
  scrolling, and the metadata is 16 bytes at p50.
- **Take dimensions from the acquired texture, not `DXGI_OUTDUPL_DESC.ModeDesc`.** Measured: rotate270 output
  reports `ModeDesc` 2160x3840 and hands back a 3840x2160 texture.
- **Dirty rects, pointer positions and the texture are all in output-local un-rotated coordinates** — proven
  by the `(0,0)-(3840,2160)` bounding box on an output whose desktop rect starts at (-2160, -1138). Task 6.4's
  transform is `texture → rotate → + DesktopCoordinates.topleft → virtual desktop`, and 4.4's cursor hotspot
  goes through the same chain plus the per-monitor DPI ratio (96 vs 120 on this box). The streamer must set
  `DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2` before its first DXGI call or every one of those numbers is
  silently scaled.
- **Do not assume an unattended machine is idle.** A genuinely static output gives 99.54% `WAIT_TIMEOUT` and
  0.28 fps, but the primary on this same box ran at 59.97 fps continuously with ordinary apps open.

**ACCESS_LOST recovery sequence (in this order):**

1. On `DXGI_ERROR_ACCESS_LOST` from *any* output, **tear down and recreate every output's duplication**, not
   just the one that reported it. Measured: 6 of 6 mode-change events killed both outputs, and the output
   that was *not* mode-changed reported it first.
2. Release the duplication and drop the stale `IDXGIFactory`; re-enumerate adapters and outputs, because the
   output's `DesktopCoordinates` and mode can have changed under you.
3. Re-`DuplicateOutput` with a **50 ms retry, retrying on `0x80070005` E_ACCESSDENIED,
   `DXGI_ERROR_UNAVAILABLE`, `DXGI_ERROR_SESSION_DISCONNECTED` and a missing output**, and failing to exit
   code 12 only after a bounded deadline. E_ACCESSDENIED occurred in 3 of 12 events and cleared on the next
   attempt. **`0x80070057` E_INVALIDARG is not retryable** — it means the device is on the wrong adapter
   (§2) and needs a new device on the output's own adapter, not another attempt.
4. **Do not treat the first successful `AcquireNextFrame` as recovery.** It carried `LastPresentTime == 0` in
   4 of 6 events (p50 22 ms), while the first frame with an actual desktop image arrived at p50 107 ms. Gate
   "recovered" on a frame with `LastPresentTime != 0`, and on a fully static desktop a frame may not come at
   all for seconds — so arm a short timer (≈ 250 ms) after which the streamer copies the duplication's
   current surface and emits an IDR regardless.
5. Budget **p50 ≈ 210 ms, max ≈ 330 ms from detection to the first real picture** (n = 6), on top of p50
   328 ms to notice. That is ~0.5 s of black on a mode change. It is inside the 1.5 s first-frame success
   criterion but not by much, so the client must hold the last frame rather than clear to black, and the
   recreate path must not re-run the session handshake.

**Parsec virtual adapter: do not filter it out of the output list — filter the *adapter* selection instead,
and drive everything from outputs.**

It contributes **zero outputs**, so the output list needs no filtering today, and filtering by adapter
description, vendor id or VRAM is impossible anyway: adapter 1 is byte-identical to the real GPU on all three
(only the LUID differs). The correct rule, and the one Task 3.6 should implement, is:

- **Never choose a capture device by adapter.** For each `IDXGIOutput` with `AttachedToDesktop = TRUE`,
  create the D3D11 device on *that output's own* `IDXGIAdapter`. This is forced by the measured cross-adapter
  result (`E_INVALIDARG` in 4 of 4 mismatched pairs) and it makes the Parsec adapter a non-issue whether or
  not it ever has an output.
- **Skip any adapter with zero attached outputs** when enumerating capture sources, and skip
  `DXGI_ADAPTER_FLAG_SOFTWARE` (WARP, adapter 2) — both are measured to be output-less here and neither can
  duplicate anything.
- **Task 7.3's `probe` verb must not treat "an NVIDIA adapter exists" as "NVENC is available".** This box
  reports two adapters that both look like an RTX 2080 Ti and only one of them is a GPU. Probe encoders by
  opening them, not by reading `DXGI_ADAPTER_DESC1`.
- **Open question for Task 6.4** (flagged, not decided here): once Parsec *does* create a virtual display,
  adapter 1 gains an output that is a real capturable desktop on this machine. Whether swoop should offer it,
  hide it, or prefer it for headless machines is a product decision — but it will need its own D3D11 device
  on adapter 1, i.e. **a second capture device**, and that is exactly the case the "device per output's own
  adapter" rule above already handles for free.
