The only hardware MFT on this box is **NVIDIA's own** (over NVENC), so `mf-hw` here proves the asynchronous MFT
path, the D3D11 NV12 hand-off and the bitstream fixes — not Intel or AMD silicon.

**Why H.264 only, on both rungs.** These are the fallback rungs: plan.md D5 makes H.264 the codec every viewer can
decode, HEVC is NVENC's to offer, and HEVC through Media Foundation was not attempted. Both rungs report H.264 alone
in their caps, so the selector never asks them for HEVC.

reaching the sink on the pump thread. `mf-sw` is synchronous, so its figure is the whole `encode()` call.

margin: about 11 ms p50 of a 33 ms budget. It was **not** measured on a 4-core VM; this box has 10 cores.

## 2. Chrome decode

Page: **`agent/swoop/spikes/mf-decode-check/`** (new, no dependencies): `run.mjs` serves `page.html` and every
`*.h264` the ignored tests wrote (`MF_ANNEXB_DIR`) on 127.0.0.1, opens installed Chrome, and decodes each with
WebCodecs `VideoDecoder` as Annex-B with no `description`, codec string from the stream's own SPS, at
`no-preference`, `prefer-hardware` and `prefer-software`.

| stream | headless | headed |
|---|---|---|
| `mf-hw-1080p60.h264` (300 AUs, avc1.64002a) | 300/300 decoded at all three settings, 1920x1080, white panel reads (240,240,240) | same |
| `mf-sw-720p30.h264` (150 AUs, avc1.4d401f) | 150/150 at all three, 1280x720, panel (238,240,242) | same |
| `mf-sw-warp-720p30.h264` (120 AUs, CPU convert) | 120/120 at all three, panel (238,240,242) | same |

The panel is the test frames' 0xf0 white; reading it back as 240 means the limited range declared in the media
type and produced by both converts (GPU: luma blue 32 / red 63, measured; CPU: the same levels, unit-tested)
round-trips. Both MF encoders also emit access-unit delimiters and the software one two SEIs per IDR; Chrome takes
them.

## 3. Findings the owner should know

- **A forced keyframe is crushed by the one-frame buffer**, on both rungs: 73.5 KB (hw) and 64.1 KB (sw) against a
  first keyframe of 428 KB and 203 KB. This is the defect NVENC fixed with `lowDelayKeyFrameScale = 4`; Media
  Foundation has no such knob. On a still desktop a recovery keyframe will look soft until something redraws.
  Not fixed here.
- **`CODECAPI_AVEncMPVGOPSize` = 0 is not "infinite" on the in-box encoder**: it means its default, an IDR every
  30 frames. And from 65 535 up its rate control collapses (deltas 5.9 KB against a 41.7 KB target). 30 000 holds
  the rate and is used for both rungs: an IDR every 8 minutes at 60 fps.
- **WARP has no video processor**, so neither the session's downscaler nor the NV12 convert worked on a machine
  with no GPU — the case `mf-sw` exists for. Both now fall back to the CPU there, and only there
  (`ScaleError::NoVideoProcessor`); a release build keeps 30 fps at 720p.
- **A rung that cannot encode its first frame leaves the chain for the rest of the session.** A hardware MFT can
  enumerate and still fail on the capture device's adapter (a display on a BMC VGA beside a GPU that has an
  encoder); the session then re-plans its tiers from the rung below — `mf-sw`'s 720p — instead of retrying the same
  failure every frame.
- **The hardware probe's ceiling is only as good as the MFT's own check**: NVIDIA's MFT accepts a test-only
  8192x8192 H.264 output type. The probe starts at 4096x4096, so it answers H.264's own cap; whether AMD's and
  Intel's MFTs refuse what they cannot do is unmeasured.
- **N editions**: `mfplat.dll` is resolved at run time by absolute path, never imported, so an N edition without
  the Media Feature Pack still starts the streamer (NVENC and `probe` work); it just has no MF rungs. Verified by
  the imports table of the built exe (no `mfplat.dll`), not on an N install.
- **`BackendCaps` for the MF rungs**: `max_fps` is 0 on both — the probe never encodes, so nothing is measured,
  and nothing selects on it; `mf-sw`'s 30 fps cap is the encoder's own. `concurrent_sessions` is a fixed 4:
  Media Foundation has no session count to ask for, both rungs are H.264 only so every viewer shares one encoder,
  and `session::tiers::admit` caps *viewers* at this figure, so 4 is the bundle's default viewer cap.

## 4. Fallback chain for 7.3

`nvenc` (H.264 + HEVC) → `mf-hw` (H.264, up to 4096x4096) → `mf-sw` (H.264, 1280x720, 30 fps). On this box the
probe resolves H.264 to all three and HEVC to `nvenc` alone; NVENC wins every session.

## 6. Intel and AMD rows — not measurable on available hardware

Every Intel and AMD cell in §1 is **not measurable on available hardware**: this box has neither. On an Intel iGPU
box and on an AMD box, from a checkout of this branch with a Rust toolchain and Google Chrome installed:

```
cd agent\swoop
mkdir C:\mf-annexb
set MF_ANNEXB_DIR=C:\mf-annexb
cargo test --release --lib -- --ignored encode::mf --test-threads=1 --nocapture > C:\mf-annexb\results.txt
node spikes\mf-decode-check\run.mjs C:\mf-annexb --headed >> C:\mf-annexb\results.txt
```

Then paste `results.txt` here. The tests open the MFT for the default adapter's device, so run with the Intel or
AMD GPU driving the main display. What to read off it: the `mf-hw` lines (latency at 1080p60 and 4K60, forced IDR,
iraps, the 60 s rate, the probe's ceiling — AMD should answer 4096x4096 and nothing above), the `own sps` line
(whether the restriction had to be added), the `ltr` line, and whether Chrome decoded every access unit.
