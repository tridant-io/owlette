### 1.1 Method, and what the numbers do and do not mean

The node half stands in for the browser: same WebSocket handshake, same subprotocol-carried token, same
message shapes. The python half is the real client the agent will ship. One-way numbers subtract a python
wall-clock stamp from a node one; on Windows both `Date.now()` and `time.time()` read
`GetSystemTimePreciseAsFileTime`, so they share a clock. `Date.now()` is integer-truncated, which puts roughly
±1 ms of quantisation on a sub-2 ms figure — the one-way hop number should be read as "about a millisecond
locally", not as 0.83.

These are loopback numbers with no network in them. They are useful for exactly two things: they prove the
protocol works end to end, and they isolate the **software** cost of each path. The important comparison is
that the ring path (`POST /v1/ring` → Worker → DO stub fetch → socket) costs ~7 ms more than a message on an
already-open socket (~0.8 ms). That gap is an HTTP request plus a Worker→DO subrequest, and on the edge it
becomes a full extra origin round trip. `research/04-nat-turn-signaling.md` §4.6 budgets 20–80 ms for "offer to
host over warm WS"; nothing here contradicts that, and nothing here confirms it either. Only §6 can.

The idle-ring figure (16 ms after a 20 s silence, twice the warm p50, and stable across both runs) is
suggestive of the isolate going cold, but local `wrangler dev` does not evict Durable Objects, so **this spike
cannot demonstrate real hibernation**. What it does demonstrate is the property hibernation rests on: see §3.2.

## 2. What was built

A Worker (`src/worker.js`) plus one Durable Object per machine (`src/room.js`) on the WebSocket hibernation
API — `ctx.acceptWebSocket()`, `serializeAttachment()`, `ctx.setWebSocketAutoResponse()`. Routes and message
names are the plan's names registry exactly: `GET /health`, `GET /v1/room/{siteId}/{machineId}` (WS),
`POST /v1/ring`, `POST /v1/kill`; messages `hello`, `ring`, `viewer-join`, `host-ready`, `offer`, `answer`,
`candidate`, `kill`, `bye`, `error`.

**Room addressing.** The Durable Object name is `${claims.site}:${claims.machine}` from the *verified token*.
The path is a readability aid that must agree with the claims or the upgrade is refused 403 `room_mismatch`
(`review-2-security.md`, "sections that held up"). A client cannot address another machine's room by asking
for it, and the room never sees the token at all — the Worker strips `Authorization` and
`Sec-WebSocket-Protocol` and forwards resolved identity as `x-swoop-*` headers on the internal hop.

**Token carriage.** The agent sends `Authorization: Bearer <jwt>`. A browser cannot set handshake headers, so a
viewer sends `Sec-WebSocket-Protocol: owlette.swoop.v1, jwt.<token>` and the Worker echoes back only
`owlette.swoop.v1`. A query parameter was rejected: it would put the token in Cloudflare's access logs. Both
paths are exercised by the tests.

**Fan-out.** A viewer's traffic reaches the host and doorbell sockets and never another viewer; the agent side
answers a named viewer (`to`) or broadcasts to all viewers when it names none; `viewer-join` is announced to
host and doorbell on join. `offer` is viewer-only, `answer`/`host-ready` are host-only, and `ring`/`kill`/
`hello`/`viewer-join`/`error` from a client are refused `forbidden_type` — a client cannot forge a ring or a
kill over its own socket.

**Two active keys.** `SWOOP_JWT_PUBLIC_KEYS` is a JSON array of at most two `{kid, key}` entries (base64url raw
32-byte Ed25519 public keys). Both are accepted; an unknown `kid` is refused `unknown_kid`
(`review-3-delivery.md` F6.3). Tested with both kids and with a token whose header claims `kid` k1 but is
signed by k2 (→ `bad_signature`).

**Claim checks**, each with its own refusal code: `alg=EdDSA`, `kid`, `iss=owlette-api`, `aud=swoop-signal`,
`role ∈ {viewer, host, doorbell}`, `exp` with 30 s skew, `exp - iat ≤ 300 s`, `site`/`machine`/`viewer`/`sid`
against `^[A-Za-z0-9_-]{1,64}$`, 4 KiB token ceiling. Refusals carry a code and nothing else.

## 3. The two runtime facts the task asked for

### 3.1 The Ed25519 algorithm identifier

Probed directly on workerd 1.20260917.1 with a throwaway Worker (run outside the repo, deleted):

| `crypto.subtle.importKey('raw', …)` algorithm | imported | resulting `key.algorithm.name` |
|---|---|---|
| `{ name: 'Ed25519' }` | yes | `Ed25519` |
| `{ name: 'ed25519' }` | yes | `Ed25519` (normalised) |
| `{ name: 'NODE-ED25519', namedCurve: 'NODE-ED25519' }` | yes | `NODE-ED25519` |

**Use `Ed25519`.** No compatibility flag is needed on `compatibility_date = 2026-09-01`. The legacy
vendor-prefixed name still imports, but it keeps its own algorithm identity, so a key imported as
`NODE-ED25519` must also be *verified* as `NODE-ED25519` — mixing the two throws. Task 1.4 should hardcode
`Ed25519` in one place and never branch on it. `/health` reports the constant the Worker uses so a deployed
instance can be checked without a token.

### 3.2 Hibernation is real in the code path, not just in the config

`ctx.setWebSocketAutoResponse(new WebSocketRequestResponsePair('ping', 'pong'))` is installed in the DO
constructor. The test `answers an app-level keepalive without waking the room` sends the bare string `ping`:
had it reached `webSocketMessage` the answer would have been an `error` frame, because `ping` is not JSON.
It answers `pong`. That is a positive proof the runtime handled the keepalive without waking the object — the
property the entire idle-cost model in §5 rests on, and the one that would silently disappear if someone later
made the object non-hibernatable.

The python doorbell additionally uses **protocol** pings (`run_forever(ping_interval=20, ping_timeout=10)`),
which `research/04-nat-turn-signaling.md` §4.3 records as auto-answered and **not billed**. The app-level
`ping`/`pong` pair exists for the browser, which has no way to send a protocol ping from JavaScript.

## 4. Ring, flood and the cap

`POST /v1/ring` carries `{site, machine, sid}` and nothing else, authenticated by
`SWOOP_SIGNAL_RING_SECRET` in an `x-swoop-ring-secret` header, compared in constant time. A wrong secret is
401 `bad_ring_secret` before anything else happens, and before any Durable Object is touched.

Demonstrated end to end: node posts a ring, the Worker routes to the room derived from the body, the DO sends
`{"type":"ring","sid":…}` to every doorbell socket, and the python `SpikeDoorbell` callback fires on its own
daemon thread and prints the latency. 200 consecutive rings, zero losses, p50 7.79 ms (§1).

**Ring cap** (`review-2-security.md` M5): 10 rings per 60 s per machine, enforced inside the DO so it cannot be
bypassed by hitting a different Worker instance. Over the cap is HTTP 429 with
`{code:'ring_capped', retryAfterMs}`. Flood result, measured against a live doorbell at the shipped cap:

```
sent 25 · accepted 10 · capped 15 · cap 10 · window 60000 ms · delivered to python 10
```

The cap is worth having even though the API rate-limits first, because
`web/lib/rateLimit.server.ts:446-450` fails **open** for a capability nobody added to the table, and every
accepted ring spawns a SYSTEM process holding an encoder session on a customer's machine.

**Known limitation, and the recommendation that follows.** The window lives in the DO's memory, so hibernation
resets it. A flood keeps the object awake, so the cap holds against the case it exists for; a paced attacker
under 10/min is not a cost problem by definition. Task 2.8 should nonetheless persist the window head in
`ctx.storage` (one small write per accepted ring — rings are rare by design) so the ceiling survives eviction,
and should keep the read path free of storage so an idle room still costs nothing.

The measurement pass needs more than 10 rings, so the DO reads an optional `SWOOP_RING_CAP` override; it is
unset in `wrangler.toml`, unset in every test, and passed only as `--var` for the latency run, which is why the
flood pass boots a second, default-cap worker.

## 5. Idle cost, line by line

All rates from `research/04-nat-turn-signaling.md` §4.3, which cites Cloudflare's Durable Objects pricing page
(last updated 2026-08-25):

- **R1** Paid plan: 1,000,000 DO requests/month included, then **$0.15 per additional million**.
- **R2** Incoming WebSocket messages are billed **20:1** (20 incoming = 1 billed request; the page's own
  worked example is 1M incoming = 50,000 billed requests = $0.0075, which checks out against R1).
- **R3** Outgoing messages and WebSocket **protocol pings are free**.
- **R4** Hibernation-eligible objects incur **no duration charge**, even before actual eviction — so the
  $12.50/million GB-s rate (400,000 GB-s/month included) applies to nothing here.
- **R5** SQLite storage: 5 GB-month included, $0.20/GB-month. This room stores nothing → $0.
- **R6** Free plan alternative: 100,000 requests/day, 13,000 GB-s/day.
- **R7** Outbound connections keep an object alive up to 15 minutes **and do incur duration charges**.

### 5.1 One permanently-connected doorbell, 30-day month

| line | quantity | billed |
|---|---|---|
| L1 WebSocket upgrade (the dial) | 1 | 1 DO request (R1) |
| L2 protocol pings at 20 s | 129,600 frames | **0** (R3) |
| L3 pongs back to the agent | 129,600 frames | **0** (R3, outgoing) |
| L4 object duration while idle | 2,592,000 s | **0 GB-s** (R4) |
| L5 storage | 0 bytes | **$0** (R5) |
| L6 re-dials after a reboot or a blip, `d` per day | 30·`d` | 30·`d` DO requests (R1) |

Idle requests per doorbell per month = **1 + 30·d**. Nothing else on an idle socket is billable.

### 5.2 The fleet numbers

| fleet | `d` = 1 re-dial/day | `d` = 24 re-dials/day (a flapping network) |
|---|---|---|
| 1,000 doorbells | 31,000 req/mo → inside the 1M included → **$0.00** | 721,000 req/mo → inside → **$0.00** |
| 10,000 doorbells | 310,000 req/mo → inside → **$0.00** | 7,210,000 req/mo → 6,210,000 over × $0.15/M → **$0.93/mo** |

Free-plan check (R6) at `d` = 1: 10,000 doorbells ≈ 10,000 requests/day against a 100,000/day cap, and 0 GB-s
against 13,000 GB-s/day. **Idle doorbells alone fit the free plan at 10,000 machines.** Sessions do not — see
below — but the doorbell is not what forces the paid plan.

For scale, the same fleet *in use* at 5 sessions/machine/day, one viewer each, ~40 incoming room messages per
session (§4.3's own estimate): per machine/month = 31 dials + 150 rings + 150 viewer upgrades + 150 host
upgrades + (150 × 40 ÷ 20 =) 300 message-requests + 15 kills = **796 DO requests**. 1,000 machines →
796,000/mo → **$0.00**. 10,000 machines → 7,960,000/mo → 6,960,000 over → **$1.04/mo**.

### 5.3 What would break this model

1. **Anything that makes the object non-hibernatable** — an `alarm`, a `setInterval`, a held outbound fetch
   (R7). Losing R4 turns the GB-s line from zero into the dominant cost: 10,000 rooms held awake for a month at
   the standard 128 MB per object would be ~3.3 billion GB-s ≈ $41,500/month. (The 128 MB figure is *not* in
   §4.3; treat the arithmetic as an order of magnitude, not a quote.) **This is the single most expensive
   mistake available in Task 2.8.** The keepalive test in §3.2 is the regression guard for it and should be
   carried into the product suite.
2. **App-level keepalives from the agent.** Protocol pings are free; a JSON `{"type":"ping"}` every 20 s is
   not — 129,600 incoming messages/month ÷ 20 = 6,480 billed requests per doorbell per month, which at 10,000
   doorbells is 64.8M requests, 63.8M of them over the included million: **$9.57/month** for nothing. Small in
   money, but it is a 10× multiple of the entire real workload in §5.2, and it is invisible until the invoice.
   The agent must use `ping_interval` on `run_forever`, never an application heartbeat. Browsers have no
   choice, but viewer sockets are minutes long, not months.
3. **A reconnect storm.** 10,000 doorbells re-dialling every 30 s is 864M requests/month, 863M of them
   billable: **$129/month**, and a self-inflicted DDoS on one's own Worker. The backoff and circuit breaker in
   spike 0.6 are a cost control as much as an availability one.
4. **§4.3 prices Durable Objects only.** Every DO request above is also a Workers request, and §4.3 gives no
   Workers rate. Task 1.4 must price that line separately before quoting a total.

## 6. PENDING — deployed edge pass `[human]`

This is the half the agent cannot do: it needs the owner's Cloudflare account. The spike is written so the same
script produces the same report against the real edge.

```
cd agent/swoop/spikes/signal-worker
npm install
npm run keys                                   # fresh throwaway keyset + ring secret -> .dev.vars
npx wrangler login
npx wrangler secret put SWOOP_JWT_PUBLIC_KEYS      # paste the value from .dev.vars, quotes stripped
npx wrangler secret put SWOOP_SIGNAL_RING_SECRET   # same
npx wrangler deploy
curl https://swoop-signal-spike.<subdomain>.workers.dev/health
node scripts/measure.mjs --remote https://swoop-signal-spike.<subdomain>.workers.dev
```

`--remote` changes the running order by itself: the flood goes first at the shipped cap of 10, the script waits
out the 60 s window, then takes the ring-latency samples. Expect ~3 minutes. Paste the JSON it prints into
§1 and record, next to it, the `colo` from `/health` (the edge that served the request) and the physical
location of the machine you ran it from.

**The DO home-location effect is what this pass is for.** A Durable Object is pinned to where it was first
created and cannot be moved afterwards. `measure.mjs` starts the python doorbell before it sends anything else,
so the room is created by the agent's dial and homes near the agent — which is what §4.3 advises. Run the pass
twice if a second machine is available (one near the doorbell, one far from it): the difference between the two
`roomHopMs` figures **is** the home-location effect, and it is the number that tells Task 1.4 whether a ring
from Railway's region to a machine's home DO fits inside the ≤ 1.5 s first-frame budget.

Tear-down when finished: `npx wrangler delete` (the spike Worker is not the product Worker) and rotate nothing
— the keys were throwaway and never left the machine.

## 7. Against the research

- **`research/04-nat-turn-signaling.md` §4.3's last bullet is stale.** It says doorbell "reconnect/backoff must
  live inside `ConnectionManager`, per this repo's guardrails". plan.md's owner ruling reverses exactly that,
  and spike 0.6 is the design. The research doc predates the ruling; do not follow it.
- **New, not in the research: the ring costs an order of magnitude more than a room message.** 7.8 ms vs
  0.8 ms locally, all of it the HTTP request plus the Worker→DO subrequest. §4.3 treats "one message hop" as a
  single figure. For the connect budget the ring and the in-room hop are different animals and should be
  budgeted separately.
- **New, and an operational landmine: whoever touches a room name first owns its home location forever.** If a
  `POST /v1/ring` reaches a machine whose agent has never dialled, the room is created from the API's colo and
  stays homed near Railway, permanently, for that machine. Task 3.2 must not ring a machine that is not already
  connected, and Task 2.8 should treat "ring with no doorbell attached" as a refusal, not a no-op.
- **New: a browser cannot send a WebSocket protocol ping from JavaScript**, so the free keepalive of §4.3 is
  available to the agent and not to the viewer. Handled with an auto-response pair; noted so nobody "fixes" the
  viewer keepalive into an expensive one.
- **Still unverified, as §4.3 said:** no documented max-concurrent-WebSockets-per-DO limit. Our room holds one
  doorbell, one host and N viewers, so it is not a near-term concern; it would become one only if a room were
  ever reused as a fleet-wide channel. Do not do that.
- `serializeAttachment()`'s 16,384-byte ceiling is honoured with room to spare — the attachment is
  `{role, id, sid, ctl, joinedAtMs}`, about 140 bytes — and an oversized one is refused at join rather than
  discovered at runtime.

## 8. Recommendation for Task 1.4 / 2.8 — the Worker's shape

Take this spike's shape essentially as-is. Specifically:

1. **One Durable Object per machine, named from the verified token's `site`+`machine` claims.** Refuse a path
   that disagrees (`room_mismatch`). Never accept a client-supplied room id, and never let the API create a
   room for a machine that has not dialled (§7).
2. **Every socket through `ctx.acceptWebSocket`, no alarms, no timers, no outbound fetches in the DO.** Keep
   `setWebSocketAutoResponse('ping','pong')` and carry the bare-`ping` test into the product suite as the
   hibernation regression guard. This is worth more than any other single decision in the file (§5.3).
3. **`Ed25519` via WebCrypto, one constant, no branching**, with a keyset of at most two `{kid, key}` entries
   read from one secret. Unknown `kid` → refuse. Keep the refusal codes distinct and boring; they are the only
   thing that will ever be logged.
4. **Three files, not one**: `jwt.js` (verification, no I/O), `room.js` (the DO), `worker.js` (routing and the
   ring secret). The spike splits this way and the seams held; the JWT module is the one worth unit-testing in
   isolation because it is where a subtle acceptance bug would live.
5. **Keep the room a dumb pipe.** It routes by role and `to`, refuses server-only types from clients, and knows
   nothing about sessions, capabilities, step-up or Firestore. Every authorisation decision was made by the API
   before the token was minted. This is what makes plan.md D8's "a compromised relay cannot mint a session"
   true in code and not just on paper.
6. **Persist the ring window** (§4) and keep the cap in the DO, not in the Worker.
7. **Token carriage**: `Authorization` for the agent, `Sec-WebSocket-Protocol: owlette.swoop.v1, jwt.<token>`
   for the browser, echoing back only the plain subprotocol. No query parameters, ever.
8. **`/health` must not touch a Durable Object** — it would home a room from wherever the health check ran.
   Report the keyset's kids, the algorithm constant and the colo; that is enough to debug a deploy.
9. **Two secrets, both `must-match`**: `SWOOP_JWT_PUBLIC_KEYS` and `SWOOP_SIGNAL_RING_SECRET`. The spike's
   `npm run keys` → `.dev.vars` → `wrangler secret put` flow is the same shape 3.4 needs; `.dev.vars` and
   `testdata/` are gitignored and no key is ever committed.
