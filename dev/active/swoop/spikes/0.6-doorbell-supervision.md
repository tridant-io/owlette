## 1. Why the doorbell supervises itself

plan.md's owner ruling makes the doorbell a documented exception to "never spawn reconnection logic outside
`ConnectionManager`". The evidence, re-verified:

| fact | file:line (verified) |
|---|---|
| `ConnectionManager.register_thread(name, factory)` — registers a thread the watchdog will police | `agent/src/connection_manager.py:698` |
| `_watchdog_loop` scans `_supervised_threads` and, on **any** dead one, calls `report_error(...)` | `connection_manager.py:765-786` (the `report_error` call is exactly `:783-786`) |
| watchdog cadence | `WATCHDOG_INTERVAL = 10.0`, `connection_manager.py:217` |
| `report_error` sets `DISCONNECTED` and calls `_trigger_reconnect` — on the **Firestore** connection | `connection_manager.py:436-471` (the brief cites `:436-472`; the method ends at `:471`) |
| circuit breaker trip point | `FAILURE_THRESHOLD = 5`, `connection_manager.py:210` |
| Firestore reconnect ladder | `BACKOFF_BASE = 30.0` / `BACKOFF_MAX = 3600.0`, `connection_manager.py:205-206` |
| the only two legitimately supervised threads | `firebase_client.py:173` (`command_listener`), `:177` (`config_listener`) |

`ConnectionManager` is not a generic socket supervisor: its state **is** the Firestore connection's state.
A doorbell registered at `:698` would mean that a Cloudflare Worker incident — one origin, one failure, the
whole fleet at once — kills the doorbell thread on every machine, and ten seconds later
(`WATCHDOG_INTERVAL = 10.0`) every agent reports a Firestore error it does not have, drops to `DISCONNECTED`
and re-establishes Firestore. Repeat until the circuit opens at five failures, then on the 30 s → 1 h ladder.
Nothing about Firestore was wrong. (`research/review-3-delivery.md` F1.)

**Hard rules for `swoop_doorbell.py`:**

1. It **never** calls `ConnectionManager.register_thread` (`:698`) or `report_error` (`:436`), and never
   `force_reconnect`, `report_success` or `_restart_all_threads`.
2. It does not `import connection_manager` **at all**. The offline gate is an *injected callable*
   (`is_connected: Callable[[], bool]`), wired by Task 3.1 as `service.firebase_client.is_connected`
   (`firebase_client.py:575`, which returns `connection_manager.is_connected`, `connection_manager.py:301-303`,
   itself a lock-guarded read of the `state` property at `connection_manager.py:287-291`). Reading that
   property has no side effects. The absent import is what makes "zero calls into ConnectionManager"
   testable as a property of the module rather than of one code path.
3. Nothing restarts the doorbell thread from outside. **The loop supervises itself from the inside**: every
   state handler runs under a top-level `except BaseException` that logs once and re-enters the state machine
   as a dial failure, so the thread body cannot terminate short of `shutdown_event` or interpreter teardown.

## 2. State machine

Seven operational states plus a terminal one. `HALF_OPEN` is the circuit's probe step (the brief's
"half-open probe"); everything else is the brief's list verbatim.

```
                 shutdown_event (any state)
                 ─────────────────────────────────────────────► STOPPED
   ┌──────┐  online   ┌──────────┐  101 upgrade  ┌───────────┐
   │ IDLE │──────────►│ DIALLING │──────────────►│ CONNECTED │
   └──────┘           └──────────┘               └───────────┘
      ▲   ▲                │ │ │                    │      │
      │   │      failure   │ │ │ 403 swoop_disabled │      │ drop / ping timeout
      │   │  ┌─────────────┘ │ └──────────┐         │      ▼
      │   │  ▼               │            ▼         │  ┌─────────┐
      │  ┌─────────┐         │    ┌───────────────┐ │  │ BACKOFF │
      │  │ BACKOFF │─────────┘    │ DISABLED_SLOW │ │  └─────────┘
      │  └─────────┘ window ends  └───────────────┘ │       │ 12 consecutive failures
      │       │ offline                  │  ▲       │       ▼
      │       └──────────────────────────┼──┼───────┘  ┌──────────────┐
      │  offline                         │  │          │ CIRCUIT_OPEN │
      └──────────────────────────────────┘  │          └──────────────┘
                                            │             │ probe timer   ▲
                                            │             ▼               │ probe failed
                                            │        ┌───────────┐        │
                                            └────────│ HALF_OPEN │────────┘
                                          403        └───────────┘
                                                      │ 101 upgrade
                                                      ▼  CONNECTED
```

### 2.1 Transition table (complete)

| # | from | event | to | actions |
|---|---|---|---|---|
| 1 | *(none)* | `start()` | IDLE | create daemon thread `swoop-doorbell`; `failures = 0`, `exponent = 0` |
| 2 | IDLE | `is_connected()` is false | IDLE | `shutdown_event.wait(OFFLINE_RECHECK_SECONDS)`; no dial, no ladder movement |
| 3 | IDLE | `is_connected()` is true | DIALLING | reset `failures = 0`, `exponent = 0`, clear the circuit flag (an offline→online edge is a genuinely new network situation — DHCP, VPN, a changed uplink — and is the most likely thing to have fixed a long doorbell outage on one machine) |
| 4 | DIALLING | no cached token, or cached token past its deadline | DIALLING | mint: `POST {get_api_base_url()}/agent/swoop/doorbell-token`, `Authorization: Bearer <agent id token>`, `timeout=10` (pattern `firebase_client.py:2531-2546`) |
| 5 | DIALLING | mint 200 | DIALLING | cache token + `expiresIn`; compute the monotonic refresh deadline (§4) |
| 6 | DIALLING | mint 403 `swoop_disabled` | DISABLED_SLOW | drop any cached token; `failures` unchanged (a 403 is a healthy server answering) |
| 7 | DIALLING | mint 401 / 404 / any other 4xx | DISABLED_SLOW | log the status once per episode. A 401 here means the *agent's* Firebase token is bad — `auth_manager.get_valid_token` (`auth_manager.py:503`) owns that ladder; the doorbell must not add a second one, and must not report it |
| 8 | DIALLING | mint 5xx / network / timeout | BACKOFF | `failures += 1`, `exponent += 1` |
| 9 | DIALLING | WSS upgrade returns 101 | CONNECTED | record `connected_at = time.monotonic()`; arm the stability timer (§3, `STABLE_CONNECTION_SECONDS`) |
| 10 | DIALLING | upgrade 401, or close with the Worker's auth reason, **and** the free-retry credit is available | DIALLING | discard the token, re-mint, dial again with **no wait**; spend the credit (`AUTH_RETRY_COOLDOWN_SECONDS`) |
| 11 | DIALLING | upgrade 401 with the credit already spent | BACKOFF | `failures += 1`, `exponent += 1` |
| 12 | DIALLING | upgrade 403 `swoop_disabled` | DISABLED_SLOW | drop the token |
| 13 | DIALLING | connect refused / TLS error / timeout (`DIAL_TIMEOUT_SECONDS`) | BACKOFF | `failures += 1`, `exponent += 1` |
| 14 | CONNECTED | frame is exactly `{"type":"ring","sid":"<str>"}` | CONNECTED | push `sid` onto the bounded ring queue; the single-flight worker calls `on_ring(sid)` **off the socket thread** |
| 15 | CONNECTED | frame malformed, extra field, non-string `sid`, unknown type, or non-JSON | CONNECTED | drop it, increment a counter, log `"rejected ring frame (reason=<enum>)"` — never the payload |
| 16 | CONNECTED | frame larger than `MAX_MESSAGE_BYTES` | BACKOFF | close the socket; an over-cap frame is a protocol violation, not a bad ring; `failures += 1` |
| 17 | CONNECTED | socket closed / read error / ping timeout, uptime ≥ `STABLE_CONNECTION_SECONDS` | BACKOFF | `failures = 0`, `exponent = 0` **first**, then wait window 1 |
| 18 | CONNECTED | socket closed, uptime < `STABLE_CONNECTION_SECONDS` | BACKOFF | `failures += 1`, `exponent += 1` |
| 19 | CONNECTED | close with the Worker's auth reason (expired token / unknown `kid`) | DIALLING | as row 10 (free retry) |
| 20 | CONNECTED | monotonic refresh deadline reached **and** a new token is in hand | DIALLING | send `bye`, close, dial on the new token (see §4 — mint first, close second) |
| 21 | CONNECTED | refresh deadline reached, mint failing, still > `TOKEN_HARD_DEADLINE_SECONDS` before `exp` | CONNECTED | keep the working socket; retry the mint on the ladder in the background |
| 22 | CONNECTED | mint still failing at `exp − TOKEN_HARD_DEADLINE_SECONDS` | BACKOFF | close; `failures += 1` |
| 23 | CONNECTED | `is_connected()` goes false | CONNECTED | **no action.** A warm socket that still works is worth keeping even when Firestore is unhappy. The offline gate gates *dialling*, never teardown |
| 24 | CONNECTED | `refresh_now()` | CONNECTED | logged no-op (the socket is already warm); returns immediately |
| 25 | BACKOFF | `shutdown_event.wait(w)` elapses, `failures < FAILURE_THRESHOLD`, `is_connected()` true | DIALLING | `w = uniform(0, min(BACKOFF_MAX, BASE × FACTOR^min(exponent, CEILING)))` |
| 26 | BACKOFF | window elapses, `failures ≥ FAILURE_THRESHOLD` | CIRCUIT_OPEN | arm the probe timer |
| 27 | BACKOFF | window elapses, `is_connected()` false | IDLE | park; do not burn ladder steps while the box has no network |
| 28 | BACKOFF | `refresh_now()` | DIALLING | collapse the remaining wait to zero; keep `failures` (an operator action is evidence the *policy* changed, not that the origin recovered) |
| 29 | CIRCUIT_OPEN | probe timer elapses | HALF_OPEN | — |
| 30 | CIRCUIT_OPEN | `refresh_now()` | HALF_OPEN | collapse the probe wait |
| 31 | CIRCUIT_OPEN | `is_connected()` false at the timer | IDLE | clear the circuit (row 3 will reset on the way back) |
| 32 | HALF_OPEN | one dial, 101 upgrade | CONNECTED | close the circuit; `failures = 0`, `exponent = 0` |
| 33 | HALF_OPEN | one dial fails | CIRCUIT_OPEN | re-arm the probe timer; **never** ladder from here — exactly one dial per probe window |
| 34 | HALF_OPEN | 403 `swoop_disabled` | DISABLED_SLOW | clear the circuit — the server answered, so the origin is up |
| 35 | DISABLED_SLOW | wait elapses | DIALLING | `failures = 0`, `exponent = 0` |
| 36 | DISABLED_SLOW | `refresh_now()` | DIALLING | collapse the wait; `failures = 0` |
| 37 | DISABLED_SLOW | `is_connected()` false | IDLE | — |
| 38 | any | `shutdown_event` set, or `stop()` | STOPPED | send `bye` if a socket is open, close it, return from the thread. Every wait in the machine is `shutdown_event.wait(timeout)` — never `time.sleep` — so the exit latency is the socket close, not the pending window |
| 39 | any | unhandled exception inside a state handler | BACKOFF | log once (`type(e).__name__` + `str(e)`, never a payload), `failures += 1`. **The thread does not die.** |

## 3. Parameters — every number with its reason

Constants for Task 2.3 to lift verbatim into `swoop_doorbell.py`.

| constant | value | why this number |
|---|---|---|
| `BACKOFF_BASE_SECONDS` | `2.0` | The first retry after a single dropped socket. A Worker redeploy, a DO eviction race or a transient edge 502 resolves in under a second, so a 2 s first window keeps a one-machine blip invisible — re-warm lands inside the 2 s floor of the Firestore command poll, i.e. before the polled fallback could have covered it. Small enough to be free, large enough that a crash-looping peer cannot spin the thread. (`ConnectionManager`'s 30 s is right for Firestore, where each attempt is expensive and the machine is *down*; a cold doorbell is a degradation, not an outage, but the cheapest thing to fix.) |
| `BACKOFF_FACTOR` | `2.0` | Plain doubling. Anything slower needs more steps to reach the cap; anything faster skips the middle of the ladder, which is where a 30–60 s Worker deploy window lives. |
| `BACKOFF_MAX_SECONDS` | `300.0` (5 min) | Bounds the fleet's **re-warm time after a Cloudflare incident ends**. Worst case a machine is warm 5 min after the Worker returns, and with full jitter the fleet's re-dials spread uniformly across that window, giving the recovering Worker a smooth ramp instead of a step. `ConnectionManager`'s 1 h cap (`:206`) would leave the fleet cold for up to an hour after recovery, and every session start in that hour would fall to the ~35 s polled path — directly contradicting the "first frame p50 ≤ 1.5 s with a warm doorbell" criterion. The cost of the shorter cap is one failed TCP connect per machine per 5 min during a total outage: at 10,000 machines that is ~2,900 connects/minute at the edge, which never reaches a Durable Object and is not billed as a DO request. |
| `BACKOFF_EXPONENT_CEILING` | `8` | `2 × 2^8 = 512 > 300`, so step 9 is already at the cap. Clamping the exponent keeps the ladder an explicit twelve-element list instead of an unbounded float, and makes the test in §6 a literal comparison. |
| full-jitter rule | `wait = random.uniform(0, window)` | **Full jitter, not `ConnectionManager`'s 50–100 %** (`connection_manager.py:649-650`: `BACKOFF_JITTER + random() * BACKOFF_JITTER`). Firestore failures are uncorrelated across machines, so half-width jitter is enough there. Doorbell failures are *perfectly* correlated — one origin, one Worker, one moment — so the re-dials must be spread over the whole window or the fleet arrives in the top half of it together. Full jitter is the variant AWS's "Exponential Backoff And Jitter" measured as minimising both total client work and time-to-completion under contention, and the difference only matters when failures are correlated, which is exactly this case. This divergence from `ConnectionManager` is deliberate and belongs in a comment in `swoop_doorbell.py`. |
| `FAILURE_THRESHOLD` | `12` | Consecutive failures before the circuit opens. Twelve is the point where the ladder has clearly saturated: windows 1–8 climb 2 → 256 s, windows 9–12 sit at the 300 s cap, so twelve failures is `2+4+8+16+32+64+128+256+4×300 = 1710 s` worst case and ~855 s expected under full jitter — **~14 min expected, ~29 min worst**, plus up to 12 × 10 s of dial timeouts. That is long enough to ride out a Worker deploy, a DNS blip or a regional Cloudflare event without giving up, and short enough that a machine whose signal origin is permanently unreachable (an outbound firewall rule on a customer's kiosk VLAN) stops retrying every five minutes within the half hour. `ConnectionManager`'s `5` (`:210`) is tuned for a resource whose loss is an emergency; this one is tuned for a resource whose loss is a slower session start. |
| `CIRCUIT_PROBE_SECONDS` | `900.0` (15 min), jittered to `uniform(450, 900)` | The probe's only job is to notice recovery after we have already established the origin is down, so it trades latency for cost. Expected cadence ~11 min ⇒ ~130 probes/machine/day; even at 10,000 machines and even if every probe reached a DO that is 1.3 M requests/day at $0.15/M ≈ $0.20/day, and during a real outage they fail at the edge and cost nothing. A half-width jitter (not full) is correct here: the circuit-open population is already decorrelated by the ladder that got them there, and a full-jitter draw could return 10 s, which would be a fast retry wearing a probe's name. |
| half-open rule | exactly **one** dial per probe window | A half-open state that retries is just a slower ladder. One dial, then the verdict: success closes the circuit and resets both counters; failure re-arms the timer. No more than one in-flight dial ever exists in any state. |
| `STABLE_CONNECTION_SECONDS` | `120.0` | Uptime at which a connection counts as evidence of health, resetting `failures`/`exponent`. Two full keepalive round trips (2 × 45 s) plus margin: a socket that has answered two pings has demonstrably passed the whole path — client NAT, corporate middlebox, Cloudflare edge, DO. Without this rule a socket that connects and drops every 3 s never advances the ladder (hot loop), and a socket up for eight hours that finally blips would restart at the 5 min cap. |
| `DISABLED_RETRY_SECONDS` | `1800.0` (30 min), jittered to `uniform(900, 1800)` | The steady state for **most machines in the fleet**, since swoop is off by default per the owner's security ruling: one HTTPS request to our own API per machine per ~22 min ≈ 65/day/machine, negligible against the heartbeat. It is deliberately not shorter, because nobody waits on it — enabling swoop sends `swoop_refresh` (§5), which collapses the wait to zero. It is deliberately not longer (e.g. hourly) because `swoop_refresh` only reaches machines that are online at the moment of the toggle; a machine that boots an hour later needs a bounded time-to-warm without operator action. |
| `OFFLINE_RECHECK_SECONDS` | `30.0` | How often IDLE re-reads the injected `is_connected()`. `ConnectionManager`'s own watchdog runs at 10 s (`:217`) and its backoff floor is 30 s (`:205`), so a 30 s recheck can never out-poll the thing it observes, and the read itself is one lock-guarded attribute fetch. Worst case the doorbell is warm 30 s after the network returns, against a Firestore reconnect that itself takes ≥ 30 s. |
| `DIAL_TIMEOUT_SECONDS` | `10.0` | Whole-dial budget (TCP + TLS + HTTP upgrade). Generous enough for an LTE or satellite-backed kiosk (p99 handshake well under 5 s) and short enough that twelve consecutive timeouts add only 120 s to the circuit's trip time. Also bounds `stop()` latency during a dial. |
| `PING_INTERVAL_SECONDS` | `45.0` | Two protocol pings inside the ~100 s idle window that intermediaries (Cloudflare's edge, and corporate middleboxes that drop idle TCP at 60 s) are most likely to enforce, so one lost ping does not cost the socket. Free: incoming protocol pings are auto-ponged without waking the Durable Object and are **not billed** (`research/04-nat-turn-signaling.md` §4.3). ~1,920 pings/machine/day at zero cost. |
| `PING_TIMEOUT_SECONDS` | `10.0` | Must be `< PING_INTERVAL` for `websocket-client`'s `run_forever`. 10 s is ~10× the p99 RTT to the Cloudflare edge from a bad link, so it never produces a false disconnect, and it detects a black-holed socket within 55 s — comfortably inside the window where a missed ring still has the polled command fallback behind it. |
| `MAX_MESSAGE_BYTES` | `4096` | A ring is `{"type":"ring","sid":"…"}` ≈ 50 bytes; the largest legitimate inbound frame is an `error` with a reason string. 4 KiB is ~80× the largest expected frame, and small enough that a hostile or broken peer cannot make a SYSTEM-adjacent agent allocate. Over-cap closes the socket (row 16). |
| `RING_QUEUE_MAX` | `8` | The ring worker is single-flight, mirroring `_process_cortex_ipc_commands` (`owlette_service.py:2254-2288`). Eight is more pending sids than a machine can plausibly have — one per viewer opening a session, against a multi-viewer target of three and a per-machine ring cap already enforced at the Worker (review-2 M5). Above eight, drop the **oldest** and log a counted warning: the newest sid is the one a user is waiting on. |
| `AUTH_RETRY_COOLDOWN_SECONDS` | `60.0` | One free, un-laddered re-mint-and-re-dial per minute on a 401. `kid` rotation runs with a two-key overlap (Task 0.4 / 2.8), so a token minted just before rotation can outlive the old key's acceptance window; one free retry turns a rotation into a sub-second hiccup instead of a half-day of `DISABLED_SLOW`. Capped at one per 60 s so a Worker that rejects everything cannot become a hot loop. |
| `STOP_JOIN_TIMEOUT_SECONDS` | `5.0` | `stop()`'s join budget. The design target is a thread exit **within 2 s**; 5 s is the assertion boundary. Both sit well inside `SCM_STOP_GRACE_SECONDS = 20.0` (`owlette_service.py:116`), which is the whole budget `graceful_shutdown` has for the offline write. |

**Ladder, printed**: `2, 4, 8, 16, 32, 64, 128, 256, 300, 300, 300, 300` — each the *upper bound* of a
`uniform(0, w)` draw.

## 4. Doorbell-token lifecycle

**Mint**: `POST {shared_utils.get_api_base_url()}/agent/swoop/doorbell-token`,
`Authorization: Bearer <auth_manager.get_valid_token()>`, `timeout=10`, on the doorbell's own thread
(pattern: `firebase_client.py:2531-2546`). Returns a `role=doorbell`, `aud=swoop-signal` EdDSA JWT with `kid`,
whose `machine` claim is what the Worker derives the Durable Object name from (Task 3.3).

**Requested TTL: 12 hours.** Two costs pull against each other. Short TTL means socket churn — at 1 h, a
10,000-machine fleet mints 240,000 tokens/day and re-dials 240,000 sockets/day, and every re-dial is a window
in which a ring is missed. Long TTL means a stolen token stays usable — but this token's authority is narrow:
it joins exactly one machine's room and receives `ring` frames carrying a sid, and it cannot start a session,
cannot fetch a bundle (that is a separate call under the agent's Firebase identity), and cannot mint anything.
12 h gives two mints and two ~1 s re-dial windows per machine per day, and a stolen token expires the same
working day. *Exit condition*: if spike 0.5's threat model rates doorbell-token theft above the modelled
level, drop to 4 h — the cost is linear and still small.

**The refresh deadline is monotonic, not wall-clock.** Task 3.3's response must carry **`expiresIn`**
(seconds) beside the token; the doorbell schedules off `time.monotonic() + expiresIn − margin`. Kiosks drift
and NTP steps; anchoring on `time.time()` would make a stepped clock either churn the socket or miss `exp`
entirely. (See §7 — this is an interface requirement on Task 3.3.)

**Refresh margin: `exp − uniform(600, 900)` seconds** (10–15 min before expiry).
- The 10-minute floor buys room for the mint to fail and recover: Railway rolls the container on every push
  to `dev`/`main` and the Cloudflare LB can fail over to Vercel, so the mint has a real error rate. Ten
  minutes is ~8 attempts on the ladder (`2+4+8+16+32+64+128+256 = 510 s`) before the token actually dies.
  For comparison, `auth_manager`'s own Firebase buffer is `TOKEN_REFRESH_BUFFER_SECONDS = 5 * 60`
  (`auth_manager.py:29`) on a 1 h token — the same one-sixth-of-lifetime shape.
- The jitter spreads the fleet's mints. Without it, machines that came up together in a site power-cycle mint
  together forever, phase-locked to their boot time on a 12 h cadence.

**Order of operations on a planned refresh: mint first, close second.** Never tear down a working socket to
go looking for a token. Rows 20–22: with a new token in hand, send `bye`, close, re-dial (typical gap
200–600 ms); while the mint is failing, hold the existing socket, which is still valid; only at
`exp − TOKEN_HARD_DEADLINE_SECONDS` (30 s) without a token do we close and enter BACKOFF.

**Re-dial on 401.** A 401 at the upgrade, or a close frame carrying the Worker's auth reason, means the token
is expired, revoked or signed by a `kid` the Worker no longer accepts. Response: discard the cached token
immediately, re-mint, and dial again **once with no wait** (rows 10, 19), spending the
`AUTH_RETRY_COOLDOWN_SECONDS` credit. A second 401 inside 60 s is a failure like any other (row 11). A 401
from the *mint* route is a different animal — it means the agent's own Firebase identity is bad, which
`auth_manager` (`:503`) already ladders — so it goes to `DISABLED_SLOW` and is never reported anywhere (row 7).

### Timeline, one machine, 12 h TTL

| monotonic | event |
|---|---|
| `T+0` | mint → `{token, kid, expiresIn: 43200}`; refresh deadline drawn at `T + 43200 − uniform(600,900)` = `T+42300 … T+42600` |
| `T+0.3` | WSS upgrade 101 → CONNECTED |
| `T+45, T+90, …` | protocol ping every 45 s, auto-ponged, unbilled, DO stays hibernated |
| `T+120` | uptime ≥ `STABLE_CONNECTION_SECONDS` → `failures = 0`, `exponent = 0` |
| *any time* | `ring` → `on_ring(sid)` off the socket thread → `SwoopManager.ensure_streamer(sid)` |
| `T+42480` | refresh deadline fires (10–15 min of headroom left). Mint the **new** token |
| `T+42480.2` | new token in hand → send `bye`, close, dial. Socket gap ~300 ms |
| `T+42480.5` | CONNECTED on the new token; deadline redrawn from the new `expiresIn` |
| *(failure branch)* | mint fails → stay CONNECTED, ladder the mint in the background (row 21); at `T+43170` (`exp − 30 s`) with still no token → close, BACKOFF (row 22) |

Two planned re-dials per machine per day. Steady-state cost per machine per day: 2 HTTPS mints against our
own API, 2 DO upgrade requests, ~1,920 free pings, 0 billed incoming messages outside actual rings. At 10,000
machines that is ~20,000 DO requests/day ≈ 0.6 M/month — inside Cloudflare's 1 M included
(`research/04-nat-turn-signaling.md` §4.3).

**Logging**: never the token, never any prefix or suffix of it, never at debug. The only mint fields that may
be logged are `kid` (public) and `expiresIn`. Log lines name the state and the reason enum, nothing else.

## 5. `swoop_disabled` and the forced re-dial

**403 `swoop_disabled` → `DISABLED_SLOW`, retried every `uniform(900, 1800)` s (15–30 min).** Task 3.3's route
returns this when `sites/{siteId}/settings/swoop.enabled` is false or the machine is in `excludedMachineIds`,
so a machine with swoop off holds no signalling socket at all — which is what the off-by-default ruling means
in practice. A 403 is a healthy server answering: it **never** increments `failures`, never moves the
exponent, and never opens the circuit. That distinction matters — without it, a fleet where swoop is off
everywhere would sit permanently circuit-open and would take 15 minutes to notice an enablement.

**`swoop_refresh` forces an immediate re-dial** through a `refresh_now()` method on the doorbell that does
exactly one thing: `set()` an internal `threading.Event` that every wait in the machine is already parked on
(`_wake`, waited alongside `shutdown_event`). It performs no I/O and returns in microseconds, because the
caller is a command handler on the fast lane and must not block. The waiting state handler wakes, discards
the remaining window and proceeds per rows 24, 28, 30 and 36 — DISABLED_SLOW and BACKOFF go straight to
DIALLING, CIRCUIT_OPEN goes to HALF_OPEN, CONNECTED logs a no-op.

The path end to end: operator toggles site enablement (Task 5.4) → `swoop_refresh` written by the dedicated
action module with **no `sid`** (Task 2.11) → fast lane, since Task 2.2 adds the three swoop types to
`_FAST_COMMAND_TYPES` (`firebase_client.py:1570`) → `swoop_commands.py` handler (Task 2.7) →
`service.swoop_manager.on_session_change()` → `refresh_now()`. **The last hop does not exist in the drafted
task text** — see §7.1.

Worst case for an enablement to become a warm socket: the machine is online and gets the command
(≤ ~35 s on the adaptive poll), then one mint + one dial ≈ 1 s. A machine that is offline at the toggle warms
within `uniform(900, 1800)` s of coming back, without operator action.

## 6. Thread lifecycle

**One daemon thread**, `name='swoop-doorbell'`, created in `main()` by Task 3.1 right after
`firebase_client.start()`. Daemon, because a socket wedged in a kernel read must never hold the interpreter at
exit — the service already carries a 30 s hard-exit timer (`owlette_service.py:1910`) for exactly that class
of straggler.

**It never touches the 5-second loop.** `SLEEP_INTERVAL = 5` (`owlette_service.py:82`) is the whole budget
for process monitoring, heartbeats and the status write. Every doorbell method callable from the tick or from
a command handler — `start()`, `stop()`, `is_connected()`, `refresh_now()` — is a field read or an
`Event.set()` and returns in microseconds. All network I/O (mint, dial, read) and every wait happen on the
doorbell's own thread; `on_ring` runs on a second single-flight worker so a slow `ensure_streamer` (which
spawns a process and fetches a bundle) cannot stall the socket or the pings.

**No `time.sleep` anywhere in the module.** Every wait is `shutdown_event.wait(timeout)` — or a two-event wait
that also observes `_wake` — so the longest possible shutdown latency is the socket close, never a pending
300 s or 1800 s window. §6's test plan asserts this at the source level.

**Shutdown observation.** `graceful_shutdown` (`owlette_service.py:1397`) is the single funnel: it is one-shot
under `_shutdown_lock` and is reached from **both** triggers — `SvcStop` at `:1952` (which sets
`_scm_stop_requested = True` at `:1934`; the field is initialised at `:907`) and the SCM stop watcher at
`:1653` and `:1660`, which fires when the service is hosted by `owlette-host` and no console event ever
arrives. The doorbell's shutdown event must be set in `graceful_shutdown`, not only in `SvcStop` — see §7.2.
Exit target: the thread returns **within 2 s** of the event, measured against `SCM_STOP_GRACE_SECONDS = 20.0`
(`:116`), which is the entire budget for the offline write; the doorbell may not spend a tenth of it.

**Failure of the thread itself.** Nothing outside restarts it, by design (§1). Row 39 makes that safe: the
run loop's top-level handler catches everything, logs once and re-enters the machine as a dial failure. A
doorbell that has nevertheless stopped must be *visible* rather than silently absent — `is_connected()`
returns false and `SwoopManager.status()` surfaces it, which is what the tray indicator (Task 8.3) reads.

## 7. Interface requirements this design places on other tasks

These are **not** changes made here; they are what Task 2.3 and its neighbours need in order to implement
§4 and §5. Each is small and belongs in the named task's text.

### 7.1 `swoop_refresh` has no path to the doorbell as drafted *(blocking for §5)*

Task 2.7 fixes the handler chain as `swoop_refresh → service.swoop_manager.on_session_change()`, and Task
2.1 fixes `SwoopManager`'s surface as `ensure_streamer / kill / on_session_change / status` with no doorbell
reference. Nothing in that chain reaches `refresh_now()`.

**Recommended fix, one line each, no contract change:** Task 2.1's `SwoopManager.__init__` takes an optional
`on_refresh: Callable[[], None] | None = None`, invoked by `on_session_change()` when present; Task 2.3 adds
`refresh_now()` to the doorbell's public surface beside `start` / `stop` / `is_connected`; Task 3.1, which
constructs both objects, passes `on_refresh=doorbell.refresh_now`. Task 2.7 and the command contract are
untouched.

### 7.2 Task 3.1 sets the shutdown event in the wrong place *(correctness)*

Task 3.1 says to set the doorbell's shutdown event "beside `terminate_cortex()`" in `SvcStop`
(`owlette_service.py:1952-1956`). Under `owlette-host` the SCM watcher path (`:1653`, `:1660`) reaches
`graceful_shutdown` **without** `SvcStop` running at all — that is precisely why the two-trigger funnel exists
(`:1397-1417`). Set the event inside `graceful_shutdown`, early, beside `session_state.set_intent_if_none`;
keep the `SvcStop` line as belt and braces (`graceful_shutdown` is already idempotent).

### 7.3 `doorbell-token` must return `expiresIn` *(needed for §4)*

Task 3.3's response needs `{ token, kid, expiresIn }`. Without `expiresIn` the agent must parse the JWT and
trust the kiosk clock to compute the refresh deadline; §4 anchors on `time.monotonic()` instead, which needs
the server's own view of the lifetime. Also confirm the 12 h TTL there.

### 7.4 The Worker needs a distinguishable auth close reason *(needed for rows 10/19)*

Task 2.8 should close an expired or unknown-`kid` socket with a reason the client can tell apart from a
generic drop (a distinct close code or a `{"type":"error","reason":"auth"}` frame before the close).
Otherwise the free re-mint in row 19 cannot be triggered and a `kid` rotation costs every machine a full
backoff ladder.

## 8. Test plan — named cases for `agent/tests/unit/test_swoop_doorbell.py`

Task 2.3 writes these. All are unit tests with an injected clock, an injected socket factory, an injected
`is_connected`, and a seeded `random`; none touches the network. Case 1 is the headline.

1. **`test_signalling_outage_10_minutes_never_touches_connection_manager`** — *headline.* The socket factory
   raises `ConnectionRefusedError` for a simulated 600 s; the injected `is_connected` returns `True`
   throughout. Assert: (a) a `NonCallableMock(spec=ConnectionManager)` handed to the fixture records **zero**
   calls — `register_thread`, `report_error`, `force_reconnect`, `report_success` all unconfigured, so any
   call raises; (b) `is_connected` was only ever *read*, and its return value never changed, i.e. the
   simulated `ConnectionState` never leaves `CONNECTED`; (c) no captured log record originates from the
   `connection_manager` logger and none contains `[ERROR REPORTED]`, `[WATCHDOG] Dead threads detected` or
   `Reconnect`; (d) the doorbell reached `CIRCUIT_OPEN`; (e) dial attempts in the window are `≤ 12` — and
   `≥ 6`, so the case also fails if the backoff is so slow the feature is useless.
2. **`test_module_has_no_connection_manager_import`** — source-level: `swoop_doorbell.py` contains neither
   `import connection_manager` nor `from connection_manager`, and importing it in a clean interpreter leaves
   `connection_manager` out of `sys.modules`. Makes case 1's guarantee a property of the module, not of one
   path.
3. **`test_backoff_ladder_grows_and_caps`** — the un-jittered windows are exactly
   `[2,4,8,16,32,64,128,256,300,300,300,300]` and every drawn wait lies in `[0, window]`.
4. **`test_backoff_uses_full_jitter_not_equal_jitter`** — over 1,000 draws at a fixed step, the minimum drawn
   value is `< 5 %` of the window and the mean is within `10 %` of `window/2`. A 50–100 % implementation
   copied from `connection_manager.py:649` fails this.
5. **`test_stable_connection_resets_the_ladder`** — up for 120 s then dropped → next window is 2 s; up for
   119 s then dropped → the exponent advances.
6. **`test_circuit_opens_after_twelve_failures_and_half_open_probes_once`** — state is `CIRCUIT_OPEN` after
   the twelfth consecutive failure; exactly one dial per probe window; each probe wait lies in `[450, 900]`;
   a successful probe returns to `CONNECTED` with both counters reset.
7. **`test_offline_parks_in_idle_without_burning_the_ladder`** — `is_connected` false: zero dials, one
   re-check per 30 s; flipping it true dials within 30 s at ladder step 1.
8. **`test_403_swoop_disabled_enters_slow_retry_without_counting_a_failure`** — a 403 `swoop_disabled` from
   the mint puts it in `DISABLED_SLOW`, each wait lies in `[900, 1800]`, `failures` stays 0, the circuit never
   opens, and a simulated hour produces `≤ 4` mint attempts and **zero** WebSocket dials.
9. **`test_refresh_now_forces_an_immediate_redial`** — from `DISABLED_SLOW` and from `BACKOFF` it collapses
   the wait and dials on the next loop turn; from `CIRCUIT_OPEN` it goes to `HALF_OPEN`; from `CONNECTED` it
   is a logged no-op. In every case the call itself returns in `< 50 ms` and performs no I/O (strict mocks on
   the socket factory and the HTTP client).
10. **`test_token_refresh_fires_before_exp_with_a_jittered_margin`** — with `expiresIn = 43200`, the scheduled
    refresh lands in `[42300, 42600]` monotonic seconds, and over 200 seeded runs the drawn margins are
    distributed across the whole `[600, 900]` range.
11. **`test_refresh_deadline_survives_a_clock_step`** — step the fake `time.time()` forward 6 h mid-connection;
    the refresh still fires at the monotonic deadline. Proves the schedule is off `expiresIn` + `monotonic`.
12. **`test_failing_mint_does_not_tear_down_a_working_socket`** — the mint fails from the refresh deadline
    onward: the socket stays `CONNECTED` and the mint ladders; only at `exp − 30 s` does it close and go to
    `BACKOFF`.
13. **`test_401_gets_one_free_remint_then_backs_off`** — the first 401 at the upgrade triggers an immediate
    re-mint and re-dial with no wait; a second 401 inside 60 s goes to `BACKOFF` with `failures` incremented;
    the cached token is discarded on both.
14. **`test_mint_401_is_not_a_signal_outage`** — a 401 from the *mint route* goes to `DISABLED_SLOW`, does not
    ladder, and calls nothing on the auth mock beyond `get_valid_token`.
15. **`test_ring_with_only_a_sid_invokes_on_ring`** — `{"type":"ring","sid":"abc"}` → `on_ring("abc")` exactly
    once.
16. **`test_ring_with_any_extra_field_is_rejected`** — parameterised over: an extra key, a missing `sid`, a
    non-string `sid`, an unknown `type`, non-JSON, and a frame over `MAX_MESSAGE_BYTES`. `on_ring` is never
    called; the first five leave the socket `CONNECTED`; the oversize one closes it. No part of any payload
    appears in a captured record.
17. **`test_on_ring_never_blocks_the_socket_thread`** — an `on_ring` that blocks for 30 s does not delay the
    next frame's receipt or the ping schedule; a second ring arriving during the first is still delivered;
    a ninth pending sid drops the oldest and logs a counted warning.
18. **`test_token_never_appears_in_log_records`** — inject a distinctive token; assert the literal, its first
    8 and its last 8 characters appear in no captured record across every transition, including every error
    path and the 401 branches. Mirrors Task 2.1's bundle case.
19. **`test_stop_and_shutdown_event_end_the_thread_within_two_seconds`** — from each of the eight states,
    including mid-`BACKOFF` with a 300 s window and mid-`DISABLED_SLOW` with a 1800 s window pending;
    `stop()` is idempotent and safe before `start()`.
20. **`test_unexpected_exception_does_not_kill_the_thread`** — the socket factory raises `RuntimeError`, then
    `ValueError`, then recovers; the thread survives, counts each as a dial failure, logs each once, and
    reconnects.
21. **`test_module_contains_no_time_sleep`** — source-level assertion that `time.sleep(` does not appear in
    `swoop_doorbell.py`; every wait is `Event.wait`.

**Field verification (hand to Wave 3, Task 3.1's integration tests — `[human]`, needs an elevated click for
the block rule, so no agent path raises UAC).** A unit test cannot prove the *real* `ConnectionManager` stays
connected. On this dev box, with the service running and swoop enabled, block outbound access to the signal
origin (an outbound firewall rule, or a `127.0.0.1` hosts entry) for 10 minutes, then assert from
`logs/`: `ConnectionState` never leaves `CONNECTED`, there is no `[ERROR REPORTED]` line, no
`[WATCHDOG] Dead threads detected`, no additional Firestore reconnect, the 5 s loop's status writes continue
uninterrupted, and the doorbell log shows the ladder growing to the cap and reaching `CIRCUIT_OPEN`. Remove
the rule; the doorbell is warm again within one probe window. This is plan.md's success criterion "a
10-minute signalling outage leaves the agent's Firestore connection CONNECTED".

## 9. Recommendation

Build it as specified: a single self-supervising daemon thread with the eight-state machine in §2, the
constants in §3, a 12 h monotonic-anchored token with a jittered 10–15 min refresh margin (§4), and
`refresh_now()` as a bare `Event.set()` (§5). The design's whole load-bearing idea is that **the doorbell's
failure domain is Cloudflare and `ConnectionManager`'s is Firestore**, and the only way to keep them apart on
a fleet is for the doorbell to have no reference to `ConnectionManager` at all — hence the injected
`is_connected` callable and test case 2's import assertion, which is cheaper to enforce than a code-review
convention that a Wave-6 agent will eventually "fix" back.

**The backoff numbers, in one paragraph.** The ladder is `2 → 300 s` with full jitter because the two
constraints are asymmetric: a *single* machine losing its doorbell is cheap to fix and cheap to retry, so the
base is small (2 s) and the first few steps are free; the *whole fleet* losing it at once is the realistic
failure, so the cap is 5 minutes — short enough that the fleet is warm again within five minutes of Cloudflare
recovering (the "first frame p50 ≤ 1.5 s with a warm doorbell" criterion depends on it), long enough that a
prolonged outage costs one failed connect per machine per five minutes at the edge. Full jitter rather than
`ConnectionManager`'s 50–100 % is not a style preference: doorbell failures are perfectly correlated across
the fleet, and half-width jitter leaves every machine re-dialling in the top half of the same window. Twelve
failures before the circuit opens puts the trip point at ~14 minutes expected and ~29 minutes worst — past any
Worker deploy or regional blip, short enough that a permanently firewalled kiosk stops trying every five
minutes within the half hour. And the two "not a failure" paths matter as much as the ladder: a 403
`swoop_disabled` is the steady state for most of the fleet and must cost one request per ~22 minutes without
ever touching the counters, and an offline machine must park in IDLE rather than spend ladder steps it will
need when the network returns.

**Blocking on**: §7.1 (`swoop_refresh` has no route to the doorbell) and §7.3 (`expiresIn`). §7.2 and §7.4 are
correctness fixes in Tasks 3.1 and 2.8. All four are one-line amendments to existing task text; none changes
a contract in plan.md's names registry.
