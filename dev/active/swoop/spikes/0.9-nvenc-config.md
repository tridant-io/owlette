## Re-running it

```
cd agent/swoop/spikes/nvenc-probe        # never --manifest-path: it drops .cargo/config.toml and +crt-static
cargo run --release -- caps              # capability dump
cargo run --release -- measure           # measurements 2-6, plus measurement 1's four H.264 streams -> out/streams/
cargo run --release -- serve             # serves out/ + the WebCodecs page on 127.0.0.1:8099, exits on the report
```

Then, for measurement 1's decoder half, point Chrome at
`http://127.0.0.1:8099/?auto=1` **with a clean profile**:

```
chrome.exe --user-data-dir=<temp-dir> --no-first-run --no-default-browser-check \
           --disable-background-timer-throttling --disable-renderer-backgrounding \
           --new-window "http://127.0.0.1:8099/?auto=1"
```

The clean profile is not optional. On this box's normal Chrome profile an extension blocked `probe.js`:
the page loaded, silently did nothing, and the only symptom was a server log showing `GET /` with no
follow-up request. The page posts its results to the spike's server, which writes
`out/webcodecs-results.json` and exits. It also beacons `GET /progress?done=...` after each run, so a run
that stalls can be told from one that is merely slow.

## The configuration under test

Exactly what plan.md D5/D7 and Task 3.7 specify. NVENC **accepted all of it** and initialised a session on
both codecs, at 1080p and at 4K: preset `P1` + `NV_ENC_TUNING_INFO_ULTRA_LOW_LATENCY`, `enablePTD = 1`,
`gopLength = idrPeriod = NVENC_INFINITE_GOPLENGTH`, `frameIntervalP = 1` (no B-frames),
`NV_ENC_PARAMS_RC_CBR` with `averageBitRate == maxBitRate`, `vbvBufferSize = bitrate/fps` with
`vbvInitialDelay` equal and a 1/60 s floor, `zeroReorderDelay = 1`, `enableLookahead = 0`,
`lowDelayKeyFrameScale = 1`, `multiPass = NV_ENC_TWO_PASS_QUARTER_RESOLUTION`, `repeatSPSPPS = 1`,
`sliceMode = 3` / `sliceModeData = 1` (single slice), DPB 4 with `numRefL0 = NV_ENC_NUM_REF_FRAMES_1`,
`enableEncodeAsync = 1` with a completion event waited on one frame at a time, and
`NV_ENC_BUFFER_FORMAT_ARGB` `B8G8R8A8` D3D11 textures registered and fed straight in — no shader, no
VideoProcessor. Intra refresh off and no LTR / reference invalidation, per review-1 F4.

Input is a synthetic desktop-like pattern (grid, three window rectangles with text-like rows, a sliding
block, and a small high-entropy region), 16 pre-filled textures cycled. Real capture is spike 0.8's.

Every loop is paced at 60 fps rather than run flat out; a flat-out encoder measures throughput, and what
the streamer needs is the latency of one frame submitted into an otherwise idle encoder. The first 60
frames of each run are discarded as warm-up.

## Results

### 1. The H.264 VUI fix — measured before/after

Two otherwise identical 1080p60 NVENC streams, 300 access units each, differing only in
`h264VUIParameters.bitstreamRestrictionFlag`, submitted to a Chrome `VideoDecoder` (Annex-B, no
`description`, `prefer-hardware`) one per 16.7 ms the way a live stream arrives, and timed from
`decode()` to the `output` callback for the same timestamp. Measured submit interval p50 was **16.60 ms in
all eight runs**, so the tab was not throttled and the pacing is real.

**The headline pair, at the level NVENC picks for itself (4.2):**

| | chunks in | frames out before flush | held at end of stream | submit→output p50 | p95 | mean | n |
|---|---|---|---|---|---|---|---|
| `bitstreamRestrictionFlag = 0` (NVENC's default) | 300 | 296 | **4** | **67.2 ms** | 69.1 ms | 68.8 ms | 296 |
| `bitstreamRestrictionFlag = 1` | 300 | 300 | **0** | **0.5 ms** | 0.8 ms | 0.53 ms | 300 |

**Why 67 ms here and "~208 ms" in the claim: the SPS level sets the size of the penalty.** A second pair
was emitted with `level_idc` forced to 5.1 and everything else unchanged:

| SPS level | without the flag | frames held | with the flag |
|---|---|---|---|
| 4.2 — `avc1.64002a`, NVENC's automatic choice at 1080p/20 Mbps | 67.2 ms (n=296) | **4** | 0.5 ms (n=300) |
| 5.1 — `avc1.640033`, forced | **267.2 ms** (n=284) | **16** | 0.4 ms (n=300) |

Without bitstream restriction a decoder must assume the largest DPB the level permits,
`min(MaxDpbMbs / PicSizeInMbs, 16)` — 4 frames at level 4.2 and 1080p, the 16-frame ceiling at level 5.1.
Multiplied by the 16.7 ms frame interval that is 66.8 ms and 267 ms, which is what was measured, to within
half a millisecond. plan.md D5's "~208 ms" is the same effect at a level implying ~12–13 frames. **The
claim is confirmed in mechanism and direction; its magnitude is not a constant but a function of the level
the encoder advertises — and it gets worse, not better, as swoop raises resolution and bitrate, because
4K needs level 5.1 or above.**

**`optimizeForLatency` is not a substitute for the fix.** Every arm was run with
`VideoDecoderConfig.optimizeForLatency` both `true` and `false`. The two differ by less than 0.5 ms
everywhere, including in the 267 ms case (267.20 ms vs 267.20 ms). No decoder errors in any of the eight
runs.

SPS bytes exactly as NVENC emitted them, so a later regression can be diffed against them (these are also
the fixtures in `src/nal.rs`'s tests):

| stream | SPS |
|---|---|
| level 4.2, flag off | `6764002aac2b280f0044fcb808800001f40000ea6042` |
| level 4.2, flag on | `6764002aac2b280f0044fcb808800001f40000ea60478e152c` |
| level 5.1, flag off | `67640033ac2b280f0044fcb808800001f40000ea6042` |
| level 5.1, flag on | `67640033ac2b280f0044fcb808800001f40000ea60478e152c` |

With the flag on, the VUI parses to `max_num_reorder_frames = 0` and `max_dec_frame_buffering = 4` at both
levels — see amendment 1 below.

### 2. Forced-IDR latency (request → IDR emitted)

`NV_ENC_PIC_FLAG_FORCEIDR` on a picture in a running 60 fps loop, confirmed by NAL parse that the same
access unit contains an IDR (H.264) / IRAP (HEVC).

| codec | requests (n) | IDR on the same picture | p50 | p95 | steady-state P frames, same run (n=580) |
|---|---|---|---|---|---|
| H.264 | 20 | **20 / 20** | **8.66 ms** | 8.77 ms | p50 8.37 ms |
| HEVC | 20 | **20 / 20** | **9.69 ms** | 10.02 ms | p50 7.26 ms |

A forced IDR costs **nothing beyond an ordinary frame's encode**: 0.3 ms over the P-frame p50 on H.264,
2.4 ms on HEVC. There is no keyframe pipeline flush. This figure is the encoder-side component only; a
request that arrives between submits also waits up to one frame interval (16.7 ms at 60 fps) for the next
submit, which the Wave 5 cooldown policy has to budget for separately.

### 3. Bitrate reconfigure with no reset and no IDR

`NvEncReconfigureEncoder` with `resetEncoder = 0`, `forceIDR = 0`, alternating 20 Mbps ↔ 5 Mbps every 60
frames over a 1260-frame run.

| | |
|---|---|
| reconfigures (n) | **20** |
| IRAP access units after the first picture | **0** |
| mean frame size at 5 Mbps (n=400, 20-frame settle) | 9 859 B → **4.73 Mbps** implied |
| mean frame size at 20 Mbps (n=400) | 41 227 B → **19.79 Mbps** implied |

Confirmed: the rate changes and no keyframe is produced. **`vbvBufferSize` and `vbvInitialDelay` must move
with the bitrate in the same reconfigure** — a one-frame VBV sized for the old rate clamps the new one.

### 6. Encode latency, submit → output

Submit (`nvEncEncodePicture` returning) to the async completion event signalling, 60 fps paced, n=600 per
row after 60 warm-up frames.

| codec | resolution | target | p50 | p95 | max | achieved |
|---|---|---|---|---|---|---|
| H.264 | 1920×1080 | 20 Mbps | **8.32 ms** | 8.44 ms | 8.61 ms | 19.8 Mbps |
| HEVC | 1920×1080 | 20 Mbps | **7.26 ms** | 7.58 ms | 10.46 ms | 19.6 Mbps |
| H.264 | 3840×2160 | 50 Mbps | **10.12 ms** | 10.38 ms | 10.54 ms | 49.6 Mbps |
| HEVC | 3840×2160 | 50 Mbps | **12.10 ms** | 12.19 ms | 12.65 ms | 50.6 Mbps |

The whole host-side per-frame cost (map, submit, wait, lock, copy out, unlock, unmap) is within 0.1 ms of
these numbers, so map/unmap and the bitstream copy are not worth optimising.

An earlier run of the same code on a busier desktop produced 1080p60 H.264 p50 between 5.96 ms and
9.93 ms across 13 independent runs of n=600. The table above is the quiet-machine run; treat **8–10 ms
p50 at 1080p60 and 10–12 ms at 4K60** as the planning number, and expect the spread, not the point.

### 6b. Two settings plan.md asserts without a source

Both were A/B'd three times alternately at n=600, because a first pass at n=300 showed a 5 ms swing
between reps of the *same* setting and would have "found" whichever effect the machine was in the mood for.

**Async encode with depth 1 vs. synchronous `nvEncLockBitstream`** (1080p60 H.264, p50 submit→output):

| rep | async | sync |
|---|---|---|
| 0 | 8.43 ms | 8.33 ms |
| 1 | 8.46 ms | 8.29 ms |
| 2 | 8.25 ms | 8.33 ms |

No difference. Async mode costs nothing and buys nothing measurable in latency on this part.

**`multiPass = NV_ENC_TWO_PASS_QUARTER_RESOLUTION` vs. disabled** (1080p60 H.264, 20 Mbps target):

| rep | two-pass p50 | achieved | single-pass p50 | achieved |
|---|---|---|---|---|
| 0 | 8.32 ms | 19.8 Mbps | 6.62 ms | 13.9 Mbps |
| 1 | 8.32 ms | 19.8 Mbps | 6.58 ms | 13.9 Mbps |
| 2 | 8.33 ms | 19.8 Mbps | 6.63 ms | 13.9 Mbps |

Two-pass costs a consistent **1.7 ms p50** and is the only configuration that hits the requested bitrate:
single-pass CBR with a one-frame VBV undershoots by 30 % (13.9 of 20 Mbps), which a rate governor would
read as spare headroom that is not there.

## Recommendation — the settings Task 3.7 should ship

Ship the D5/D7 configuration as written, with the four amendments below. Concretely, and in the spellings
Task 3.7 uses:

```
preset                   NV_ENC_PRESET_P1_GUID
tuningInfo               NV_ENC_TUNING_INFO_ULTRA_LOW_LATENCY
enablePTD                1
enableEncodeAsync        1          // no latency benefit measured; keep it for the thread model, not the budget
gopLength / idrPeriod    NVENC_INFINITE_GOPLENGTH
frameIntervalP           1          // no B-frames
rateControlMode          NV_ENC_PARAMS_RC_CBR
averageBitRate           == maxBitRate
vbvBufferSize            max(bitrate / fps, bitrate / 60)
vbvInitialDelay          == vbvBufferSize
zeroReorderDelay         1
enableLookahead          0, lookaheadDepth 0
enableAQ / TemporalAQ    0
lowDelayKeyFrameScale    1
multiPass                NV_ENC_TWO_PASS_QUARTER_RESOLUTION   // costs 1.7 ms p50; the alternative misses the bitrate by 30 %
maxNumRefFrames / maxNumRefFramesInDPB  4
numRefL0                 NV_ENC_NUM_REF_FRAMES_1
sliceMode / sliceModeData 3 / 1     // one slice per picture
repeatSPSPPS             1
enableIntraRefresh       0, enableLTR 0, enableFillerDataInsertion 0
outputAUD / outputPictureTimingSEI / outputBufferingPeriodSEI  0
h264VUIParameters.bitstreamRestrictionFlag  1    // mandatory, see measurement 1
bufferFormat             NV_ENC_BUFFER_FORMAT_ARGB, D3D11 B8G8R8A8 registered and fed straight in
```

Amendments to Task 3.7's current text:

1. **Drop `max_dec_frame_buffering = 0` from the specification.** The NVENC API has no field for it (the
   whole of `NV_ENC_CONFIG_H264_VUI_PARAMETERS` is reproduced in the spike's vendored header: the only
   relevant knob is `bitstreamRestrictionFlag`). With the flag set, NVENC emits
   `max_num_reorder_frames = 0` and `max_dec_frame_buffering = 4`, the latter tracking `maxNumRefFrames`.
   `max_num_reorder_frames` is the field that removes the decoder's output delay, and it is 0. Asking for
   `max_dec_frame_buffering = 0` asks for something the encoder cannot express and does not need.
2. **Keep `multiPass = NV_ENC_TWO_PASS_QUARTER_RESOLUTION`, and carry its 1.7 ms in the latency budget.**
   It is not free, and it is not optional either: single-pass misses the target bitrate by 30 %.
3. **Budget 8–12 ms for encode, not the 1–3 ms in `research/03-windows-host-stack.md` §2.2.** That figure
   is from a quiet bench rig on newer silicon. On a live desktop — which is exactly swoop's target, a
   machine running TouchDesigner or signage — this Turing part measures 8.3 ms p50 at 1080p60 and 12.1 ms
   at 4K60 HEVC, and drifts by ±2 ms with whatever else holds the GPU. Against the plan's 55 ms p50
   end-to-end criterion that is ~15–20 % of the whole budget.
4. **Verify the slice count by parsing the bitstream, not by reading `numSlices`.** `reportSliceOffsets`
   requires `enableEncodeAsync = 0`, so it is unavailable in the shipping configuration.

Also worth carrying forward: the reconfigure path must move `vbvBufferSize`/`vbvInitialDelay` with the
bitrate in the same `NvEncReconfigureEncoder` call, and `NV_ENC_RECONFIGURE_PARAMS::reInitEncodeParams`
needs a live pointer to the `NV_ENC_CONFIG` it was initialised with (the spike keeps it boxed for the
session's lifetime).

## What the measurements contradict

Six things. Nothing else in D5/D7 was contradicted: single slice, `repeatSPSPPS`, infinite GOP, no
B-frames, no lookahead, CBR with a one-frame VBV, ARGB straight in with no shader, a cost-free forced IDR
and a keyframe-free bitrate reconfigure all held up exactly as specified.

1. **`max_dec_frame_buffering = 0` is not a thing NVENC can be asked for.** Task 3.7's text pairs it with
   `max_num_reorder_frames = 0`; only the latter is achievable, and only it matters. Measured: 0 and 4.
2. **"208 ms → 8.3 ms" is not the pair.** Measured 67.2 → 0.5 ms at level 4.2 and 267.2 → 0.4 ms at level
   5.1. The "before" is the level's DPB in frames, not a constant, and the "after" is essentially zero on
   this decoder rather than 8 ms. Task 3.7's comment should read "up to 16 frames of decoder output delay,
   set by the SPS level" rather than quoting a single figure — and the fix is *more* important at 4K, not
   less.
3. **Encode latency is 8.3 ms p50 at 1080p60, not the 1–3 ms in `research/03-windows-host-stack.md`
   §2.2.** That research figure is explicitly flagged "verify on your own hardware"; this is the
   verification, and it is 3–8× higher on a live desktop.
4. **`multiPass = NV_ENC_TWO_PASS_QUARTER_RESOLUTION` is not free**: 1.7 ms p50, reproduced 3/3. Keep it —
   the alternative undershoots the target bitrate by 30 % — but stop treating it as a costless default.
5. **"Async encode with depth 1" is not a latency measure.** plan.md D7 and the task text list it among
   the low-latency settings; it is indistinguishable from synchronous `nvEncLockBitstream` here
   (8.43/8.46/8.25 vs 8.33/8.29/8.33 ms). Its value is that the encode thread can wait on a handle rather
   than block inside the API — a threading property, not a latency one.
6. **`NV_ENC_LOCK_BITSTREAM::numSlices` is unavailable in the shipping configuration**, because
   `reportSliceOffsets` requires `enableEncodeAsync = 0`. Any slice-count assertion has to parse NALs.

## Caveats — what this does not establish

- **One GPU, one driver, one browser.** Turing, 591.86, Chrome 153. Intel/AMD are spike 6.7's; other
  drivers and Safari/Edge are not covered.
- **Synthetic input.** The pattern is desktop-*like*, not a real Desktop Duplication frame, and not a
  TouchDesigner render. Plan risk 3 (a GPU-saturated box pushing encode to 20–30 ms) is untested here.
- **The machine was in use.** Every number carries the variance of a live desktop; the earlier busy-run
  spread is quoted in measurement 6 rather than hidden.
- **Header 12.1, not SDK 13.x.** Everything needed exists in 12.1 and the driver accepts it. If Task 3.7
  wants anything newer (split-frame encoding is the obvious candidate, and is irrelevant on this
  single-engine part), it needs a newer binding source.
- **No spike binary was copied into `C:\ProgramData\Owlette`.** Nothing here touches the installed agent.
