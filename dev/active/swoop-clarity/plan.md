# swoop text clarity (4.1.28) — Plan
**Created**: 2026-11-04 | **Revised**: 2026-11-04, after two plan reviews (tasks.md, Log) | **Status**: Active (not started; built on `release/4.1.28`, cut from dev after 4.1.27 merges)

Owner requirement (2026-11-04): text on the remote desktop must be as clear as possible at any viewer resolution or window size. His case: a Windows machine viewed in owlette swoop (WebView2, H.264 only, ADR 0012) at a window smaller than the machine's screen looks stair-stepped.

Research this rests on: the session scratchpad's `research/swoop-clarity.md` (causes with file:line anchors) and `research/owner-decisions.md` (full releases, lowercase copy, e2e for user-facing behaviour, docs in the same change). Line anchors below are `release/4.1.27` @ f5a97522, re-read for this revision; find code by the quoted text when a line has moved.

## Summary

Two halves, one release. **The web half** works with every fielded streamer the day dev deploys. The `<video>` element's own box becomes the picture's box, laid out in device pixels, so a picture near full size or half size snaps to exactly 1:1 or 1:2 on whole device pixels, and a **sharp** choice beside **fit** shows the machine's pixels whole at any window size. Below 1:1 at any other size, a WebGL2 canvas averages each frame down in place of the browser's bilinear filter: on by default in Chrome, Edge and owlette swoop on Windows, where it is measured, off elsewhere until it is, and **smooth scaling** in the quality menu is the off switch. The stats say what size the picture is shown at, which path drew it, and the canvas's estimated cost on a row of its own. **The streamer half** ships as agent 4.1.28 on every system with no wire change: a bad path costs frame rate and bitrate but never resolution; NVENC encodes text at P4 (P3 above 1440p) under an encode-time gate that falls back to P1; the Media Foundation hardware encoder runs at balanced quality under the same gate; on NVENC a picture that stops moving sharpens in half a second; and the Windows scalers average instead of skipping pixels when the streamer downscales.

## Scope

In (decided by the orchestrator from the research; refined here, not relitigated):

1. **Sharp-fit snapping, DPR-aware**, plus a **sharp** choice beside **fit**; contentRect and the fit agree; DPR changes re-lay the picture; the 48 px bar checks and the phone one-row rule hold.
2. **Proper minification below 1:1** through a WebGL2 canvas sized in device pixels, the `<video>` kept as the composited source; touch zoom follows it (the magnifier keeps its own draw, C7); the canvas's cost measured against the video's before it is a default anywhere; an off switch, so a regression is turned off without a deploy. Reverses plan D17's "no canvas in the shipping path" (C2).
3. **"shown at N%"** in the stats overlay.
4. **Native resolution under congestion**: the automatic resolution rungs go; the menu's explicit resolutions stay.
5. **A text-friendly NVENC preset**: P4 at 2560x1440 pixels and below, P3 above; ULL tuning, the quarter-res two-pass and AQ off kept; a measured encode-time gate with the documented p50 budget falls back to P1; a quality-vs-speed value on Media Foundation hardware encoders.
6. **Faster still-screen refinement**: once motion stops, re-send at the rung's rate for 0.5 s, then the 2 Hz floor; bits stay inside CBR.
7. **Better streamer scalers** when the streamer downscales: the D3D11 video processor at OPTIMAL_QUALITY for the downscale (if it measures cheap), area averaging on the CPU path.

Refinements, each argued in Decisions: snapping only shrinks (C3); sharp reaches 1:3 and below through the canvas (C4); the canvas draws only what the video cannot draw exactly (C5); smooth scaling is on by default only where measured (C6); the magnifier keeps a 2D draw from the video (C7); the ladder drops resolution rungs outright (C8); the gate counts steady frames only, decides early when far over, and splits the budget among a capture pass's tiers (C9); mf-hw gets the same gate (C10); refinement is NVENC's, starts once motion stops, and ships only if its premise measures (C11); the Mac's scaler is measured, not changed (C12); the canvas's cost is measured, not estimated, before it is a default (C15); the browser measurements run the shipped renderer through a committed probe (C16).

Out: auto-requesting 1440p/1080p/720p by window size (each change is a new encoder and an IDR, there are only three heights, and a lower cap narrows the encoder tier for every viewer on that codec, `agent/swoop/src/session/tiers.rs`); viewer-sized encode and 4:4:4 (Backlog).

## Approach

### Web: one box, two ways to draw it

```
stage    SwoopStage's focusable wrapper, data-testid="swoop-stage": input capture, fullscreen and the letterbox colour bind here
 └─ area   normal-flow div, data-testid="swoop-area"; the phone keyboard's padding on the stage shrinks it
     ├─ <video>   absolute, object-fill, left/top/width/height written by useSwoopView from layoutPicture()
     │            = the picture's box. contentRect() = its getBoundingClientRect() (zoom transform included).
     │            receiver.ts owns it as today; its single rVFC chain now also calls onPresent.
     └─ <canvas>  absolute inset-0, pointer-events none, aria-hidden, sized in device pixels. presenter.present()
                  draws the current frame through smooth.ts when the picture is shown below 1:1 at a size the
                  video cannot draw exactly, and hides itself otherwise.
```

- **Layout** (`web/lib/swoop/view.ts`, pure): device-pixel fit of the frame into the area, snapped down to 1:1 or 1:2 within 10%, or **sharp** (the largest whole fraction 1:n that fits), on a whole device-pixel origin computed from the area's absolute device position. `useSwoopView` re-runs it on an area resize (device-pixel-content-box where the browser has it), a frame-size change, a DPR change, fullscreen, the bar moving and the size or smooth-scaling setting changing, and writes the box straight onto the video's style. It guards ResizeObserver and matchMedia, because two jest page tests render the real stage in jsdom.
- **Consumers read the element, not a formula.** Input (`input.ts`) normalises over `contentRect()` as today; touch's `picture()` is the video's layout box and its `area()`/`stageOrigin()` the area, with the zoom's transform-origin set at the area's origin so `ZoomState` and `clampZoom`/`pinchZoom` keep their meaning; the cursor and presence overlays (`useSwoopPictureBox`) and the magnifier read `contentRect()`. `fitBox` (zoom.ts:49) goes; the warning at SwoopStage.tsx:17-23 is rewritten. That is how contentRect and the fit cannot disagree: there is one box. Tests stop finding the stage as the video's parent and use its test id.
- **Smooth scaling** (`web/lib/swoop/video/smooth.ts`): a WebGL2 area average (box filter with coverage weights, up to 8 texels per axis, in the encoded colour space), fed by `texImage2D(video)` on the GPU. It mirrors the video's on-screen rect, zoom included, so a pinch is drawn by the canvas too. `smoothAvailable()` asks for `requestVideoFrameCallback`, a WebGL2 context that is not a major-performance-caveat one, and a hardware renderer (SwiftShader, llvmpipe and WARP refused; only the e2e's emulator build accepts SwiftShader, because CI's runner has no GPU). Drawn from the existing rVFC chain on every presented frame; a zoom, layout or toggle change redraws the same frame once from rAF (not frame presentation). Context loss falls back to the video.
- **Stats**: `shown at` (device pixels per machine pixel, zoom included), `scaling` (`exact`, `smooth`, `standard`), and while the canvas draws, `smooth scaling +N ms (estimate)` on its own row. `capture → display` stays the video's measured figure: no browser reports when a canvas reaches the screen, so in the overlay the canvas's cost is an estimate, and it is measured only by tasks 4.1 and 8.1 (C15).
- **Settings** (`web/lib/swoop/viewStore.ts`): `size` (fit | sharp) and smooth scaling per browser in localStorage, read through `useSyncExternalStore`, set in the quality menu (whose trigger becomes "quality and display"). Smooth scaling defaults on in Chromium desktop engines and off elsewhere (C6); a viewer's own choice wins. Nothing goes on the wire.
- **Measurement** (`agent/swoop/spikes/smooth-probe`, after spike 2.12's `browser-matrix`): a page server and driver that install nothing, serve the shipped `smooth.ts` through Node's built-in type stripping, stream a canvas through a same-page WebRTC loopback into a `<video>`, and report what a cover does to callbacks and frames, the draw time, and the canvas's added latency, read from two barcodes in one screenshot. It runs in Chromium and Edge on this box, Safari on TEC-MBA and WebKitGTK on the kiosk VM (C16).

### Streamer: legibility before motion

- **Ladder** (`session/quality.rs` `Ceiling::rungs`): frame-rate rungs only (60 → 30 → 15 at the ceiling's resolution). The governor still cuts bitrate first and only then walks the frame rate down (`transport/governor.rs:756-793`). Every rung move is still a new encoder at the new rate with an IRAP first (`TierPass::retarget`, session/mod.rs:4031-4054), now always at native size.
- **Encode-time gate** (`encode/gate.rs`, new, ungated): measures a gated setting where it runs. A sample counts only while frames are steady (the previous submit within two frame intervals), so the 2 Hz floor's repeats at idle clocks never decide; 30 steady frames warm up; an early verdict after 20 samples when their median is past min(1.5x the budget, the frame interval); otherwise a decision at 120 samples; too few steady samples keep measuring with the setting kept. The capture pass encodes its tiers one after another, so each gated encoder judges its share: 12 ms divided by the tiers in the pass, told through a defaulted `Encoder::share_encode_time`. The verdict is logged in one line that names the p50, the sample count and the frame rate.
- **NVENC** (`encode/nvenc/mod.rs`): the preset is chosen per encoder by size; over budget, the session drops, the next frame opens a P1 session whose first picture is an IDR, and later NVENC encoders in that streamer start at P1.
- **mf-hw** (`encode/mf/hw.rs`): `CODECAPI_AVEncCommonQualityVsSpeed` 50, measured submit → sink, the same gate and fallback.
- **Capture loop** (`session/mod.rs`): tells each encoder its share when it opens and when the tier count changes; on NVENC, refinement once motion stops (C11).
- **Scalers** (`gpu/scale.rs`): the BGRA downscale takes OPTIMAL_QUALITY if task 4.1 measures it within 1 ms of OPTIMAL_SPEED; the same-size BGRA→NV12 convert that mf-hw and mf-sw run on every frame stays OPTIMAL_SPEED; the CPU (WARP) path averages. The Mac's `VTPixelTransferSession` is measured (`gpu/vt_transfer.rs`), not changed (C12).

### Mixed fleet and the ADRs

- **No wire change.** PROTOCOL.md changes in prose only: `rungResolution` stays and reads the preset's own resolution on a 4.1.28 streamer, and `rungFps` loses a stale clause. `Encoder::share_encode_time` and the gate are internal to the streamer. A 4.1.28 web against a 4.1.27 streamer gets every web gain and the old ladder; a 4.1.28 streamer behind any web is identical on the wire. ADR 0006: nothing here changes what a machine does while it updates, so there is no installer half.
- **ADR 0009** (50–100 ms input-to-photon): the canvas lands after the video, by up to a refresh, and nothing has measured it yet. Spike 2.12's 0–2.3 ms (presenter.ts:26-29) is a canvas *readback* cost, not a texture upload and draw, and spike 0.1's camera rows are still pending. So the canvas is a default only where task 4.1 measures a draw p95 ≤ 4 ms for a 4K source and an added median latency ≤ one refresh, task 8.1 checks it glass to glass, and every viewer can turn it off.
- **ADR 0012** (owlette swoop hosts the web viewer): unchanged; the app gets the web half from the web deploy. WebView2 is Chromium, so smooth scaling is on there by default; WKWebView and WebKitGTK are not, so it is off there until measured.
- **Plan D17** (dev/active/swoop/plan.md): partly reversed, C2. Not an ADR.

## Decisions

- **C1 — The video element's box is the picture's box.** Today three places derive the letterboxed picture from an `object-contain` element (`contentRect`, useSwoopSession.ts:320-339; `fitBox`, zoom.ts:49 via touch.ts:340; the warning at SwoopStage.tsx:17-23). Snapping needs the box placed on whole device pixels, which `object-contain` cannot do; one element-sized box removes the agreement problem instead of adding a fourth derivation. The stage gets `data-testid="swoop-stage"`, because the video's parent is now the area and four e2e lookups found the stage as the video's parent (session.spec.ts:462, 1014, 1084; viewer-app.spec.ts:89).
- **C2 — Plan D17 is reversed on the web for minification, and it is not an ADR.** D17 bound the browser to present from the decoder callback, never rAF, with rVFC only to measure; after gate G1 chose arm B, presenter.ts read it as "no VideoDecoder, no canvas and no VideoFrame in the shipping path". From 4.1.28 a WebGL2 canvas mirrors the `<video>` and draws each presented frame from the one rVFC chain when the picture is shown below 1:1 at a size the video cannot draw exactly. Still binding: no frame is presented from rAF (rAF only redraws the same frame after a view change, and measures); one rVFC chain; no dejitter buffer; no per-frame CPU readback. Why: Chromium and WebKit draw video with a bilinear filter and no mipmaps, so below half size thin strokes drop out and between half and full size their weights go uneven — the owner's stair-steps. Why no ADR: it is reversible per viewer by a toggle and everywhere by a one-line default and a web deploy, and it touches no data, wire or fleet; both plan reviews agreed. Task 3.1's `/verify` reviewers judge it again; if either argues it is hard to reverse, task 6.1 writes ADR 0016 in one paragraph.
- **C3 — Snapping only shrinks.** Fit snaps to 1:1 when the device-pixel fit r is in [1, 1.1] and to 1:2 when r is in [0.5, 0.55]. A fit just under 1 (or 0.5) is never snapped up: that would crop the machine's edges and put input out of reach.
- **C4 — Sharp is the largest whole fraction that fits.** 1:1, 1:2, 1:3… A 4K machine in a 1300 px window is 1:3 (1280x720) where fit would be 0.33. 1:3 and below are exact only through the canvas's area average, so where smooth scaling is off or unavailable (every engine but Chromium desktop by default), sharp beyond 1:2 falls back to fit.
- **C5 — The canvas draws only what the video cannot draw exactly.** At 1:1 and at 1:2 on whole device pixels the browser's bilinear filter is exact (a copy, and a clean 2x2 average), so the video draws those for free and at no added latency; the canvas draws other sizes below 0.98, and 1:3 and below. Area average rather than mipmaps and trilinear: it is the exact box filter at any ratio, needs no per-frame mip chain, and does not blur between levels. Averaging stays in the encoded colour space, as the browser and both systems' scalers do.
- **C6 — Smooth scaling is on by default only where it is measured, and it is the off switch.** On in Chromium desktop engines — client hints name a `Chromium` brand and `mobile` is false: Chrome, Edge and owlette swoop on Windows (WebView2), the owner's case — which tasks 2.5 and 4.1 measure. Off in WebKit (Safari, owlette swoop on macOS and Linux, every iPhone browser), Firefox and phones: Retina and phone viewers are below 1:1 most of the time and would upload a full frame on every presented frame and every pinch move, untested; a viewer there can turn it on. A viewer's own choice beats the default either way. It is the off switch, never a kill switch (Kill and Kick are swoop's words for ending sessions). No query parameter: owlette swoop users cannot edit a URL. No fleet flag: per viewer is enough to undo a regression on the spot, a global default is one line and a web deploy, and turning it on elsewhere waits for task 8.1's sections D and E (Backlog).
- **C7 — The magnifier keeps its 2D draw from the video.** It must follow the finger every animation frame on a still screen (the canvas draws on presented frames, 2 Hz then), and it sits above the DOM pointer overlay. Its geometry already moves with the shared box through `contentRect()`; its filter improves with `imageSmoothingQuality = 'high'`. On phones it usually magnifies (twice the on-screen size is above 1:1 for most machines), where bilinear is right. This refines "the magnifier moves to the canvas".
- **C8 — The ladder drops resolution rungs outright.** The alternative, keeping them below a much lower floor, still ends a bad path at 720p, where a 4K desktop's text is unreadable however clean the motion; 4.1.28's refinement makes a native picture at 15 fps legible once it stops; and a person who wants motion over text on a bad path picks 1080p or 720p in the menu, which still applies at once. The decision stands on legibility alone: the moves that remain are native-size IRAPs, the largest there are.
- **C9 — NVENC's text preset by pixel count, under an encode-time gate that measures only what decides.** P4 up to 2560x1440 pixels (3,686,400), P3 above (3440x1440 and 4K included). The budget is a p50 ≤ 12 ms per capture pass: the top of the 8–12 ms budget nvenc/mod.rs:49-51 documents (spike 0.9's 4K60 HEVC P1), so no session pays more encode time than the slowest path already shipping. *Steady frames only*: a sample counts only when the previous submit on that encoder was within two frame intervals. On a still desktop the only encodes are the 2 Hz floor's repeats (FLOOR_INTERVAL, session/mod.rs:584; Desktop Duplication brings no new picture for a pointer move), at idle clocks that read slow, and judging P4 by them would drop it while the owner reads still text. A gap restarts the 30-frame warm-up and keeps the samples already taken; too few steady samples keep measuring, with the setting kept (a still desktop costs nothing to encode). *Early verdict*: Exceeded after 20 samples whose median is past min(1.5x the budget, the frame interval), so a GPU far over budget pays for under a second of motion (P4 at 1080p on this box's Turing would be about 19 ms against a 16.7 ms frame). *Per pass*: the capture thread encodes its tiers one after another (session/mod.rs:4307-4400), so an H.264 viewer in owlette swoop and an HEVC viewer in Chrome could each meet 12 ms and together miss the frame; each gated encoder judges its share, 12 ms divided by the tiers in the pass. Over budget, the encoder reopens at P1 (an IDR first) and later NVENC encoders in that streamer start at P1. The verdict lasts one streamer process, which is one session; remembering it per adapter and driver is an open question.
- **C10 — mf-hw runs at quality-vs-speed 50 under the same gate.** 50 is the balanced setting in each vendor's MFT mapping, NVENC P4's counterpart. Intel and AMD MFTs are unmeasured, which is exactly what the gate is for; the vendor default is logged before the set.
- **C11 — Refinement is NVENC's, starts once motion stops, and ships only if its premise measures.** The burst is what NVENC's quarter-res two-pass does with a picture that just stopped (QP from ~29 toward 8, research 01:497); task 2.1 measures it at P1 and at the text preset, and if the QP falls by less than 8 at both, task 3.3 is not built. Motion is three fresh frames inside 100 ms, so a caret, a clock or typing never arms it. A repeat is allowed only once no fresh frame has arrived for max(50 ms, two rung frame intervals): a 24–60 fps source is coded from its own frames while it moves (a 30 fps video on a 60 fps rung would otherwise drive the encoder at 60 Hz and spend the whole CBR target where today it spends half). Then a repeat is due every rung frame interval until 500 ms after the last fresh frame, then the 2 Hz floor. Not mf-sw (each repeat costs the machine's CPU), not mf-hw (its rate control is unmeasured on Intel and AMD; Backlog), not VideoToolbox (it keeps its settle keyframe, `settles`, session/mod.rs:595-605).
- **C12 — The Windows scalers average; the Mac's is measured.** The D3D11 BGRA downscale takes OPTIMAL_QUALITY only if its 4K→1080p blit p50 is within 1.0 ms of OPTIMAL_SPEED in task 4.1. Only that call site: `Downscaler::open_nv12` is the same-size convert mf-hw and mf-sw run on every frame (mf/hw.rs:524, mf/sw.rs:320), on the Intel and AMD machines mf-hw exists for, before any gate could see a slowdown; it stays SPEED, measured both ways for the record. The CPU (WARP) path becomes a separable area average. The Mac's `kVTPixelTransferPropertyKey_DownsamplingMode` is chroma-only ("ignored if chroma downsampling is not performed", objc2-video-toolbox 0.3.2) and the transfer is 420v to 420v, a scale and never a conversion (vt_transfer.rs:10-12), so setting it would change nothing; task 3.4 measures VideoToolbox's scale with RealTime on and off, and if it aliases, the fix is a Metal or vImage area scaler (Backlog), not this release.
- **C13 — Copy and settings are local.** `size` and smooth scaling describe this screen, not the machine: per browser, not reset per session, never sent. The three ceilings keep resetting per session as today.
- **C14 — The agent measures before the release, the owner after the merge.** Task 4.1 measures the encoders, the scalers and the canvas on this box (TEC-A4D, RTX 2080 Ti) with nothing else running; task 3.4 measures the Mac's scaler and Safari; task 5.2 checks WebKitGTK. owlette swoop loads the deployed viewer, so the owner's sitting (8.1) follows the merge to dev; the streamer half is measured before and after the test machine's update in the same sitting.
- **C15 — The canvas's cost is measured, not estimated, before it is a default.** `capture → display` stays the video's figure; the overlay's canvas row is labelled an estimate (`performance.now()` in the second animation-frame callback after the draw, minus the frame's `expectedDisplayTime`; never the rAF timestamp, which spike 2.12 found 16.1 ms behind a draw, presenter.ts:18-20). The ground truth is a screenshot holding two clocks: the probe's barcode on the source canvas and a live barcode the page paints, with the canvas cover and without, 30 shots each in Edge (task 4.1); and the owner's photos of a millisecond clock on the machine's own screen beside owlette swoop showing it (task 8.1, C). Gates for the default: a draw p95 ≤ 4 ms for a 4K source in Edge, and an added median latency ≤ one refresh (16.7 ms). Failing either, smooth scaling ships off by default everywhere and the default goes to the owner. A machine swooped from itself cannot measure it: the streamer ends such a session (`same_machine`, agent/swoop/src/signal/client.rs:575, PROTOCOL.md:114).
- **C16 — The browser measurements run the shipped renderer through a committed probe.** `agent/swoop/spikes/smooth-probe` follows spike 2.12's `browser-matrix`: no install, `playwright-core` from `web/node_modules` for the driver, results written to its own ignored `runs/`, runnable from a plain checkout on the MBA and the kiosk VM. Its server serves `web/lib/swoop/video/smooth.ts` through `node:module`'s `stripTypeScriptTypes` (Node 22.13 or later; this box has 22.20), so `smooth.ts` imports nothing and uses erasable TypeScript only, and no copy of the shader can drift from the one that ships.

## Backlog (not tasks)

**Viewer-sized encode.** The clearest text at any size is a picture encoded at the viewer's own device-pixel box and shown 1:1, as Parsec and RDP do. It needs the viewer's device size and DPR on the wire (today `widthCss/heightCss`, `agent/swoop/src/signal/messages.rs:509-510`, are CSS pixels and nothing reads them), so it is a protocol change under ADR 0006: a new preset token is safe because an older streamer reads an unknown token as native (`quality.rs:135-143`), but the size needs a field older streamers ignore, a resize debounce (every size is a new encoder and an IDR), and an encoder-tier rule so a small watcher cannot shrink the controller's picture (`session/tiers.rs`). Plan it once 8.1 says how much is left after snapping and smooth scaling.

**4:4:4, behind a capabilities spike.** ClearType's colour fringes and coloured text lose half their chroma in 4:2:0, which nothing in 4.1.28 touches. NVENC can encode H.264 and HEVC 4:4:4; Media Foundation, AMF, oneVPL and the Mac's capture path cannot; whether a WebRTC receiver decodes it is unverified (the research saw 8-bit HEVC 4:4:4 decode only through WebCodecs in Chrome, and Chromium may offer H.264 High 4:4:4 `profile-level-id=f4001f` with software decode only). The spike is one page: `RTCRtpReceiver.getCapabilities('video')` and a loopback decode in WebView2, Chrome and WKWebView. Only a yes in WebView2, the owner's viewer, makes it worth a release.

**Smooth scaling on by default beyond Chromium desktop.** One predicate in `viewStore.ts`, after 8.1's D (owlette swoop on the Mac) and E (a phone) show it inside C15's gates, and, for WebKitGTK, a Linux viewer with a GPU (the kiosk VM has none).

**A Mac area scaler** (Metal or vImage), if task 3.4 finds VideoToolbox's scale aliasing at 3:1.

**Refinement on mf-hw**, once an Intel or AMD MFT shows still frames refining the way 2.1 shows for NVENC.

**Remembering the gate's verdict** per GPU adapter and driver across sessions, if the owner wants older GPUs to skip the per-session trial (open question).

Also noted, not planned: `desynchronized: true` on the WebGL context if the measurements show a full refresh of extra latency; VideoToolbox's `PrioritizeEncodingSpeedOverQuality` off, measured on the MBA.

## Risks

- **The video may stop presenting under a cover.** If an engine stops rVFC or decode for a covered `<video>`, the canvas has nothing to draw and the freeze watchdog, which counts the video's shown frames (useSwoopSession.ts ~1131, stall.ts), would call it a freeze. Task 2.5 checks Chromium and Edge before anything is wired (an opaque canvas over a visible video, else the video at opacity 0, else no canvas path); 3.4 checks Safari; 5.1 keeps the canvas drawing for 12 s and asserts no freeze.
- **One more refresh of latency.** Drawing from rVFC lands the canvas a compositor frame after the video would have (up to 16.7 ms at 60 Hz). Measured by the probe (4.1) and glass to glass (8.1); a default only within one refresh; one toggle away for every viewer.
- **An engine nobody measured.** Smooth scaling is off by default outside Chromium desktop engines, and `smoothAvailable()` refuses software renderers and browsers without rVFC, so the untested cases see today's picture plus the snap.
- **Whole device pixels at fractional DPR.** Chromium lays out in device pixels (zoom for DSF) and snaps composited layers, so 1.25/1.5/1.75 should land exactly; WebKit lays out in CSS pixels at 1/64. The e2e proves dpr 1, 1.5 and 2 in Chromium; WKWebView at 2x has half-pixel room. A hardware overlay scaling the video at 1:1 is still exact.
- **WebGL2 in headless CI.** Chromium 137+ dropped the automatic SwiftShader fallback; 5.1 adds `--enable-unsafe-swiftshader` to both chromium projects and the emulator build accepts SwiftShader, so the canvas path runs at odd fractions in every swoop e2e — hence the full swoop set after it.
- **P4 may not fit older GPUs.** P4 costs ~2.3x P1's encode time; this box's Turing measures P1 at 8.3 ms at 1080p, so P4 likely falls back here. The improvement then reaches only newer classes; 4.1's table and each machine's verdict line say which.
- **Each session pays the trial on a slow GPU.** The verdict lasts one streamer process; on a GPU far over budget the early verdict ends the trial after 50 steady frames, under a second of motion at P4's encode time (possibly below 60 fps for that second). Remembering the verdict is an open question.
- **A misjudged gate.** Steady-only samples avoid the idle-clock trap; the gate still errs to P1 when a busy GPU reads slow. The verdict line names the sample count and frame rate, so a wrong call is visible in the logs 8.1 reads.
