    - `#[derive(Debug, Clone, Copy, PartialEq, Eq)] pub enum GateVerdict { Measuring, Keep { p50: Duration }, Exceeded { p50: Duration } }`.
    - `pub struct EncodeTimeGate` with `pub fn new(budget: Duration, fps: u32) -> Self`, `pub fn observe(&mut self, submitted: Instant, took: Duration, is_irap: bool) -> GateVerdict`, `pub fn set_budget(&mut self, budget: Duration) -> GateVerdict`, `pub fn verdict(&self) -> GateVerdict` and `pub fn samples(&self) -> usize`.
    - Rules. A submit is **steady** when the previous submit on this gate was no more than two frame intervals (2 × 1/fps) earlier: motion or a burst, never the 2 Hz floor's repeats on a still screen (`FLOOR_INTERVAL`, session/mod.rs:584), whose GPU clocks are idle and read slow. A submit that is not steady restarts the warm-up; samples already taken stay. IRAPs never count (a keyframe's own encode is not the delta budget; NVENC's IDR costs 0.3–2.4 ms more, spike 0.9 §2) and do not break steadiness. The first `WARMUP` steady non-IRAP frames after a (re)start are discarded. **Early verdict**: once `EARLY` samples are in, `Exceeded` at once if their median is over min(1.5 × budget, one frame interval). Otherwise the verdict is decided once at `SAMPLES` from their median (a p50 equal to the budget keeps); the buffer is freed and every later call returns the same verdict. Too few steady samples keep it `Measuring` for as long as that lasts (a still desktop costs nothing to encode, so the trial costs nothing either). `set_budget`: while measuring, the new budget applies to the decision; after `Keep`, a budget below the decided p50 turns it `Exceeded`; a larger budget never undoes `Exceeded`.
    - `pub fn verdict_line(backend: &str, setting: &str, size: (u32, u32), verdict: GateVerdict, samples: usize, fps: u32, budget: Duration) -> Option<String>`, the one line both encoders log, e.g. `swoop: nvenc p4 encodes 2560x1440 at p50 13.4 ms over 120 steady frames at 60 fps, over its 12.0 ms share; p1 from here` and `...; keeps p4`; `None` while measuring. It names the sample count and rate, so the logs say which kind of samples a verdict came from.
    - Module doc: who uses it (task 2.1's NVENC preset, task 2.2's Media Foundation quality vs speed), that every GPU class therefore answers for itself, why only steady frames count, the early verdict, the per-pass share, and that a verdict lasts one streamer process, which is one session.
