# Task 3.1: gate M0 — the app's child sees the screen

**Run on 2026-09-30, with the owner at the Mac. Verdict: go.**

The question: when the installed app launches `owlette-swoop` as its own child, does macOS credit the app's
grants to that child? Wave 4 depends on a yes for ScreenCaptureKit.

**The answer is yes, for all three permissions:**
- **Screen Recording.** The child read the display list through ScreenCaptureKit on the app's grant, in every run.
- **Accessibility.** The child's two checks went from false to true when the owner granted owlette.
- **Local Network.** macOS recorded the permission under the app's identity, and no entry names `owlette-swoop`.

No dialog named `owlette-swoop`. Two problems were found on the way; neither changes the verdict. Both are under
"Found on the way".

## The script

`m0_selfcheck.py`, beside this memo. It runs as root under the runtime's interpreter with the runtime's
`agent/src` on its path. It uses `swoop_spawn_posix`'s own `_listen` and `_launch_job`, swaps the job's args for
`["selfcheck", "--force"]`, submits it through `osadapter.run_job`, accepts the connection, reads one line, and
prints one json object. It captures nothing.

## Local Network: who the prompt was for

- The prompt appeared at run 1, the streamer's first LAN send. It is one of the two prompts the plan expects.
- The owner allowed it and does not remember the application name in the dialog.
- The system's record, `/Library/Preferences/com.apple.networkextension.plist`, read as root after the answer:
  it has an entry whose signing identifier is `app.owlette.desktop`, with the multicast preference set and not
  denied. It has no entry for `owlette-swoop`.
- From run 1b on, `localNetworkSend` is `ok`.
- So **a child's LAN send raises the prompt in the app's name**, and the app's answer covers the child.

## Found on the way

**1. The running app does not notice its own Accessibility grant (a product bug).**
- After the owner granted Accessibility at about 09:09, the app (pid 8242, running since the install) kept
  reporting `accessibility: false` in `ipc/tcc.json`: at 09:09:33 and again at 09:10:33.
- In the same minutes the streamer it launched read `postEventPreflight: true` and `axTrusted: true`.
- The owner saw the same thing: the notice stayed in the window after the grant.
- After a relaunch the app reported `accessibility: true` within ten seconds.
- Measured further the same morning, with the owner toggling switches in the Accessibility list:
  - A command-line probe under ssh (`~/src/tcc-check-2/live.swift`, both calls every 2 s, 120 samples): when
    the owner switched `sshd-keygen-wrapper` off and on, `CGPreflightPostEventAccess` followed within 2 s in
    both directions (true, false at 10:44:20, true, false from 10:44:28 to 10:44:36, true from 10:44:38).
    `AXIsProcessTrusted` stayed true throughout.
  - The installed app (pid 29737), with owlette switched **off** at about 11:42: its report stayed
    `accessibility: true` at 11:43:08, 11:44:08 and 11:45:08.
  - So inside the app the call follows neither a grant nor a revocation, while in a plain process it follows
    both. The difference is in the process, not the call. Why is not known: the app is a GUI process with a run
    loop, and its check runs off the main thread on a timer.
- Effect on swoop itself: none. The streamer is a fresh process each session and reads the truth every time.
- Not fixed here: it is outside this task's files. Task 4.9 owns it. The robust fix is for the app to ask a
  fresh process (its sidecar, with a check that touches neither ScreenCaptureKit nor the network); the cheap
  thing to try first is calling the check on the app's main thread.

**2. A stray copy of the app (a hazard of this rig, not of the product).**
- The owner quit the app and reopened it through Spotlight. What started was
  `~/src/owlette/agent/build/macos/work/payload/app/owlette.app`, an older build in a build tree, with the same
  bundle id.
- That build has no `launch` job and no Accessibility report. The first attempt at run 3 therefore answered
  `{"launch": {"error": "unsupported_job", "message": "no runner for a \"launch\" job on this app"}}`, and
  `tcc.json` lost its `accessibility` key.
- The stray copy was quit by its pid, and the installed app was started with
  `launchctl kickstart gui/<uid>/app.owlette.desktop`. Run 3 above is from that.
- Spotlight knows seven bundles with this bundle id on the Mac: `/Applications/owlette.app` and six under
  build trees in `~/src`. A customer's Mac has one.
- This does show one product fact: the daemon's spawn refuses cleanly when the app in front of it cannot
  launch the streamer.
