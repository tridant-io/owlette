# Wave 12: what every area task shares

Read this whole file before your task. It is the same for every area.

## What you are adding to

hoot mcp lets an AI agent on one paired machine (the **calling machine**) use tools on the other machines of its site, under a grant a site owner or site admin sets. The web server offers the tools (`web/lib/fleet/catalog.server.ts`) and checks every call (`web/lib/fleet/dispatch.server.ts`). Your task adds tools **the server answers itself**: each is a `FleetServerTool` (`web/lib/fleet/context.ts`).

- A `target: 'machine'` tool acts on the one machine named by the call's `machine` parameter. Before `run(ctx, machine, params)` is called, dispatch has already checked that the machine is in the site, is inside the grant and has hoot on, and has written the allow row. `run` receives only the parameters your definition declares. Do **not** declare a `machine` parameter yourself: the catalog adds it.
- A `target: 'machines'` tool acts on several machines in one call (a deployment's, a roost's). It has two functions. `machines(ctx, params)` returns `{ machines: string[] }`, every machine the call would act on, taken from the parameters or read from the stored thing they name, or `{ error: '<words for the caller>' }` when they cannot be told (no such deployment, for example). Dispatch then checks **each** machine exactly as it checks the one a 'machine' tool names (a valid id, inside the grant for the tool's tier, in the site, hoot on), refuses the whole call when one fails, writes an allow row per machine, and only then calls `run(ctx, machines, params)` with the de-duplicated list. At most 50 machines a call. So inside `run` you may act on exactly `machines` and on nothing else: never widen it there. The tests of this kind are in `web/__tests__/lib/fleet/dispatchMachines.test.ts`.
- A `target: 'site'` tool names no machine. It is a read, and it must narrow what it returns to the grant itself with `grantCovers(ctx.grant, machineId)` from `@/lib/fleet/policy.server`. `ctx.grant.machineIds === null` is the whole site; an empty list reaches nothing, so return an empty result without reading.
- `ctx` (`FleetContext`): `actor` (the calling machine as a `MachineActor`), `siteId`, `machineId` (the calling machine, never the machine acted on), `grant`, `correlationId`, `db` (admin Firestore).

**Things that belong to the whole site.** A person limited to some machines is refused the site's settings, its audit log, its deployments and its roosts outright (`web/content/docs/reference/authentication.mdx`, the list under "limited to some machines"). A machine whose grant names its machines must not read more than such a person can. So a read of something site-wide that cannot be narrowed row by row to the grant's machines answers only a grant that reaches the whole site (`ctx.grant.machineIds === null`), and gives every other grant a failed answer without reading: see `wholeSiteOnly` in `web/lib/fleet/tools/reads.server.ts`, and reuse it by importing it if you need it. A list whose rows each name their machines (a deployment's machines, a roost's) may instead be narrowed: return a row only when **every** machine it names is inside the grant, and say how many rows were left out.

## Rules

1. **Your files only.** Other agents work in this worktree at the same time. Create and edit only the files your task names. Do not edit `catalog.server.ts`, `context.ts`, `dispatch.server.ts`, any doc, the changelog or anyone else's file. Do not commit, stage, stash, switch branches or run any git command that changes the tree. If you need a change in a file that is not yours, stop and say so in your report. Never use Edit or Write on a path containing `agent/src/`.
2. **Call the core that already exists.** Each tool calls the server core the dashboard or the public API route already uses for that operation (look in `web/lib/actions/`, `web/lib/` and the route file itself). Do not reimplement validation or writes a core already does. For a read whose route has its logic inline, read Firestore the same way the route does, in a small reader, and never write. For a write with no core to call, stop and report instead of copying the route's logic.
3. **Writes act as the calling machine.** Pass the core `{ siteId: ctx.siteId, actor: ctx.actor, auditActor: machineAuditActor(ctx.machineId) }` (`machineAuditActor` is in `@/lib/actions/auditActor.server`), so the audit row names `machine:<id>`. If a core's types do not accept a machine actor, report it; do not cast around it.
4. **Tiers**: 1 read, 2 bounded change, 3 privileged. Use the tier your task gives.
5. **Definitions** are `McpToolDefinition` (`web/lib/mcp-tools.ts`): a snake_case name that no tool in `allTools` (same file) or in the existing fleet tool files already has; a description written for an AI agent in plain sentences, saying what comes back and any limit (read the existing ones); `parameters` as JSON schema with a description on every property.
6. **Answers** are `FleetAnswer`: `{ status: 'completed', content: [{ type: 'text', text: JSON.stringify(result, null, 2) }] }`, or `{ status: 'failed', error }` for a refusal the caller can act on (a core's input error such as `ActionInputError` becomes a failed answer with its message). Anything unexpected is rethrown, not swallowed.
7. **Bound every read**: cap list sizes and time ranges, validate numbers before they reach a query (see how `get_site_logs` treats `limit` and `hours`), and say in the result when something was cut off.
8. **Export** one `readonly FleetServerTool[]` from your tools file under the name your task gives. Someone else adds it to the catalog.
9. **Style**: comments only for the non-obvious why, in lowercase, like the surrounding files. No dead code, no new packages, no speculative options. Words: machine, site, agent, hoot, tier. Never "target" for a machine (that is roost's word), never "relay", never "fleet mcp" in a description.
10. **Tests first** (jest, in the test file your task names): write them, watch them fail for the right reason, then implement. For each tool: the happy path through `tool.run(...)`; for a 'site' tool, what a grant naming one machine sees, what a whole-site grant sees, and that an empty grant reads nothing; for a write, that the core is called with the machine actor and the `machine:<id>` audit actor, and that a core's input error becomes a failed answer; every bound, and an empty result.
11. **Checks before you report**: `cd web && npx jest <your test files>`, `npx eslint <your files>`, then `npx tsc --noEmit` once at the end. Do not run the whole jest suite (other agents are running theirs). Fix every error and warning in your files.
