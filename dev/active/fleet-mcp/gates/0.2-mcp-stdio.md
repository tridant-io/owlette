# Gate 0.2 — `mcp` stdio spike with the installed interpreter

**Run**: 2026-11-10 on the dev box, agent 4.1.27, with `C:\ProgramData\Owlette\python\python.exe -I` and the `mcp` 2.2.0 that ships in its site-packages. Nothing was installed. The two throwaway scripts lived in the session scratchpad and are not in the repo.

**Result: it works.** A low-level server with a tool list built at request time, driven over stdio by the client from the same package: initialize, list, call, and an error result.

## Imports that are current in mcp 2.2.0

```python
from mcp import types
from mcp.server import Server                 # the low-level server (mcp.server.lowlevel.Server)
from mcp.server.stdio import stdio_server
from mcp import Client                         # for tests
from mcp.client.stdio import StdioServerParameters
```

- `mcp.server.fastmcp` is gone in mcp 2: importing it raises `ModuleNotFoundError`. `MCPServer` (`mcp.server.mcpserver`) is its replacement and is decorator-based, so it does not fit a catalog that arrives at request time. Use the low-level `Server`.
- Handlers are constructor arguments, not decorators:

```python
async def list_tools(ctx, params):           # params: types.PaginatedRequestParams | None
    return types.ListToolsResult.model_validate({'tools': catalog})

async def call_tool(ctx, params):            # params.name, params.arguments
    return types.CallToolResult.model_validate({'content': [...], 'isError': False})

server = Server('owlette', version=..., on_list_tools=list_tools, on_call_tool=call_tool)
async with stdio_server() as (read_stream, write_stream):
    await server.run(read_stream, write_stream, server.create_initialization_options())
```

- The Python field on `types.Tool` is `input_schema`; the wire name is `inputSchema`. Building results with `model_validate` on wire-shaped dicts (`inputSchema`, `isError`) works and keeps the script free of the Python names, which is what lets it pass the web server's catalog straight through.
- Content items validate from `{'type': 'text', 'text': …}`. `types.ImageContent` exists (`{'type': 'image', 'data': <base64>, 'mimeType': …}`); the spike did not exercise it.
- Progress for a long call: `ctx.session.report_progress(progress, total, message)` exists. Not exercised.
- Test client: `async with Client(StdioServerParameters(command=sys.executable, args=[script])) as client:` then `await client.list_tools()` and `await client.call_tool(name, arguments)`.

## Surprise: a stray `print` reaches the wire on Windows

`stdio_server`'s docstring says a handler's stray output misses the wire. On this box it did not: a `print()` inside `call_tool` arrived at the client as a line it could not parse (`Failed to parse JSONRPC message from server … input_value='stray stdout line from a handler\r'`), once per call. The bundled client logged it and carried on; another client may not.

**Guard, verified**: set `sys.stdout = sys.stderr` as the first statement inside `async with stdio_server() as (...)`. With it, five runs gave zero parse failures and the stray lines went to stderr.

Task 4.2 must do that, log only to stderr, and its test must include a handler that prints.
