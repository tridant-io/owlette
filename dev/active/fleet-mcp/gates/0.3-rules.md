# Gate 0.3 — rules tests for the new documents

**Run**: 2026-11-10 in the Firestore emulator, against `firestore.rules` as it ships on dev (293f5d08). The rules file was not edited.

**Result: no rules change is needed.** `web/__tests__/rules/fleet.test.ts` holds 49 tests, all passing, and the whole rules suite passes with it (7 suites, 248 tests on the first run, before the last two tests were added).

| document | who | read | write or delete |
|---|---|---|---|
| `fleet_sessions/{hash}` | site owner, site admin, site member, superadmin, the machine agent, a member of another site, an unauthenticated client | denied (get and list) | denied |
| `sites/{siteId}/settings/fleet` | site owner, site admin, site member, superadmin | allowed | denied |
| `sites/{siteId}/settings/fleet` | the machine agent of that site | denied | denied |
| `sites/{siteId}/settings/fleet` | a member of another site, an unauthenticated client | denied | denied |

Why:

- `fleet_sessions` has no rule, so the catch-all at the bottom of the file (`match /{document=**} { allow read, write: if false; }`) covers it.
- `sites/{siteId}/settings/{settingId}` is `allow read: if canAccessSite(siteId); allow write: if isServiceAccount();`, and `canAccessSite` is a superadmin or an active member. An agent token is neither.

What this settles for the plan:

- The dashboard can listen to the grant with `onSnapshot` (task 2.1's hook) with no rules change.
- A machine cannot read its own grant from Firestore. It learns it from the session route (task 2.3) answering 200 or 403, which is what the plan assumed.
- Only the server writes either document, through the admin SDK.

How to run only this file: `firebase emulators:exec --only firestore --project demo-rules-harness "cd web && npx jest --config jest.rules.config.js --runInBand rules/fleet.test"` from the repo root. A bare `fleet` filter matches every suite when the checkout's own path contains the word.
