## installation

### npm release target

```bash
npm install -g @owlette/cli@rc
owlette --version
```

the CLI is prepared for the `@owlette/cli@1.0.0-rc.0` release channel, but it is not externally complete until the [SDK and CLI distribution gate](/docs/api/distribution) is verified. install from source until the npm `rc` tag is published.

### local dev (from the monorepo)

```bash
git clone https://github.com/tridant-io/owlette.git
cd owlette/cli
npm install
npm run build
npm link            # makes `owlette` available on your PATH
owlette --version
```

the CLI needs Node.js 20 or later. the `bin/owlette` launcher prefers the compiled `dist/` output but falls back to running the TypeScript source through `ts-node`, so `node bin/owlette …` works without `npm run build`.

## first 15 minutes

### 1. log in (device-code flow)

```bash
owlette auth login
```

the CLI prints a 3-word pairing phrase and opens your browser at `owlette.app/cli/authorize` with the phrase filled in. approve the request there, and the CLI stores the issued API key for the `default` profile: in the OS keychain when one is available, otherwise in `~/.config/owlette/credentials.json`, a token file readable only by you (`0600`). the phrase expires after 10 minutes.

if you can't open a browser on the CLI host (SSH, headless CI and so on):

```bash
owlette auth login --no-browser
# copy the pairing phrase and url it prints, and open the url on another machine
```

### 2. confirm who you are

```bash
owlette whoami
# user id     u_abc...
# email       you@example.com
# scopes      site:*=read|write|deploy
# environment live
# apiUrl      https://owlette.app
# profile     default
# configPath  /home/you/.config/owlette/config.toml
# credential  keychain
```

`owlette auth status` is an alias of `whoami` and prints byte-identical output.

### 3. push your first roost

a "roost" is a content-addressed bundle of files: a TouchDesigner project, a media payload, an npm build artifact, anything. pushing it dedupes chunks against the server and publishes a new immutable version.

```bash
owlette roost push ./my-project --to rst_my_project_id --site site-1
```

the CLI walks the directory, computes content-addressed chunks, asks the server which chunks it doesn't have yet, uploads the missing ones through signed URLs, then publishes a new version on the named roost. later pushes upload only the chunks that changed.

### 4. trigger a deploy

```bash
owlette roost deploy rst_my_project_id --site site-1 --dry-run
# inspect the canary / fleet split + extract path

owlette roost deploy rst_my_project_id --site site-1
# real deploy, auto idempotency-keyed so a network blip can be retried safely
```

that's the loop. `owlette roost diff <roostId> --against <versionRef>` shows what changed between any two versions; the top-level `owlette rollback <roostId>` reverts to the previous version.

## config precedence

config resolution is first-wins, but the credential store and the config profile swap places depending on the field:

```
token (auth):
1. env var             (OWLETTE_TOKEN)
2. credential store    (OS keychain, then ~/.config/owlette/credentials.json)
3. profile in config   (legacy token in ~/.config/owlette/config.toml)
4. built-in default    (none)

api_url / environment:
1. cli flag / env var  (--api-url, OWLETTE_API_URL, OWLETTE_ENVIRONMENT)
2. profile in config   (~/.config/owlette/config.toml)
3. credential store    (OS keychain, then ~/.config/owlette/credentials.json)
4. built-in default    (api_url=https://owlette.app)
```

the active profile is `--profile`, then `OWLETTE_PROFILE`, then `default`. `OWLETTE_CREDENTIAL_BACKEND` picks the credential store: `auto` (the default: the keychain when available, else the token file), `keychain` or `token-file`.

### config file schema

```toml
# top-level defaults, used when the active profile doesn't override them
api_url = "https://owlette.app"
environment = "live"

[profiles.default]
api_url = "https://owlette.app"

[profiles.dev]
api_url = "https://dev.owlette.app"
environment = "test"
```

legacy `token = "owk_*"` fields are still read for migration, but `owlette auth login` now writes secrets to the credential store and keeps `config.toml` for non-secret profile metadata. switch profiles with `--profile dev` or `OWLETTE_PROFILE=dev`.

## global flags

flags inherited by every command:

| flag | env var | default | purpose |
|---|---|---|---|
| `--profile <name>` | `OWLETTE_PROFILE` | `default` | named profile from config.toml |
| `--json` | — | false | emit structured JSON instead of ASCII tables on stdout |
| `--api-url <url>` | `OWLETTE_API_URL` | `https://owlette.app` | target API host |
| `-h, --help` | — | — | show help for the current command |
| `-V, --version` | — | — | print the CLI version |

global flags work before or after the command: `owlette --json machine list --site site-1` and `owlette machine list --site site-1 --json` are the same.

`--json` output is scriptable, but its shape is command-specific: newer commands use `{ ok, data }` or `{ ok: false, error }` wrappers, while older ones return raw payloads or compatibility objects. check the per-command page before scripting against a field.

## noun matrix

every command lives under one of these top-level groups. **ready** verbs hit a public API today. a **stub** reserves the name and exits 3 with a pointer to what replaces it. **planned** means the API exists but the CLI group does not yet.

### top-level verbs

| command | tier | description |
|---|---|---|
| [`owlette auth login`](/docs/cli/reference/auth) | ready | device-code login; stores the key for the active profile |
| [`owlette auth status`](/docs/cli/reference/auth) | ready | alias of `owlette whoami` |
| [`owlette auth logout`](/docs/cli/reference/auth) | ready | clear the key from the active profile |
| [`owlette whoami`](/docs/cli/reference/whoami) | ready | print the server-resolved identity and scopes |
| [`owlette version`](/docs/cli/reference/version) | ready | print the CLI version, the server version and the supported API date catalog |

### operator nouns (site-scoped)

| noun | tier | verbs | what it does |
|---|---|---|---|
| [`roost`](/docs/cli/reference/roost) | ready | `push` `list` `get` `diff` `versions` `deploy` | content-addressed project distribution |
| [`machine`](/docs/cli/reference/machine) | ready | `list` `get` `deployments` `reboot` `shutdown` `screenshot` | inspect machines on any platform and queue reboot, shutdown and screenshot commands |
| [`machine live-view`](/docs/cli/reference/machine#live-view) | stub | — | remote desktop ships as swoop, so the stub points at `owlette swoop` |
| [`swoop`](/docs/cli/reference/swoop) | ready | — | open the remote-desktop viewer for a machine in owlette swoop when it is installed, and in your browser otherwise |
| [`audit-log`](/docs/cli/reference/audit-log) | ready | `list` `get` | site audit log + hash-chain verification |
| [`quota`](/docs/cli/reference/quota) | ready | `show` `history` | site storage + bandwidth usage |
| [`chat`](/docs/cli/reference/chat) | ready | `new` `list` `send` `delete` `rename` | hoot ai chat |
| [`webhook`](/docs/cli/reference/webhook) | planned | `create` `list` `get` `update` `delete` `rotate-secret` `deliveries` `delivery get` `retry` `probe` | the public routes exist; the CLI group is deferred |
| [`deploy`](/docs/cli/reference/deploy) | ready | `create` `list` `get` `retry` `cancel` `uninstall` `delete` | classic agent-installer deploys (NOT `roost deploy`) |
| [`process`](/docs/cli/reference/process) | ready | `list` `get` `create` `update` `delete` `kill` `restart` `start` `stop` `schedule` | process lifecycle on machines |

### user nouns

| noun | tier | verbs | what it does |
|---|---|---|---|
| [`site`](/docs/cli/reference/site) | ready | `list` `get` `members` `add-member` `set-role` `remove-member` `transfer-ownership` | sites you have access to, and their members and roles |
| [`key`](/docs/cli/reference/key) | ready | `list` `create` | your API keys. rotate and revoke are dashboard-only |

### superadmin nouns

| noun | tier | verbs | what it does |
|---|---|---|---|
| [`user`](/docs/cli/reference/user) | ready | `list` `get` `promote` `demote` `assign-sites` `remove-sites` `delete` | platform user management |
| [`installer`](/docs/cli/reference/installer) | ready | `list` `latest` `upload` `set-latest` `delete` | agent installer binary management |

### legacy top-level verbs (kept for muscle memory)

| command | description |
|---|---|
| [`owlette rollback <roostId>`](/docs/cli/reference/rollback) | top-level rollback helper for roost versions |
| [`owlette listen`](/docs/cli/reference/listen) | open the scoped SSE liveness stream and forward received events to a local URL |
| [`owlette trigger <event>`](/docs/cli/reference/trigger) | fire a synthetic webhook for local testing |

> **disambiguation**: `owlette deploy …` is the **classic installer** deploy group (silent exe pushes). `owlette roost deploy <roostId>` is the **content-addressed** deploy that ships per-version diffs to a fleet. same word, different surfaces; the help text tells them apart.

## exit codes

scripts can branch on these; they're stable and meaningful:

| code | meaning | example trigger |
|---|---|---|
| `0` | success | `owlette roost push ./dist --to rst_abc` |
| `1` | generic error: network failure, API error, unexpected state, or a usage error caught before the command runs (a missing required flag or argument, an unknown command) | server unreachable; invalid response shape; `owlette roost push` with no path |
| `2` | usage error the CLI catches: no token configured, or a flag value it rejects | `owlette machine screenshot m-1 --site site-1 --monitor all` |
| `3` | **stub: the name exists but has no public API** | `owlette machine live-view m-1 --site site-1` |

exit code `3` is deliberately distinct from `1`, so CI can tell "this will never work until the backend ships" apart from "transient failure, retry". per-command pages list their own codes.

## JSON output shapes

commands that accept `--json` write one JSON document to stdout. newer commands generally use the wrapper shapes below; older commands can return raw server payloads or command-specific objects, so the per-command reference is authoritative.

**wrapped success**
```json
{ "ok": true, "data": { /* command-specific payload */ } }
```

`roost list`, `key list`, `site list`, `machine list`, `whoami`, `swoop` and `trigger`, among others, print raw payloads or command-specific objects rather than this envelope.

**wrapped failure**
```json
{ "ok": false, "error": { "code": "<stable_string>", "message": "human-readable", "detail": { /* optional */ } } }
```

when a command surfaces API problem+json details, the stable `code` values match the API's (`scope_insufficient`, `token_expired`, `idempotency_key_mismatch`, `manifest_stale`, `rate_limited`, `unsupported_version`).

**stub (exit 3 only)**
```json
{ "ok": false, "stub": true, "noun": "machine", "reason": "remote desktop ships as swoop — run `owlette swoop <machineId> --site <siteId>`", "dashboard_url": "https://owlette.app/dashboard", "future_plan": "public-api deferred: swoop" }
```
