description: "key lists and mints API keys from the terminal. it needs a superadmin key (user=*:admin), and a new key copies the calling key's scopes — it can never widen them."
keywords: ["api token", "access token", "credentials"]
---

verbs:

- [`key list`](#list) — list your API keys; never shows a raw key
- [`key create`](#create) — mint a key with the calling key's scopes; prints the raw key once

<Callout type="warn" title={"most key management belongs in the dashboard"}>

this command drives `/api/account/api-keys`, the key route that accepts API-key authentication. it is deliberately narrow:

- **superadmin only** — the calling key needs `user=*:admin`; anything less gets `403 scope_insufficient`.
- **scopes are copied, not chosen** — `create` clones the calling key's scopes exactly, so you cannot mint an `installer`- or `user`-scoped key unless the calling key already holds that scope.
- **no rotate, scope edit or revoke verb** — rotation and scope edits live on `/api/keys/{keyId}`, which accepts only a dashboard session. revocation also has an API-key route, `DELETE /api/account/api-keys/{keyId}`, but the CLI has no verb for it.

for custom scopes, a different expiry, rotation, revocation, or anything a non-superadmin needs, use **settings → api keys** in the dashboard.

</Callout>

## list

lists the API keys on your account, newest first. raw key values are never returned — only the display prefix.

```bash
owlette key list [--json]
```

no verb-specific flags. the table has these columns, or prints `no api keys`:

| column | meaning |
|---|---|
| `id` | key ID — the ID the dashboard's edit, rotate and revoke actions use |
| `name` | label |
| `prefix` | the first 15 characters of the raw key, for matching audit entries |
| `created`, `last used`, `expires` | dates as `YYYY-MM-DD`, `—` when unset |
| `scopes` | `<resource>=<id>:<perm>,<perm>` per scope, space-separated, or `legacy (full access)` |

`--json` prints the raw response, `{ success, keys }`, where each key has `id`, `name`, `keyPrefix`, `environment`, `scopes`, `expiresAt`, `createdAt` and `lastUsedAt`.

### examples

```bash
owlette key list
```

```bash
# id and expiry (epoch ms) of every key
owlette key list --json | jq -r '.keys[] | "\(.id) \(.expiresAt)"'
```

backing: `GET /api/account/api-keys`.

## create

mints a `live` key carrying **the same scopes as the key you call with**. there is no `--scope` or `--preset` flag, and the route accepts none. the key expires 90 days after it is minted.

```bash
owlette key create [--name <name>] [--json]
```

| flag | type | required | description |
|---|---|---|---|
| `--name <name>` | string | no | label for the key (default `API Key`) |

human output ends with the raw key on its own line — the only time it is shown:

```text
created ci publisher (3f0c9a52-…)
scopes inherited from the calling key — widen them in the dashboard
copy this now — it is not shown again:
owk_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

`--json` prints the raw response: `success`, `key` (the raw value), `keyId`, `name`, `environment`, `scopes`, `expiresAt` and `keyPrefix`.

### examples

```bash
owlette key create --name "ci publisher"
```

```bash
# the raw key is the last line, so this captures it
OWLETTE_TOKEN=$(owlette key create --name ci | tail -1)
```

backing: `POST /api/account/api-keys` with body `{ name }`.

## exit codes

- `0` — success
- `1` — network failure or a non-2xx response; the message carries the status and problem code (`403 scope_insufficient` when the calling key is not `user=*:admin`)
- `2` — no token configured: run `owlette auth login` or set `OWLETTE_TOKEN`

---

## notes

- **scope**: your own account; the route is gated on `user=*:admin`
- **store the key immediately**: the server keeps only its SHA-256 hash, so a lost raw key cannot be recovered — mint a new one
- **you may not need this**: `owlette auth login` already stores a key for you through the device-code flow
- **expiry**: keys minted here last 90 days with no override; the dashboard lets you pick 1 to 365 days
- **related**: [`whoami`](/docs/cli/reference/whoami) shows the scopes of the key you are using, [authentication](/docs/api/authentication) explains scopes
