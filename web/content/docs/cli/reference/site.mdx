title: "site"
description: "a site is the scope every operator command nests under — roosts, machines, the audit log, quota, deploys and processes are all site-scoped. the CLI reads site records and manages site membership; it has no verbs to create, update or delete a site."
keywords: ["team", "invite", "permissions"]
---

verbs:

- [`site list`](#list) — list the sites you can access
- [`site get`](#get) — print one site's record
- [`site members`](#members) — list a site's members and their roles on that site
- [`site add-member`](#add-member) — add someone to a site, by uid or email
- [`site set-role`](#set-role) — change a member's role on **this** site
- [`site remove-member`](#remove-member) — remove someone from a site
- [`site transfer-ownership`](#transfer-ownership) — hand a site to another user

<Callout type="warn">
  `site set-role` and `owlette user promote` are different commands. `set-role`
  changes a role on **one** site. `user promote` changes a **global** role on the
  account. to let someone administer one site, use `set-role`.
</Callout>

---

## list

lists every site the active token can reach: sites you belong to or own (every site for a superadmin), narrowed to the site IDs your key is scoped to, sorted by name.

```bash
owlette site list [--json]
```

no verb-specific flags. the table has `id`, `name`, `plan`, `timezone` and `createdAt`, or prints `(no sites)`. `--json` prints `{ "sites": [...] }`.

### examples

```bash
owlette site list
```

```bash
# just the ids
owlette --json site list | jq -r '.sites[].id'
```

backing: `GET /api/sites`.

## get

prints one site's record.

```bash
owlette site get <siteId> [--json]
```

no verb-specific flags. human mode prints `id`, `name`, `plan`, `timezone`, `owner` and `createdAt`. `--json` prints the raw record with no wrapper: `id`, `name`, `plan`, `tier`, `tierUpgradedAt`, `timezone`, `owner`, `createdAt` and `schedulesFollowSiteTime`.

### examples

```bash
owlette site get site-1
```

```bash
owlette --json site get site-1 | jq -r '.timezone'
```

backing: `GET /api/sites/{siteId}`.

## members

lists the active members of a site with the role each holds **on that site**.

```bash
owlette site members <siteId> [--json]
```

no verb-specific flags. the table has `uid`, `email`, `role` and `globalRole`, or prints `(no members)`. `--json` prints `{ "members": [...] }`, each with `uid`, `email`, `role`, `globalRole` and `displayName`.

`role` comes from the member record and is `owner`, `admin` or `member`. `globalRole` is the account-wide role, which grants nothing on this site by itself. a member's other site memberships are never returned — that would show a site admin the IDs of every other organisation the person belongs to.

### examples

```bash
owlette site members site-1
```

```bash
# emails of this site's admins
owlette --json site members site-1 | jq -r '.members[] | select(.role=="admin") | .email'
```

backing: `GET /api/sites/{siteId}/members`.

## add-member

adds someone to a site at the role you ask for. identify them with **exactly one** of `--uid` or `--email`.

```bash
owlette site add-member <siteId> (--uid <uid> | --email <email>) [--role member|admin] [--idempotency-key <key>]
```

| flag | type | required | description |
|---|---|---|---|
| `--uid <uid>` | string | one of `--uid` / `--email` | the user's ID |
| `--email <email>` | string | one of `--uid` / `--email` | the user's email; the server resolves it to a uid |
| `--role <role>` | `member` or `admin` | no | role on this site (default `member`) |
| `--idempotency-key <key>` | string | no | `Idempotency-Key` header (default `cli-add-member-<uuid>`) |

supplying both identifiers or neither, or any other `--role`, fails before a request is sent.

adding someone who is already a member is a no-op that still succeeds, and their existing role is kept. the response then carries `roleHonored: false`; when you asked for `admin`, the CLI prints a `WARNING role 'admin' was NOT honored` line. to change an existing member's role, use [`set-role`](#set-role). the site owner cannot be re-added: `409 target_is_owner`.

`--json` prints the raw response: `uid`, `siteId`, `requestedRole`, `roleHonored` and `globalRole`.

### examples

```bash
owlette site add-member site-1 --email alice@example.com
```

```bash
owlette site add-member site-1 --uid u_123 --role admin
```

backing: `POST /api/sites/{siteId}/members` with body `{ uid | email, role }`.

## set-role

changes a member's role on this site only. their global role is untouched.

```bash
owlette site set-role <siteId> <uid> <admin|member> [--idempotency-key <key>]
```

| flag | type | required | description |
|---|---|---|---|
| `--idempotency-key <key>` | string | no | `Idempotency-Key` header (default `cli-set-role-<uuid>`) |

`owner` is not a settable role — ownership moves only through [`transfer-ownership`](#transfer-ownership), and the CLI refuses `set-role ... owner` before sending anything. the server refuses to change the owner's role (`409 cannot_change_owner_role`), to change your own role (`403 cannot_modify_own_membership`), and answers `404` when the uid is not a member.

`--json` prints the raw response: `siteId`, `uid` and `role`.

### examples

```bash
owlette site set-role site-1 u_123 admin
```

```bash
owlette site set-role site-1 u_123 member
```

backing: `PATCH /api/sites/{siteId}/members/{uid}` with body `{ role }`.

## remove-member

removes someone from a site. removing a non-member succeeds and prints `was not a member of <siteId> (no change)`.

```bash
owlette site remove-member <siteId> <uid> [--talon-successor <uid>]
```

| flag | type | required | description |
|---|---|---|---|
| `--talon-successor <uid>` | string | no | reassign the talons this member authored to another user before removing them |

talons the person authored **survive** the removal — they belong to the site — but a talon with a hoot output re-checks its author's access on every run, so it starts failing once the author is gone. when talons are left in place the CLI prints a `WARNING <n> talon(s) authored by <uid> were left in place` line. reassignment never happens unless you pass `--talon-successor`.

the server refuses to remove the site owner (`409 cannot_remove_owner` — transfer ownership first) and to remove yourself (`403 cannot_modify_own_membership`). this verb sends no `Idempotency-Key`; the route is idempotent on its own.

`--json` prints the raw response: `siteId`, `uid`, `wasMember`, `talonCount` and `reassignedTalonIds`.

### examples

```bash
owlette site remove-member site-1 u_123
```

```bash
# hand their automations to someone else on the way out
owlette site remove-member site-1 u_123 --talon-successor u_456
```

backing: `DELETE /api/sites/{siteId}/members/{uid}`, with `?talonSuccessorUid=<uid>` when `--talon-successor` is set.

## transfer-ownership

hands a site to another user in one transaction.

```bash
owlette site transfer-ownership <siteId> <successorUid> [--idempotency-key <key>]
```

| flag | type | required | description |
|---|---|---|---|
| `--idempotency-key <key>` | string | no | `Idempotency-Key` header (default `cli-transfer-owner-<uuid>`) |

only the **current owner or a superadmin** can transfer; a site admin gets `403 not_owner`. the successor does not need to be a member already — the same transaction adds them. the outgoing owner stays a member, as a site `admin`. transferring to the current owner returns `409 successor_already_owner`, a deleted successor returns `400`, and an unknown site or user returns `404`.

`--json` prints the raw response: `siteId`, `previousOwnerUid` and `newOwnerUid`.

### examples

```bash
owlette site transfer-ownership site-1 u_456
```

```bash
# someone leaving: transfer, then remove
owlette site transfer-ownership site-1 u_456
owlette site remove-member site-1 u_departing --talon-successor u_456
```

backing: `POST /api/sites/{siteId}/transfer-ownership` with body `{ successorUid }`.

---

## exit codes

- `0` — success, including the no-op cases (re-adding a member, removing a non-member)
- `1` — network failure or a non-2xx response (for example `404` for a site you cannot reach); also the local checks on `add-member` and `set-role` (both or neither of `--uid`/`--email`, a `--role` or role other than `member`/`admin`, `owner` passed to `set-role`)
- `2` — no token configured for the active profile

## notes

- **scope**: `list` and `get` need read access to the site; `members` needs `site=<id>` with `read` **and** `admin`; `add-member`, `set-role` and `remove-member` need `write` **and** `admin`
- **JSON**: every verb prints a raw object with no `{ ok, data }` wrapper — `list` is `{ sites }`, `members` is `{ members }`, the rest print the response body
- **site records**: the CLI cannot create, update or delete a site; use the dashboard
- **roles**: a site role (`owner`, `admin`, `member`) is separate from the global account role. `site set-role` changes the first; [`user promote`](/docs/cli/reference/user#promote) changes the second
- **related**: [overview](/docs/cli/overview), and every site-scoped noun — [roost](/docs/cli/reference/roost), [machine](/docs/cli/reference/machine), [quota](/docs/cli/reference/quota), [audit-log](/docs/cli/reference/audit-log) — takes `--site <siteId>` with an ID from `site list`
