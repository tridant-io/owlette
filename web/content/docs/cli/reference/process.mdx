---
title: "process"
description: "process manages the long-running processes owlette keeps alive on a machine: register, update and delete them, set their run mode and schedule, and queue start, stop, restart and kill commands. every verb takes --site and --machine."
keywords: ["restart app", "kill app", "watchdog"]
---

verbs:

- [`process list`](#list) — managed processes on a machine, with live status
- [`process get`](#get) — one process's record
- [`process create`](#create) — register a new managed process
- [`process update`](#update) — change fields on a process
- [`process delete`](#delete) — remove a process
- [`process start` / `stop` / `restart` / `kill`](#start-stop-restart-kill) — queue a control command on the agent
- [`process schedule`](#schedule) — set the run mode and schedule blocks

mutations other than `delete` send an `Idempotency-Key` (default `cli-process-<verb>-<uuid>`); the server caches the response against it for 24 hours. if a mutation fails before a response arrives, the CLI prints the key and the `--idempotency-key` to re-run with.

---

## list

lists every managed process on a machine — its stored config merged with the live status from the agent's last report.

```bash
owlette process list --site <siteId> --machine <machineId> [--json]
```

| flag | type | required | description |
|---|---|---|---|
| `--site <siteId>` | string | yes | site that owns the machine |
| `--machine <machineId>` | string | yes | machine to read |

the table has `processId`, `name`, `launch_mode`, `status` and `pid`, or prints `(no processes)`. `--json` prints `{ "processes": [...], "nextPageToken": null }`, each process shaped like [`get`](#get).

### examples

```bash
owlette process list --site site-1 --machine m_abc123
```

```bash
owlette --json process list --site site-1 --machine m_abc123 | jq '.processes[] | select(.status != "running")'
```

backing: `GET /api/sites/{siteId}/machines/{machineId}/processes`.

## get

prints one process: `processId`, `name`, `exe`, `cwd`, `priority`, `visibility`, `launch_mode`, `autolaunch`, `status`, `pid`, `responsive` and `last_updated`.

```bash
owlette process get <processId> --site <siteId> --machine <machineId> [--json]
```

| flag | type | required | description |
|---|---|---|---|
| `--site <siteId>` | string | yes | site that owns the machine |
| `--machine <machineId>` | string | yes | machine that owns the process |

`--json` prints the record: `processId`, `name`, `exe_path`, `file_path`, `cwd`, `priority`, `visibility`, `time_delay`, `time_to_init`, `relaunch_attempts`, `autolaunch`, `launch_mode`, `schedules`, `schedule`, `schedulePresetId`, and the live fields `status`, `pid`, `responsive` and `last_updated`.

### examples

```bash
owlette process get pr_main_td --site site-1 --machine m_abc123
```

```bash
owlette --json process get pr_main_td --site site-1 --machine m_abc123 | jq -r '.status'
```

backing: `GET /api/sites/{siteId}/machines/{machineId}/processes/{processId}`.

## create

registers a new managed process. `--name` must be unique on the machine; a duplicate returns `409 duplicate_process_name`. a new process starts with `launch_mode` `off` unless you set one.

```bash
owlette process create --site <siteId> --machine <machineId> --name <name> --exe <path> [--cwd <path>] [--priority <priority>] [--visibility <visibility>] [--launch-mode <mode>] [--idempotency-key <key>] [--json]
```

| flag | type | required | description |
|---|---|---|---|
| `--site <siteId>` | string | yes | site that owns the machine |
| `--machine <machineId>` | string | yes | machine to add the process to |
| `--name <name>` | string | yes | display name, unique on the machine |
| `--exe <path>` | string | yes | absolute path to the executable |
| `--cwd <path>` | string | no | working directory |
| `--priority <priority>` | string | no | Windows priority label — `Low`, `Normal`, `High` or `Realtime` |
| `--visibility <visibility>` | string | no | Windows window state — `Normal` or `Hidden` |
| `--launch-mode <mode>` | `off` or `always` | no | `off` leaves the process unmanaged; `always` keeps it running and relaunches it after a crash |
| `--idempotency-key <key>` | string | no | `Idempotency-Key` header |

`--priority` and `--visibility` are stored exactly as given — the server does not check them, and the CLI's `--help` lists other spellings. use the values the dashboard writes, shown above. both apply only on Windows; macOS and Linux agents ignore them.

`--launch-mode scheduled` passes the CLI's check but the server refuses it with `400 missing_schedules`, because `create` cannot send schedule blocks. create the process, then run [`schedule`](#schedule) with `--mode scheduled`.

human mode prints `owlette: process <name> created (processId=<id>)`. `--json` prints `{ "processId": "..." }`.

### examples

```bash
owlette process create --site site-1 --machine m_abc123 \
  --name "main-td" \
  --exe "C:\Program Files\Derivative\TouchDesigner\bin\TouchDesigner.exe" \
  --cwd "C:\projects\signage" \
  --priority High \
  --launch-mode always
```

backing: `POST /api/sites/{siteId}/machines/{machineId}/processes`.

## update

changes the fields you pass and leaves the rest alone. at least one field flag is required.

```bash
owlette process update <processId> --site <siteId> --machine <machineId> [--name <name>] [--exe <path>] [--cwd <path>] [--priority <priority>] [--visibility <visibility>] [--launch-mode <mode>] [--idempotency-key <key>] [--json]
```

| flag | type | required | description |
|---|---|---|---|
| `--site <siteId>` | string | yes | site that owns the machine |
| `--machine <machineId>` | string | yes | machine that owns the process |
| `--name <name>` | string | no | new name, still unique on the machine |
| `--exe <path>` | string | no | new executable path |
| `--cwd <path>` | string | no | new working directory |
| `--priority <priority>` | string | no | as for [`create`](#create) |
| `--visibility <visibility>` | string | no | as for [`create`](#create) |
| `--launch-mode <mode>` | `off` or `always` | no | as for [`create`](#create); `scheduled` is refused the same way — use [`schedule`](#schedule) |
| `--idempotency-key <key>` | string | no | `Idempotency-Key` header |

`--json` prints `{ "processId": "..." }`.

### examples

```bash
owlette process update pr_main_td --site site-1 --machine m_abc123 --priority Normal
```

```bash
owlette process update pr_main_td --site site-1 --machine m_abc123 --name "main-td-v2" --visibility Hidden
```

backing: `PATCH /api/sites/{siteId}/machines/{machineId}/processes/{processId}`.

## delete

removes a process from the machine. deleting one that is already gone succeeds and prints `was already deleted (no-op)`. this verb sends no `Idempotency-Key`.

```bash
owlette process delete <processId> --site <siteId> --machine <machineId> [--yes] [--json]
```

| flag | type | required | description |
|---|---|---|---|
| `--site <siteId>` | string | yes | site that owns the machine |
| `--machine <machineId>` | string | yes | machine that owns the process |
| `--yes` | boolean | no | skip the `[y/N]` prompt; required when stdin is not a tty |

`--json` prints `{ "processId": "...", "alreadyDeleted": false }`.

### examples

```bash
owlette process delete pr_main_td --site site-1 --machine m_abc123
```

```bash
owlette --json process delete pr_main_td --site site-1 --machine m_abc123 --yes
```

backing: `DELETE /api/sites/{siteId}/machines/{machineId}/processes/{processId}`.

## start, stop, restart, kill

queues a control command for the agent: `start` launches the process, `stop` asks it to exit, `restart` stops it and starts it again, and `kill` terminates it. the server answers `202` with a command ID as soon as the command is queued; the result arrives when the agent next picks it up.

```bash
owlette process <start|stop|restart|kill> <processId> --site <siteId> --machine <machineId> [--idempotency-key <key>] [--json]
```

| flag | type | required | description |
|---|---|---|---|
| `--site <siteId>` | string | yes | site that owns the machine |
| `--machine <machineId>` | string | yes | machine that owns the process |
| `--idempotency-key <key>` | string | no | `Idempotency-Key` header |

human mode prints `owlette: <verb> queued for process <processId> (commandId=<id>)`. `--json` prints `{ "commandId": "...", "status": "pending" }`. to follow the command, poll `GET /api/sites/{siteId}/machines/{machineId}/commands/{commandId}`.

### examples

```bash
owlette process start   pr_main_td --site site-1 --machine m_abc123
owlette process stop    pr_main_td --site site-1 --machine m_abc123
owlette process restart pr_main_td --site site-1 --machine m_abc123
owlette --json process kill pr_main_td --site site-1 --machine m_abc123
```

backing: `POST /api/sites/{siteId}/machines/{machineId}/processes/{processId}/<verb>`.

## schedule

sets the process's run mode and, for `scheduled`, the time windows it runs in. this writes the process config directly — no command is queued — and the agent applies it on its next monitoring pass.

```bash
owlette process schedule <processId> --site <siteId> --machine <machineId> --mode <off|always|scheduled> [--blocks <json>] [--idempotency-key <key>] [--json]
```

| flag | type | required | description |
|---|---|---|---|
| `--site <siteId>` | string | yes | site that owns the machine |
| `--machine <machineId>` | string | yes | machine that owns the process |
| `--mode <mode>` | `off`, `always` or `scheduled` | yes | `off` unmanaged, `always` kept running, `scheduled` running only inside `--blocks` |
| `--blocks <json>` | JSON array | with `--mode scheduled` | schedule blocks, inline |
| `--idempotency-key <key>` | string | no | `Idempotency-Key` header |

each block is `{ "days": [...], "ranges": [{ "start": "HH:MM", "stop": "HH:MM" }] }`, with an optional `name`. days are lowercase three-letter names (`mon` … `sun`) and times are 24-hour machine time; a `stop` earlier than its `start` runs overnight into the next day.

human mode prints `owlette: process <processId> schedule set to '<mode>'`. `--json` prints `{ "processId": "...", "mode": "..." }`.

### examples

```bash
owlette process schedule pr_main_td --site site-1 --machine m_abc123 --mode always
```

```bash
owlette process schedule pr_main_td --site site-1 --machine m_abc123 \
  --mode scheduled \
  --blocks '[{"days":["mon","tue","wed","thu","fri"],"ranges":[{"start":"08:00","stop":"22:00"}]}]'
```

backing: `POST /api/sites/{siteId}/machines/{machineId}/processes/{processId}/schedule` with body `{ mode, blocks? }`.

## exit codes

- `0` — success, including a declined delete prompt and an already-deleted process
- `1` — network failure, a non-2xx response (`409 duplicate_process_name`, `404 process_not_found`, `403 scope_insufficient`, `400 missing_schedules`, `forbidden_field`), or a missing `--site`, `--machine` or other required flag. for known codes the CLI adds a `hint:` line
- `2` — `update` with no field flags; a `--launch-mode` or `--mode` outside `off`, `always`, `scheduled`; `--blocks` that is not a JSON array, or missing or empty with `--mode scheduled`; `delete` without `--yes` when stdin is not a tty; or no token configured

## notes

- **scope**: reads need `machine=<id>:read`; mutations need `machine=<id>:write`
- **JSON**: the server wraps responses in `{ ok, data }`; the CLI prints only `data`
- **platforms**: `--priority` and `--visibility` apply only on Windows; macOS and Linux agents ignore them
- **schedules follow machine time** unless the site is set to follow site time — see [site get](/docs/cli/reference/site#get) for `schedulesFollowSiteTime`
- **related**: [`machine`](/docs/cli/reference/machine) to find machine IDs and reboot or shut a machine down
