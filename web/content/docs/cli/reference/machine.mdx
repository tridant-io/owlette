cross-reference: `owlette machine deployments` shows the per-roost intended-versus-reported state from the **machine's** side. `owlette roost get` shows the same data from the **roost's** side: one source of truth, two lenses.

for remote desktop, use [`owlette swoop`](/docs/cli/reference/swoop), not `machine live-view`.

## list

list every machine on a site, with online state and last heartbeat.

**synopsis**: `owlette machine list --site <siteId> [--json]`

| flag | required | purpose |
|---|---|---|
| `--site <siteId>` | yes | site ID to list machines for |

the table's columns are `id`, `name`, `online`, `last-heartbeat`, `agent` and `roosts`. `--json` prints `{ "machines": [...] }`.

```bash
owlette machine list --site site-1
owlette machine list --site site-1 --json | jq '.machines[] | select(.online == false) | .id'
```

**backing endpoint**: `GET /api/sites/{siteId}/machines`

## get

print the detail record for one machine: host info, a metrics snapshot and the live process list.

**synopsis**: `owlette machine get <machineId> --site <siteId> [--json]`

| flag | required | purpose |
|---|---|---|
| `--site <siteId>` | yes | site ID that owns the machine |

`--json` prints the API's machine record unchanged, including `osFamily` (`windows`, `macos` or `linux`) and `capabilities`, such as `capabilities.swoop`.

```bash
owlette machine get m_abc123 --site site-1
owlette machine get m_abc123 --site site-1 --json | jq '.metrics.cpu'
```

**backing endpoint**: `GET /api/sites/{siteId}/machines/{machineId}`

## deployments

per-roost deployment state for one machine: the intended version (what the roost says should be running) beside the reported version (what the agent last reported). use it when a roost rollout looks stuck on one machine.

**synopsis**: `owlette machine deployments <machineId> --site <siteId> [--json]`

| flag | required | purpose |
|---|---|---|
| `--site <siteId>` | yes | site ID that owns the machine |

the table's columns are `roostId`, `name`, `intended`, `reported`, `status` and `reportedAt`.

```bash
owlette machine deployments m_abc123 --site site-1
owlette machine deployments m_abc123 --site site-1 --json | jq '.deployments[] | select(.currentVersionId != .reportedVersionId)'
```

**backing endpoint**: `GET /api/sites/{siteId}/machines/{machineId}/deployments`

## reboot

reboot the machine and wait for the agent to accept or refuse it. the CLI posts a `reboot_machine` command, then polls its state every 1.5 seconds for up to 60 seconds, printing a dot per poll. every request carries an `Idempotency-Key`, generated unless you pass one, so retrying after a network blip is safe.

on Windows the agent refuses a reboot while the machine is inside its [active hours](/docs/reference/agent-commands#active-hours), 08:00–17:00 when nobody set any. pass `--after-active-hours` to restart when they end, or `--override-active-hours --reason <text>` to restart now.

**synopsis**: `owlette machine reboot <machineId> --site <siteId> [--after-active-hours | --override-active-hours --reason <text>] [--delay-seconds <n>] [--idempotency-key <key>]`

| flag | required | purpose |
|---|---|---|
| `--site <siteId>` | yes | site ID that owns the machine |
| `--after-active-hours` | no | restart once the machine's active hours end, or now if it is outside them. the CLI reads the machine first: an agent without the active-hours guard (older than 4.1.21, or on macOS or Linux) would ignore the flag and restart at once, so the CLI stops with an error instead. when it can't read the machine it warns and sends the command, and the API refuses it with `409 held_restart_unsupported` |
| `--override-active-hours` | no | restart inside active hours anyway. needs `--reason`, and does not go with `--after-active-hours` |
| `--reason <text>` | with `--override-active-hours` | why, 500 characters or fewer. the agent writes it to the site log with your key as the approver |
| `--delay-seconds <n>` | no | non-negative number of seconds the agent waits before firing (default 0; a fraction is rounded down) |
| `--idempotency-key <key>` | no | the `Idempotency-Key` to send. reuse the one a failed run printed to retry it safely |

after the dots it prints one of:

- `owlette: reboot accepted by machine <id> (commandId=<id>): <the agent's answer>`, such as `Reboot deferred until 17:00 (machine time)`. when the agent sends no answer the line stops at the command id; with `--after-active-hours` it then adds that it restarts when its active hours end, or now if it is outside them
- a refusal, on stderr: `owlette: reboot refused by machine <id>: inside active hours 08:00–17:00 (machine time); they end at 17:00`, with a hint naming both flags. exit 1
- any other failure the agent reports: `owlette: reboot failed on machine <id>: <error>`. exit 1
- `owlette: reboot queued for machine <id> (commandId=<id>); no answer from the agent after 60s`, when the agent has not answered. exit 0
- the queued line, after a note on stderr, when the key cannot read the outcome, which needs `machine=<id>:read`. exit 0

`--json` prints no dots, and prints the command's final state, `{ "commandId", "status", "createdAt", "updatedAt" }` with `result` (the agent's answer) when it completed and `error` on a failure, exiting 1 when `status` is `failed`. without a final state it prints the queued command, `{ "commandId", "status" }`.

```bash
owlette machine reboot m_abc123 --site site-1
owlette machine reboot m_abc123 --site site-1 --after-active-hours
owlette machine reboot m_abc123 --site site-1 --override-active-hours --reason "venue closed today" --json
```

**backing endpoints**:
- `GET /api/sites/{siteId}/machines/{machineId}`, with `--after-active-hours` only
- `POST /api/sites/{siteId}/machines/{machineId}/commands` with `{ "type": "reboot_machine" }`, plus `when: "after_active_hours"` or `active_hours_override: { "reason" }` in `params`
- `GET /api/sites/{siteId}/machines/{machineId}/commands/{commandId}` (polled until terminal)

## shutdown

shut the machine down and wait for the agent to accept or refuse it, with the same idempotency, delay, polling and output as `reboot`. a shutdown inside active hours cannot wait for them to end, so there is no `--after-active-hours`.

**synopsis**: `owlette machine shutdown <machineId> --site <siteId> [--override-active-hours --reason <text>] [--delay-seconds <n>] [--idempotency-key <key>]`

| flag | required | purpose |
|---|---|---|
| `--site <siteId>` | yes | site ID that owns the machine |
| `--override-active-hours` | no | shut down inside active hours anyway. needs `--reason` |
| `--reason <text>` | with `--override-active-hours` | why, 500 characters or fewer, written to the site log |
| `--delay-seconds <n>` | no | non-negative number of seconds the agent waits before firing (default 0) |
| `--idempotency-key <key>` | no | the `Idempotency-Key` to send |

```bash
owlette machine shutdown m_abc123 --site site-1
owlette machine shutdown m_abc123 --site site-1 --override-active-hours --reason "replacing the projector"
```

**backing endpoints**:
- `POST /api/sites/{siteId}/machines/{machineId}/commands` with `{ "type": "shutdown_machine" }`
- `GET /api/sites/{siteId}/machines/{machineId}/commands/{commandId}` (polled until terminal)

## screenshot

capture a screenshot on the machine and download it. this is a queue → poll → download flow: the CLI posts a `capture_screenshot` command, polls the command's state every 1.5 seconds for up to 60 seconds (printing a dot per poll), then fetches the image from the signed URL the agent uploaded to.

**synopsis**: `owlette machine screenshot <machineId> --site <siteId> [--monitor <n>] [--output <path>] [--idempotency-key <key>]`

| flag | required | purpose |
|---|---|---|
| `--site <siteId>` | yes | site ID that owns the machine |
| `--monitor <n>` | no | a non-negative integer monitor index; `0` captures all monitors. named values such as `all` or `primary` are refused. omitted, the CLI sends no monitor and the agent captures all monitors |
| `--output <path>` | no | where to write the PNG (default: `screenshot-<machineId>-<timestamp>.png` in the current directory) |
| `--idempotency-key <key>` | no | the `Idempotency-Key` to send |

prints `owlette: screenshot saved to <path> (<n> bytes)`. `--json` prints `{ "commandId", "screenshotPath", "sizeBytes" }` and no dots.

```bash
owlette machine screenshot m_abc123 --site site-1
owlette machine screenshot m_abc123 --site site-1 --monitor 0 --output /tmp/wall.png
owlette machine screenshot m_abc123 --site site-1 --monitor 1 --json
```

**backing endpoints**:
- `POST /api/sites/{siteId}/machines/{machineId}/commands` with `{ "type": "capture_screenshot" }`
- `GET /api/sites/{siteId}/machines/{machineId}/commands/{commandId}` (polled until terminal)

## live-view

> **stub.** remote desktop ships as swoop, so this verb does nothing but point at [`owlette swoop`](/docs/cli/reference/swoop). it exits 3, the code reserved for stubs, so a script can tell it apart from an error.

**synopsis**: `owlette machine live-view <machineId> --site <siteId>`

| flag | required | purpose |
|---|---|---|
| `--site <siteId>` | yes | site ID that owns the machine |

human mode writes the stub notice to stderr. `--json` prints the stub envelope on stdout:

```bash
owlette --json machine live-view m_abc123 --site site-1
# → exit 3
# {
#   "ok": false,
#   "stub": true,
#   "noun": "machine",
#   "reason": "remote desktop ships as swoop — run `owlette swoop <machineId> --site <siteId>`",
#   "dashboard_url": "https://owlette.app/dashboard",
#   "future_plan": "public-api deferred: swoop"
# }
```

`dashboard_url` follows the active profile's API URL.

**backing endpoint**: none.

## exit codes

- `0`: success
- `1`: generic error: network failure, an API error, an unexpected response shape, the screenshot poll timing out, the agent reporting a failure, the agent refusing a reboot or shutdown inside active hours, `--after-active-hours` on an agent without the active-hours guard (or the API's `409 held_restart_unsupported`), or a missing `--site` (a usage error)
- `2`: usage error: no token configured, a bad `--monitor` value, a negative `--delay-seconds`, `--override-active-hours` without `--reason`, `--reason` without it, or it together with `--after-active-hours`
- `3`: stub (`machine live-view` only)

API errors print their problem code, with a hint for `machine_offline`, `unsupported_command_type` and `scope_insufficient`.

## notes

- **scope**: site-scoped. the mutating verbs need an API key with `machine=<id>:write` (or `machine=*:write`); `screenshot` needs `machine=<id>:read` as well. `reboot` and `shutdown` read their outcome, and `--after-active-hours` the machine, with `read` too; without it they warn on stderr and still send the command. permissions are exact: `write` does not imply `read`
- **active hours**: Windows always has active hours, so a daytime `reboot` or `shutdown` from a script is refused by a guarded agent unless it passes `--override-active-hours --reason`, or `--after-active-hours` for a reboot. an agent from before the guard reboots or shuts down at once with or without an override, and the API refuses `--after-active-hours` for it
- **tier**: A for `list`, `get`, `deployments`, `reboot`, `shutdown`, `screenshot`; C stub for `live-view`
- **idempotency**: every mutation sends an `Idempotency-Key`, so retrying a failed `reboot`, `shutdown` or `screenshot` will not fire it twice. a request that never got a confirmed response prints its key and the flag to retry with
- **screenshot TTL**: the agent's signed URL expires shortly after capture; the CLI downloads it at once, so you never handle the expiry
- see [overview](/docs/cli/overview) for the global flags (`--profile`, `--json`, `--api-url`) and config precedence
