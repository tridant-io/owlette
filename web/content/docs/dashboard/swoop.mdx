swoop puts a machine's screen in your browser, or in a window of [owlette swoop](#owlette-swoop), the desktop viewer app, live, and lets you drive it. it replaces the old screenshot slideshow ("live view") on any machine whose agent can stream.

two things are true of every session and worth knowing before you turn it on:

- **control asks for a second factor, every time the window lapses.** watching does not.
- **an API key can never start a session.** swoop is a human-in-the-loop surface; the session routes refuse a key outright with `api_key_not_permitted`.

a machine with someone in a session shows the count on its menu button and on the menu's swoop row.

---

## which machines can host it

you can watch and control from any computer with a current browser, or from [owlette swoop](#owlette-swoop). the machine on the other end has to run the swoop streamer, and that depends on its platform:

| platform | hosts swoop | what it needs |
|---|---|---|
| Windows | yes | agent 4.0.0 or later and an NVIDIA GPU. some features need a later agent; see [agent versions](#agent-versions) |
| macOS | yes | Apple silicon, macOS 15 or later, agent 4.1.0 or later, someone logged in, and the owlette app running. see [on macOS](#on-macos) |
| Linux | no | the Linux package ships no streamer, so the agent reports `capabilities.swoop: 0`. the menu keeps live view and screenshot, but both fail on Linux for now |

a machine whose agent cannot stream never offers swoop: its menu keeps the live-view entry instead. on Linux that entry, and **screenshot** beside it, still fail for now — a Linux machine cannot capture its screen yet (see [platform support](/docs/reference/platform-support#screens)).

the Windows streamer encodes on the GPU's NVENC encoder, the only one it ships with. a Windows machine without an NVIDIA GPU still offers swoop, but no session starts there: the streamer finds no encoder and exits, and the viewer reports that the machine did not answer.

## turning it on

swoop is **off** until a site turns it on: that is the default, and it is per site.

a site owner or admin flips it in **site settings** (in the site switcher, or **manage sites** → the site's pencil) → the **swoop** switch, beside [keep screens awake](/docs/dashboard/getting-started#site-settings). the switch takes effect the moment it moves; it is not part of the panel's save. turning it off reaches machines that are already connected, so a live session ends rather than waiting out its lease.

while a site has swoop off, the menu of a machine that can stream shows **turn on swoop…** to a site owner or admin, which opens site settings, and tells a member that swoop is off and to ask a site owner or admin. both get live view in the meantime.

the rest of the policy has no dashboard control yet. it is set with `PATCH /api/sites/{siteId}/swoop-settings` from a signed-in session as a site owner or admin; an API key is refused here too.

| setting | default | what it does |
|---|---|---|
| `enabled` | `false` | the site-wide switch, the one the dashboard exposes |
| `membersMayWatch` | `true` | whether a plain site member may watch. control always needs more than membership |
| `excludedMachineIds` | `[]` | up to 1,000 machines swoop may never reach, whatever the rest of the policy says |
| `indicator` | `banner` | how the machine signals a live session: `banner`, `tray` or `none`. today the owlette app's menu shows a swoop row with the viewer count during every session, and `tray` also raises a notification when one starts |

## starting a session

the **swoop** entry appears in a machine's context menu once that machine's agent reports it can stream. on a machine that cannot, the old live-view entry stays instead: exactly one of the two is ever offered.

the viewer opens in a new browser tab at `/swoop/<siteId>/<machineId>`. the monitor icon beside **swoop** opens it in [owlette swoop](#owlette-swoop) instead. `/swoop` lists a site's machines as cards, each one click from a session, with the same icon. you can also get there from a terminal with [`owlette swoop`](/docs/cli/reference/swoop), which opens the page in owlette swoop when it is installed and in your browser otherwise; the session itself starts in the page.

a session needs the machine to be online. swoop cannot reach a machine that has not dialled in: the request is refused with `machine_offline`, and the viewer keeps retrying until the machine is back.

swoop does not open the machine you are sitting at. a browser cannot tell which computer it runs on, so the first try reaches the machine, which sees the session coming from itself and ends it with "you're on this machine". from then on that browser shows swoop greyed out for that machine, labelled **you're on this machine**. the record lives in that browser only (owlette swoop keeps its own) and covers one machine at a time, and a session that does connect to the machine clears it. this needs agent 4.1.6; an older agent shows you a picture of your own screen instead.

## watching versus control

| | who | what it takes |
|---|---|---|
| watch | site members, owners and admins | site membership. a member also needs `membersMayWatch` on |
| control | site owners and admins | the machine remote-control capability **and** a live second factor |

the viewer always asks for control when your role allows it, and falls back to watching only when it does not.

a viewer that started watch-only stays watch-only. renewing its lease cannot promote it.

### the second factor

control is gated on a **step-up**: a fresh second-factor check, prompted in the viewer, that covers that machine for 12 hours, reconnects included. any of your factors answers it:

- a **passkey** (**use a passkey**), with user verification
- an **authenticator code**, the 6 digits from your authenticator app
- a **backup code** (**use a backup code instead**). each one works once

the 12 hours run from the check itself, and using the window does not extend it. the window belongs to you and that machine, so a new tab or a reload inside it does not ask again, but only from a sign-in that itself passed a second-factor check: a browser that skipped it because it was remembered asks once more. a tab (or owlette swoop window) that holds control also keeps it across its own reconnects and across a reload of the page, even after the 12 hours. a new tab asks, and ending the session yourself gives it up. a [kill](#ending-and-killing) on the machine closes every window on it.

in the owlette swoop desktop app, the prompt offers **verify in your browser** in place of a passkey: it opens a page in your browser, where your password manager's passkeys work, and the app takes control once you pass the check there. it is the same window, 12 hours for you and that machine. it works only if the app's own sign-in passed a second factor; if that sign-in skipped it because the browser was remembered, the app says so, and an authenticator or backup code in the app does the job.

an account with no passkey and no authenticator app cannot take control, and backup codes alone do not count. signing in with Google or a password is not a second factor. the viewer says so, offers only **cancel**, and links to two-factor setup; add a factor there or under [account settings](/docs/dashboard/account-settings#security) → security, then start the session again. because the viewer asks for control first, an owner or admin in that state cannot open the viewer to watch either.

## in the viewer

the toolbar carries the session state, an **end** button, and:

- **back to dashboard**: the arrow at the start of the bar, there in every state. leaving the page ends your session. in owlette swoop it is **back to machines** and leads to the machine picker
- **fullscreen with keyboard and mouse capture**: takes `alt+tab`, `ctrl+w` and the rest, which a remote desktop needs. hold `esc` for two seconds to get out; a session that ends or fails for good also lets go of fullscreen. a browser without keyboard lock keeps its own shortcuts, and the toolbar says so. what owlette swoop captures is [below](#fullscreen-and-the-keyboard)
- **latency stats**: an overlay, off by default because it covers the picture. its codec row shows what the picture is arriving in, and **frozen pictures** how often the picture [froze](#when-the-picture-freezes) in this tab or window
- **display picker**: which of the machine's monitors you are looking at
- **quality**: see [quality](#quality) below
- **audio**: off unless you ask for it
- **special keys**: the combinations your browser, or your own computer, will not let through
- **bar position**: the bar along the top, down the left or right edge, or **auto**, the default, which puts it wherever the picture comes out bigger in your window and moves it when you resize. a 16:9 picture in a 16:9 window has empty space at its sides, so a side bar gives the picture the height a top bar takes. on a side the machine's name runs vertically and the buttons stack at the bottom; a phone keeps the bar on top. the choice is kept in your browser, or in owlette swoop
- **presence**: who else is in the session

outside fullscreen, every key you press while the picture has focus goes to the machine, `tab` included. press `esc` twice to hand the keyboard back to the page: focus moves to the toolbar.

every button in the bar says what it does when you hover it, a greyed-out one included. a watch-only session is labelled **view only**.

over the dark bars around the picture your own pointer shows and nothing reaches the machine, so a click there never lands on the edge of its screen. a drag that runs off the picture keeps going, held at its edge.

### quality

the quality menu has one row per setting. it opens once the session has connected, and it sets your view only; other viewers keep their own.

| setting | options | when it applies |
|---|---|---|
| bandwidth | **auto**, or 5, 10, 20, 30, 50, 80 or 100 Mbps | at once |
| resolution | native, 1440p, 1080p, 720p | at once |
| frame rate | 60 or 30 fps | at once |
| codec | **auto**, or h264 and, where your browser can decode it in hardware, HEVC (never in owlette swoop on Windows) | at once, by reconnecting; see below |

bandwidth, resolution and frame rate are upper limits: the machine lowers them when the connection needs it. **auto** bandwidth starts a source above 2.5 megapixels, such as a 1440p or 4K-class display, at 80 Mbps, and anything smaller at 20 Mbps. a new session starts back at the defaults: auto, native, 60 fps.

the machine settles the codec once, when a session starts: HEVC when your browser offers it and the machine can encode it, otherwise h264. so choosing a codec reconnects: the viewer starts a new session in the same tab or window, without asking for the second factor again. **h264** offers only h264. **HEVC** asks for it first and still gets h264 from a machine that cannot encode it. **auto** lets the machine pick. the choice holds for that machine until the tab or window closes, and the latency stats show the codec in use.

### clipboard

the clipboard is shared both ways: copy on the machine and paste on your computer, or the reverse, with text up to 256 KB and images up to 15 MB. pasting into the machine needs control: ctrl+v (cmd+v on a Mac) in the viewer sends what you copied to the machine and pastes it there, with nothing for the browser to ask.

a copy made on the machine reaches your clipboard at once when you have just clicked or pressed a key in the viewer. at any other time, such as a copy made at the machine itself, the browser first asks whether the site may use the clipboard (Chrome and Brave word it as "see text and images copied to the clipboard"): choose **allow**. if you close that question, the copy waits, the session bar says so, and your next click or key press in the picture takes it. if you chose **block**, change it in the site's settings, from the icon at the left of the address bar. the browser also takes a copy only while the viewer's tab is the one in front.

in owlette swoop on Windows nothing asks: the app allows owlette's own pages to read the clipboard, so a copy on the machine reaches you whenever the window is in front.

### UAC prompts, lock and sign-in screens (Windows)

on a Windows machine, UAC prompts, the lock screen and the sign-in screen come through like the rest of the desktop: you see the prompt and answer it with your mouse and keyboard, including typing an administrator's name and password. type the password rather than pasting it: Windows keeps the clipboard away from its security screens, so swoop does too.

- **ctrl + alt + del** in the special keys menu brings up the Windows security screen, for a machine whose sign-in or UAC prompts ask for it. the machine raises it at most once every two seconds
- **win + l** in the same menu locks the machine. pressing win+l yourself locks your own computer, fullscreen or not, so use the menu

UAC prompts and ctrl + alt + del need agent 4.1.4, and win + l needs 4.1.5.

## owlette swoop, the desktop viewer app [#owlette-swoop]

owlette swoop is a small app that shows the swoop viewer in windows of its own instead of browser tabs. every window is the same viewer page from owlette.app, so the rest of this page holds in it too. what the app adds is what a browser cannot do: the session bar as the window's title bar, shortcuts your own computer would keep sent to the machine in fullscreen, and links from the dashboard and the owlette app that open straight into a session.

### getting it

every agent installer carries it, so a machine with owlette on it already has it:

| platform | installed as |
|---|---|
| Windows | `C:\ProgramData\Owlette\app\owlette-swoop-viewer.exe`, with an **owlette swoop** shortcut in the Start menu |
| macOS | `/Applications/owlette swoop.app` |
| Linux | `/usr/bin/owlette-swoop-viewer`, with an **owlette swoop** entry among the applications |

the installer also registers `owlette-swoop://` links, which is how the dashboard opens the app. a download for a computer without the agent, such as an operator's own workstation, is not published yet; until it is, use swoop in the browser there. **get it**, on the dashboard's notice that the app is not installed, leads here.

the app opens only owlette.app and dev.owlette.app, so an owlette you run yourself is used from the browser.

### opening it

- **from the dashboard**: the monitor icon beside **swoop** in a machine's menu, or on a machine's card at `/swoop`, opens that machine in owlette swoop, already signed in as you. when nothing has opened after a second and a half, the dashboard says the app is not installed on this computer
- **from a machine with owlette**: **swoop** in the owlette app's tray menu (the menu bar on macOS), and at the top of its window's menu, opens owlette swoop on the machine picker of the server the machine is paired with. where the app is missing the tray item is greyed out and the window's menu leaves it out
- **from a terminal**: [`owlette swoop`](/docs/cli/reference/swoop) opens a machine in owlette swoop when it is installed, and in your browser otherwise

started from the Start menu or Applications, it opens the machine picker of the server you used last, owlette.app the first time.

### the picker and sessions

the app opens on the machine picker, the same cards as `/swoop`. a click on a card opens its session in the same window; right-click the card, or press shift+enter on it, and choose **open in new window** to give that machine a window of its own and keep the picker. a machine already open in a window is brought to the front rather than opened twice.

closing a window ends its session at once, and closing the last one quits the app. when a session that had connected ends, its window goes back to the picker, or closes if it was a window of its own. a session that never connected, because it was refused or failed, keeps its reason on screen with **back to machines**.

the session bar is the window's title bar: drag it to move the window and double-click it to maximize. on Windows and Linux the minimize, maximize and close buttons sit at its right end; on macOS the window's own three buttons sit at its left. with the bar down a side, a thin strip across the top of the window holds the buttons. fullscreen hides all of it.

### fullscreen and the keyboard

**fullscreen with keyboard and mouse capture** works as in a browser, and holding `esc` for two seconds leaves it; a reminder says so for a few seconds as you go in. what else reaches the machine depends on your computer:

- **macOS**: in fullscreen the Dock hides and switching apps is off, and cmd+q, cmd+w, cmd+h and cmd+m go to the machine instead of quitting, closing, hiding or minimizing the app. cmd+tab switches nothing but does not reach the machine either, because macOS keeps it; send it from the keyboard menu. cmd+space, Mission Control, ctrl+arrows and ctrl+cmd+q (lock) stay with macOS. the mouse is never captured: WebKit gives the app no pointer lock, so a game or a 3D view that wants raw mouse motion does not get it. outside fullscreen the app behaves like any other Mac app
- **Windows**: the app captures no shortcuts of its own yet. fullscreen asks WebView2 for keyboard lock, as Chrome does, but how much of it takes effect in the app has not been measured yet; the keyboard menu sends the rest. win+l and ctrl+alt+del always stay with Windows. a lone `alt` tap puts the window into its menu mode until you press `esc`

### signing in

the app keeps its own sign-in, apart from your browser's, and you rarely meet it:

- opened from the dashboard's monitor icon, it arrives signed in as you, carrying over your browser's second-factor check
- started any other way, its sign-in page offers **sign in with your browser**: your browser opens owlette, you choose **approve** there, and the app signs in the same way. Google and passkey sign-in are not offered in the app, because neither works inside it; your email and password still do
- taking control asks for the [second factor](#the-second-factor) as in a browser, with **verify in your browser** in place of a passkey

### known gaps

- on Windows the app gets h264 only: WebView2, the engine inside it, cannot decode HEVC over WebRTC, any more than Edge can. on a Mac it gets h264 for now too, until a fix to the viewer's HEVC check lands
- the machine's cursor is drawn at its real size but looks soft, because the machine sends it shrunk to 32 pixels; it sharpens once the streamer sends it whole
- cmd+tab cannot be sent from macOS, and the mouse is not captured there (above)
- on Linux the app is in the package, but no session has been tried in it yet

## how long a session lasts

- a session has **no time limit**: it lasts as long as the tab or owlette swoop window that started it
- a dropped network does not end it. after a short drop the same session picks up where it was; after a longer one, a sleeping laptop or a machine that stops answering, the viewer starts a new session on its own, on a growing delay (up to 30 seconds between attempts), and says so while it waits
- an update or restart of the machine's agent sends the viewer to reconnect too, once the agent is back. agents older than 4.0.4 end the session instead, and so does the update from one of them
- what does end it: the **end** button, closing the tab or the window, an admin's kill, another tab or device opening swoop on the same machine, or the lease check below refusing
- a viewer holds a **5-minute lease**, renewed silently while the tab or window is open. the lease is the point at which authorisation is re-checked. a removed member, a revoked capability, a machine added to `excludedMachineIds`, or a site that turns swoop off all take effect within one lease rather than at the next sign-in

### when the picture freezes

the viewer watches the picture as well as the connection. when the machine keeps sending frames and none appear for three seconds, with the tab in front and the connection up, the viewer says **picture stalled — reconnecting** and starts a new session on its own, in the same tab or window and without asking for the second factor again. a picture that arrives and is only not being painted is first restarted in place (**picture stalled — restarting the picture**), and the new session follows only if that shows nothing within two seconds.

- a still screen never counts: the machine sends at least two frames a second even when nothing moves, and each of them shows. neither does a pause on the machine's side, such as a UAC prompt or a display switch
- it starts a new session this way at most twice in ten minutes; restarting the picture in place does not count. after that the session stays up and the viewer says **the picture froze**, which goes away if the picture comes back. **reconnect** in the bar starts a new session, and the ten minutes again
- when the browser's HEVC decoder was the cause, the new session and every later one in that tab use h264: Chrome has no software fallback for HEVC once its hardware decoder fails. the quality menu's codec row shows **h264**; set it back to **auto** to try HEVC again
- each freeze is recorded on the server with the browser's video counters, for diagnosis. nothing reaches the machine

## from another network

swoop connects the browser to the machine directly. on the same network that always works. across the internet, both ends ask a public STUN server for the address their router shows the world, and each offers it to the other: that gets through most home and office routers. the machine's half of this needs agent 4.1.3.

- when either end sits behind a strict router (phone hotspots and most mobile networks, some corporate firewalls), a direct path is not possible and swoop needs a **relay**. a relay is set up per deployment, not per site, by whoever runs owlette: it is a Cloudflare TURN key, set in the [swoop environment variables](/docs/setup/environment-variables#swoop-required-for-remote-desktop)
- with a relay set up, **the machine takes a relayed address of its own** (agent 4.1.8 and newer) and offers it to the viewer, so a viewer behind any router can reach it. the browser tries its own relay as well, over UDP, TCP or TLS, when nothing has connected after three seconds, which is what gets through a network that blocks UDP altogether
- **what the machine's network has to allow out**: UDP to the STUN and TURN servers on port 3478. a firewall that allows no UDP out leaves the machine with no public address and no relay, and only viewers on its own network can reach it. the browser's side needs UDP out, or failing that TCP out to the relay on 3478 or 443
- after 20 seconds without a path the viewer stops saying **connecting** and says **can't reach this machine from your network**, with which end never reached the relay: the machine's side (its firewall, or an agent older than 4.1.8), this browser's, or neither. it keeps trying underneath, and the picture appears if a path comes up later
- a machine's own firewall must let the owlette agent receive on UDP. on Windows the agent adds that rule itself when swoop is turned on for the site
- the machine's swoop log (`logs/swoop/swoop.log` under the agent's data folder) says which candidates each session gathered: `server-reflexive candidate gathered`, `relay candidate gathered`, or why not

## ending and killing

ending your own session is the **end** button in the toolbar. anyone who may be in the room may leave it.

a site owner or admin can also stop **whatever anyone is running** on a machine, from **admin** → **swoop** (below) or with `POST …/swoop/kill`. a kill is deliberately not gated on the site's swoop settings: stopping a stream has to work after the feature has been switched off, which is exactly when an operator wants it most. a kill also closes every second-factor window on that machine, so anyone it cut off, a tab that was reconnecting at the time included, confirms again before taking control.

on a Windows machine, the owlette app's tray menu has **kill all swoop sessions on this machine** under its swoop row while a session captures the screen. anyone at the machine can click it, and every session there ends within a second, but unlike a kill from the dashboard it closes no second-factor window. macOS and Linux do not offer it yet.

## what is recorded

every session start, every refusal and every end is written to the session's own audit trail, with the actor, the machine and whether control was held. a session whose audit row cannot be written is not started (`audit_unavailable`).

## on macOS

a Mac hosts swoop on Apple silicon with macOS 15 or later, from agent 4.1.0. a session there works as it does on Windows, apart from what follows.

**someone must be logged in.** swoop shows and controls the logged-in user's desktop, and macOS does not let it reach the login window. logging out or switching users ends the session.

**the owlette app must be running.** the agent runs as root with no display of its own, so it asks the owlette app to start the streamer, and the streamer runs under the app's grants. with the app not running, the agent refuses to start one (it logs `desktop_not_running`), and the viewer reports that the machine did not answer and keeps retrying. quitting the app ends a live session; the viewer starts its next one once the app is back. the app starts at every login, and if someone quits it from its menu it stays closed until they reopen it or log in again.

**a Mac paired before 4.0.6 may need pairing again.** macOS names a machine `Name.local`, which the API's machine ID rule does not allow, so a Mac paired under that name has every swoop token refused. a Mac pairing for the first time now takes its ID without `.local`; one already paired as `Name.local` keeps that ID until you pair it again.

**four grants**, each switched on at the Mac in **System Settings** → **Privacy & Security**:

| grant | what it is for | where it is asked |
|---|---|---|
| **Screen Recording** (the **Screen & System Audio Recording** list) | the picture and the audio. without it the Mac offers no swoop | the owlette app asks when it starts, and shows a notice while it is off. the grant takes effect once owlette is quit and reopened; the swoop entry appears within a couple of minutes of that |
| **Accessibility** | your keyboard and mouse | only from the owlette app's notice, whose **open system settings** button asks macOS and opens the pane. the notice clears within seconds of the grant, with no restart, and control works from the next session |
| **Local Network** | a viewer on the same network reaching the Mac directly | macOS asks, in owlette's name, at the first session. until someone at the Mac allows it, a viewer on the same network cannot reach the Mac directly |
| **Paste from Other Apps** | the clipboard from the Mac to you | never asked: set owlette to always allow. see the clipboard below |

without Accessibility you can still watch: the picture, the cursor, the audio and the clipboard from the Mac all work, but your keyboard and mouse are dropped, so a paste reaches the Mac's clipboard without being pasted.

- **the screen stays lit.** a session wakes the Mac's display and keeps it from sleeping while it captures
- **the menu bar shows the capture.** while a session captures, macOS shows its own screen recording indicator in the menu bar, and owlette cannot hide it. stopping the capture from that indicator ends the session for everyone, as an admin's kill does, rather than restarting it over the person at the Mac
- **macOS asks again after about thirty days** without a capture whether owlette may keep recording the screen. someone at the Mac has to answer it; owlette can neither answer it nor turn it off
- **the keyboard follows the Mac.** from a PC, ctrl acts as cmd, so ctrl+c copies on the Mac. the keyboard menu has two settings: **shortcuts match** (the default), where ctrl and the Windows key both send cmd, and **keys match**, where ctrl is the Mac's own control key and the Windows key is cmd. the menu shows what each of your modifier keys does under the setting you chose. outside fullscreen your own Windows keeps the Windows key for itself, so the menu's **hold cmd for the next key** sends cmd with your next key press. a Mac viewing a Windows machine does the reverse: cmd acts as ctrl. the keyboard menu lists the Mac's own shortcuts (cmd+tab, cmd+space, cmd+q, and cmd+ctrl+q to lock) in place of ctrl+alt+del, print screen and pause are dropped because a Mac has no key for them, and the Mac's keyboard layout decides what a key types
- **the clipboard** carries text and images both ways, within the limits above. an image the Mac copied as a TIFF reaches you as a PNG, and copied files are never carried. what you paste into the Mac arrives whatever macOS is set to. what the Mac copies reaches you only while owlette is set to always allow under **Paste from Other Apps**, because any other answer has macOS raise a paste alert at the Mac, and a session never raises one; each session reads the setting once, when it starts. macOS lists an app there only after the app has raised that alert once: while clipboard sharing is off, the owlette app shows a notice whose button reads the clipboard once, which raises the alert, and opens the setting. allow the alert, then set owlette to always allow. macOS before 15.4 has no such setting, and there the clipboard travels both ways

## admin → swoop

**admin** → **swoop** (`/admin/swoop`) lists everyone in a swoop session right now, pending or live, across the sites you can see: the machine, the site, each viewer with **control** or **watch**, the session's state, when it started and how long it has run. site owners and admins see the sessions on their own sites, and a superadmin sees every site. a plain member does not get the page. see the [admin panel](/docs/dashboard/admin).

**kill** ends one session after a confirm. the viewer is disconnected at once, and, like every kill above, it also closes every open second-factor window on that machine, so anyone it cut off confirms again before taking control.

you do not need the page to spot a busy machine: the dashboard's machine menu shows the live viewer count on its button and on its swoop row.

## refusal codes

a refused session arrives as a [problem](/docs/api/errors) with a `code`. the viewer shows its sentence in the middle of the screen with a **back to dashboard** button (**back to machines** in owlette swoop), and the last column says whether it tries again by itself.

| code | status | when | the viewer |
|---|---|---|---|
| `api_key_not_permitted` | 403 | the caller used an API key | stops |
| `swoop_disabled` | 403 | the site has swoop off | stops, and offers a site owner or admin **open site settings**; a member is told to ask one |
| `machine_excluded` | 403 | the machine is in `excludedMachineIds` | stops |
| `forbidden` | 403 | your role on the site does not include the capability, as when a member asks for control. the detail reads "capability not granted" | asks to watch instead |
| `capability_missing` | 403 | the same, caught at a lease renewal: you lost control or access during the session | stops |
| `members_may_not_watch` | 403 | you are a member and `membersMayWatch` is off | stops |
| `step_up_required` | 401 | control needs a second factor and no window is open, or your account has none enrolled | opens the second-factor prompt |
| `machine_offline` | 409 | the machine is not connected | retries until it is |
| `swoop_not_configured` | 503 | the deployment has no signalling server (`SWOOP_SIGNAL_URL` unset) | retries |
| `audit_unavailable` | 503 | the session's audit row could not be written | retries |
| `validation_failed` | 400 | the request was malformed | stops |
| `not_found` | 404 | the machine or the session does not exist | stops |

a second factor that does not check out comes back with its own code, such as `invalid_totp_code`, and the prompt stays open.

## notes

- **nothing secret travels in a URL**, with one exception: the link that opens owlette swoop signed in carries a sign-in code that works once, within 60 seconds. the viewer URL names a site and a machine; the signalling URL names a room. tokens and keys are only ever in a response body
- **running owlette yourself**: swoop needs a signalling worker and its keys, and a relay for strict routers; see the [swoop environment variables](/docs/setup/environment-variables#swoop-required-for-remote-desktop) and the [architecture](/docs/architecture#swoop-remote-desktop)
- **related**: [`owlette swoop`](/docs/cli/reference/swoop) (open the viewer from a terminal), [machine monitoring](/docs/dashboard/machine-monitoring) (the machine cards the entry lives on), [errors](/docs/api/errors) (the problem envelope the codes above arrive in)
