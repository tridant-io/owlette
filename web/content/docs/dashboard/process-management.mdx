## adding a process

1. click a machine in the dashboard.
2. click **add process**.
3. fill in the dialog. the fields are described in the [settings reference](#process-settings-reference) below; only the name and the path are required.
4. click **create process**.

the agent receives the new configuration and starts monitoring the process.

the dialog adapts to the machine's operating system: the path field is labelled **executable path** on Windows, **app path** on macOS and **program path** on Linux, and **task priority** and **window visibility** appear only for a Windows machine. see [on macOS and Linux](#on-macos-and-linux).

---

## editing a process

1. click **edit** on a process row or card.
2. the **edit process** dialog opens with the current settings.
3. change any fields.
4. click **save changes**.

changes reach the agent through Firestore straight away. the dialog's delete button (bin icon, bottom left) deletes the process after a confirm.

## process actions

from the process row, the machine card or the edit dialog:

| action | what it does | requires |
|--------|--------------|----------|
| **launch mode** | set `off`, `always on` or `scheduled`. a managed mode (`always on` or `scheduled`) needs a path. | `MACHINE_CONFIG_WRITE` |
| **configure schedule** | edit schedule blocks, days, time ranges and overnight windows. offered in every launch mode; editing from `off` or `always on` saves the blocks without changing the mode. | `MACHINE_CONFIG_WRITE` |
| **edit** | open the process dialog to change paths, timing, relaunch attempts, schedule and, on Windows, priority and visibility. | `MACHINE_CONFIG_WRITE` |
| **duplicate** | copy the process on the same machine. every setting carries over except the name, which gains a ` (copy)` suffix (` (copy 2)` and so on if that is taken), and the launch mode, which is forced to `off` so the copy cannot start a second instance of the same program behind your back. | `MACHINE_CONFIG_WRITE` |
| **restart** | queue a `restart_process` command. enabled for `RUNNING`, `LAUNCHING` or `STALLED` processes. | `MACHINE_EXEC_COMMAND` |
| **kill** | queue a `kill_process` command. enabled for `RUNNING`, `LAUNCHING` or `STALLED` processes. | `MACHINE_EXEC_COMMAND` |
| **delete** | remove the process from the machine configuration. a running process is not stopped. | `MACHINE_CONFIG_WRITE` |

site admins, site owners and superadmins hold `MACHINE_CONFIG_WRITE` and `MACHINE_EXEC_COMMAND`. members can see process state and configuration but cannot create, edit, delete, schedule, change launch mode, restart or kill.

restart and kill send commands to the agent. create, edit, delete, launch-mode and schedule changes update the machine configuration the agent watches.

when a process goes from `off` to `scheduled`, the agent clears stale killed and cooldown markers at once. if the current time is outside the schedule, the process stays stopped until the next window opens, then launches normally.

if the configured path no longer exists, the agent aborts the launch and the process shows `STOPPED` (`INACTIVE` means the launch mode is `off`, not a missing file). the dashboard shows an error toast — *executable not found for …*, or *app* or *program* on a Mac or Linux machine. when the agent finds likely sibling paths, the toast lists up to two, and its **use path** action opens the edit dialog with the first one filled in.

## schedules

a process in `scheduled` launch mode runs inside **blocks**: a set of days plus one or more start/stop ranges. a range whose stop time is earlier than its start is an overnight window and carries into the next day.

the editor previews the whole week as a **seven-day bar**: one column per day, with a coloured segment for every range. each block keeps its own colour, so a process with a morning block and an evening block reads at a glance, and a pattern that accidentally covers only four days is obvious before you save. the same bar appears on the process row and in the schedule preset list.

rather than rebuild a common pattern on every machine, save it once as a [schedule preset](/docs/dashboard/admin/schedule-presets) and apply it. four presets are built in, including `business hours` and `24/7`.

windows are wall-clock rules, not absolute instants. which clock they are read against depends on the site — the editor names it — see [timezones](/docs/dashboard/timezones#process-schedules).

## process settings reference

| setting | type | default | description |
|---------|------|---------|-------------|
| **name** | string | required | display name. |
| **launch mode** | enum | `off` | `off` (not managed), `always on` (kept running, relaunched after a crash), or `scheduled` (runs only inside its schedule blocks). |
| **executable path** / **app path** / **program path** | string | required | full path to what the process runs: an `.exe` on Windows (`C:\Program Files\...\app.exe`), an `.app` bundle on macOS (`/Applications/YourApp.app`), a binary on Linux (`/usr/bin/your-program`). stored as `exe_path` on every platform. |
| **file path / command arguments** | string | `""` | a file to open, or arguments to pass. a path that exists is passed as one argument, never split on its spaces. |
| **working directory** | string | `""` | directory the process runs in. |
| **task priority** | enum | `normal` | `low`, `normal`, `high` or `realtime`. **Windows only.** |
| **window visibility** | enum | `normal` | `normal` for a visible window, or `hidden` for console apps. **Windows only.** |
| **launch delay (sec)** | number | `0` | seconds to wait before launching, for boot ordering. |
| **init timeout (sec)** | number | `10` | grace period before responsiveness checks begin. |
| **relaunch attempts** | number | `3` | crash restarts before the process is treated as failed. |
| **schedule configuration** | blocks | `null` | blocks of days and start/stop ranges. pinned open in `scheduled` mode, and opened in `off` or `always on` from the gear at the end of the launch-mode control. blocks saved from `off` or `always on` are kept with the process and do not change its launch mode. a `scheduled` process with no saved blocks starts the editor on a weekday 09:00-17:00 block. |

paths must be absolute and cannot be symbolic links; on Windows they cannot be network (UNC) paths either. the agent refuses a launch that breaks either rule.

## on macOS and Linux

- **the path field** asks for an **app path** on macOS and a **program path** on Linux. on a Mac, an `.app` bundle is opened the way Finder opens it, so a running instance is brought forward rather than started twice. the file path field hands the app a file to open as a document, or command-line arguments, which reach the app after `--args`.
- **arguments** are split the way a shell splits them, so quote a value that contains spaces.
- **priority and visibility** are not offered: only the Windows launcher applies them, and a Mac or Linux agent ignores them if they are set another way (the API, hoot, or a process copied from a Windows machine).
- **someone must be signed in.** the agent runs as root and launches processes as the user signed in at the machine's screen, never as root. with nobody signed in at a graphical session, the agent refuses the launch and logs that nobody is signed in.

[platform support](/docs/reference/platform-support) lists everything else that differs.

## tips

<Callout type="idea" title={"launch ordering"}>

use **launch delay** to control startup order. for example, give a database a 0s delay and the application that depends on it 15s.

</Callout>
<Callout type="idea" title={"hidden processes"}>

on Windows, use **hidden** visibility for background services like Node.js servers or Python scripts that don't need a window.

</Callout>
<Callout type="warning" title={"realtime priority"}>

setting priority to **realtime** can starve other processes and make the machine unresponsive. use it with extreme caution.

</Callout>
