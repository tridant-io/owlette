## first login

### email and password

1. go to your dashboard URL (e.g., `https://owlette.app` or `https://dev.owlette.app`)
2. click **sign up** on the login page, fill in the form, and click **create account**
3. after registration, you're signed in automatically

### Google

1. click **continue with Google** on the login page
2. select your Google account
3. you're registered and signed in automatically

### passkey (passwordless)

if you've registered a passkey, click **continue with passkey** on the login page. authenticate the way you already unlock the device — Windows Hello, Touch ID, Face ID, a hardware security key, or a password manager that holds passkeys (1Password, Bitwarden, iCloud Keychain). no password, and no 2FA code either: the passkey satisfies both in the same step.

## set up two-factor authentication

after your first login you're taken to 2FA setup. it's required, but you choose how to satisfy it — a passkey or an authenticator app, and either one on its own is enough.

### passkey (recommended)

choose **passkey** and approve the prompt with whatever already unlocks the device: Windows Hello, Touch ID, Face ID, a hardware security key, or a password manager that stores passkeys (1Password, Bitwarden, iCloud Keychain). these are all the same WebAuthn standard — there's nothing extra to install, and nothing to configure per vendor.

a passkey covers both halves of sign-in at once. signing in with it proves who you are *and* clears the second factor in a single ceremony, so you're never asked for a code on top of it.

### authenticator app

choose **authenticator app** if you'd rather use 6-digit codes:

1. open an authenticator app (1Password, Bitwarden, Authy, Google Authenticator)
2. scan the QR code displayed on screen
3. enter the 6-digit code from your authenticator

authenticator apps are **not phone-only**. 1Password, Bitwarden, and Authy all have desktop apps, so you can enroll and sign in without a phone in the loop at all.

### backup codes

either route finishes on your **backup codes** — save them somewhere safe. they work for any factor, including a passkey-only account, and they're what gets you back in if you lose the device.

you can regenerate them later from account settings, but you'll have to prove a factor in the same step — a current 6-digit code, an unused backup code, or your passkey. a sheet of recovery codes is powerful enough to turn 2FA off outright, so a signed-in browser alone isn't enough to mint a new one.

<Callout type="idea" title={"you can change your mind later"}>

add the other method (or more passkeys) any time from account settings. removing your last factor is allowed — the account simply re-arms 2FA setup, and you'll be asked to enroll a new factor before you can use the dashboard again.

</Callout>

## create your first site

sites are the top-level organizational unit — think of them as locations, departments, or projects.

1. if you have no sites yet, click **create your first site**. otherwise open the site switcher, choose **manage sites**, then click **new site**.
2. in **create new site**, enter a **site name** (e.g., "NYC Gallery").
3. keep the generated **site ID** or open **customize site ID** to set one manually. the ID is permanent and used in URLs.
4. click **create site**.

you're automatically assigned as the owner with full access.

## site settings

open the site switcher, choose **manage sites**, then click the pencil (**edit site**) on a site's row. site admins and owners see the pencil; members don't. the panel changes the **site name** and **timezone**, which apply on **save**, and holds the site's two switches, which take effect the moment they move:

| switch | default | what it does |
|---|---|---|
| **swoop** | off | lets owners and admins watch and control this site's machines from the browser, and members watch them by default. see [swoop](/docs/dashboard/swoop#turning-it-on). |
| **keep screens awake** | on | machines on this site never sleep, blank or lock. |

### keep screens awake

keep screens awake is **on** for every site until a site admin turns it off. an online machine follows a change within seconds; an offline one picks it up when it reconnects. turning it off releases every hold, and the machine goes back to its own power and lock settings.

each machine holds it in two parts. the service holds sleep, which works with nobody signed in. the desktop app holds the signed-in session's blanking and lock, and on Windows the display as well. each part lets go when the switch goes off or its process ends, so a crash never leaves a machine held.

| OS | the service holds | the desktop app holds |
|---|---|---|
| Windows | a system-sleep power request | the display, kept on, and the session's screensaver, switched off — the user's own setting is put back on release |
| macOS | display and system idle-sleep assertions | a display assertion, and the user kept active every 30 seconds so the screensaver and lock stay away |
| Linux | a `systemd-inhibit` lock on sleep, idle and the lid switch | the GNOME session's idle inhibit, or the freedesktop screensaver's where there is no GNOME session |

a machine with nobody signed in keeps only the service's part: there is no session to keep from blanking or locking. on Linux that also covers a server with no desktop at all. the service's hold shows in each OS's own inspector: as `owlette keep screens awake` in `powercfg /requests` on Windows and `pmset -g assertions` on macOS, and as who `owlette`, why `keep screens awake` in `systemd-inhibit --list` on Linux.

in manage sites, a machine's row in the machines panel reads **awake** while it holds. agents older than 4.1.1 ignore the setting, and a Windows machine on 4.1.1 held only the session's part, so a Windows machine needs 4.1.2 or later to stay out of sleep with nobody signed in.

over the API, `PATCH /api/sites/{siteId}/display-settings` with `{ "keepAwake": false }` turns it off. it needs a site admin or owner signed in; an API key is refused.

## add your first machine

1. click the `+` (**add machine**) button on the dashboard.
2. on the **enter code** tab, download or copy the agent installer link and run it on the target machine. the button detects the platform you are browsing from — Windows, macOS on Apple silicon, or Linux — and offers the other two in a menu.
3. enter the 3-word **pairing phrase** shown on that machine. Windows shows it when the installer finishes; on macOS and Linux, open the owlette app from the menu bar or top bar and choose **join site**.
4. click **authorize**. the success state reads **machine authorized**, and the machine appears on the dashboard shortly.

for a machine nobody is standing in front of, use the **generate code** tab instead. click **generate code**, then copy the generated **pairing phrase** — or, for Windows, the whole **silent install command**. pass the phrase to the Windows installer as `/ADD=`, or on macOS and Linux write it to a pairing preseed before installing; both are in [installation](/docs/agent/installation#method-2-silent-install-with-add). a generated phrase pairs one machine and expires in 10 minutes, so generate one per machine.

within 30 seconds, the machine appears in your dashboard:

- a green **online** indicator
- CPU, memory, disk metrics populating
- the agent version

## understanding the dashboard layout

### machine cards

each machine is displayed as a card showing:

- **machine name** (hostname)
- **online/offline status** with last seen time
- **system metrics** — CPU, memory, disk, GPU percentages
- **process list** — configured processes with status indicators
- **agent version**

see [machine monitoring](/docs/dashboard/machine-monitoring).

### view modes

- **card view** — a grid of machine cards with sparkline charts
- **list view** — a compact table with sortable columns

### navigation

- **dashboard** — the main monitoring view
- **hoot** — AI chat for machine management
- **talons** — automations: a trigger, an optional condition, and actions
- **roost** — content-addressed file sync, version publishing, and rollback at `/roosts`
- **deploy** — software deployment and agent updates
- **logs** — the activity event viewer
- **admin panel** — site admins manage members, agent tokens, schedule presets, alert rules, webhooks and live swoop sessions for the sites they belong to
