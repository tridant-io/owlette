## overview

hoot's tools are grouped by risk:

| tier | type | approval |
|------|------|----------|
| **tier 1** | read-only diagnostics and site context | auto-approved |
| **tier 2** | process and machine management with validated parameters | auto-approved |
| **tier 3** | privileged shell, file, deployment, reboot and shutdown actions | in-chat approval (on by default, per site) |

what you can use depends on who you are. site admins, owners and superadmins get the full tool set. members are limited to read-only tools, and so are chat API keys, even when the key's owner is an admin.

## setup

### your key

there is exactly one place an LLM key lives: your own account settings. every hoot feature — chat, talons, visual checks, autonomous investigations — resolves a key that belongs to a specific person.

1. open the dashboard account menu.
2. select **account settings**.
3. open the **hoot** section.
4. choose **Anthropic (Claude)** or **OpenAI** as the provider.
5. pick a model.
6. paste the provider's API key and click **save key**.

the key is encrypted server-side and stored under your user settings at `users/{uid}/settings/llm`. it is never returned to the browser after it is saved.

**changing the model later** does not need the key again: leave the key field empty, pick the model, and the button reads **save model** — it keeps the stored key. changing the provider does need that provider's key. see [account settings → hoot](/docs/dashboard/account-settings#hoot).

### models

| provider | default | the list |
|---|---|---|
| Anthropic | Claude Sonnet 5 | read live from Anthropic with your saved key; before a key is saved, a built-in list from Claude Sonnet 5 and Opus 5 back to the Claude 4 models |
| OpenAI | GPT-4.1 | read live from OpenAI with your saved key; before a key is saved, GPT-4.1 (and its mini and nano), GPT-4o, GPT-4o mini, o3 and o4 mini |

**the advisor.** on Anthropic, when your model is Claude Sonnet 5, Sonnet 4.6, Haiku 4.5, or Opus 4.6, 4.7 or 4.8, hoot can consult Claude Opus 5 partway through a reply when the model judges a problem needs it. the chat shows *consulting Claude Opus 5…* while it does. it is capped at one consultation per model call and two per reply, and each is billed at Opus 5 rates to your own key. OpenAI models and other Claude models get no advisor.

small background jobs — titling and categorizing conversations — use the provider's cheapest model on your key: Claude Haiku 4.5 or GPT-4.1 nano.

### which key an unattended run spends

nobody is in the chat when a talon fires at 3am, so each unattended feature names the person whose key it spends:

| unattended work | key it resolves |
|---|---|
| a talon's hoot output | the talon's **creator** (`createdBy`) |
| a talon's visual check | the talon's **creator** (`createdBy`) |
| autonomous hoot | the **site owner** |

a talon's creator is re-checked on every run, not trusted from the day it was written. if the creator has left the site, had their account deleted, or removed their key, the talon is switched off at once with the reason recorded on the talon and on the run that found out — it does not keep failing silently.

<Callout type="warning" title="changed in 3.0.0 — the site-level key is gone">
  the site-level key scope (`sites/{siteId}/settings/llm`) and its admin endpoint (`/api/settings/site-llm-key`) have been **removed**. nothing in the dashboard could ever create a site key, which made every AI talon un-runnable; the scope is gone rather than given a UI. any `sites/{siteId}/settings/llm` document created through the old API is no longer read by anything and can be deleted. save a key in **account settings → hoot** instead.
</Callout>

## using hoot

1. open **hoot** from the dashboard header.
2. tick the machines the conversation should talk to in the target picker at the top of the chat.
3. type a request in plain language.

a chat talks to a *set* of machines. with one machine ticked, hoot reports and acts on that machine. with several, tool calls fan out to each of them and hoot aggregates the per-machine results, tagged by machine.

### choosing machines

the target picker is a checkbox menu over the site's machines, with an **all machines** row at the top.

- **all machines** is dynamic, not a shortcut for ticking every box: a machine added to the site later joins the target on its own. unticking one machine spells the rest out; ticking the last missing one collapses back to **all machines**.
- the menu stays open while you tick, so a set takes one visit. the trigger shows the target — `all machines`, `kiosk-01`, `kiosk-01, kiosk-02`, or `kiosk-01, kiosk-02 +3` — and, in brackets, how many of those machines are online.
- each row carries its status as text: *offline*, *hoot off*, or both.

**changing the ticks continues the conversation.** the chat keeps its ID and its full history, and the next turn goes to whatever is ticked when you send it — so a chat can follow a problem from one machine to its neighbours. changing the **site** starts a new conversation: a chat belongs to one site.

the selection is stored on the conversation and remembered per site across your devices, so reopening an old chat restores the machines it was talking to. if a saved target cannot be read, hoot asks you to *pick machines for this chat* and refuses to send until you do — it never falls back to every machine.

a follow-up that hoot schedules for later fires on the machines **that turn** was targeting, re-validated when it comes due — not on whatever the chat is pointed at by then. see [`schedule_followup`](/docs/reference/hoot-tools#schedule_followup).

### machines that can't take the turn

a ticked machine that is offline, or that has hoot switched off, is **skipped**: the turn runs on the rest, and the model is told which machines were left out so it can say so. the header warns before you send — for example *2 of 5 machines will be skipped — offline or hoot off*.

if nothing is left to run on, the send is refused rather than half-delivered: *no machines are currently online in this site*, or, when the hoot toggle is the whole reason, *hoot is disabled on …*.

### narrowing one turn with `@`

typing `@` in the composer opens a machine list; picking one inserts `@kiosk-01` and a chip reads **this turn → kiosk-01**. a mention narrows *that turn only* — the chat's ticks are untouched and the next message goes back to them. several mentions target their union, and a machine that is not ticked can still be named for one turn.

mentions are deliberately conservative, so ordinary prose and pasted shell are never read as targeting: `@` counts only at the start of the text or after whitespace or `(`, the name has to match a machine in the site and end at a boundary, and inline code spans and fenced blocks are skipped — PowerShell `@(...)`, `@splatting` and an email address are text. anything that does not resolve stays plain text.

a machine you *named* is never quietly skipped: if it is offline or has hoot off, the send is refused instead.

mentions come from the dashboard composer. the public conversations API, the SDK, the CLI and chat-scoped API keys get no narrowing — `@text` there is plain text.

### Mac and Linux machines

hoot works on every platform, but 13 of its tools — the Windows Update, registry, power plan, scheduled task and PowerShell tools among them — exist only on Windows. on a Mac or Linux machine they come back as `unsupported_on_platform`, and hoot reaches for what does work there: the system log, `systemctl` or `launchctl`, and the POSIX command allow-list. screenshots need the owlette app with Screen Recording on a Mac, and are not available on Linux. with nobody signed in — a login screen, or a server with no desktop — hoot still works, because its tools run in the agent's service; only the tools the owlette app carries out — `show_notification`, and `capture_screenshot` on a Mac — need someone's session. see [platforms](/docs/reference/hoot-tools#platforms).

### example conversations

**check site health:**
> "which machines look unhealthy right now?"
>
> hoot can read site logs and fan out diagnostics across online machines, then summarize the differences by machine.

**manage one process:**
> "restart TouchDesigner on this machine."
>
> hoot calls the process-management tool for the selected machine and reports the result.

**update process configuration:**
> "fix the TouchDesigner executable path to C:\Program Files\Derivative\TouchDesigner.2025\bin\TouchDesigner.exe."
>
> hoot can update configured process fields, add a new process, or delete one through the same validated server actions the dashboard uses.

**diagnose a display issue:**
> "why is the output frozen?"
>
> hoot can inspect process state, logs, GPU usage and screenshots before suggesting or taking an action.

**run a privileged command:**
> "check the detailed network configuration."
>
> hoot asks for confirmation before running a privileged shell command.

## the conversation list

the column beside the chat lists your conversations on the selected site, plus the site's autonomous investigations, newest first. more load as you scroll.

**new hoot** at the top starts a conversation. it sits above every group until its first message gives it a title.

### groups

after its first reply, a conversation is titled and put in a category automatically: **performance**, **crashes**, **network**, **display**, **processes**, **system info**, **configuration** or **general**. the list groups conversations by category, each group with its count:

- groups holding the most recent conversations come first, then **general**, then **unsorted** last.
- **unsorted** holds conversations that were never categorized — older ones, or ones whose categorizing failed. it is a group of its own, not part of general, because general is a category hoot assigns.
- **categorize N unsorted**, at the foot of the list, sorts them in one go. it titles and categorizes from what each conversation already says, with the cheapest model on your key.

click a group's heading to collapse or expand it. the button beside **new hoot** collapses or expands every group at once. a collapsed group that holds the open conversation marks its heading with a dot. which groups you collapsed is remembered per device and restored when the list opens.

### search

the search button turns the header into a search field. while you type, the list drops its groups and shows every loaded conversation whose title matches.

### rows

each row shows the title, with an **auto** badge on an autonomous investigation. hover a row to **rename** or **delete** it.

### resizing and hiding the list

- drag the list's edge to resize it, from 200 to 560 pixels; double-click the edge to reset it to 300. with the edge focused, the arrow keys resize it (hold shift for bigger steps), and home and end jump to the limits.
- **hide sidebar** / **show sidebar** in the chat header collapses the list entirely.

the width and whether the list is open are remembered per device, like the collapsed groups. on a phone the list opens as a sheet from the left instead, and is closed each time you come back.

## turn controls & reliability

a hoot turn — the model's reasoning plus any tool calls it makes — runs on the server, decoupled from your browser connection. a turn keeps running, and its results still land in the chat, if your connection drops, you close the tab, or you reload the page mid-turn. when you come back, the dashboard reattaches to the turn in flight and streams it live from where it left off. long-running tools (for example `sfc /scannow`, DISM, or a multi-minute script) survive the same interruptions.

- **stop a turn** — the stop control halts the whole turn server-side, not just your local view. the model loop stops and no further tool calls are made.
- **cancel a running tool** — while a tool call is executing, its card shows a **cancel** control. cancelling ends the work on the machine — for the shell tools (`run_command`, `run_powershell`, `execute_script`) it kills the process tree within a few seconds — and the card resolves to "cancelled by user". when a turn targets more than one machine, one cancel reaches every machine the call fanned out to.
- **interrupted tool calls self-heal** — if a tool's result is lost mid-stream, hoot repairs it into an honest error (or recovers it from the machine's completed-command record), so the conversation always continues. sending a new message while a tool is still running does not break the chat.

## approving privileged (tier-3) actions

tier-3 tools (shell, file writes, deployments, reboot, shutdown) are governed by a per-site **approval** setting, the shield toggle in the hoot header (site admins only):

- **approval required** (the default) — privileged tool calls pause in the chat for an explicit approve or deny before they run.
- **approval off** — privileged tool calls run at once, with no prompt. turning the gate off weakens safety, so the toggle asks for confirmation first. it also re-enables the lower-latency [local hoot path](#local-hoot-public-conversations-api-only) on the public conversations API; the dashboard chat always runs server-side, gate or no gate.

the setting is stored per site at `sites/{siteId}/settings/cortex.requireTier3Approval`.

### an approval belongs to the turn that asked for it

an approval card says what **that turn** resolved to, and approving runs the call on exactly those machines — not on whatever the picker shows when you come back to the chat. ticking more machines in the meantime never widens an approval that is already waiting.

a turn aimed at chosen machines names them (*on kiosk-01 and kiosk-02*, or *on 7 machines: …* past a handful). a turn aimed at **all machines** says so instead — *on every machine in this site (7 reachable)* — because a chosen seven and a whole site otherwise read the same on the one prompt where the difference matters. the count is the machines the turn can actually reach: offline machines and machines with hoot off are already excluded.

if another turn has run in the conversation since the approval was requested — a scheduled follow-up firing, or a message sent from another device — the approval no longer matches the turn it belongs to, and it is refused: *that approval expired — another turn ran in this chat. ask again.* nothing is queued on any machine and the approval is not spent; the conversation reloads and the request can be made again.

the bound machines are re-checked when you answer. one that went offline, or had hoot switched off while the card waited, is dropped from the call. if none of them is reachable, the approval is left unanswered rather than consumed, so it can still be approved once a machine comes back.

## sharing a conversation

a conversation you started can be published as a read-only web page. the **share conversation** control in the chat header opens a dialog that previews the finished page, then creates a link to it at `/share/{token}`.

a share is a **snapshot**, not a live view. it is frozen when the link is created, so messages you send afterwards never appear in a link that already exists — to publish more of a conversation, create a new link. a conversation can be shared once it has messages and nothing is running.

### what a reader sees

published:

- your messages and hoot's replies, as text
- the conversation title, and the machines the chat targeted — one name, a list such as *kiosk-01, kiosk-02 +3*, or *All Machines* for a site-wide chat
- each tool call, collapsed to the tool's name and how it ended — *completed*, *failed*, *denied*, or *not completed*

never published:

- what a tool was asked and what it answered — hostnames, paths, log lines, command output, file contents
- image attachments and screenshots
- system messages, the model's reasoning, and every other internal part of a turn

<Callout type="warning" title="the preview is the page">
  hoot's replies are published exactly as written, so a machine name, a file path, or a log line the model quoted **in its answer** goes out with the share. the dialog renders the finished page before anything is created — read it, then create the link.
</Callout>

### links, expiry, and revoking

anyone holding the link can read the page — there is no sign-in. treat the link itself as the secret: it is unguessable and never listed anywhere, but nothing beyond the link gates the page. the page is marked `noindex`, so search engines do not list it.

a link expires **30 days** after it is created by default. the dialog also offers **7 days**, **90 days**, and **never (until revoked)**.

every link you have created for a conversation is listed in the same dialog under **active links**, each with a **revoke** control. revoking takes effect at once and cannot be undone: the page starts reporting that the conversation is not available, and sharing again means creating a new link. an expired link behaves the same, and a reader cannot tell a revoked link from an expired one or from one that never existed.

**autonomous conversations cannot be shared.** a share is published by the person who started the conversation, and an autonomous investigation has no author, so the **share conversation** control does not appear on those chats.

## tool tiers

tier-1 tools read machine or site state: system info, logs, process lists, disk usage, GPU state, agent health, and site deployment presets.

tier-2 tools perform bounded management actions with validated parameters: restarting configured processes, adding, editing and deleting process config, capturing screenshots, managing services or Windows Update settings, and changing safe machine configuration.

tier-3 tools can make broader changes: shell execution, file writes, deployment orchestration, reboots and shutdowns. these are governed by the per-site tier-3 approval setting (on by default): while it is on, they pause for an explicit approve or deny before running. see [approving privileged (tier-3) actions](#approving-privileged-tier-3-actions).

the [hoot tools reference](/docs/reference/hoot-tools) has the current tool list and parameter schemas.

## how it works

every dashboard chat runs the same way. `POST /api/hoot` carries the chat's target as `target.machineIds` — an explicit list, or `null` for the dynamic **all machines** — and the web server resolves it **once**, before the turn starts: the IDs have to belong to this site, and machines that are offline or have hoot off drop out. the turn is then handed that resolved list and can only ever narrow it, never widen it. which execution path it takes depends on how many machines are left.

### one machine

when a turn effectively targets one machine — one machine ticked, one `@mention`, or **all machines** on a site that has exactly one — hoot runs the single-machine path: that machine's configured processes go into the prompt, tool output is reported unwrapped, and the machine's hoot power toggle is in the header. the turn runs detached from your browser connection, so it survives disconnects and reloads:

```text
dashboard chat
  -> POST /api/hoot with target.machineIds
  -> resolve the signed-in user's key
  -> resolve the target: in this site, online, hoot on
  -> web server runs the turn (detached from your connection)
  -> tier-1/2 tool calls are relayed to the agent through Firestore commands
  -> tier-3 calls pause for in-chat approval, then run
  -> agent writes completed-command results
  -> web server feeds results back to the model and streams the answer to the chat
```

members always use this path, capped at read-only tools.

### several machines (fan-out)

when more than one machine survives resolution, the web server fans tool calls out to each of them and aggregates the per-machine results:

```text
dashboard chat
  -> POST /api/hoot with target.machineIds (null = all machines)
  -> web server resolves the set: in this site, online, hoot on
  -> the model is told which machines this turn targets, and which were skipped
  -> web server calls the LLM provider
  -> tools either run server-side or fan out through Firestore commands
  -> per-machine results are aggregated for hoot
```

server-side tools such as site logs, system presets, deployment orchestration and process config changes run in the web server instead of going through an agent. the process create, update and delete tools call the same validated process actions as the dashboard; the agent applies the resulting config through its normal Firestore listener.

### local hoot (public conversations API only)

there is a third path, where the model loop and tools run on the agent itself, closer to the machine, for lower latency — at the cost of the approval gate and the tier caps, which the web server cannot enforce inside the agent. it is reached only through the [public conversations API](/docs/api/hoot), for a single-machine conversation, when the caller is a site admin, the site's tier-3 approval gate is **off**, and local hoot is healthy on that machine. on macOS and Linux local hoot runs as the signed-in user, so it needs someone signed in at the machine.

```text
POST /api/hoot/conversations/{conversationId}
  -> Firestore active-chat pending message
  -> local hoot on the agent runs the LLM and local tools
  -> local hoot writes response updates to Firestore
  -> the caller streams those updates back
```

the dashboard chat never takes this path — it always runs server-side, so the approval gate and the tier caps hold.

## autonomous mode

autonomous hoot can investigate a process crash or a failed process start without anyone starting a chat. the agent's alert triggers it, it is authenticated with `CORTEX_INTERNAL_SECRET`, and it runs against the one affected machine.

### flow

```text
agent alert
  -> POST /api/agent/alert
  -> internal POST /api/hoot/autonomous with x-cortex-secret
  -> check site autonomous settings
  -> deduplicate by machine/process cooldown and nonce
  -> enforce per-site concurrency
  -> run an LLM investigation with tier-capped tools
  -> store the event and conversation for review
  -> escalate by email when unresolved, offline, or disabled
```

autonomous conversations appear in the [conversation list](#the-conversation-list) with an **auto** badge. event records are stored at `sites/{siteId}/cortex-events/` with status, summary, tool-call actions, timestamps and outcomes.

### directive

every autonomous investigation is guided by a directive. the default mission is to keep configured processes running and machines operational: check agent and system logs when a process crashes, restart it, and escalate to site admins if a restart fails twice.

a custom directive can be set in Firestore at `sites/{siteId}/settings/cortex`, in the `directive` field.

### enabling autonomous mode

1. set `CORTEX_INTERNAL_SECRET` in the web runtime environment.
2. make sure the **site owner** has saved an LLM key in their account settings — autonomous investigations run on that key.
3. set `sites/{siteId}/settings/cortex.autonomousEnabled` to `true`.

### configuration options

| setting | default | description |
|---------|---------|-------------|
| `autonomousEnabled` | `false` | master switch for autonomous investigations |
| `directive` | default directive | site-specific mission text for autonomous hoot |
| `maxTier` | `2` | highest tool tier an investigation may use |
| `cooldownMinutes` | `15` | deduplication window for the same machine and process |
| `escalationEmail` | `true` | sends an escalation email when hoot cannot resolve the issue |

### guardrails

- autonomous mode is opt-in per site.
- events are deduplicated by machine and process for the cooldown window.
- duplicate nonces are rejected.
- a site runs at most three autonomous investigations at once.
- each investigation is limited to 15 steps.
- the default tier cap rules out shell commands unless the site raises `maxTier`.
- the per-machine hoot toggle blocks tool execution for that machine on every path: single-machine chats, multi-machine fan-out, scheduled follow-ups, talons, autonomous investigations, and the public conversations API.
- offline machines escalate instead of spending LLM calls.

## security

- LLM keys are encrypted at rest and resolved only on the server.
- every key belongs to one person. chat spends the signed-in user's key; a talon spends its creator's, re-checked against site access on every run; autonomous mode spends the site owner's.
- tier-3 tools are governed by the per-site approval setting (on by default): while it is on, they need an explicit in-chat approve or deny before running.
- an approval is bound to the turn that requested it and runs only on that turn's machines. an approval a later turn has made stale is refused, never re-aimed at a target nobody reviewed.
- the machines a turn may reach are resolved on the server from IDs that must belong to the verified site; a request can only narrow that set, never widen it, and an unreadable stored target sends nothing at all.
- server-side hoot checks site access before every chat request, and sending, stopping or cancelling a turn verifies the caller owns the conversation.
- members and chat-scoped API keys are capped at read-only tools, and a follow-up they schedule fires under the same cap.
- agent-routed tool calls are delivered through Firestore command documents and return through completed-command records. server-side tools run in the web process and write their own records or config changes.
- the autonomous endpoint takes `x-cortex-secret` and is not a public user-session endpoint.
