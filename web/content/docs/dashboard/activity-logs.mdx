open **logs** in the dashboard navigation, or go to `/logs`. it shows the current site's events, newest first. every member of the site can read it; clearing it needs a site owner or admin.

who started a [swoop](/docs/dashboard/swoop) session, and who was refused, is kept in the session's own audit trail, not here; see [what is recorded](/docs/dashboard/swoop#what-is-recorded).

---

## reading the timeline

the page loads 50 entries at a time. the first 50 update live; scroll to the end and the next 50 load, with **loading more...** while they do.

| column | shows |
|---|---|
| level | **info**, **warning** or **error**. any other level shows as plain text: `display_monitor_removed` is logged as `critical` |
| time | how long ago, such as "2m ago". hover it for the full date and time |
| event | the stored action with underscores as spaces: `scheduled_reboot_success` reads "scheduled reboot success", while the filter calls it **scheduled restart completed** |
| machine | the machine's name. a talon run that is not tied to one machine shows `site` |
| process | the process, for process events, and the installer, for deployment events |
| details | the start of the details text. a camera icon means a crash screenshot is attached |

click a row to expand it: the machine ID, the user when a person caused the event, the full timestamp, the full details, and the crash screenshot, which opens full size when clicked. the button beside **search** expands or collapses every loaded row (**expand all**, **collapse all**).

the header counts **events**, **warnings** and **errors** among the entries loaded and shown, search included, not across the whole site. a `critical` entry counts in neither warnings nor errors.

full timestamps follow your **display times in** setting in [account settings](/docs/dashboard/account-settings#preferences). in the per-machine mode the log uses the site's timezone, since a row does not carry its machine's.

## filtering

**show filters** opens the filter row.

| filter | options |
|---|---|
| **action type** | a searchable list of the actions below, grouped as they are here (**search actions…**). tick any number; none ticked is **all actions**. **select all** (or **select matches** while searching the list) and **none** set it in one go |
| **machine** | **all machines**, or a machine ID among the entries loaded |
| **level** | **all levels**, **info**, **warning**, **error** |
| **date range** | **all time**, **last hour**, **last 24 hours**, **today**, **yesterday**, **last 7 days**, **last 30 days**, **this week** (from Monday), **this month**, **last month**, **custom range** |

**custom range** adds **from** and **to** dates. ranges use your computer's clock. **reset filters** clears all four.

the filters run on the server, so they reach every entry the site has, not only the ones loaded. the action list holds the common actions; others reach the feed too, and search finds them.

---

## searching

**search** opens a field, "search logs...". it matches the event text, the raw action, the machine name and ID, the process, the details and the level.

while you search, the page loads every entry matching the filters, up to the 2,000 most recent, and searches those. past that cap it says "searching the most recent 2,000 logs in scope — add a date or machine filter to reach older entries." scrolling does not load more while searching. `esc` clears the field.

## event types

grouped as in the **action type** filter.

### agent

| action | filter label | level | when |
|---|---|---|---|
| `agent_started` | agent started | info | the agent's service started |
| `agent_stopped` | agent stopped | info | the service stopped cleanly |
| `update_success` | agent update succeeded | info | a self-update came back on the target version |
| `update_failed` | agent update failed | error | a self-update came back on the old version |
| `update_unknown` | agent update version mismatch | warning | a self-update came back on neither version |
| `watchdog_restart` | watchdog restart | warning | the agent restarted itself because its connection stopped working. the reason is in the details |
| `watchdog_budget_exhausted` | watchdog budget exhausted | warning | out of self-restarts. the agent keeps running and reconnecting, without restarting |
| `unexpected_service_restart` | unexpected service restart | warning | the service started again with no shutdown signal and no reboot |
| `install_permissions_repaired` | install permissions repaired | warning | at startup the agent found and reset changed permissions on its install folders (Windows) |

### processes

| action | filter label | level | when |
|---|---|---|---|
| `process_started` | process started | info | owlette launched a managed process |
| `process_restarted` | process restarted | info | a restart command restarted it, or someone did from the owlette app on the machine |
| `process_stopped` | process stopped | warning | a stop command stopped it |
| `process_killed` | process killed | warning | a kill command killed it, or owlette did to restart it. a schedule window closing logs it at info |
| `process_crash` | process crashed | error | it stopped unexpectedly; a crash screenshot may be attached |
| `process_exited` | process exited | info | it exited on its own with exit code 0 |
| `process_start_failed` | process start failed | error | launching it raised an error |
| `process_launch_failed` | process launch failed | error | its executable path does not exist |
| `exe_missing` | executable missing | error | the same missing executable, written with suggested paths; it drives the dashboard's executable-missing toast |

### commands

| action | filter label | level | when |
|---|---|---|---|
| `command_executed` | command executed | info, sometimes warning or error | a remote command ran on the machine; the details name it. a cancel from the dashboard during a restart countdown is logged here as "Pending reboot/shutdown cancelled from dashboard" |

### deployments

one row per machine when its install, or an agent update sent with a deployment, finishes. the process column carries the installer name.

| action | filter label | level | when |
|---|---|---|---|
| `deployment_completed` | deployment completed | info | the install finished on that machine |
| `deployment_failed` | deployment failed | error | it failed there; the details carry the agent's result |
| `deployment_cancelled` | deployment cancelled | warning | listed in the filter, but the current agent does not write it: a cancelled target leaves no row |

see [deployments](/docs/dashboard/deployments).

### restarts

| action | filter label | level | when |
|---|---|---|---|
| `scheduled_reboot_announced` | scheduled restart announced | warning | a scheduled restart's countdown started |
| `scheduled_reboot_success` | scheduled restart completed | info | the machine came back and the agent matched it to the attempt |
| `scheduled_reboot_failed` | scheduled restart failed | error | the OS refused it, or the attempt was interrupted |
| `scheduled_reboot_missed` | scheduled restart missed | warning | it was noticed more than five minutes late and skipped |
| `scheduled_reboot_cancelled` | scheduled restart cancelled | info | the schedule was edited while an attempt was pending, which dropped the attempt |
| `external_reboot` | external restart | warning | the machine restarted outside owlette, after a clean shutdown |
| `unexpected_reboot` | unexpected restart | warning | the machine booted with no shutdown signal before it. Windows only: on macOS and Linux such a boot is not reported |

the scheduled outcomes are explained in [restart schedules](/docs/dashboard/restart-schedules#what-shows-up-in-the-logs).

### displays

fifteen actions, from `display_monitor_added` to `display_auto_restore_circuit_breaker_tripped`, described in [displays](/docs/dashboard/displays#events). displays are Windows only, so only Windows machines log them.

### talons

| action | filter label | level | when |
|---|---|---|---|
| `talon_triggered` | talon triggered | info | a talon run started |
| `talon_succeeded` | talon succeeded | info | the run succeeded |
| `talon_failed` | talon failed | error | the run failed |
| `talon_skipped` | talon skipped | warning | the run was skipped, or a delayed run was missed |

the details read `talon name — trigger — result`. see [talons](/docs/dashboard/talons#runs-failures-and-audit).

### swoop

| action | filter label | level | when |
|---|---|---|---|
| `swoop_session_start` | swoop session started | info | the machine started a streamer for a session |
| `swoop_session_end` | swoop session ended | info | the streamer stopped; the details give the reason |
| `swoop_spawn_refused` | swoop spawn refused | warning | the agent refused to start a streamer; the details give the reason |

the agent writes a few more `swoop_*` rows, such as token refreshes and firewall changes, that the filter does not list; search finds them.

## clearing logs

**clear logs** permanently deletes entries from the current site. site owners and admins see it, and it is disabled while nothing is loaded.

the **clear event logs** dialog lists what it will delete: the **action type**, **machine** and **level** you have filtered on, plus its own **from (optional)** and **to (optional)** dates. the page's **date range** filter is not part of it; only the dialog's dates are, taken as whole days in your display timezone. the search box never limits a clear, and the dialog says so while you are searching. with nothing set, it warns that it will delete every event log on the site, across all machines.

**clear logs** in the dialog deletes. the list empties and refills from what remains.

## over the API

entries live in `sites/{siteId}/logs/{logId}`. the dashboard reads them there directly; the API reads the same collection.

```http
GET /api/sites/{siteId}/logs?action=process_crash&machineId=machine-1&level=error&since=2026-10-01T00:00:00Z
```

- **filters**: `action` (one), `machineId`, `level` (`debug`, `info`, `warning`, `error` or `critical`), and `since` / `until`, each unix milliseconds or ISO 8601
- **pages**: `page_size`, 50 by default and at most 200, and `page_token` from the last response's `next_page_token`. see [pagination](/docs/api/pagination)
- **each entry**: `id`, `siteId`, `timestamp` (ISO 8601), `action`, `level`, `machineId`, `machineName`, `processName`, `details`, `userId`, `screenshotUrl`
- **one entry**: `GET /api/sites/{siteId}/logs/{logId}`

reading needs read access to the site. clearing is a `DELETE` on the same path:

```http
DELETE /api/sites/{siteId}/logs
Idempotency-Key: <unique-key>
Content-Type: application/json

{ "actions": ["process_crash", "process_start_failed"], "machineId": "machine-1", "since": 1790812800000 }
```

- **filters**: `action` or `actions` (a list, not both), `machineId`, `level`, `since`, `until`
- **everything**: with no filter the body must be `{ "all": true }`, and `all` must be left out when any filter is set
- **who**: a site owner or admin, or an API key with admin permission, with an [`Idempotency-Key`](/docs/api/idempotency)
- **response**: `siteId`, `deletedCount` and the `filters` applied. a clear cannot be undone

## retention

entries older than 400 days are deleted by a scheduled job, along with talon runs of the same age. each run removes a bounded number, so a large backlog clears over several runs.
