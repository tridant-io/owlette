## how it works

```text
browser
  -> hash files into 4 MiB SHA-256 chunks
  -> ask owlette which chunks already exist
  -> upload missing chunks directly to R2 signed URLs
  -> publish an immutable version body
  -> queue sync_pull commands for target machines
  -> agents download chunks, assemble files, and commit atomically
```

the browser builds the version before anything is published. each file entry records its relative path, size and ordered chunk list. re-uploading a folder with one changed file reuses the existing chunks and uploads only what is missing.

versions are immutable. publishing writes the version JSON to R2, derives a stable `versionId` from the canonical version content, and updates `sites/{siteId}/roosts/{roostId}` in a Firestore transaction. the roost document holds the current and previous version pointers, the version number, description, targets, extract path, and file and size totals.

targets receive `sync_pull` commands. the agent fetches a fresh signed URL for the version body, downloads any missing chunks, keeps crash-safe local state in `sync-state.db` in its data directory, assembles the files under the extract path, and commits the result atomically.

roost syncs on every platform the agent runs on; [on macOS and Linux](#on-macos-and-linux) covers where files may land there.

## creating a roost

1. open **roost** from the dashboard header.
2. click **new roost**.
3. enter a roost name and an optional description.
4. drop a folder, or browse for a folder or files.
5. choose an optional extract path.
6. select target machines.
7. click **upload and distribute to N machines**.

**upload** publishes a version without sending it anywhere. use it to store the version first, then add targets or re-sync later.

before the upload starts, the dialog checks size and targets: it estimates the total bytes, warns when a target's free disk is unknown or too small, and blocks only hard failures. during the upload the dialog can be minimized; the floating upload card keeps showing hashing, duplicate-check, upload and finalize progress.

a name that is already taken creates a separate roost under a new ID, and the dialog says so. to add a version to an existing roost, use **+ new version** on it instead.

### source and paths

files are chunked and hashed in the browser. empty files are skipped, because a version needs at least one chunk per file.

the extract path defaults to `~/Documents/Owlette/`. a relative path lands under `~/Documents/` (`projects/show1` becomes `~/Documents/projects/show1/`), and an absolute path is used as typed. the dialog shows what the path resolves to.

the agent writes only inside its allowlist, `agent_config.allowed_extract_roots` in the machine's config. without one, each platform accepts its own default root:

| platform | default root |
|---|---|
| Windows | the signed-in user's `Documents` folder |
| macOS | `/Users/Shared/Owlette` |
| Linux | `/var/lib/owlette/projects` |

a path outside the root needs an allowlist entry on the target machine. when a path looks outside the Windows root, the dialog shows the exact config block to add and reminds you to restart the agent.

## on macOS and Linux

- **the default path is mapped.** a Mac or Linux target receives the default `~/Documents/Owlette/` as its own platform's root, so a roost left on the default lands in `/Users/Shared/Owlette` or `/var/lib/owlette/projects`.
- **other relative paths are not.** `~` resolves to the signed-in user's home, and anything under it is outside the default root, so a relative path needs an allowlist entry — or use an absolute path inside the platform's root, such as `/var/lib/owlette/projects/show1`. with nobody signed in, a `~` path is refused outright.
- **the dialog's path check assumes Windows.** it warns about any path that is not allowed on Windows — a POSIX path such as `/opt/exhibit` reads as *not a path a Windows machine can use* — whatever the targets run. for a Mac or Linux target, check the path against that platform's root above instead.
- **files belong to the signed-in user.** synced files are owned by the user at the machine's screen, and a script or program is made executable.

see [platform support](/docs/reference/platform-support#roost).

## publishing new versions

open an existing roost and click **+ new version** from its version history. the dialog title becomes `publish new version of "<name>"`; the name, extract path and target machines stay locked to the roost. drop the replacement folder or files, add a description, then publish.

each publish creates a new immutable version and increments the roost's version number (`v1`, `v2`, `v3`, ...). the version list shows the current marker, description, relative publish time, file count and size, with actions to copy the version ID, view files, diff against current, edit the description, or roll back.

descriptions can be edited; version content cannot. to change files, publish another version.

## targets and status

targets are stored on the roost and shown in its detail panel. adding a target from the panel updates the list and sends the current version to the new machines at once. removing a target stops future dispatches to that machine; it does not delete files already written.

use **re-sync targets** after fixing a failed machine, or whenever every target should pull the current version again. re-sync clears stale `target_state` records for the roost, removes the previous rollout record for the current version, and queues fresh `sync_pull` commands for all current targets.

| target state | dashboard label | meaning |
| --- | --- | --- |
| `pending` | queued | command accepted, or the target has not reported progress yet |
| `downloading` | downloading | the agent is fetching missing chunks; chunk counts may show |
| `assembling` | assembling | the agent is rebuilding files under the extract path |
| `committed` | synced | files were assembled and committed atomically |
| `failed` | failed | the agent reported an error; the message is in the target row's tooltip |
| `cancelled` | cancelled | the sync was cancelled before commit |

collapsed rows roll these up as `synced`, `syncing`, `partial`, `queued`, `failed` or `no targets`. a report for an older version counts as awaiting the current one, so a row never shows stale success.

## rollback

rollback moves the roost's current pointer back to an existing version; it does not create a new one. the rollback API accepts aliases such as `previous`, `current` and `first`, numbers such as `3` or `v3`, and version IDs.

after a rollback the roost document's `currentVersionId`, `currentVersionNumber`, `previousVersionId`, totals and version URL change, and the route queues `sync_pull` commands so every target pulls the older version. if a target does not move, use **re-sync targets**.

rollback is refused when the selected version is already current. if a version's metadata exists but its body has been reclaimed from storage, file view, diff and rollback cannot use it.

publishing and rolling back send the `version.published` and `version.rolled_back` [webhook](/docs/api/webhooks) events to subscribed endpoints.

---

## presets

the **presets** row in **new roost** stores reusable path settings. built-in presets can be applied but not edited. custom presets can be created, renamed, deleted and replaced.

while a custom preset is active, edits to its extract path save on their own after a short pause; the status reads **autosaves**, then **saving...**, then **saved**. presets do not save dropped files, descriptions, selected targets or versions.

## troubleshooting

### chunk upload failures

- an upload stuck on **checking for duplicates** means the browser could not finish the chunk-presence check. refresh and retry after confirming the site is selected and you are still signed in.
- an upload stuck on **uploading** means one or more signed R2 PUTs failed. the queue retries with backoff; past the retry cap, the upload fails with the failed chunk count.
- reopen the same roost and drop the same folder or files to resume. the browser keeps an IndexedDB queue per site and roost, so chunks that already succeeded are skipped and in-flight ones replay.
- clearing the browser's site data removes that queue. the next attempt still skips chunks R2 already holds, but the browser no longer knows which of its own tasks finished.

### R2 or signed URL issues

- the server needs `R2_S3_ENDPOINT`, `R2_S3_ACCESS_KEY_ID` and `R2_S3_SECRET_ACCESS_KEY` to reach R2.
- a finalize error saying chunks are missing means the version references hashes R2 does not hold. retry the upload so `/api/chunks/upload-urls` can mint fresh PUT URLs for them.
- agent download errors can come from expired or rejected signed URLs. the agent asks the API for fresh version and chunk URLs during `sync_pull`; check API auth and R2 credentials if those requests fail.
- `version body gone` means the version's metadata exists but its body in R2 cannot be read.

### IndexedDB queue recovery

during an upload, tasks are kept in the browser's IndexedDB. on restart, any in-flight task goes back to pending and is retried. recovery needs the same browser profile, site, roost and local files, so the chunk hashes match.

if recovery keeps failing, cancel the upload, clear the selected files, reselect the folder and start again. chunks already in R2 are still skipped.

### publish failures

- roost cannot publish an empty version. if every selected file is zero bytes or rejected by path sanitization, add at least one non-empty file.
- chunk hashes must be lowercase 64-character SHA-256 hex. prefixes or uppercase characters are invalid.
- publishing checks that every referenced chunk exists before the pointer changes; missing chunks return a precondition failure.
- two publishes at once can conflict when the expected current version no longer matches. reopen the roost, check the new current version, and publish again.

### agent assembly or commit failures

- check the target row's error tooltip first; the full detail is in the agent log and its local sync state.
- confirm the machine is online and running an agent with `sync_pull` support.
- confirm the extract path is inside the machine's allowlist — on a Mac or Linux machine, against that platform's root (see [on macOS and Linux](#on-macos-and-linux)).
- check free space on the destination volume.
- if downloads succeed but assembly fails, fix the path, permission or disk issue, then **re-sync targets**.
- if a new version is bad, roll back to the previous one and let targets pull it.

### rollback does not move targets

- confirm the selected version is not already current.
- confirm the older version's body still exists in R2.
- check whether the row shows an old target report: a report for the previous current version counts as awaiting work.
- **re-sync targets** queues fresh `sync_pull` commands after you fix the storage, auth or agent issue.

## legacy URL distribution

removed. the old by-URL distribution path — the dialog's `by url` source, the `/api/sites/{siteId}/project-distributions` routes and the agent's `distribute_project` command — no longer exists. roost is the only distribution system: upload a folder on `/roosts`.
