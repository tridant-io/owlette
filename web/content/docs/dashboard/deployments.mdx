the **deploy** page (`/deployments`) installs software across a site's machines. each deployment is one record with one target per machine, and every target is tracked from queued to installed.

**deployments run on Windows only.** the dashboard lets you pick a Mac or Linux machine as a target, but its agent cannot run the installer: it closes the processes you chose, downloads and checks the file, then fails the target with "Error: No interactive user session available for installation. A user must be logged in." see [platform support](/docs/reference/platform-support#software).

creating, retrying, cancelling, uninstalling and deleting need a site owner or admin.

## creating a deployment

1. open **deploy** and click **new deployment**. the **deploy software** dialog opens.
2. optionally pick a starting point in **template**: **none**, a preset from the library (grouped by category), or one of the site's own templates under **Saved**.
3. enter the **installer URL**, a direct `https://` link. the filename is taken from the last part of the URL and needs an extension.
4. wait for the checksum to finish (see [the checksum](#the-checksum)).
5. set **silent install flags**, **parallel install (keep existing versions)** and **close running processes before install** as needed.
6. choose the **target machines**: **online only (N)**, **select all**, or tick machines one by one.
7. click **deploy to N machines**.

the deployment's name is the name in the template row. pick a template, or click the pencil (**rename template**) and type one. left blank, it takes the selected template's name, then the installer filename, then `Deployment`.

| field | what it does |
|---|---|
| **template** | fills the form from a preset or a saved template. see [templates and presets](#templates-and-presets) |
| **installer URL** | required. a direct `https://` download, not a landing page. the API refuses anything else |
| **silent install flags** | passed to the installer as one command line; line breaks are folded into spaces. empty is allowed, but most installers need flags to run unattended |
| **parallel install (keep existing versions)** | installs alongside an existing version: the agent hides the registry entries of software with the same name (the filename up to its first dot) while the installer runs, so it cannot find and remove the old one |
| **close running processes before install** | closes processes before the install starts. see [closing processes](#closing-processes) |
| **target machines** | the site's machines, each marked online or offline. an offline machine picks the install up when it reconnects |

**verify path.** the dialog has no field for it: it comes from a preset or a saved template. without one, the agent takes the folder from a `/DIR=` flag. after the installer exits, the agent checks the path exists and fails the target if it does not, which usually means the installer showed a dialog or needs different flags.

**target limit.** a deployment reaches at most 100 machines unless the site has its own `deployQuota`. more is refused with `413 over_quota`.

### the checksum

every install carries the installer's SHA-256. the agent refuses an install without one ("Refusing to install … without sha256_checksum") and aborts when the downloaded file does not match.

the dialog computes it for you. once the URL stops changing, owlette's server downloads the installer and hashes it: the row shows **computing sha256 checksum…**, then `sha256:` with the start and end of the digest. **deploy to N machines** is disabled while it computes, and neither deploying nor saving a template goes ahead without a checksum.

- **the server cannot reach the URL** (a LAN-only host, for example): the row shows the error with **retry** and **enter manually**. paste the 64-character hex digest, or click **compute automatically instead** to go back. **enter manually** is also offered while it computes
- **templates and presets** carry their checksum, so picking one skips the download. one saved before checksums existed is hashed again
- **the file behind a URL changes**: the stored checksum no longer matches, and every machine fails the check. point the template at the new file so the dialog hashes it, and save it again

### closing processes

**close running processes before install** opens two inputs:

- **managed processes**: the processes owlette manages on the machines you selected, so select machines first. a ticked process is closed and kept from relaunching until the install ends, then owlette starts it again
- **additional process names**: comma-separated executable names. the agent closes only processes owlette manages, so a name that matches no managed process on that machine is skipped, whatever the field's hint says

a warning lists everything that will be closed before you deploy.

## templates and presets

the **template** list has two sources:

- **presets** come from the [system preset library](/docs/dashboard/admin/system-presets) that owlette curates. they are read-only here: while one is selected, the rename, save and delete buttons are hidden. picking one names the deployment `Deploy <software name>`
- **saved templates** belong to the site and store the name, installer URL and filename, silent flags, SHA-256 checksum and parallel-install setting, plus a verify path and the processes to close when they have them

| button | what it does |
|---|---|
| **new template** (+) | clears the form and opens the name field, for a template from scratch. always shown |
| **rename template** (pencil) | swaps the list for a name field |
| **save as new template** / **save changes to template** (disk) | saves a new template, or updates the saved template that is selected. needs a name and a checksum |
| **delete template** (bin) | deletes the selected saved template after a confirm. shown only for a saved template |

a template saves processes to close as executable names: the ticked managed processes' executables plus the additional names.

## following a deployment

each row shows a status icon, the name, the installer filename, a status badge and when it was created. hover a **failed** or **partial** badge to see each failed machine's error. click the row to expand it: the installer URL, silent flags and verify path, then one line per target with its progress, its state, its error in full, and the buttons below.

the page header counts **total**, **in progress** and **templates**. times follow your **display times in** setting in [account settings](/docs/dashboard/account-settings#preferences); in the per-machine mode they use the site's timezone, since a deployment spans machines.

### target states

| state | meaning |
|---|---|
| `pending` | the install is queued for the agent |
| `closing_processes` | the agent is closing the processes you chose |
| `downloading` | the agent is downloading the installer; progress may show |
| `installing` | the installer is running; progress may show |
| `completed` | the installer succeeded, and the verify path exists if one was set. exit code 3010 counts as success and says a reboot is required |
| `failed` | something stopped it; the error is on the target line |
| `cancelled` | a cancel reached this target |
| `uninstalling` / `uninstalled` | an uninstall tied to this deployment is running, or finished. see [uninstalling](#uninstalling) |

### overall status

| status | when |
|---|---|
| `in_progress` | at least one target has not finished. a new deployment shows it almost at once |
| `completed`, `failed`, `cancelled`, `uninstalled` | every target ended in that state |
| `partial` | any mix of finished states: completed with failed, completed with cancelled, failed with cancelled |
| `uninstalling` | set by the API's deployment uninstall until its targets report |
| `pending` | only for the moment the record is being written |

one exception: when a cancel is what finishes the last targets, a mix of failed and cancelled with nothing completed reads `failed` rather than `partial`.

### how an install runs

on Windows the agent runs the installer with SYSTEM rights in the machine's console session, not in the service's own session, so installers that start sub-installers have a desktop to run them on. anything the installer shows appears on the machine's screen. with no active console session, the target fails with the message above.

the agent stops an installer that runs longer than 40 minutes. separately, a scheduled sweeper is meant to fail targets whose agent stops reporting: `pending` after 15 minutes, and `downloading`, `installing` or `uninstalling` after 30, both counted from when the deployment was created, not from the target's last change. it only reaches sites it is already sweeping, so do not count on it: a target whose agent never reports back can stay in its state.

each finished target also writes `deployment_completed` or `deployment_failed` to [activity logs](/docs/dashboard/activity-logs#deployments).

## retrying

- **retry failed**, in the row's menu (**more options**), requeues every failed target on the same record. the targets go back to `pending` with their errors cleared, and the deployment returns to `in_progress`. no new record is made
- **retry this machine**, on a failed target's line, does the same for that one machine

a deployment created before checksums were pinned has none. a retry then downloads and hashes the installer first, which takes a while for a large file (the button spins), and saves the checksum on the record.

a retry sends the installer, flags, checksum, verify path and parallel setting again, but not the processes to close. close them yourself first, or start a new deployment.

## cancelling

the × on a target that is `pending`, `closing_processes`, `downloading` or `installing` cancels the **whole deployment**, not that machine, and asks for no confirm:

- every target still `pending`, `closing_processes` or `downloading` has its queued install removed, gets a `cancel_installation` command, and is marked `cancelled`
- targets that are `installing` or finished are left alone. the × shows on an installing target, but when nothing cancellable remains the request is refused with `409 no_cancellable_targets`, and the page shows nothing

a cancel is only certain for a target the agent has not picked up. one already closing processes or downloading is marked `cancelled`, but the agent has no installer running to stop yet, so the install can carry on and the target can still end `completed`.

## uninstalling

**uninstall software**, in the row's menu, opens the **uninstall software** dialog with the deployment's installer name used to find a match. it is hidden once the record is `uninstalled`.

1. **select target machines**: the online machines are selected when it opens.
2. **select software to uninstall**: the programs installed on the selected online machines, merged into one list with **filter software...**. the selected one shows its name, version, publisher, type and location.
3. click **uninstall software** and confirm.

owlette sends one uninstall per machine, by program name, and looks the program up in that machine's software list. a machine that does not list it stops the run there: the machines before it are queued and the rest are not, so select only machines that have it. an offline machine runs the uninstall when it reconnects.

| platform | what happens |
|---|---|
| Windows | the program's own uninstaller runs silently, for up to 20 minutes. if it still appears in the registry afterwards, the result says a reboot may be needed |
| macOS | the agent quits the application and removes its bundle, only for an application bundle the machine's software list shows (type `APP`) |
| Linux | the uninstall fails |

today the uninstall is not tied to the deployment: its targets keep their install states, the record never reaches `uninstalled`, and the menu keeps offering **uninstall software**.

## deleting a record

**delete record**, in the row's menu, removes the record after a confirm. it does not uninstall anything.

the API deletes only a record that is `completed`, `failed`, `partial`, `cancelled` or `uninstalled`, with no target still `pending`, `closing_processes`, `downloading` or `installing`. otherwise it refuses with `409 deployment_in_flight`, and the page shows the reason.

## troubleshooting

### download failed

- the URL must be a direct `https://` download, not a page that links to one. for Dropbox, use a direct-download form such as `?dl=1`
- a signed or time-limited URL may have expired by the time a machine downloads it
- test the URL in a browser on the machine's network: the machine downloads it itself, not through owlette's server

### checksum verification failed

the file the machine downloaded is not the one that was hashed. a URL that always points at the latest build changes under a saved checksum; use a versioned URL, or update the template so it is hashed again.

### installation fails

- check the silent flags for that installer family: `/VERYSILENT /SUPPRESSMSGBOXES` for Inno Setup, `/S` for NSIS, `/qn` for an MSI, `/s /v"/qn"` for InstallShield. try them by hand on one machine first
- check for prerequisites such as .NET, the Visual C++ runtimes or a license service
- read the agent log, `logs/service.log` in the data directory: `C:\ProgramData\Owlette\logs\service.log` on Windows, `/Library/Application Support/Owlette/logs/service.log` on macOS, `/var/lib/owlette/logs/service.log` on Linux. see [log locations](/docs/agent/troubleshooting#log-locations)
- on a Mac or Linux machine, the failure is expected: see the top of this page

### a target is stuck

a target whose agent stops reporting, because it went offline or restarted mid-install, can stay in `downloading` or `installing`. an installing target cannot be cancelled or retried, and it keeps the record from being deleted; the dashboard has no way to clear it today. a machine that never picked the install up stays `pending` and takes it when it reconnects.

### the deployment cannot be cancelled

the cancel only reaches targets still `pending`, `closing_processes` or `downloading`. once every target is installing or finished, there is nothing to cancel: use **retry failed** for failures, or **uninstall software** to remove a finished install.

### the record cannot be deleted

wait until every target has finished, or cancel what can be cancelled. deleting never uninstalls; use **uninstall software** first when the program should go.

## notes

- **trust the source.** the agent runs installers with SYSTEM rights. deploy only installers you trust, and try new ones on one machine first
- **agent updates** are not deployments: **update owlette**, beside **new deployment**, updates the agent itself. see [self-update](/docs/agent/self-update#from-the-dashboard)
- **over the API**: `POST /api/sites/{siteId}/deployments` creates one; `…/{deploymentId}/retry` (with an optional `machines` list), `…/cancel` and `…/uninstall` act on it; `DELETE …/{deploymentId}` removes the record. every change takes an [`Idempotency-Key`](/docs/api/idempotency). the API does not compute the checksum: send `sha256_checksum` yourself, or every agent refuses the install. the same calls are in the [`owlette deploy`](/docs/cli/reference/deploy) CLI
