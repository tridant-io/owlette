**location**: admin panel → schedules (`/admin/schedules`)

**storage**: Firestore `config/{siteId}/schedule_presets/{presetId}`

**API**: `/api/sites/{siteId}/presets/schedule`, capability `PRESET_MANAGE` (site owners and admins)

---

## what they are

a schedule preset is a named set of **process launch windows**, days plus time ranges, stored on a site and reusable across its machines. picking a preset for a process in `scheduled` launch mode saves rebuilding the same weekday 09:00–17:00 pattern on every machine.

presets belong to one site. the page's site selector offers the sites you belong to.

there are three preset families in owlette, and they are easy to confuse:

| preset family | controls | lives at |
|---|---|---|
| **schedule presets** | when a process is allowed to run | `/admin/schedules` (this page) |
| **restart presets** | when a machine reboots | the [restart schedule](/docs/dashboard/restart-schedules#presets) editor |
| **[system presets](/docs/dashboard/admin/system-presets)** | installer templates for deployments | `/admin/presets` |

## built-in presets

four ship with every site and carry a `built-in` badge:

| preset | windows |
|---|---|
| **business hours** | Mon–Fri, 09:00–17:00 |
| **extended hours** | Mon–Fri, 07:00–22:00 |
| **weekday 24h** | Mon–Fri, 00:00–23:59 |
| **24/7** | every day, 00:00–23:59 |

a built-in has no delete. editing one writes a site-level copy that this page shows from then on, and the page offers no way back to the original. the schedule editor's preset pills still apply the original built-in definitions, not a site's edited copy.

## creating and editing

**create preset** opens the preset dialog. it renders its labels in title case, as **Create Schedule Preset**:

| field | notes |
|---|---|
| **Name** | required. shown wherever a preset is picked |
| **Description** | optional. shown on the row in place of the schedule summary |
| **Schedule** | one or more blocks. a block is a set of days plus one or more start/stop ranges, and can carry its own name (it shows `block 1` until you name it). a block with no day or no range is dropped on save, and at least one complete block is required |

**Create Preset** saves it; when editing, **Save Changes**.

each row previews the preset as a seven-day bar (not on a phone), so a preset that covers only half the week is obvious before you use it. a range whose stop time is earlier than its start is an overnight window and runs into the next day.

the pencil edits a preset; the bin, on custom presets only, deletes it after **delete schedule preset**. neither changes a process that already uses it: applying a preset copies its blocks onto the process, with a `schedulePresetId` noting where they came from. edit a preset and the processes using it keep their old blocks until you apply it to each one again.

## from the schedule editor

presets are applied from a process, not from this page. pick **configure schedule** from the process's launch-mode menu, and the **configure schedule** dialog shows the presets as pills: the built-ins first, then the site's custom presets. click one to fill in its blocks, then **save schedule**. see [process management](/docs/dashboard/process-management#schedules).

the same row of pills manages custom presets without leaving the process:

- **new preset** saves the blocks you have as a new preset; name it and click save
- with a custom preset selected, **update preset** (shown once the blocks differ from it) saves your changes into it, **rename** renames it, and **delete** deletes it

built-ins cannot be changed from the schedule editor.

## which clock they run on

launch windows follow **the site's schedule clock**: the site's own timezone if the site has opted into site time, each machine's local timezone otherwise. presets store wall-clock times and nothing else, so the same preset means different absolute instants at a site spread across timezones.

restart schedules work the other way and are always machine-local. [timezones](/docs/dashboard/timezones#process-schedules) explains why, and how a site opts in.
