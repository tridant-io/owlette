the admin panel holds two kinds of page: site-scoped pages, for the people who run a site, and internal pages, for owlette itself.

---

## site-scoped pages

these open for anyone who is an **owner** or **admin** on at least one site:

| page | URL | what it does |
|------|-----|--------------|
| sites | `/admin/sites` | list your sites, and open one's settings: its name and timezone, its members with their roles and swoop modes, its machines, its switches, and deleting it. see [sites](/docs/dashboard/admin/sites) and [member management](/docs/dashboard/admin/member-management) |
| agent tokens | `/admin/tokens` | list and revoke a site's agent refresh tokens. see [token management](/docs/dashboard/admin/token-management) |
| swoop | `/admin/swoop` | see everyone in a [swoop](/docs/dashboard/swoop) session right now, and end a session |
| schedules | `/admin/schedules` | manage [schedule presets](/docs/dashboard/admin/schedule-presets) |
| alerts | `/admin/alerts` | manage a site's threshold alert rules. see [email alerts](/docs/dashboard/admin/email-alerts) |
| webhooks | `/admin/webhooks` | manage a site's outbound [webhook](/docs/dashboard/admin/webhooks) subscriptions |

**sites** lists every site you belong to, with a gear on each one you own or administer. the other pages act on one site at a time: their site selector offers the sites you belong to, and a change goes through only on a site where you are owner or admin; on a site where you are a plain member the server refuses it. the swoop page simply leaves out the sites you only belong to as a member.

---

## internal pages

installers (`/admin/installers`), the template library (`/admin/presets`), users (`/admin/users`) and email (`/admin/email`) cover platform-wide operations run by owlette. they are hidden from the sidebar for customer accounts, and their routes send anyone else back to the dashboard.

---

## roles

your role is set **per site**: the same person can own one site, administer a second and be a plain member of a third. the role on your owlette account grants nothing on a site by itself. the one exception is owlette's superadmins, who reach every site.

| role on a site | what it can do there | admin panel |
|------|-------------|-------------|
| **member** | read-only: view machines, capture screenshots, open live view, and watch a [swoop](/docs/dashboard/swoop) session when the site lets members watch | none from this site |
| **admin** | everything a member can, plus machine commands and configuration, swoop control and swoop settings, deployments, roosts, talons, webhooks, logs, alert rules, enrolling machines, revoking their tokens and managing members | the six site-scoped pages above |
| **owner** | everything an admin can, plus deleting the site and transferring ownership. every site has exactly one | the six site-scoped pages above |

a person's [swoop mode](/docs/dashboard/admin/member-management#swoop-mode) on a site can change what they get from swoop there, and nothing else.

---

## getting admin on a site

ask an owner or admin of that site to change your role. the change applies to that site only, and it takes effect at once. they make it, with any change to your swoop mode, in the site's members section: see [changing a role](/docs/dashboard/admin/member-management#changing-a-role).

ownership is not a role anyone can assign: it moves by transfer, from the current owner (or an owlette superadmin).

---

## opening the panel

- **profile menu** → **admin panel**. the entry shows once you are an owner or admin on at least one site, and opens on **sites** (owlette's superadmins land on installers)
- **direct URLs**: `/admin/sites`, `/admin/sites/{siteId}`, `/admin/tokens`, `/admin/swoop`, `/admin/schedules`, `/admin/alerts`, `/admin/webhooks`

someone who is owner or admin on no site is sent back to the dashboard with an error, and so is a site admin who opens an internal page directly.

---

## capability matrix

every permission check in the web app asks for one capability. a site-scoped capability is held only on the site where you have that role; reading the sites you belong to is baseline membership, not a capability.

| capability | member | admin | owner | scope |
|-----------|:------:|:-----:|:-----:|-------|
| read access to the site | yes | yes | yes | site membership |
| `MACHINE_VIEW` (screenshots, live view) | yes | yes | yes | site |
| `MACHINE_REMOTE_VIEW` (watch swoop) | yes | yes | yes | site |
| `MACHINE_EXEC_COMMAND` | no | yes | yes | site |
| `MACHINE_REMOTE_CONTROL` (control swoop) | no | yes | yes | site |
| `SWOOP_SETTINGS_MANAGE` | no | yes | yes | site |
| `MACHINE_CONFIG_WRITE` | no | yes | yes | site |
| `MACHINE_REMOVE` | no | yes | yes | site |
| `MACHINE_ENROLL` (installers, setup tokens, pairing codes) | no | yes | yes | site |
| `AGENT_TOKEN_REVOKE` | no | yes | yes | site |
| `DEPLOYMENT_MANAGE` | no | yes | yes | site |
| `DISTRIBUTION_MANAGE` (roost) | no | yes | yes | site |
| `UNINSTALL_TRIGGER` | no | yes | yes | site |
| `PRESET_MANAGE` (site presets) | no | yes | yes | site |
| `SITE_MEMBER_MANAGE` | no | yes | yes | site |
| `WEBHOOK_MANAGE` | no | yes | yes | site |
| `SITE_LOGS_MANAGE` | no | yes | yes | site |
| `TALON_MANAGE` | no | yes | yes | site |
| `ALERT_RULES_MANAGE` | no | yes | yes | site |
| `SITE_DELETE` | no | no | yes | site |
| `USER_SELF_PREFS` | yes | yes | yes | your own account |
| `USER_SELF_DELETE` | yes | yes | yes | your own account |
| `USER_ROLE_MANAGE` | no | no | no | platform |
| `USER_DELETE` | no | no | no | platform |
| `SYSTEM_PRESET_MANAGE` (deployment template presets) | no | no | no | platform |
| `INSTALLER_MANAGE` | no | no | no | platform |
| `ISSUE_MANAGE` (issue triage status) | no | no | no | platform |
| `GLOBAL_SETTINGS_WRITE` | no | no | no | platform |

the six platform capabilities back the internal pages, and no site role holds them. a superadmin holds every capability on every site.

a capability is the floor, not the whole check. watching swoop also needs the site's `membersMayWatch` setting for a member with no swoop mode of their own, and taking control also needs a fresh second factor; see [watching versus control](/docs/dashboard/swoop#watching-versus-control). a swoop mode on a person's member row overrides their role for `MACHINE_REMOTE_VIEW` and `MACHINE_REMOTE_CONTROL` only, and never on the owner's row; see [swoop mode](/docs/dashboard/admin/member-management#swoop-mode).

hoot follows the same line. anyone who can read a site can chat with hoot about it, but a member's hoot gets read-only tools; an owner's or admin's hoot can also run commands, change configuration and deploy. LLM keys are per user, managed by each person in their own [account settings](/docs/dashboard/account-settings#hoot); there is no shared key for an admin to manage.
