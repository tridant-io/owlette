**location**: admin panel → agent tokens (`/admin/tokens`)

<Callout type="info" title={"permissions"}>

the page opens for anyone who is an owner or admin on at least one site. listing and revoking both need `AGENT_TOKEN_REVOKE` on the site, so a token you cannot list is a token you cannot revoke. issuing one, by authorizing a pairing phrase or generating an installer registration code, needs `MACHINE_ENROLL`, which the same roles hold.

</Callout>

## the token list

pick a site and the page loads its **live** tokens from `GET /api/sites/{siteId}/agent-tokens`, newest first. a live token is one an agent can still use: not rotated away from, not expired. the response also carries `prunableCount`, the dead records that are hidden.

the toolbar above the table:

- **search machine id or agent uid** filters the rows
- a version filter, **all versions** or one agent version (not on a phone)
- **duplicates**, with the number of machine IDs that have more than one live token, shows only those rows
- **prune dead (N)** appears when there are dead records; see [pruning](#pruning-dead-records)
- the count reads `N live`, or `N of M live` while a filter is on

the header holds a refresh button and, when the site has tokens, **revoke all**.

| column | what it shows |
|---|---|
| **machine ID** | the ID the agent paired with, normally its hostname. a `duplicate` badge marks an ID with more than one live token |
| **version** | the agent version recorded when it paired, or `N/A`. rotation carries it forward unchanged, so it does not follow later agent updates |
| **status** | `Never expires` for a token with no expiry, which is nearly all of them; otherwise `Expires in Nd`, `Expires <date>` or `Expired` |
| **created** | when this token record was created. an agent that rotates gets a new record at every refresh, so for a running agent this is usually within the last hour |
| **last used** | when the agent last refreshed with this token. for a rotating agent it is the same moment as **created** |
| **actions** | **revoke** |

**duplicates** come from repeated re-pairs, or from separate machines cloned with the same hostname. compare **last used** before revoking one: revoking disconnects whichever agent holds that token.

## rotation

every refresh from agent 2.12.0 or later, which identifies itself with an `X-Owlette-Agent-Version` header, returns a **new** refresh token:

- a new record is written for it, carrying the old record's site, machine ID, version, creator and agent identity, plus `predecessorHash` pointing back at the old one
- the old record gets `supersededAt`, `supersededBy` and `retiresAt`: it keeps working for 5 more minutes, so an agent that lost the response can retry
- the record before that is deleted once it is dead, so a machine normally holds about two records

an older agent, or a request without the header, keeps its token: the refresh only updates `lastUsed`.

to give a machine a new token outside rotation, revoke it and pair the machine again.

---

## pruning dead records

a record is **dead** once it is past its 5-minute grace after rotation, or expired. **prune dead (N)** asks **prune dead tokens?**, then **prune N dead tokens** sends `{ "prune": true }` to the revoke route, which deletes only dead records. live tokens, and rotated ones still inside their grace, are never touched, so no connected agent is affected.

---

## revoking tokens

every revoke is `POST /api/sites/{siteId}/agent-tokens/revoke` with exactly one of `tokenId`, `machineId`, `all` or `prune`. each deletes `agent_refresh_tokens` records for the selected site only.

| what | how | body |
|---|---|---|
| one token | **revoke** on its row, then **revoke token** | `{ "tokenId": "…" }`, checked to belong to the site |
| every token on the site | **revoke all**, then **revoke all N tokens** | `{ "all": true }`, which also deletes dead records. every agent on the site has to be paired again |
| a machine's current token | the machine's menu → **revoke token** → **revoke current token** | `{ "machineId": "…", "latestOnly": true }`: only the most recently used live token for that ID |
| every token for a machine ID | the machine's menu → **revoke token** → **revoke all for hostname** | `{ "machineId": "…" }`, which also disconnects any other machine sharing that hostname |

the machine menu is described in [revoke token](/docs/dashboard/machine-monitoring#revoke-token). `latestOnly` is accepted only with `machineId`.

## effect on agents

revoking deletes the record at once. a running agent keeps its cached one-hour access token until it expires; at its next refresh the server answers `401`, and the agent wipes its token store. it then shows as disconnected and stays that way until it is paired again with a new phrase or registration code. a `403`, which the server returns when the machine ID does not match the token, wipes the store the same way.

the refresh endpoint allows 120 requests per hour per IP address, shared by every machine behind one NAT. a refused (`429`) refresh does not wipe anything; the agent retries.

## lifecycle

```text
1. issuing a token starts with a short-lived code, which needs MACHINE_ENROLL:
   - an installer registration code expires after 24 hours
   - a pairing phrase expires after 10 minutes
2. once the code is authorized, the server creates:
   - a Firebase ID token for immediate use
   - a random refresh token
   - a record in agent_refresh_tokens keyed by the token's SHA-256 hash
3. the agent stores the refresh token in its encrypted token file
4. it caches the one-hour ID token and refreshes 5 minutes before it expires
5. each refresh returns a new ID token, and on agent 2.12.0 and later a new refresh token
```

the raw token is never stored server-side. during pairing it sits only on the short-lived pairing document until the agent's single poll picks it up and the document is deleted.

### the token file

| platform | path |
|---|---|
| Windows | `C:\ProgramData\Owlette\.tokens.enc` |
| macOS | `/Library/Application Support/Owlette/.tokens.enc` |
| Linux | `/var/lib/owlette/.tokens.enc` |

it holds the refresh token, the cached access token and its expiry, and the site ID, encrypted with a key derived from the machine itself: the `MachineGuid` on Windows, the hardware UUID on macOS, `/etc/machine-id` on Linux. the hostname is no longer part of the key, so renaming the machine does not lock the agent out. a store written under the older key, which mixed in the hostname, is rewritten under the new one on first read, and the original is kept beside it as `.tokens.enc.v1`. see [where things live](/docs/reference/platform-support#where-things-live).

## token records

records live in the `agent_refresh_tokens` collection, server-side only. the document ID is the SHA-256 of the refresh token.

| field | description |
|---|---|
| `siteId` | the site the token authorizes |
| `machineId` | the machine ID. a refresh from a different machine ID is refused with `403` |
| `version` | the agent version from pairing |
| `createdBy` | the user who authorized the pairing or generated the registration code |
| `createdAt` | when this record was created |
| `lastUsed` | when it was last used to refresh |
| `agentUid` | the agent's Firebase Auth identity |
| `expiresAt` | optional. absent means the token never expires |
| `supersededAt`, `supersededBy`, `retiresAt` | set when a rotation replaces the token |
| `predecessorHash` | on a rotated token, the record it replaced |

---

## when to revoke

- **decommissioning a machine**: revoke its tokens before removing or repurposing it
- **a suspected compromise**: revoke at once with **revoke all for hostname**, which also deletes the rotated record that stays usable for 5 minutes after each refresh
- **duplicates**: after reinstalling or re-pairing, revoke the stale token, checking **last used** first
- **a fresh credential**: revoke, then pair the machine again
