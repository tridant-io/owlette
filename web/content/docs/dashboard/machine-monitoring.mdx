## machine status

### online and offline

the agent sends a **heartbeat** to Firestore on an adaptive interval: every 5 seconds while the owlette app's window is open on the machine, every 30 seconds while a managed process is running or launching, and every 120 seconds when idle.

the status indicator is binary:

| status | condition | indicator |
|--------|-----------|-----------|
| **online** | the agent reports the machine online | green dot (hover for *online*) |
| **offline** | the agent reports offline, or the dashboard's own timeout marks an old heartbeat offline | red **offline** pill |

while a restart or shutdown is counting down, the indicator becomes the [countdown](#reboot-countdown--cancel) instead.

### last seen

beside it, the last-heartbeat time follows its own rule: a heartbeat newer than 5 minutes shows as a clock time in your [display timezone](/docs/dashboard/account-settings#preferences); an older one shows its age, such as `14m ago`, in red. the tooltip always carries the full date, time and timezone.

## system metrics

the agent reports metrics with each heartbeat:

![machine detail view](/docs-screens/machine-detail.png)

| metric area | values shown |
|-------------|--------------|
| **CPU** | per-CPU usage, model, and temperature when reported |
| **memory** | RAM usage percentage plus used and total GB |
| **disk** | per-volume usage, used/total GB, and read/write throughput when reported |
| **GPU** | per-GPU usage, VRAM, and temperature when reported |
| **network** | per-NIC transmit/receive throughput and utilization, plus gateway latency and packet loss |
| **displays** | live monitor topology, monitor count, resolution after rotation, primary display, mosaic, drift and auto-restore indicators. see [displays](/docs/dashboard/displays) |
| **local time** | the machine's clock and IANA timezone, when machines in more than one timezone are visible |

not every platform reports every value. disk read/write throughput and CPU temperature are Windows only; a Mac reports its Apple GPU's load and memory but no temperatures; Windows and Linux report NVIDIA GPUs. the [platform support](/docs/reference/platform-support#metrics) page has the full list. a value a machine does not report is simply absent from its rows.

### color coding

usage values share five bands, used by the accent bars and hover rings:

| color | range | meaning |
|-------|-------|---------|
| emerald | 0-29% | low |
| violet | 30-49% | medium-low |
| sky | 50-69% | medium |
| amber | 70-84% | high |
| red | 85-100% | critical |

temperatures use hardware thresholds instead: normal below 70 °C, warning from 70 °C, critical from 85 °C. they show in Celsius or Fahrenheit, as set in your [preferences](/docs/dashboard/account-settings#preferences).

### picking which device a row shows

a machine with more than one CPU, disk, GPU or network interface gets a small dropdown on that metric row; with one device there is no dropdown.

**auto (most active)** is the default: the row follows whichever device the agent reports as primary. pick a specific device and the row pins to it.

the choice is yours alone. it is remembered per machine in card view, and once for the whole table in list view (in the column header). if a pinned device disappears from a machine — a disk unmounted, a NIC removed — the row falls back to the primary device rather than going blank.

## view modes

### card view

the default view shows each machine as a card:

- a header with the display button, the machine name, the OS line (or the local clock, for an agent that reports no OS), the status indicator, the last heartbeat and the machine menu (**⋮**)
- a **metrics** section: collapsed, a one-line summary of CPU, memory, disk, GPU and network; expanded, a row per metric with a sparkline of recent values
- a **displays** section with the topology summary and the drift and auto-restore indicators
- a **processes** section listing each configured process with its status badge and controls

each section collapses on its own. click a metric row to open its history in the [detail panel](#historical-metrics).

### list view

a compact table, one row per machine:

- the display button and hostname, with the OS line under it, shortened to fit the column (`Win 11 Pro`, `Ubuntu 24`)
- status
- CPU, RAM, disk, GPU and network
- last heartbeat
- the machine menu

on narrower screens the metric columns drop out, network first. expand a row to see its processes. useful when watching many machines.

## historical metrics

click a metric to open the detail panel with its history.

### time ranges

**hour**, **day**, **week**, **month**, **year** and **all**.

### charts

the panel draws interactive line charts for:

- CPU usage and temperature
- memory usage
- per-disk storage usage
- per-volume disk read/write activity
- GPU usage, VRAM and temperature
- per-NIC transmit/receive utilization or throughput

hover a point for its exact value and time. the display button opens the [displays](/docs/dashboard/displays) panel in the same place.

## process status

each machine lists its configured processes with a status badge:

| badge | state | meaning |
|-------|-------|---------|
| green | `running` | the process is alive and responding |
| amber | `launching` | a launch is in progress |
| amber | `queued` | a launch is queued or waiting out its launch delay |
| amber | `restarting` | an operator restart is in flight |
| amber | `stalled` | the process exists but its window is not responding. Windows only — macOS and Linux do not detect hangs |
| red | `failed` | a launch was attempted and failed (`LAUNCH_FAILED`) |
| red | `killed` | the process was terminated |
| red | `stopped` | the launch mode is not `off` but nothing is running: crashed, outside its schedule, not yet launched, or the path is missing |
| grey | `inactive` | the launch mode is `off`; owlette is not supervising it |

when a machine is offline the dashboard cannot know the current state, so every badge reads `unknown` instead of its last status.

click a process to open the [process dialog](/docs/dashboard/process-management) to manage and configure it.

## restart pending

when a managed process uses up its relaunch attempts, the agent stops trying and asks for a restart instead of deciding on its own. it raises a **restart pending** flag on the machine, and the card shows an amber banner naming the process — `restart pending: ndi_recording crashed 3 times`.

what happens next depends on the platform:

- **Windows**: the machine also opens a restart prompt on its own screen, as a fallback for a machine nobody is watching from the dashboard. **that prompt counts down two minutes and restarts the machine if nobody touches it**, so the banner is usually a record of a restart about to happen anyway, not a decision waiting on you. see [relaunch limits](/docs/agent/process-monitoring#relaunch-limits).
- **macOS and Linux**: there is no prompt, and the machine does not restart on its own. the process stays down and the banner waits for you.

site admins get two actions on the banner:

| action | what it does |
|--------|--------------|
| **approve** | sends the restart command, exactly as **restart machine** would. offered only while the machine is online, since the command would be refused otherwise. |
| **dismiss** | clears the flag and resets that process's relaunch counter, so it gets a fresh set of attempts. |

**the banner outlives an unreachable machine.** the flag is written by the agent and only the agent's next service start clears it locally, so a machine that crashed and never came back keeps showing it. the banner renders grey instead of amber then, and adds *machine offline, cannot restart* — a record of something that happened, not a live alarm.

dismiss still works on an offline machine: it clears cloud state through the API rather than asking the agent, which is exactly the case that most needs clearing. dismissing requires `MACHINE_EXEC_COMMAND`, the same bar as sending the restart itself.

## reboot countdown & cancel

when a restart or shutdown is scheduled — from the dashboard, from hoot, from a [restart schedule](/docs/dashboard/restart-schedules), or by the tier-3 `reboot_machine` / `shutdown_machine` tools — the status indicator becomes a red pulsing pill with a restart or power icon and an **MM:SS** countdown, so there is a visible window in which to stop it.

- the countdown is **one minute** on every platform, counted to the time the agent reported. (the confirm dialogs still say 30 seconds.)
- for a site admin, the pill is the cancel button: hovering it swaps the countdown for **cancel**, and on a touch screen an × stands in for the icon. the machine menu also offers **cancel restart** or **cancel shutdown** while it runs. either sends `cancel_reboot`.
- cancel closes for the final **5 seconds**, when the shutdown may already be committing. from then on, and for anyone who is not a site admin, the pill shows the countdown without an action.
- once the countdown runs out, a restarting machine keeps its restart pill until it is back online; a machine that shut down shows offline.

## the machine menu

the **⋮** button on a card or row opens the machine menu. when someone is in a [swoop](/docs/dashboard/swoop) session on the machine, the button carries the viewer count. what the menu offers depends on whether the machine is online and whether you are a site admin:

| action | needs | what it does |
|--------|-------|--------------|
| **restart machine** | online, site admin | restarts the machine after a one-minute countdown. see [reboot countdown & cancel](#reboot-countdown--cancel) |
| **schedule restarts** | site admin | opens the [restart schedule](/docs/dashboard/restart-schedules) editor. on an online machine it is the small sliders icon beside **restart machine**; on an offline one it is a menu item of its own |
| **shutdown machine** | online, site admin | powers the machine off after the same countdown |
| **cancel restart** / **cancel shutdown** | online, site admin, countdown running | replaces the entries above while a countdown runs |
| **swoop** | online, the machine can host swoop | opens the live remote-desktop session in a new browser tab, with the viewer count when anyone is in it; the monitor icon at the row's end opens it in [owlette swoop](/docs/dashboard/swoop#owlette-swoop), the desktop viewer app, instead. greyed out with *you're on this machine*, and without the icon, when that is the machine you are using. see [swoop](/docs/dashboard/swoop), which covers the site policy that decides whether a session is allowed |
| **live view** | online, the machine cannot host swoop | the older screenshot slideshow. exactly one of swoop and live view is offered, so the menu never loses its screen entry |
| **screenshot** | online | captures the machine's screen and opens the screenshot history |
| **view displays** | any signed-in user | opens the [displays](/docs/dashboard/displays) panel |
| **mute alerts** / **unmute alerts** | any signed-in user | silences every alert email for this machine, **for you only**. listed under [account settings → alerts](/docs/dashboard/account-settings#muted-machines) |
| **revoke token** | site admin | invalidates the agent's refresh token for this hostname and cuts the agent off. see below |
| **remove machine** | site admin | removes the machine from the site. see below |

which machines can host swoop, take screenshots or show live view depends on the platform. a Mac needs the owlette app running with Screen Recording granted. a Linux machine cannot host swoop, and although its menu still shows **live view** and **screenshot**, both fail on Linux for now. see [platform support](/docs/reference/platform-support#screens).

an offline machine keeps **schedule restarts**, **view displays**, **mute alerts**, **revoke token** and **remove machine** — everything else needs an agent on the other end.

### revoke token

revoking invalidates the agent's stored refresh token and tells the agent to leave the site: within a minute it confirms with the server that its token is gone, drops its site and credentials, ends any swoop session and the hoot process, goes offline on the dashboard, and the owlette app on the machine offers **join site**. the machine stays listed, offline, until it is removed or paired again with a new phrase. two scopes are offered: **revoke current token**, the most recently used token for the hostname, which leaves any other machine sharing that hostname running, or **revoke all for hostname**, every token for it — which cuts off every machine sharing that hostname.

an agent that is offline when you revoke leaves the site the moment it comes back and the server refuses its refresh. agents on 4.1.7 or earlier do not act on the revoke until that refresh either, so they stay online on the dashboard for up to an hour.

this is the per-machine version of the [token management](/docs/dashboard/admin/token-management) page, which does the same across a whole site.

### remove machine

removal is permanent: it deletes the machine's data, process configuration and command history, and revokes the agent's token.

- **a machine with deployments in progress cannot be removed.** the dialog blocks confirmation until they finish.
- **an online machine can be removed.** an agent on 4.1.8 or later notices within seconds, stops syncing, drops its credentials and offers **join site** in the app. an older agent keeps writing on its access token, so the machine comes back and stays until that token expires, within the hour; remove it again then, or update the agent first.
- getting it back means pairing again from the app on that machine, or running the installer again, with a fresh three-word phrase.

## machine information

each machine reports these about itself:

| field | where you see it | what it is |
|-------|------------------|------------|
| **machine name** | the card and row title | the machine's ID: its hostname when it was first paired. it is kept from then on, so renaming the computer later does not create a second machine |
| **OS** (`osVersion`) | under the name on the card and the row | the operating system as people name it: `Windows 11 Pro 24H2`, `macOS 15.6`, `Ubuntu 24.04.5 LTS`. the list view shortens it to fit; the full string is in its tooltip |
| **platform** (`osFamily`) | not shown on its own | `windows`, `macos` or `linux`. it decides what the dashboard offers for the machine — the process dialog's path label and Windows-only fields, the installer an update sends, swoop's keyboard mapping. an agent that reports none is treated as Windows |
| **architecture** (`arch`) | not shown on its own | `x64` or `arm64`. with the platform, it picks the installer file a fleet update sends |
| **CPU model** | the CPU row | the processor name |
| **agent version** | the update dialog | the owlette version installed |

agents before 4.0.0 report no OS, platform or architecture, so their cards show the local clock under the name instead. the same fields are in `GET /api/sites/{siteId}/machines` (`osFamily`, `arch`, `osVersion`, `null` for an older agent) and in [`owlette machine`](/docs/cli/reference/machine).
