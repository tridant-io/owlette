**last updated**: 2026-10-05

a webhook is an HTTP `POST` that owlette sends to a URL you control when a subscribed event happens on your site. the body is a JSON envelope describing the event, and the `Roost-Signature` header lets you prove owlette sent it. answer with any `2xx` status to acknowledge it.

each subscription belongs to one site and lists the event types it wants. its signing secret is shown once, at creation, and can be rotated with a 24-hour grace window.

what is live today:

- `version.published` and `version.rolled_back` are dispatched to every matching subscription.
- `machine.offline` is delivered by an older alerting sender, with a different body, signature, and retry behavior — see [machine.offline](#machineoffline).
- every other event in the [catalog](#event-catalog) is accepted on subscriptions and by the probe, but nothing emits it yet.
- `POST /api/webhooks/probe` sends one signed test delivery on demand.
- `owlette listen` holds a liveness stream only; it does not carry webhook events yet.

the examples use `$OWLETTE_API_URL` (`https://owlette.app`) and `$OWLETTE_API_KEY`, set up as in the [quickstart](/docs/api/quickstart).

## envelope

a dispatched delivery's body is this envelope, serialized as compact JSON with object keys sorted at every level (the examples here are indented for reading):

```json
{
  "data": {
    "createdBy": "uid_123",
    "description": "fixed broken lobby video",
    "roostId": "rst_lobby",
    "siteId": "kiosk-fleet-01",
    "totalFiles": 342,
    "totalSize": 2147483648,
    "versionId": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
    "versionNumber": 7
  },
  "event": "version.published",
  "occurredAt": "2026-04-22T15:30:00.000Z",
  "siteId": "kiosk-fleet-01"
}
```

- `event` is the event type, also sent as the `Roost-Event` header.
- `siteId` is the site the event belongs to.
- `occurredAt` is when the event happened, as an ISO 8601 UTC timestamp. it does not change on retries.
- `data` is event-specific; see the catalog below.
- there is no event ID in the body. the `Roost-Delivery` header identifies the delivery and stays the same across retries.

a [probe](#probe) delivery adds a top-level `"id": "evt_probe_<16 hex characters>"`; dispatched deliveries never carry one.

## event catalog

subscriptions and the probe accept exactly these event names. anything else is `400 validation_failed`.

### version.published

a publish created a new version and moved the roost's current pointer to it. it is not sent when a publish matches the current version or an older one.

| field | type | meaning |
|---|---|---|
| `roostId` | string | the roost |
| `siteId` | string | the site |
| `versionId` | string | the new version's 64-character ID |
| `versionNumber` | integer | its number in the roost's history |
| `description` | string or `null` | the publish description |
| `totalFiles` | integer | files in the version |
| `totalSize` | integer | total bytes in the version |
| `createdBy` | string | user ID of the publisher (the key's owner for an API-key call) |

### version.rolled_back

a [rollback](/docs/api/versions#rollback) moved the roost's current pointer to an earlier version.

```json
{
  "data": {
    "fromVersion": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
    "roostId": "rst_lobby",
    "siteId": "kiosk-fleet-01",
    "toVersion": "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae",
    "triggeredBy": "uid_123"
  },
  "event": "version.rolled_back",
  "occurredAt": "2026-04-22T15:35:00.000Z",
  "siteId": "kiosk-fleet-01"
}
```

`fromVersion` is the version that was current before the rollback, or `null` if there was none. `toVersion` is the version now current. `triggeredBy` is the user ID of the caller.

### machine.offline

a machine stopped reporting. it is sent when the health check, which runs every 5 minutes, finds a machine whose heartbeat has gone stale (at most once an hour per machine), and when an agent reports a connection failure through its alert channel.

this event comes from owlette's older alerting sender, not the roost dispatcher, so it does not follow the rest of this page:

```json
{
  "event": "machine.offline",
  "timestamp": "2026-10-05T18:30:00.000Z",
  "site": { "id": "kiosk-fleet-01", "name": "lobby kiosks" },
  "data": {
    "machine": { "id": "lobby-01", "name": "lobby-01", "lastSeen": "2026-10-05T18:21:12.000Z" }
  }
}
```

- the body is the shape above, not the roost [envelope](#envelope); `lastSeen` is present only on health-check deliveries.
- headers are `Content-Type: application/json`, `User-Agent: owlette-Webhooks/1.0`, `X-owlette-Event: machine.offline`, and `X-owlette-Signature: sha256=<hex>` — the lowercase hex HMAC-SHA256 of the raw body, keyed with the subscription's signing secret. there is no timestamp in the signature, so no replay window, and no `Roost-*` headers.
- a URL on `hooks.slack.com` or `discord.com/api/webhooks` receives a chat-formatted message instead, unsigned.
- each event is one attempt with a 5-second timeout: no retries, no entry in [delivery history](#delivery-history).
- after 10 consecutive failed attempts the sender disables the subscription, which also stops its version events. the API does not show that state and `PATCH` cannot clear it; create the subscription again to resume.

### not dispatched yet

you can subscribe to these and probe them, but nothing sends them yet. the `data` fields listed are what the probe sends; check this page again when an event starts firing.

| event | intended meaning | probe `data` fields |
|---|---|---|
| `deployment.started` | a rollout began | `roostId`, `rolloutId`, `siteId`, `stage` (`"started"`) |
| `deployment.completed` | a rollout finished | `roostId`, `rolloutId`, `siteId`, `stage` (`"complete"`), `succeeded`, `failed` |
| `deployment.failed` | a rollout aborted | `roostId`, `rolloutId`, `siteId`, `stage` (`"aborted"`), `abortReason`, `succeeded`, `failed` |
| `machine.online` | a machine resumed reporting | `siteId`, `machineId`, `lastHeartbeat` |
| `chunk.garbage_collected` | garbage collection deleted a chunk | `siteId`, `hash`, `sizeBytes` |
| `chunk.verify_failed` | a stored chunk did not match its hash | `siteId`, `hash`, `expectedDigest`, `actualDigest` |
| `quota.warning` | storage use crossed a warning threshold | `siteId`, `tier`, `usedBytes`, `limitBytes`, `threshold` |
| `quota.exceeded` | storage use reached the limit | `siteId`, `tier`, `usedBytes`, `limitBytes` |
| `api_key.used` | an API key was used | `siteId`, `keyId`, `keyPrefix`, `ip`, `userAgent`, `firstUseFromIp` |
| `api_key.expired` | an API key expired | `siteId`, `keyId`, `keyPrefix`, `name`, `expiresAt` |

hashes in chunk events are bare 64-character hex, as everywhere else in roost.

## signature format

every delivery carries a `Roost-Signature` header:

```
Roost-Signature: t=1745334602,v1=5f3e8a7c2b9d1e4f6a8c0e2d4f6a8c0e2d4f6a8c0e2d4f6a8c0e2d4f6a8c0e2d
```

- **`t`** is the unix time, in seconds, when the attempt was signed. every attempt is signed afresh.
- **`v1`** is the lowercase hex HMAC-SHA256 of the string `<t>.<raw body>`, keyed with the subscription's signing secret. use the whole secret, including its `whsec_` prefix, and the exact request bytes: no whitespace changes, no re-serialization.

verify in three steps:

1. recompute `v1` from your secret, the header's `t` and the raw body, and compare it with a **constant-time** comparison (`hmac.compare_digest` in Python, `crypto.timingSafeEqual` in Node).
2. reject the delivery if `t` is more than 300 seconds from your clock. this is what stops a captured delivery from being replayed later.
3. deduplicate on `Roost-Delivery`: if you already processed that ID, answer `200` without processing it again.

for 24 hours after you [rotate the secret](#rotate-the-signing-secret), accept a signature that matches either the new or the old secret. new deliveries are signed with the new secret at once, but retries of deliveries queued before the rotation still use the old one.

`v1=` leaves room for a future scheme. accept a delivery if any `v1=` value matches, and ignore schemes you do not know.

## signature verification

the Node and Python SDKs ship a `verifySignature` / `verify_signature` helper with the replay check built in and a timing-safe comparison. the bash version needs only `openssl`.

the SDKs are not on npm or PyPI yet; until they are, install them from the repository (see [distribution](/docs/api/distribution)).

### Node

```ts
// npm install @owlette/sdk@rc express   (run with: npx tsx server.ts)
import express from 'express';
import { verifySignature } from '@owlette/sdk';

const app = express();
// during a rotation, set ROOST_WEBHOOK_PREVIOUS_SECRET to the old secret for 24 hours.
const secrets = [
  process.env.ROOST_WEBHOOK_SECRET,
  process.env.ROOST_WEBHOOK_PREVIOUS_SECRET,
].filter((s): s is string => Boolean(s));
const processed = new Set<string>(); // use durable storage in production

// verify the raw bytes: register express.raw on this route, not a json parser.
app.post(
  '/webhooks/roost',
  express.raw({ type: 'application/json' }),
  (req, res) => {
    const header = req.get('roost-signature');
    const verdicts = secrets.map((secret) => verifySignature(header, req.body as Buffer, secret));
    const verdict = verdicts.find((v) => v.ok) ?? verdicts[0];
    if (!verdict?.ok) {
      // reason: missing_header | missing_timestamp | missing_v1 | timestamp_out_of_tolerance | bad_signature
      return res.status(401).json({ error: verdict?.reason ?? 'no_secret_configured' });
    }

    const deliveryId = req.get('roost-delivery') ?? '';
    if (processed.has(deliveryId)) return res.status(200).end();
    processed.add(deliveryId);

    const event = JSON.parse((req.body as Buffer).toString('utf-8'));
    console.log(event.event, event.data);
    res.status(200).end();
  },
);

app.listen(8080);
```

### Python

```python
# pip install --pre owlette-sdk fastapi uvicorn   (run with: uvicorn server:app --port 8080)
import json
import os

from fastapi import FastAPI, HTTPException, Request
from roost import verify_signature

app = FastAPI()
# during a rotation, set ROOST_WEBHOOK_PREVIOUS_SECRET to the old secret for 24 hours.
SECRETS = [s for s in (os.environ.get("ROOST_WEBHOOK_SECRET"), os.environ.get("ROOST_WEBHOOK_PREVIOUS_SECRET")) if s]
processed: set[str] = set()  # use durable storage in production


@app.post("/webhooks/roost")
async def webhook(request: Request):
    raw = await request.body()  # raw bytes; never verify request.json()
    header = request.headers.get("roost-signature")
    verdicts = [verify_signature(header, raw, secret) for secret in SECRETS]
    verdict = next((v for v in verdicts if v.ok), verdicts[0] if verdicts else None)
    if verdict is None or not verdict.ok:
        # reason: missing_header | missing_timestamp | missing_v1 | timestamp_out_of_tolerance | bad_signature
        raise HTTPException(status_code=401, detail=verdict.reason if verdict else "no_secret_configured")

    delivery_id = request.headers.get("roost-delivery", "")
    if delivery_id in processed:
        return {"ok": True, "deduped": True}
    processed.add(delivery_id)

    event = json.loads(raw)
    print(event["event"], event["data"])
    return {"ok": True}
```

### bash

no SDK, only `openssl`. useful when the receiver is a shell pipeline or a cgi script.

```bash
#!/usr/bin/env bash
# verify-roost-webhook.sh: stdin is the raw request body; headers arrive cgi-style in
# HTTP_ROOST_SIGNATURE and HTTP_ROOST_DELIVERY.

set -euo pipefail

: "${ROOST_WEBHOOK_SECRET:?set to the signing secret returned by POST /api/webhooks}"
TOLERANCE_SECONDS="${TOLERANCE_SECONDS:-300}"

body="$(cat)"                                         # raw bytes from stdin
sig_header="${HTTP_ROOST_SIGNATURE:-}"
[[ -n "$sig_header" ]] || { echo "missing Roost-Signature" >&2; exit 1; }

# parse "t=<unix>,v1=<hex>"; ignore other schemes
t=""; v1=""
while IFS= read -r part; do
  case "$part" in
    t=*)  t="${part#t=}" ;;
    v1=*) v1="${part#v1=}" ;;
  esac
done < <(tr ',' '\n' <<<"$sig_header")
[[ -n "$t" && -n "$v1" ]] || { echo "malformed signature header" >&2; exit 1; }

# replay window
now="$(date -u +%s)"
delta=$(( now > t ? now - t : t - now ))
(( delta <= TOLERANCE_SECONDS )) || { echo "timestamp_out_of_tolerance ($delta s)" >&2; exit 1; }

# recompute v1 = hmac_sha256(secret, "<t>.<body>")
expected="$(printf '%s.%s' "$t" "$body" \
  | openssl dgst -sha256 -hmac "$ROOST_WEBHOOK_SECRET" -hex \
  | awk '{print $NF}')"

[[ "${#expected}" -eq "${#v1}" ]] || { echo "bad_signature" >&2; exit 1; }
if ! cmp -s <(printf '%s' "$expected") <(printf '%s' "$v1"); then
  echo "bad_signature" >&2; exit 1
fi

echo "ok  delivery=${HTTP_ROOST_DELIVERY:-<none>}"
```

> **timing safety in bash**: `cmp` is not a constant-time comparison. the computed value is the only secret-derived side and the received `v1` has a fixed length, so the leak is not practical to exploit, but use the Node or Python version when you need a strict constant-time check.

## delivery headers

dispatched deliveries and manual retries send:

- **`Content-Type: application/json`**
- **`Roost-Event: <event>`**, the same as the body's `event`; route on it without parsing the body.
- **`Roost-Delivery: <id>`**, 32 hex characters derived from the event and its body. it stays the same across automatic retries and [manual retries](#manual-retry); use it as your idempotency key.
- **`Roost-Signature: t=<unix>,v1=<hex>`**, see [signature format](#signature-format).

the dispatcher sets no `User-Agent` of its own.

probe deliveries send the same four headers plus `User-Agent: roost-probe/1.0`; their `Roost-Delivery` is a random UUID per probe.

---

## delivery guarantees

- **queueing.** when an event happens, one delivery is queued for each matching subscription that is neither paused nor deleted. a dispatcher runs once a minute and sends up to 200 due deliveries per run.
- **at-least-once.** a delivery can arrive more than once, for example when your receiver processes it but times out before answering. deduplicate on `Roost-Delivery`.
- **response handling.** your receiver has 10 seconds to answer; a slower answer counts as a network error. redirects are followed. `2xx` is success. network errors, timeouts, `408`, `425`, `429` and `5xx` are retried. any other status fails the delivery at once, with `lastError: "http_<status>"`.
- **retries.** after a failed attempt `n`, the next attempt waits 5 seconds × 3<sup>n−1</sup>, capped at 1 hour, with ±20% jitter: about 5 s, 15 s, 45 s, 2 m 15 s, 6 m 45 s, 20 m 15 s, then 1 h. a wait shorter than a minute lands on the next dispatcher run. each attempt is signed with a fresh `t`; `Roost-Delivery` does not change.
- **give-up.** a delivery gets 10 attempts. after the 10th failure it is marked `failed` with `lastError: "retry_exhausted: <reason>"`. the dispatcher never pauses a subscription; only the [machine.offline](#machineoffline) sender disables one.
- **pause and delete.** pausing or deleting a subscription stops new deliveries from being queued for it. deliveries already queued are still sent.
- **states.** a delivery is `pending` until it succeeds (`succeeded`) or gives up (`failed`).
- **ordering.** deliveries are not ordered. use `occurredAt` when order matters.
- **subscription counters.** `lastDeliveryAt`, `lastDeliveryStatus` and `failureCount` on a subscription are not updated by the dispatcher yet; read [delivery history](#delivery-history) instead.

## subscription management

every subscription operation is a public API route, and every route takes the site as a `siteId` query parameter. the full schema is in the [API reference](/docs/api).

### authentication and scopes

send your API key as `Authorization: Bearer $OWLETTE_API_KEY` (`x-api-key` also works).

| route | API-key scope | role |
|---|---|---|
| `GET /api/webhooks`, `GET /api/webhooks/{webhookId}`, `GET .../deliveries`, `GET .../deliveries/{deliveryId}` | `site=<siteId>:read` | member |
| `POST /api/webhooks`, `PATCH` or `DELETE /api/webhooks/{webhookId}`, `POST .../rotate-secret` | `site=<siteId>:write` | site admin or owner |
| `POST .../deliveries/{deliveryId}/retry`, `POST /api/webhooks/probe` | `site=<siteId>:write` | member |

a key without the scope gets `403 scope_insufficient`; a member without the role gets `403 forbidden` (`capability not granted`). the `admin` permission is not involved. every route also accepts the optional `Roost-Version: 2026-04-22` header.

`Idempotency-Key` is optional on create, update, rotate-secret and retry: the same key with the same body within 24 hours replays the first success with `Idempotent-Replayed: true`. delete and probe ignore it. see [idempotency](/docs/api/idempotency).

### create

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/webhooks?siteId=kiosk-fleet-01" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "url": "https://hooks.example.com/roost",
    "events": ["version.published", "version.rolled_back"],
    "description": "ci notifier"
  }'
```

response (`201 Created`):

```json
{
  "id": "wh_3f9c2a7e1b8d4c6a0e",
  "siteId": "kiosk-fleet-01",
  "url": "https://hooks.example.com/roost",
  "events": ["version.published", "version.rolled_back"],
  "paused": false,
  "createdAt": "2026-04-22T15:30:00.000Z",
  "signingSecret": "whsec_<64 hex characters>",
  "description": "ci notifier"
}
```

- **`url`** must use `https`, on no explicit port or on port 80, 443, 8080 or 8443, and be at most 2048 characters. its host must not be a private, loopback, link-local, carrier-grade NAT, multicast or reserved IP address, and must resolve in DNS to public addresses only. a wrong scheme, port or address is `400` with code `bad_scheme`, `bad_port` or `private_ip`; a URL that does not parse, is too long or does not resolve is `400 validation_failed`. the URL is stored normalized, so `https://hooks.example.com` comes back as `https://hooks.example.com/`.
- **`events`** must be a non-empty list of catalog names; duplicates are dropped.
- **`description`** is optional, trimmed, and cut to 500 characters.
- **`signingSecret`** appears only in this response (and in an idempotent replay of it). store it now; if you lose it, rotate.

### list and get

```bash
curl -fsS "$OWLETTE_API_URL/api/webhooks?siteId=kiosk-fleet-01&page_size=20" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```

the list answers `{ webhooks, next_page_token, nextPageToken }`, newest first, without deleted subscriptions. `page_size` defaults to 20 with a maximum of 100. `GET /api/webhooks/{webhookId}?siteId=...` returns one subscription, or `404 not_found` once it is deleted. each subscription has `id`, `url`, `events`, `description` (when set), `createdAt`, `updatedAt`, `paused`, `lastDeliveryAt`, `lastDeliveryStatus` and `failureCount`. the secret is never returned.

### update

`PATCH /api/webhooks/{webhookId}?siteId=...` takes any of `url`, `events`, `description` and `paused`, and at least one of them. `url` and `events` are checked as on create; `description` set to `null` or blank removes it; `paused` must be a boolean. the response is the updated subscription.

### delete

`DELETE /api/webhooks/{webhookId}?siteId=...` soft-deletes the subscription and pauses it. the response is `{ id, siteId, softDeleted: true, tombstoneExpiresAt }`, 30 days out; deleting again returns the same tombstone. after delete, the subscription and its delivery history answer `404 not_found`.

### rotate the signing secret

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/webhooks/wh_3f9c2a7e1b8d4c6a0e/rotate-secret?siteId=kiosk-fleet-01" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```

```json
{
  "id": "wh_3f9c2a7e1b8d4c6a0e",
  "siteId": "kiosk-fleet-01",
  "signingSecret": "whsec_<64 hex characters>",
  "previousSecretValidUntil": "2026-04-23T15:30:00.000Z",
  "gracePeriodHours": 24,
  "rotatedAt": "2026-04-22T15:30:00.000Z"
}
```

the new secret is returned once and signs every new delivery from now on. until `previousSecretValidUntil`, accept signatures from the old secret too (see [signature format](#signature-format)).

### delivery history

```bash
curl -fsS "$OWLETTE_API_URL/api/webhooks/wh_3f9c2a7e1b8d4c6a0e/deliveries?siteId=kiosk-fleet-01" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```

the list answers `{ deliveries, next_page_token, nextPageToken }` for the last 30 days, newest first; `page_size` defaults to 20 with a maximum of 100. each delivery has `id`, `event`, `state`, `attempt`, `lastStatus`, `lastError`, `createdAt`, `completedAt` and `nextAttemptAt` (set only while `pending`). a delivery `id` is `<Roost-Delivery>__<webhookId>`, with `__retry_<8 hex>` appended for a manual retry.

### manual retry

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/webhooks/wh_3f9c2a7e1b8d4c6a0e/deliveries/0c1f5e9a2b7d4e8f9a0b1c2d3e4f5a6b__wh_3f9c2a7e1b8d4c6a0e/retry?siteId=kiosk-fleet-01" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```

response (`202 Accepted`):

```json
{
  "id": "0c1f5e9a2b7d4e8f9a0b1c2d3e4f5a6b__wh_3f9c2a7e1b8d4c6a0e__retry_9b2e41c7",
  "webhookId": "wh_3f9c2a7e1b8d4c6a0e",
  "siteId": "kiosk-fleet-01",
  "retryOf": "0c1f5e9a2b7d4e8f9a0b1c2d3e4f5a6b__wh_3f9c2a7e1b8d4c6a0e",
  "state": "pending",
  "nextAttemptAt": "2026-04-22T16:00:00.000Z"
}
```

- a retry is a new delivery with the same body and the same `Roost-Delivery`, signed with the current secret and given a fresh budget of 10 attempts. it goes out on the next dispatcher run.
- it goes to the URL stored on the original delivery, even if you have since changed the subscription's URL.
- you can retry a delivery in any state.
- a subscription with no stored secret answers `500 internal_error`; rotate the secret, then retry.

### probe

`POST /api/webhooks/probe?siteId=...` sends one signed delivery to a URL without creating a subscription, so you can test a receiver before you subscribe it.

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/webhooks/probe?siteId=kiosk-fleet-01" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://hooks.example.com/roost",
    "event": "version.published",
    "signingSecret": "whsec_test_0000000000000000000000000000000000000000"
  }'
```

- `url` follows the same rules as create. `event` must be a catalog name.
- `payload` is optional: a JSON object to send as `data` instead of the canned example.
- `signingSecret` is optional: at least 32 characters. without it the server generates one and returns it.
- the probe waits up to 10 seconds for your receiver. it is not retried, not stored in delivery history, and every call sends again.

the response is `200` whatever your receiver answered:

```json
{
  "status": 200,
  "durationMs": 184,
  "deliveryId": "6f1d3c2a-9b8e-4f7a-a1d2-3c4b5a6f7e8d",
  "event": "version.published",
  "requestBody": "{\"data\":{...},\"event\":\"version.published\",\"id\":\"evt_probe_4b1e9c7a2f3d5e6a\",\"occurredAt\":\"2026-04-22T15:30:00.000Z\",\"siteId\":\"kiosk-fleet-01\"}",
  "signature": "t=1745334602,v1=5f3e8a7c2b9d1e4f6a8c0e2d4f6a8c0e2d4f6a8c0e2d4f6a8c0e2d4f6a8c0e2d",
  "signingSecret": "whsec_test_0000000000000000000000000000000000000000",
  "responseBody": "ok"
}
```

`status` is your receiver's HTTP status, or `null` when it could not be reached, in which case `networkError` explains why. `responseBody` holds the first 2048 characters of the answer, when there is one.

## local development

```bash
# 1. log in once per machine. the api key goes to the os keychain when available,
#    otherwise ~/.config/owlette/credentials.json; profiles live in ~/.config/owlette/config.toml
owlette auth login

# 2. start your receiver on :8080 with a throwaway test secret
export ROOST_WEBHOOK_SECRET=whsec_local_dev_0000000000000000000000000000000000
npx tsx server.ts &

# 3a. send one canned, signed event straight from your machine (no api call)
owlette trigger version.published --site kiosk-fleet-01 \
  --to http://localhost:8080/webhooks/roost \
  --signing-secret "$ROOST_WEBHOOK_SECRET"

# 3b. or have the server send the exact envelope a real delivery uses (needs a public https url)
owlette trigger version.published --site kiosk-fleet-01 \
  --to https://hooks.example.com/roost --via-api
```

- **`owlette trigger --to`** posts the event's `data` object on its own, without the envelope, signed with `--signing-secret` (unsigned without it). use it to exercise your signature check; use `--via-api` to test envelope parsing.
- **`owlette trigger --via-api`** calls [`POST /api/webhooks/probe`](#probe), so the URL must pass the probe's rules: a public `https` URL, never `localhost`.
- **`owlette listen --site <id> --forward-to <url>`** opens `GET /api/events/stream?siteId=<id>`, which needs `site=<id>:read`. the stream sends `connected` and then a `keepalive` every 15 seconds, and closes after 30 minutes, at which point `owlette listen` exits; run it again. it carries no webhook events yet, so nothing is forwarded today.

a session of `owlette listen` looks like this:

```
owlette: listening on https://owlette.app/api/events/stream
       site: kiosk-fleet-01
       forwarding to http://localhost:8080/webhooks/roost
       events: version.published, deployment.failed
       re-signing with supplied secret
owlette: stream connected
```

to debug a delivery that is not arriving, read [delivery history](#delivery-history) for its `state`, `lastStatus` and `lastError`, fix the receiver, then [retry](#manual-retry) it.

## errors

errors use `application/problem+json`; branch on `code`. see [errors](/docs/api/errors).

| code | HTTP | meaning |
|---|---:|---|
| `validation_failed` | 400 | missing or invalid `siteId`, `webhookId` or `deliveryId`; invalid JSON; a URL that does not parse, is too long or does not resolve; empty or unknown `events`; a wrong field type; an update with no fields; an unknown probe event, or a probe `payload` that is not an object or a `signingSecret` under 32 characters; invalid pagination. |
| `bad_scheme` / `bad_port` / `private_ip` | 400 | the URL is not `https`, uses a disallowed port, or points at a non-public address. |
| `unsupported_version` | 400 | the `Roost-Version` header names an unsupported date. |
| `idempotency_key_invalid` | 400 | the `Idempotency-Key` is longer than 255 characters. |
| `unauthorized` / `token_expired` | 401 | no valid credential, or an expired API key. |
| `forbidden` | 403 | your account is inactive, or create, update, delete or rotate-secret without the site admin or owner role. |
| `scope_insufficient` | 403 | the API key lacks the `site=<siteId>` scope the route needs. |
| `not_found` | 404 | the site, subscription or delivery does not exist, the subscription is deleted, or the delivery belongs to another subscription. |
| `idempotency_key_mismatch` | 422 | an `Idempotency-Key` was reused with a different body. |
| `internal_error` | 500 | unexpected server error, or a retry whose subscription has no stored secret; quote the `requestId`. |
