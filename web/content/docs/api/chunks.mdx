**last updated**: 2026-10-05

a chunk is an immutable block of bytes addressed by its SHA-256 hash. a [version](/docs/api/versions) lists its files, and each file lists the hashes of its chunks in order. you upload a chunk once per site; every later version that contains the same bytes reuses it.

related:
- [versions](/docs/api/versions) - the version body that embeds chunks as `files[].chunks[]` entries of `{ hash, size }`.
- [API reference](/docs/api) - the rendered route reference.
- [quickstart](/docs/api/quickstart) - a first API smoke test before you publish roost content.

the examples use `$OWLETTE_API_URL` (`https://owlette.app`) and `$OWLETTE_API_KEY`, set up as in the [quickstart](/docs/api/quickstart).

## chunk shape

- **fixed size**: the reference chunkers cut every file into **4 MiB (4,194,304 byte)** blocks; the last block of a file is **1 to 4,194,304 bytes**. the server does not check chunk sizes, so other sizes still upload and publish, but they will not dedup against content chunked the standard way.
- **algorithm**: SHA-256 only. content-defined chunking (FastCDC, Rabin) is not supported.
- **hash format**: lowercase hex, exactly 64 characters, matching `^[0-9a-f]{64}$`. every chunk endpoint takes and returns the bare digest; do not add a `sha256:` prefix in bodies, query strings or paths.
- **in a version**: the same bare digest goes in `version.files[].chunks[].hash`.
- **zero-byte files** have `size: 0` and `chunks: []`. nothing is stored for them.
- **ordering**: chunks in a file are listed in file-offset order. concatenating them in order reproduces the file exactly.

```
file bytes  --------------------------------------------------------------->
            |-- chunk[0] --|-- chunk[1] --|-- chunk[2] --|-- chunk[3] --|
            |  4,194,304   |  4,194,304   |  4,194,304   |   812,345    |
            |  64-hex hash |  64-hex hash |  64-hex hash |  64-hex hash |
```

## storage layout

chunks live in a Cloudflare R2 bucket (`owlette-prod-content` for owlette.app) under a per-site, sharded key:

```
project-content/{siteId}/{hash[0:2]}/{hash}
```

| segment | source | purpose |
|---|---|---|
| `project-content` | fixed key prefix | separates chunks from version bodies |
| `{siteId}` | the site that owns the chunk | tenant isolation |
| `{hash[0:2]}` | first two hex characters of the hash | spreads keys across prefixes |
| `{hash}` | full 64-character SHA-256 | the content address |

example:

```
project-content/kiosk-fleet-01/4e/4e07408562bedb8b60ce05c1decfe3ad16b72230967de01f640b7e4729b49fce
```

you never build these keys yourself: the API hands you signed URLs that already contain them.

## per-site isolation

chunks belong to the site they were uploaded under. two sites never dedup against each other, even for byte-identical files: the site ID is part of the storage key, and every chunk endpoint takes a `siteId` and checks that you can access that site. the question the API answers is always "does site X have this chunk?", never "does roost have it?".

a missing or malformed `siteId` (1 to 128 letters, digits, `_` or `-`) is `400 validation_failed`. a site you cannot access is `404 not_found`, whether or not it exists.

## authentication and scopes

send your API key as `Authorization: Bearer $OWLETTE_API_KEY` (`x-api-key` also works). chunk routes are authorized against the site, so the key needs a `site=<siteId>` scope; a `roost=` scope does not cover them.

| route | API-key scope | also requires |
|---|---|---|
| `POST /api/chunks/check` | `site=<siteId>:write` | membership of the site |
| `POST /api/chunks/upload-urls` | `site=<siteId>:write` | site admin or owner role |
| `GET` or `POST /api/chunks/download-urls` | `site=<siteId>:read` | membership of the site; an agent token for the same site also works |
| `POST /api/chunks/{digest}/mount` | `site=<siteId>:write` | site admin or owner role |
| `GET /api/chunks/{digest}/referrers` | `site=<siteId>:read` | membership of the site |

a key without the scope gets `403 scope_insufficient`. a member without the admin or owner role gets `403 forbidden` (`capability not granted`) on upload-urls and mount. see [authentication](/docs/api/authentication) for scope syntax.

every chunk route also accepts the optional `Roost-Version: 2026-04-22` header. leave it out and the response carries `X-Roost-Version-Missing: true`; send an unsupported date and you get `400 unsupported_version`.

## upload flow

the client never sends bytes the site already has. each batch is three steps:

1. `POST /api/chunks/check` returns the hashes the site is missing.
2. `POST /api/chunks/upload-urls` mints signed R2 `PUT` URLs for those hashes.
3. you `PUT` each chunk straight to R2.

then publish the version with `POST /api/roosts/{roostId}/versions`; see [publish](/docs/api/versions#publish).

### step 1 - check which chunks are missing

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/chunks/check" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "siteId": "kiosk-fleet-01",
    "hashes": [
      "2e7d2c03a9507ae265ecf5b5356885a53393a2029d241394997265a1a25aefc6",
      "18ac3e7343f016890c510e93f935261169d9e3f565436429830faf0934f4f8e4",
      "4e07408562bedb8b60ce05c1decfe3ad16b72230967de01f640b7e4729b49fce"
    ]
  }'
```

- `hashes` must be a non-empty array of **at most 1000** digests; anything else is `400 validation_failed`.
- the response lists only the hashes not stored for the site. a stored object of zero bytes counts as missing.

```json
{
  "missing": [
    "4e07408562bedb8b60ce05c1decfe3ad16b72230967de01f640b7e4729b49fce"
  ]
}
```

### step 2 - mint upload URLs for the missing hashes

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/chunks/upload-urls" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "siteId": "kiosk-fleet-01",
    "hashes": [
      "4e07408562bedb8b60ce05c1decfe3ad16b72230967de01f640b7e4729b49fce"
    ]
  }'
```

- one URL per hash, up to 1000 hashes per call.
- the URLs are valid for **60 minutes**. `expiresAt` is the expiry as an ISO 8601 UTC timestamp.
- the route keeps no replay cache and ignores `Idempotency-Key`; to retry, mint fresh URLs for the hashes you still need.

```json
{
  "urls": {
    "4e07408562bedb8b60ce05c1decfe3ad16b72230967de01f640b7e4729b49fce": "https://<account-id>.r2.cloudflarestorage.com/owlette-prod-content/project-content/kiosk-fleet-01/4e/4e0740856...?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=..."
  },
  "expiresAt": "2026-04-22T16:30:00.000Z"
}
```

### step 3 - put the bytes to R2

```bash
curl -fsS --upload-file chunk.bin \
  -H "Content-Type: application/octet-stream" \
  "$SIGNED_URL"
```

- bytes go from you to R2 directly; roost never sees them.
- R2 does not check that the bytes match the hash in the key. agents re-hash every chunk they download and reject a mismatch, so upload exactly the bytes you hashed.
- retry per chunk. if a `PUT` fails, retry that chunk; if its URL has expired, mint a new one for that hash only.
- upload in parallel; 8 to 16 concurrent `PUT`s is typical.

## download flow

agents fetch chunks this way when they sync a version; you can use it to pull content too.

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/chunks/download-urls" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "siteId": "kiosk-fleet-01",
    "hashes": [
      "2e7d2c03a9507ae265ecf5b5356885a53393a2029d241394997265a1a25aefc6",
      "18ac3e7343f016890c510e93f935261169d9e3f565436429830faf0934f4f8e4"
    ]
  }'
```

for small batches you can use `GET` with one `hash` query parameter per digest:

```bash
curl -fsS "$OWLETTE_API_URL/api/chunks/download-urls?siteId=kiosk-fleet-01&hash=2e7d2c03a9507ae265ecf5b5356885a53393a2029d241394997265a1a25aefc6&hash=18ac3e7343f016890c510e93f935261169d9e3f565436429830faf0934f4f8e4" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```

- up to 1000 hashes per call, in either form.
- the URLs are valid for **15 minutes**.
- the server signs a URL for every hash you send without checking that the chunk exists; fetching the URL of a missing chunk returns an R2 error. run `check` first if you are not sure.

```json
{
  "urls": {
    "2e7d2c03a9507ae265ecf5b5356885a53393a2029d241394997265a1a25aefc6": "https://<account-id>.r2.cloudflarestorage.com/owlette-prod-content/project-content/kiosk-fleet-01/2e/2e7d2c03...?X-Amz-Algorithm=AWS4-HMAC-SHA256&...",
    "18ac3e7343f016890c510e93f935261169d9e3f565436429830faf0934f4f8e4": "https://<account-id>.r2.cloudflarestorage.com/owlette-prod-content/project-content/kiosk-fleet-01/18/18ac3e73...?X-Amz-Algorithm=AWS4-HMAC-SHA256&..."
  },
  "expiresAt": "2026-04-22T15:45:00.000Z"
}
```

then `GET` each signed URL. agents re-hash every chunk as they write it; a chunk whose hash does not match is discarded and fetched again, up to 5 attempts, and a chunk that still fails stops the sync.

## cross-roost mount

`POST /api/chunks/{digest}/mount` records that a chunk is shared from one roost to another. `{digest}` is the bare 64-character hash. no bytes move.

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/chunks/2e7d2c03a9507ae265ecf5b5356885a53393a2029d241394997265a1a25aefc6/mount" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "siteId": "kiosk-fleet-01",
    "from": "roost_lobby_td",
    "to": "roost_lobby_td_v2"
  }'
```

- send `siteId`, `from` and `to` in the JSON body or as query parameters. when a value is in both, the query parameter wins.
- `from` and `to` are roost IDs (8 to 64 letters, digits, `_` or `-`) on the same site, and must differ.
- the chunk must already be stored for the site, and both roosts must exist; otherwise `404 not_found`.
- the route writes the referrer entry `mount_{from}_{to}` for the chunk. repeating the same mount overwrites that entry, so it is safe to retry; there is no `Idempotency-Key` replay.
- a mount is bookkeeping only. chunks are already shared by every roost on the site, so a version in `to` can list the chunk without mounting it first, and a mount does not keep a chunk from being garbage collected.

a successful mount returns `201 Created`:

```json
{
  "digest": "2e7d2c03a9507ae265ecf5b5356885a53393a2029d241394997265a1a25aefc6",
  "siteId": "kiosk-fleet-01",
  "from": "roost_lobby_td",
  "to": "roost_lobby_td_v2",
  "mounted": true,
  "zeroByte": true
}
```

## referrer lookup

`GET /api/chunks/{digest}/referrers` lists what references a chunk: a `mount` entry for each mount, and a `version` entry for each new version that included the chunk.

```bash
curl -fsS "$OWLETTE_API_URL/api/chunks/2e7d2c03a9507ae265ecf5b5356885a53393a2029d241394997265a1a25aefc6/referrers?siteId=kiosk-fleet-01&page_size=25" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```


the two entry types fill different fields:

| field | `mount` entry | `version` entry |
|---|---|---|
| `entryId` | `mount_{from}_{to}` | `version_{roostId}_{versionId}` |
| `fromRoostId`, `toRoostId`, `mountedBy` | set | `null` |
| `roostId`, `versionId`, `versionNumber`, `createdBy` | `null` | set |
| `fileCount`, `pathCount` | `null` | number of files in the version that contain the chunk (the two are equal) |
| `totalBytes` | `null` | bytes the chunk contributes to the version |
| `referencedAt`, `mountedAt` | time of the latest mount | publish time |

- entries are newest first. `items` repeats `referrers` for clients that expect the generic list key.
- paginate with `page_size` (default 50, maximum 200; a larger value is `400 validation_failed`) and `page_token`; the legacy `limit` and `cursor` aliases still work. `next_page_token` is `""` on the last page. see [pagination](/docs/api/pagination).
- version entries are written only when a publish creates a new version, after it commits. treat the index as a lookup aid: garbage collection reads the version bodies themselves.

## retries

| operation | retry behavior |
|---|---|
| `POST /api/chunks/check` | safe to retry; it re-reads R2 every time. |
| `POST /api/chunks/upload-urls` | safe to retry; each call mints fresh URLs. there is no replay cache. |
| `PUT <signed url>` | safe to retry with the same bytes while the URL is valid; after that, mint a new URL. |
| `POST` or `GET /api/chunks/download-urls` | safe to retry; each call mints fresh URLs. |
| `POST /api/chunks/{digest}/mount` | safe to retry; the same `from` and `to` always write the same entry. |

the API does not rate-limit chunk routes today. back off exponentially on `5xx` from the API or from R2, and treat a `429` or `503` from R2 the same way.

## reference chunker

both versions read a file in 4 MiB blocks, hash each block with SHA-256, and yield `(hash, size, offset)` without loading the whole file into memory.

### Python (3.9+)

```python
import hashlib
from pathlib import Path
from typing import Iterator

CHUNK_SIZE = 4 * 1024 * 1024  # 4 MiB

def chunk_file(path: Path) -> Iterator[dict]:
    """
    stream-read `path` in 4 MiB blocks; yield {"hash": hex, "size": int, "offset": int}
    for each chunk. the last chunk may be 1..CHUNK_SIZE bytes. a zero-byte file yields
    no chunks.
    """
    offset = 0
    with path.open("rb") as f:
        while True:
            block = f.read(CHUNK_SIZE)
            if not block:
                return
            digest = hashlib.sha256(block).hexdigest()
            yield {"hash": digest, "size": len(block), "offset": offset}
            offset += len(block)


def file_to_version_entry(path: Path, rel_path: str) -> dict:
    chunks = list(chunk_file(path))
    return {
        "path": rel_path,
        "size": sum(c["size"] for c in chunks),
        "chunks": [{"hash": c["hash"], "size": c["size"]} for c in chunks],
    }
```

### Node (20+, ES module)

```js
import { createReadStream } from 'node:fs';
import { createHash } from 'node:crypto';

const CHUNK_SIZE = 4 * 1024 * 1024; // 4 MiB

/**
 * stream-read `path` in 4 MiB blocks; yield { hash, size, offset } per chunk.
 * last chunk may be 1..CHUNK_SIZE bytes. zero-byte files yield nothing.
 */
export async function* chunkFile(path) {
  let offset = 0;
  let pending = Buffer.alloc(0);

  for await (const buf of createReadStream(path, { highWaterMark: CHUNK_SIZE })) {
    pending = pending.length === 0 ? buf : Buffer.concat([pending, buf]);

    while (pending.length >= CHUNK_SIZE) {
      const block = pending.subarray(0, CHUNK_SIZE);
      pending = pending.subarray(CHUNK_SIZE);
      const hash = createHash('sha256').update(block).digest('hex');
      yield { hash, size: block.length, offset };
      offset += block.length;
    }
  }

  if (pending.length > 0) {
    const hash = createHash('sha256').update(pending).digest('hex');
    yield { hash, size: pending.length, offset };
  }
}

export async function fileToVersionEntry(path, relPath) {
  const chunks = [];
  for await (const c of chunkFile(path)) {
    chunks.push({ hash: c.hash, size: c.size });
  }
  return {
    path: relPath,
    size: chunks.reduce((n, c) => n + c.size, 0),
    chunks,
  };
}
```

notes for both:

- read in blocks of at least 4 MiB, or accumulate smaller reads until you have a full chunk.
- the final chunk is whatever remains at end of file.
- do not chunk a file while something else is writing it; lock it or copy it first.
- keep `files[].size` equal to the sum of `chunks[].size`. the publish API does not check this, but agents reject a version where they differ.

## errors

errors are RFC 7807 `application/problem+json` with `code`, `docsUrl`, `requestId` and, for validation errors, a field-level `errors` map. branch on `code`, not on `detail`. see [errors](/docs/api/errors).

| code | status | when |
|---|---|---|
| `validation_failed` | 400 | invalid JSON body; malformed digest; missing or invalid `siteId`; empty `hashes`, more than 1000 hashes, or a malformed hash; missing, invalid or identical `from` and `to`; invalid pagination. |
| `unsupported_version` | 400 | the `Roost-Version` header names a date the API does not support. |
| `unauthorized` / `token_expired` | 401 | no valid credential, or an expired API key. |
| `forbidden` | 403 | your account is inactive, or you lack the site admin or owner role on upload-urls or mount. |
| `scope_insufficient` | 403 | the API key has no matching `site=<siteId>` scope. |
| `not_found` | 404 | the site does not exist or you cannot access it; for mount, the chunk is not stored for the site or a roost does not exist. |
| `service_unavailable` | 503 | roost is switched off for this site. |
| `internal_error` | 500 | unexpected server error; quote the `requestId`. |

publishing a version that lists chunks the site does not have fails on the version route with `412 precondition_failed`; see [version errors](/docs/api/versions#errors).

example `validation_failed` for a malformed hash:

```json
{
  "type": "https://owlette.app/problems/validation-failed",
  "title": "validation failed",
  "status": 400,
  "detail": "field hashes contains malformed hash entries (must be lowercase 64-char hex sha-256)",
  "errors": {
    "hashes": [
      "malformed entries: bad-digest…"
    ]
  },
  "code": "validation_failed",
  "docsUrl": "https://owlette.app/docs/api/errors#validation_failed",
  "requestId": "3b0c3f0e-5d7a-4a9e-9c55-0f6f2a8e1d42"
}
```

## operational notes

- R2 enforces URL expiry, not roost. trust `expiresAt` from the response, not your local clock.
- an R2 `PUT` is atomic per object; there are no partial uploads. retry the whole chunk.
- garbage collection runs nightly per site and keeps every chunk that some version body on the site lists, current or historical, in any roost. a chunk no version lists is marked and becomes eligible for deletion 30 days later if it is still unlisted; publishing a version that lists it within that window keeps it. mount entries do not protect a chunk, and neither does a finished upload: publish within 30 days of uploading.
