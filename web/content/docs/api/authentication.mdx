## sending a key

send the key as a bearer token:

```http
Authorization: Bearer owk_live_...
```

the same key also works in an `x-api-key` header, and is checked identically:

```http
x-api-key: owk_live_...
```

a key in the query string (`?api_key=owk_live_...`) is not accepted: query strings end up in logs, proxies, and browser history. a client that cannot set headers, such as a browser `EventSource`, needs a fetch-based stream reader instead.

the CLI and both SDKs send `Authorization: Bearer`.

---

## key format

| prefix | environment | notes |
|---|---|---|
| `owk_live_` | `live` | every key minted today |
| `owk_test_` | `test` | legacy, no longer issued. existing keys authenticate exactly like `owk_live_` keys — `test` never provided a sandbox — and rotating one keeps its `owk_test_` prefix |

the part after the prefix is 32 random bytes encoded as base64url (43 characters). treat the whole key as opaque. the API returns the raw key once, at creation or rotation, and stores only its SHA-256 hash.

list responses expose a `keyPrefix` (the first 15 characters, e.g. `owk_live_kB8n3p`) for display and audit correlation; they never return the raw key again.

## creating keys

### dashboard

create keys in the dashboard at **settings → api keys** (`/settings/api-keys`). choose:

- a name (up to 100 characters)
- scopes, from a preset or custom
- an expiry, from 1 to 365 days (default 90)
- a [tool tier](#tool-tiers) (default 1)

copy the raw key immediately into a secrets manager. it is shown once.

### scripted

`POST /api/keys` creates a key and takes the same fields: `name`, `scopes`, an optional `ttlDays` (1–365, default 90), and an optional `maxToolTier` (1, 2 or 3, default 1). it requires a signed-in user session or a Firebase ID token, subject to [the second factor](#sessions-and-id-tokens) — an API key cannot create, list, edit, rotate, or revoke keys, so a leaked key cannot mint a broader replacement for itself. an agent's machine token is refused too.

the body may still carry `environment`, because older CLI and SDK builds send it; it is ignored, and every new key is `live`.

`owlette auth login` mints its key through a device-code flow instead: the CLI shows a three-word pairing phrase, you approve it in the browser while signed in and pick the scopes and lifetime, and the CLI receives the key. see [`auth`](/docs/cli/reference/auth).

`/api/account/api-keys` is a superadmin platform surface, not the self-service path.

## sessions and ID tokens

the dashboard calls the API with its session cookie, and first-party tools can send a Firebase ID token as the bearer. neither carries scopes: each acts as its user. on an account that holds a second factor, which is every account past two-factor setup:

- a session works once its sign-in has passed the second factor. until then the API answers `403 mfa_challenge_required`, and the dashboard sends you to `/verify-2fa`.
- a Firebase ID token is refused with the same `403 mfa_challenge_required`, because it carries no second factor. call the API with a key instead, and manage keys, which `/api/keys/*` won't do through a key, in the dashboard.

the routes that finish signing in or set up a factor take a session that has not passed it yet. API keys and agent tokens are unaffected.

## verifying identity

`GET /api/whoami` accepts any credential and returns who it resolved to: the user, the key's metadata and scopes, a rate-limit hint, a storage-quota summary, and a primary site.

```bash
curl -fsS "https://owlette.app/api/whoami" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" | jq
```

```json
{
  "userId": "user_01HWABCD1234EFGH5678IJKL90",
  "email": "ops@example.com",
  "role": "admin",
  "key": {
    "keyId": "9e05dd1e-47ac-4a59-a8bf-00b38faea1b4",
    "name": "ci preview",
    "keyPrefix": "owk_live_kB8n3p",
    "scopes": [
      { "resource": "site", "id": "kiosk-fleet-01", "permissions": ["read"] },
      { "resource": "machine", "id": "*", "permissions": ["read", "write"] }
    ],
    "maxToolTier": 1,
    "environment": "live",
    "expiresAt": 1798049400000,
    "lastUsedAt": 1777408200000,
    "isLegacy": false
  },
  "rateLimit": {
    "tier": "api",
    "limitPerMinute": 600,
    "note": "use RateLimit-* response headers on actual API calls for live counters"
  },
  "quota": {
    "siteId": "kiosk-fleet-01",
    "usedBytes": 23456789012,
    "pendingBytes": 104857600,
    "limitBytes": 107374182400
  },
  "primarySiteId": "kiosk-fleet-01"
}
```

- `key` is `null` when a session or Firebase ID token made the request.
- `primarySiteId` is the first concrete `site` scope on the key, falling back to the user's first assigned site. `quota` describes that site, and is `null` when there is none.
- `rateLimit` is a fixed hint, not a live counter. the limits that actually apply, and their counters, arrive as `RateLimit-*` headers on each response — see [rate limits](/docs/api/rate-limits).

## scopes

each key carries a `scopes` array. a request is allowed only when one entry matches the operation's resource, ID, and permission, **and** the key's owner could make the same request themselves — a key never grants more than its user holds, the owner's [machine scope](/docs/reference/authentication#machine-scope) included. when the owner's access to a site is limited to some machines, their key reaches only those machines there, even with `machine=*`: any other machine answers `404`, and the site's site-wide routes answer `403`.

```json
[
  { "resource": "site", "id": "kiosk-fleet-01", "permissions": ["read"] },
  { "resource": "machine", "id": "*", "permissions": ["read", "write"] },
  { "resource": "chat", "id": "kiosk-fleet-01", "permissions": ["read", "write"] }
]
```

| field | meaning |
|---|---|
| `resource` | one of `roost`, `site`, `machine`, `chat`, `deploy`, `process`, `user`, `installer`, or `issue` |
| `id` | a specific resource ID (up to 128 characters), or `*` for every resource of that type the owner can access |
| `permissions` | a non-empty list of `read`, `write`, `deploy`, `rollback`, `admin` |

a key holds at most 50 scope entries. creation and edits check that each concrete `site`, `chat`, or `deploy` ID is a site you can access, so a typo fails at creation instead of at first use.

permissions are exact, not a ladder: `write` does not imply `read`, `deploy` does not imply `write`, and `admin` does not imply anything else. a few operations need two permissions on the same scope (for example `write` and `admin`); the [interactive reference](/docs/api) names the scope on every operation.

| permission | typical use |
|---|---|
| `read` | lists and detail reads, including issues and their attachments |
| `write` | creating, updating, publishing, queueing machine commands, setting an issue's triage status |
| `deploy` | roost deploys and resyncs |
| `rollback` | roost rollbacks |
| `admin` | site creation, editing, and deletion; membership and ownership changes (together with `read` or `write`); clearing logs; deployment uninstalls (with `write`); superadmin platform, user, and installer routes |

`user`, `installer` and `issue` scopes are superadmin-only and must use `id: "*"`. `issue=*:read` lists issues, reads one by its number or ID and downloads its attachments; `issue=*:write` sets an issue's triage status.

### presets

the dashboard offers four presets as starting points. each grants its permissions on `roost`, `site`, `machine`, and `chat`, all with `id: "*"`:

| preset | permissions |
|---|---|
| read only | `read` |
| publisher | `read`, `write` |
| operator | `read`, `write`, `deploy`, `rollback` |
| admin | `read`, `write`, `deploy`, `rollback`, `admin` |

narrow a preset to the sites and machines an integration actually touches before you save it.

### tool tiers

`mcp_tool_call` on [the machine commands route](/docs/agent/remote-commands) runs a hoot tool, and each tool has a [tier](/docs/reference/hoot-tools). a key runs tools up to its `maxToolTier`:

| `maxToolTier` | runs |
|---|---|
| 1 | read-only tools. every key is here until its owner raises it, including keys made before the setting existed |
| 2 | also process, service and system setting changes that leave what a machine launches alone |
| 3 | also commands, scripts, file reads and writes, deployments and restarts, and any call that changes what a machine launches. a name that is not a known tool counts as tier 3 |

a call's tier is its tool's, except that a call that [changes what a machine launches](/docs/dashboard/hoot#changing-what-a-machine-launches), such as `update_process` with a new target or `manage_scheduled_task` `create`, counts as tier 3 whatever its tool's tier. a call above the key's tier returns `403 max_tool_tier_exceeded`, and nothing reaches the machine.

the parameters are checked against the tool's definition before anything is queued: an unknown tool or parameter, a missing required one, or a value the tool doesn't take returns `400 tool_params_invalid`, naming the parameter.

- set it when creating the key, or later in the key's editor or with `PATCH /api/keys/{keyId}`.
- going above 1, by creating, raising or rotating, needs a dashboard session that passed a second factor. anything else, an ID token included, returns `403 verified_session_required`. lowering a key needs no more than any other edit.
- a rotation keeps the tier.
- `owlette key create` and the CLI's device-code login always make tier 1 keys. raise one in the dashboard.
- it says nothing about the other command types, or about hoot conversations, which stay read only through a key.

a session or ID token has no `maxToolTier`. it runs tier 1 and 2, and tier 3, a launch change included, only from a dashboard session with an open [step-up](/docs/dashboard/swoop#the-second-factor) window on that machine, the same one swoop's control uses, else `401 step_up_required`. an ID token never holds that window.

### what an API key cannot do

some surfaces need a person, not a key:

- **key management.** `/api/keys/*` takes a session or Firebase ID token only, subject to [the second factor](#sessions-and-id-tokens).
- **swoop.** every swoop session route, the site swoop list, and `swoop-settings` refuse a key with `403 api_key_not_permitted` — swoop is a human-in-the-loop surface and a key has no second factor. see [swoop](/docs/dashboard/swoop).
- **display settings.** `GET`/`PATCH /api/sites/{siteId}/display-settings` refuse a key the same way.
- **member candidates.** `GET /api/sites/{siteId}/member-candidates` refuses a key the same way: a key scoped to one site must not read the rosters of its owner's other sites.
- **hoot tools.** a key can hold conversations, but every reply is capped at read-only tools. see [hoot](/docs/api/hoot#access).

## editing key scopes

a key scoped too narrowly does not have to be replaced. `PATCH /api/keys/{keyId}` edits `scopes`, `name` and/or [`maxToolTier`](#tool-tiers) in place and leaves the secret alone — whatever already holds the key keeps working and picks up the new scopes on its next request.

```bash
curl -X PATCH "https://owlette.app/api/keys/$KEY_ID" \
  -H "Authorization: Bearer $FIREBASE_ID_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"scopes":[{"resource":"site","id":"kiosk-fleet-01","permissions":["read","write"]}]}'
```

- `scopes` replaces the whole list; it is not merged. send the complete list you want the key to end up with.
- the creation rules apply: `user`, `installer` and `issue` stay superadmin-only, so a key cannot be edited into permissions its owner could not have been issued.
- a superadmin gives an existing key issue access by editing it and adding an `issue` scope with `read` and `write` ticked; the key's other scopes stay as they are.
- `environment` and `ttlDays` are rejected with `400`. rotate to change the expiry.
- a revoked key, or one that has been rotated, returns `409`. edit the successor instead.

the dashboard exposes the same edit as the sliders control on each key.

## expiration, rotation, and revocation

every key expires:

- default lifetime: 90 days
- maximum lifetime: 365 days
- rotation grace: the old key keeps working for 24 hours after a rotation

a key within 14 days of expiry shows as expiring soon in the dashboard, and its owner is emailed ahead of the date.

the lifecycle routes take a session or Firebase ID token, subject to [the second factor](#sessions-and-id-tokens):

- `POST /api/keys/{keyId}/rotate` issues a replacement with the same name, scopes, tool tier and environment, and returns the new raw key once. an optional body `{ "ttlDays": 1–365 }` sets the new key's lifetime (default 90). the response's `previousKey.retiresAt` is when the old key stops working. a key that is revoked or already rotated returns `409`.
- `PATCH /api/keys/{keyId}` edits scopes, name and tool tier. see [editing key scopes](#editing-key-scopes).
- `DELETE /api/keys/{keyId}` revokes the key immediately and permanently. the record is kept and stamped `revokedAt`, so the key still appears in `GET /api/keys` with `revoked: true`. repeating the call is a no-op.

rotate when a secret may have leaked or your rotation schedule says so; revoke when the integration is retired.

## auth errors

| status | code | meaning |
|---|---|---|
| 401 | `unauthorized` | the credential is missing, malformed, unknown, revoked, or a rotated key past its grace window |
| 401 | `token_expired` | the key's `expiresAt` has passed. the body carries `expiredAt` |
| 401 | `step_up_required` | a tier-3 tool call from a session with no open step-up window on that machine. see [tool tiers](#tool-tiers) |
| 403 | `mfa_challenge_required` | a session that has not passed its second factor, or an ID token for an account that holds one. see [sessions and ID tokens](#sessions-and-id-tokens) |
| 403 | `scope_insufficient` | the credential is valid but lacks the resource, ID, and permission the operation needs. the body's `required` names it |
| 403 | `api_key_not_permitted` | the operation refuses API keys whatever their scopes. use a session |
| 403 | `max_tool_tier_exceeded` | the tool's tier is above the key's `maxToolTier`. see [tool tiers](#tool-tiers) |
| 403 | `verified_session_required` | a tool tier above 1 needs a dashboard session that passed a second factor. see [tool tiers](#tool-tiers) |
| 403 | `forbidden` | the caller lacks the role, site membership, or capability, or their account is deactivated |
| 404 | `not_found` | the resource is absent, or hidden from this caller so its existence does not leak |

all of them use the [problem envelope](/docs/api/errors). branch on `code`, not on the prose in `detail`.

## key handling

- keep keys in a secrets manager, never in source code.
- never log raw keys.
- use a separate key for each integration — CI, monitoring, local development — so rate limits and audit rows are attributable.
- keep scopes narrow; after a `403 scope_insufficient`, [edit the key's scopes](#editing-key-scopes) rather than replacing it with a broader one.
- revoke keys you no longer use.
