**last updated**: 2026-10-05

a roost is a deploy unit: a named set of files that owlette keeps in sync on a list of target machines. each publish adds an immutable version to the roost's history and moves its current pointer; agents on the target machines then pull the files they are missing. the bytes themselves are [chunks](/docs/api/chunks), uploaded before the version is published.

the examples use `$OWLETTE_API_URL` (`https://owlette.app`), `$OWLETTE_API_KEY`, `$SITE_ID` and `$ROOST_ID`, set up as in the [quickstart](/docs/api/quickstart).

---

## authentication and scopes

send your API key as `Authorization: Bearer $OWLETTE_API_KEY` (`x-api-key` also works). routes under `/api/roosts/{roostId}` are authorized against the roost, so the key needs a `roost=<roostId>` scope (or `roost=*`) with the permission below; listing and creating roosts are authorized against the site instead. every route also needs membership of the site, and every route that changes something needs the site admin or owner role.

| route | API-key scope | role |
|---|---|---|
| `GET /api/roosts` | `site=<siteId>:read` | member |
| `POST /api/roosts` | `site=<siteId>:write` | admin or owner |
| `GET` on `/api/roosts/{roostId}`, `/versions`, `/versions/{versionRef}`, `/files`, `/diff`, `/deployments`, `/deployments/{rolloutId}` | `roost=<roostId>:read` | member |
| `PATCH` or `DELETE /api/roosts/{roostId}`, `POST /versions`, `PATCH /versions/{versionRef}` | `roost=<roostId>:write` | admin or owner |
| `POST /api/roosts/{roostId}/rollback` | `roost=<roostId>:rollback` | admin or owner |
| `POST /api/roosts/{roostId}/deploy`, `POST /api/roosts/{roostId}/resync` | `roost=<roostId>:deploy` | admin or owner |

a key without the scope gets `403 scope_insufficient`; a member without the role gets `403 forbidden` (`capability not granted`). permissions are exact: `rollback` and `deploy` do not include `write`, and none of them include `read`. see [authentication](/docs/api/authentication).

every route also accepts the optional `Roost-Version: 2026-04-22` header. leave it out and the response carries `X-Roost-Version-Missing: true`; send an unsupported date and you get `400 unsupported_version`.

## roosts

| operation | request | response |
|---|---|---|
| list | `GET /api/roosts?siteId=...` | `200` with `roosts[]`, newest first. soft-deleted roosts are left out unless you pass `includeDeleted=true`. `page_size` defaults to 20, maximum 100. |
| create | `POST /api/roosts` with `{ siteId, name, targets?, extractPath?, roostId? }` | `201` with `{ roostId, siteId, name, targets, extractPath? }` |
| get | `GET /api/roosts/{roostId}?siteId=...` | `200` with the roost, plus `currentVersion` and `previousVersion` summaries (or `null`) |
| update | `PATCH /api/roosts/{roostId}` with `{ siteId, name?, targets?, extractPath? }` | `200` with `{ roostId, siteId, updated }`, where `updated` names the fields written, including `updatedAt` |
| delete | `DELETE /api/roosts/{roostId}?siteId=...` | `200` with `{ roostId, siteId, softDeleted: true, tombstoneExpiresAt }` |

- `name` is required on create (`400 roost_name_required` when missing or blank); it is trimmed and cut to 200 characters.
- `targets` is the list of machine IDs that receive the roost. entries must be non-empty strings; duplicates are dropped and only the first 500 are kept.
- `extractPath` is where agents write the files. it is trimmed and cut to 500 characters; when unset, agents use `~/Documents/Owlette`. on update, an empty string clears it.
- `roostId` is optional on create: 8 to 64 letters, digits, `_` or `-`. without it the server generates `rst_` plus 18 hex characters. creating an ID that already exists is `409 conflict`, unless that roost is soft-deleted, in which case create restores it with its version history.
- delete is a soft delete: it stamps `deletedAt` and a `tombstoneExpiresAt` 30 days out, and keeps the versions. update and deploy answer `409 conflict` on a soft-deleted roost, and rollback answers `404 not_found`.
- update needs at least one of `name`, `targets` or `extractPath`; it cannot move the version pointer.

roost fields, as returned by get (list returns the same fields except `schemaVersion`, `versionUrl`, `createdBy` and the two summaries): `roostId`, `siteId`, `name`, `targets`, `extractPath`, `schemaVersion`, `currentVersionId`, `previousVersionId`, `versionCounter` (the highest version number minted), `versionUrl`, `createdAt`, `updatedAt`, `createdBy`, `deletedAt`, `tombstoneExpiresAt`, `currentVersion`, `previousVersion`.

`versionUrl` here and on versions is the unsigned R2 location of the version body. it is a hint for tooling and cannot be fetched. agents get a signed URL from `POST /api/roosts/{roostId}/version-url`, which accepts only agent tokens and superadmin callers.

## version body

`POST /api/roosts/{roostId}/versions` takes a `version` object with this shape:

```json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.owlette.version.v1+json",
  "config": {
    "producer": "owlette-cli",
    "cliVersion": "1.0.0-rc.0",
    "createdAt": "2026-04-22T15:30:00.000Z",
    "hostname": "build-runner-01",
    "platform": "linux"
  },
  "files": [
    {
      "path": "main.toe",
      "size": 5242880,
      "chunks": [
        {
          "hash": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
          "size": 4194304
        },
        {
          "hash": "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae",
          "size": 1048576
        }
      ]
    }
  ]
}
```

top-level fields:

| field | required | server validation |
|---|---:|---|
| `schemaVersion` | yes | must be exactly `2`. |
| `mediaType` | yes | must be exactly `application/vnd.owlette.version.v1+json`. |
| `config` | yes | must be a JSON object. no keys are required. |
| `files` | yes | must be a non-empty array; an empty publish is rejected. |

the CLI and SDKs write `producer`, `cliVersion`, `createdAt`, `hostname` and `platform` into `config`. they are metadata the server does not read. any extra keys you add are stored and are part of the version ID.

each `files[]` entry:

| field | required | server validation |
|---|---:|---|
| `path` | yes | non-empty string. use forward-slash relative paths. |
| `size` | yes | non-negative number. |
| `chunks` | yes | array; empty for a zero-byte file. |

each chunk needs a bare lowercase SHA-256 `hash` (64 hex characters, no `sha256:` prefix) and a positive numeric `size`.

the server checks only the rules above. agents check more when they sync, and refuse the whole version if any file breaks one:

- `size` and every chunk `size` must be integers, and `size` must equal the sum of the file's chunk sizes.
- no two files may share a `path`.
- a `path` must be relative and canonical: no leading `/`, no drive letter (`C:`), no `.`, `..` or empty segments, no `:` anywhere, no NUL bytes.

## version IDs and refs

the server computes `versionId` as the SHA-256 hex digest of the canonical JSON of the version body: object keys sorted at every level, no whitespace. publish responses return the bare 64-character ID. because `config` is part of the body, two pushes of the same files from the CLI or SDK produce different IDs, since each writes a fresh `config.createdAt`.

routes that take a `{versionRef}` path segment, `targetVersion` on rollback, and `against` on diff accept:

| form | examples |
|---|---|
| version ID | `8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92`, or the legacy form `vrs_8d969eef...` |
| version number | `3`, `#3`, `v3`, `V3` (a positive integer, no leading zeros) |
| alias | `current`, `previous`, `first` (version 1) |

surrounding whitespace is trimmed. any other form is `400 version_ref_malformed`; a well-formed ref with no match in this roost is `404 version_not_found`.

in a URL, a literal `#` starts a fragment. use `3` or `v3`, or encode the hash form as `%233`:

```bash
curl -fsS "$OWLETTE_API_URL/api/roosts/$ROOST_ID/versions/3?siteId=$SITE_ID" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"

curl -fsS "$OWLETTE_API_URL/api/roosts/$ROOST_ID/versions/v3?siteId=$SITE_ID" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"

curl -fsS "$OWLETTE_API_URL/api/roosts/$ROOST_ID/versions/%233?siteId=$SITE_ID" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```

## publish

the SDKs and CLI do the whole pipeline for you: chunk the directory, check which chunks are missing, upload them, build the version body and publish it.

Node:

```ts
const result = await owlette.roosts.push("./dist", "rst_lobby", {
  siteId: "site_kiosk_fleet",
  description: "fixed lobby video"
});
```

Python:

```python
from roost import PushOptions

result = await client.roosts.push(
    "./dist",
    "rst_lobby",
    PushOptions(site_id="site_kiosk_fleet", description="fixed lobby video"),
)
```

to publish over plain HTTP, upload the chunks first ([upload flow](/docs/api/chunks#upload-flow)), then post the body. save this as `publish.json`:

```json
{
  "siteId": "site_kiosk_fleet",
  "version": {
    "schemaVersion": 2,
    "mediaType": "application/vnd.owlette.version.v1+json",
    "config": {
      "producer": "custom-uploader",
      "createdAt": "2026-04-22T15:30:00.000Z"
    },
    "files": [
      {
        "path": "main.toe",
        "size": 5242880,
        "chunks": [
          {
            "hash": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
            "size": 4194304
          },
          {
            "hash": "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae",
            "size": 1048576
          }
        ]
      }
    ]
  },
  "description": "fixed lobby video",
  "expectedCurrentVersionId": "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae"
}
```

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/roosts/rst_lobby/versions" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  --data @publish.json
```

request body fields:

| field | required | notes |
|---|---:|---|
| `siteId` | yes | site that owns the roost. |
| `version` | yes | the full version body. |
| `description` | no | plaintext "what changed", at most 500 characters (longer is `400 validation_failed`). trimmed; blank is stored as `null`. |
| `expectedCurrentVersionId` | no | compare-and-swap guard: a version ID, or `null` to require that the roost has no current version yet. |
| `name` | no | sets the roost's display name. trimmed, cut to 200 characters. |
| `targets` | no | replaces the roost's target machine IDs. non-empty strings; duplicates dropped, first 500 kept. |
| `extractPath` | no | sets the agents' extract root. trimmed, cut to 500 characters; blank is ignored. |

what the server does:

- **chunk check**: every hash in `version.files[].chunks[]` must already be stored for the site. if any is missing, the publish fails with `412 precondition_failed` and a `missingChunks` array holding up to 20 of the missing hashes; upload them and retry.
- **compare-and-swap**: when `expectedCurrentVersionId` is present and does not match the roost's current pointer at commit time, the publish fails with `412 version_stale`. without it, publish moves the pointer unconditionally.
- **roost creation**: publishing to a roost ID that does not exist yet creates the roost, named after its ID unless you pass `name`.
- **outcome**: a body whose ID is new creates version `N+1` and answers `201 Created`. a body that is already the current version changes nothing (it still applies any `name`, `targets` or `extractPath` you sent) and answers `200`. a body that matches an older version moves the pointer back to that version without minting a number and answers `200`; machines are not reliably re-synced this way, so use [rollback](#rollback) to put an older version back on machines.
- **distribution**: when the pointer moves to a new version and the roost has targets, a canary rollout starts on its own; see [deploy](#deploy) for how waves progress. the automatic rollout picks canary machines by a stable hash of machine ID and version ID.
- **webhooks**: a new version (the `201` case only) queues a [`version.published`](/docs/api/webhooks#versionpublished) event.
- **idempotency**: `Idempotency-Key` is optional. the same key with the same body within 24 hours replays the first success with `Idempotent-Replayed: true`; a different body is `422 idempotency_key_mismatch`. see [idempotency](/docs/api/idempotency).

response:

```json
{
  "versionId": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
  "versionNumber": 3,
  "currentVersionId": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
  "previousVersionId": "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae"
}
```

the publish response has no `description`, timestamps or version body; fetch the version for those. after a stale publish, read the roost with `GET /api/roosts/{roostId}?siteId=...`, decide whether to rebuild or stop, and retry with the new `expectedCurrentVersionId`.

## edit a description

a version's content is immutable; only `description` can change after publish. send `siteId` and `description` (a string, or `null` to clear it). any other body field is `400 version_content_immutable`.

```bash
curl -fsS -X PATCH "$OWLETTE_API_URL/api/roosts/rst_lobby/versions/3" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "siteId": "site_kiosk_fleet",
    "description": "operator note corrected after publish"
  }'
```

- `description` is required, at most 500 characters, trimmed; blank is stored as `null`.
- when the version is the current one, the roost's displayed description updates too.
- `Idempotency-Key` is optional and behaves as on publish.

response (`200 OK`):

```json
{
  "versionId": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
  "versionNumber": 3,
  "description": "operator note corrected after publish",
  "roostId": "rst_lobby",
  "siteId": "site_kiosk_fleet",
  "versionUrl": "https://owlette-prod-manifests.<account-id>.r2.cloudflarestorage.com/project-manifests/site_kiosk_fleet/rst_lobby/8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92.json",
```

## list and fetch

### list versions

```bash
curl -fsS "$OWLETTE_API_URL/api/roosts/rst_lobby/versions?siteId=site_kiosk_fleet&page_size=25" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```

`siteId` is required. versions come newest first. `page_size` defaults to 20 with a maximum of 100 (a larger value is `400 validation_failed`); pass the previous `next_page_token` as `page_token` for the next page. the legacy `limit` and `cursor` aliases still work. see [pagination](/docs/api/pagination).

### diff two versions

```bash
curl -fsS "$OWLETTE_API_URL/api/roosts/rst_lobby/versions/3/diff?siteId=site_kiosk_fleet&against=previous" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```

`siteId` and `against` are required. `{versionRef}` is the version you move to, and `against` is the version you compare from, so `added` means "appears when you move to `{versionRef}`".

response:

```json
{
  "versionId": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
  "fromVersion": "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae",
  "toVersion": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
  "against": "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae",
  "roostId": "rst_lobby",
  "siteId": "site_kiosk_fleet",
  "summary": {
    "added": 1,
    "removed": 1,
    "changed": 1,
    "unchanged": 12,
    "hasChanges": true,
    "netBytesDelta": 1572352
  },
  "added": [
    {
      "path": "assets/new_logo.png",
      "size": 524288,
      "reason": "added",
      "chunks": 1
    }
  ],
  "removed": [
    {
      "path": "assets/old_logo.png",
      "size": 512,
      "reason": "removed",
      "chunks": 1
    }
  ],
  "modified": [
    {
      "path": "main.toe",
      "fromSize": 4194304,
      "toSize": 5242880,

      "fromChunks": 1,
      "toChunks": 2

```

- files are matched by path. a file is unchanged when its size and its ordered list of chunk hashes are the same in both versions; otherwise it is modified.
- `summary.changed` counts the entries in `modified`. unchanged files are counted but not listed.
- `netBytesDelta` is the total size of the `to` version minus the total size of the `from` version.
- `chunks`, `fromChunks` and `toChunks` are chunk counts. each list is sorted by path.

## rollback

rollback moves the roost's current pointer to a version already in its history. it creates no version and uploads nothing.

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/roosts/rst_lobby/rollback" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "siteId": "site_kiosk_fleet",
    "targetVersion": "previous"
  }'
```

- `siteId` is required. `targetVersion` is optional, a string or a number in any [ref form](#version-ids-and-refs); omitted or `null`, it defaults to `previous`.
- the old current version becomes `previousVersionId`, so two rollbacks to `previous` in a row swap back and forth.
- rollback skips the canary: every target machine is told to sync the version at once, and the rollout record for that version is marked `complete`.
- a [`version.rolled_back`](/docs/api/webhooks#versionrolled_back) event is queued.
- there is no compare-and-swap guard. `Idempotency-Key` is optional and behaves as on publish.

response (`200 OK`):

```json
{
  "ok": true,
  "roostId": "rst_lobby",
  "siteId": "site_kiosk_fleet",
  "currentVersionId": "2c26b46b68ffc68ff99b453c1d30413413422d706483bfa0f98a5e886266e7ae",
  "currentVersionNumber": 2,
  "previousVersionId": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92"
}
```

errors specific to rollback: a target that is already current is `400 rollback_no_op`; a missing or soft-deleted roost is `404 not_found`; a target whose stored body location is missing is `409 version_url_missing`.

## deploy

deploy starts a rollout of an existing version to machines, without moving the current pointer. omit `versionId` to deploy the current version.

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/roosts/rst_lobby/deploy" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "siteId": "site_kiosk_fleet",
    "versionId": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
    "machines": ["kiosk-01", "kiosk-02"],
    "scheduleAt": "2026-04-22T16:00:00.000Z",
    "dryRun": false
  }'
```

request body fields:

| field | required | notes |
|---|---:|---|
| `siteId` | yes | site that owns the roost. |
| `versionId` | no | a version ID from this roost's history. refs such as `3` or `current` are not resolved here. defaults to the current version. |
| `machines` | no | non-empty list of machine IDs; duplicates are dropped. defaults to the roost's `targets`. |
| `scheduleAt` | no | ISO 8601 timestamp. more than 60 seconds in the future parks the rollout at `stage: "scheduled"`; otherwise it starts now. |
| `dryRun` | no | `true` returns the plan without writing anything. |

how a rollout runs:

- the machines are sorted by ID; the first 10% (rounded up, at least 1, at most 50) form the canary wave and the rest form the fleet wave. the canary is told to sync at once.
- when every canary machine has reported and at least 90% succeeded, the fleet wave is told to sync and the rollout moves to `stage: "fleet"`. when every fleet machine has reported, it moves to `complete`.
- if more than 25% of the current wave has failed, the rollout moves to `aborted` with an `abortReason`.
- a canary that settles with more than 10% but no more than 25% failures, or machines that never report, leave the rollout at `canary`. a rollout that is not finished blocks new deploys of the same version (see `alreadyRunning` below); [resync](#resync) clears it.
- files land under the roost's `extractPath`, or `~/Documents/Owlette` when it is unset.

normal response (`202 Accepted`):

```json
{
  "rolloutId": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
  "versionId": "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92",
  "siteId": "site_kiosk_fleet",
  "roostId": "rst_lobby",
  "stage": "canary",
  "canary": ["kiosk-01"],
  "fleet": ["kiosk-02"],
  "extractRoot": "~/Documents/Owlette",
  "versionUrl": "https://owlette-prod-manifests.<account-id>.r2.cloudflarestorage.com/project-manifests/site_kiosk_fleet/rst_lobby/8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92.json"
}
```

- `rolloutId` is always the version ID: there is one rollout record per version, and deploying a version whose rollout is `complete` or `aborted` replaces that record.
- if the version's rollout is still `scheduled`, `canary` or `fleet`, the route answers `200` with that rollout's fields plus `alreadyRunning: true` and queues nothing.
- a dry run answers `200` with the planned fields plus `dryRun: true` and writes nothing. it reports `stage: "scheduled"` whenever `scheduleAt` is present.
- there is no compare-and-swap guard. `Idempotency-Key` is optional and behaves as on publish.
- errors specific to deploy: a roost with no current version and no `versionId`, or no machines to target, is `400 validation_failed`; an unknown `versionId` is `404 version_not_found`; a soft-deleted roost, or a version whose stored body location is missing, is `409 conflict`.

### scheduled rollouts

a `scheduleAt` more than 60 seconds in the future returns `202` with `stage: "scheduled"` and a `scheduled` object holding the resolved instant (`at`) and a `warning` that restates the timing below. the rollout is stored with its canary and fleet split, `versionUrl` and `extractRoot` already resolved. a scheduler sweep runs every 5 minutes, moves a due rollout to `stage: "canary"`, and queues the same sync commands an immediate deploy queues, so a scheduled rollout fires within 5 minutes of its instant and then follows the ordinary canary, fleet, complete path.

two cases do not fire:

- **missed window.** a rollout more than 30 minutes past its instant is written off instead of fired: it lands at `stage: "aborted"` with an `abortReason` saying how late it was. a stalled sweep must not push an overnight rollout to a whole fleet at midday. `aborted` is terminal, so deploying that version again starts a fresh rollout.
- **kill switch.** while roost is switched off for a site, its scheduled rollouts are left untouched, neither fired nor written off. when the switch flips back, a rollout still inside its window fires, and one more than 30 minutes late is written off.

the target list is the one resolved when the deploy was accepted, not the roost's `targets` at fire time. a scheduled rollout is not finished, so a second deploy of the same version answers `alreadyRunning: true` instead of rescheduling it.

## rollout status

```bash
curl -fsS "$OWLETTE_API_URL/api/roosts/rst_lobby/deployments?siteId=site_kiosk_fleet&page_size=20" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"

curl -fsS "$OWLETTE_API_URL/api/roosts/rst_lobby/deployments/8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92?siteId=site_kiosk_fleet" \
  -H "Authorization: Bearer $OWLETTE_API_KEY"
```

`GET /api/roosts/{roostId}/deployments` lists rollout records, newest first, in `rollouts` (repeated as `items`). `page_size` defaults to 20 with a maximum of 100. filter with `stage=scheduled`, `canary`, `complete` or `aborted` (`fleet` is not accepted as a filter and returns `400 validation_failed`). each item has `rolloutId`, `versionId`, `stage`, `canaryCount`, `fleetCount`, `extractRoot`, `versionUrl`, `triggeredBy`, `startedAt`, `completedAt`, `abortedAt`, `abortReason` and `scheduledAt`.

the list holds one record per version: publishes, deploys and rollbacks all write the record for their version, a later deploy of the same version replaces a finished one, and [resync](#resync) deletes it. `triggeredBy` is set only for deploys.

`GET /api/roosts/{roostId}/deployments/{rolloutId}` returns one record with its per-machine state:


## resync

resync tells every target machine to pull the current version again: the retry after a failed sync, or the reset for files someone edited by hand.

```bash
curl -fsS -X POST "$OWLETTE_API_URL/api/roosts/rst_lobby/resync" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "siteId": "site_kiosk_fleet" }'
```

- every target gets the sync at once, with no canary. the per-machine state is cleared and the rollout record for the current version is deleted.
- response (`200 OK`): `{ "resynced": 2, "targets": ["kiosk-01", "kiosk-02"] }`.
- a roost with no current version, or with no targets, is `409 conflict`.
- resync takes no `Idempotency-Key`; each call queues new sync commands.

## errors

errors use `application/problem+json`; branch on `code`. see [errors](/docs/api/errors).

| code | HTTP | meaning |
|---|---:|---|
| `validation_failed` | 400 | missing or invalid `siteId` or `roostId`, invalid JSON, invalid pagination, an invalid version body, a `description` over 500 characters, invalid `machines`, `targets` or `scheduleAt`, or nothing to deploy to. |
| `roost_name_required` | 400 | create without a non-blank `name`. |
| `version_ref_malformed` | 400 | a `{versionRef}`, `targetVersion` or `against` value is not an accepted form. |
| `version_content_immutable` | 400 | a version PATCH included a field other than `siteId` or `description`. |
| `rollback_no_op` | 400 | the rollback target is already the current version. |
| `unsupported_version` | 400 | the `Roost-Version` header names an unsupported date. |
| `idempotency_key_invalid` | 400 | the `Idempotency-Key` is longer than 255 characters. |
| `unauthorized` / `token_expired` | 401 | no valid credential, or an expired API key. |
| `forbidden` | 403 | your account is inactive, or a change needs the site admin or owner role. |
| `scope_insufficient` | 403 | the API key lacks the `roost=` or `site=` scope the route needs. |
| `not_found` | 404 / 410 | the site, roost or rollout does not exist or you cannot access it; rollback on a soft-deleted roost; `410` when a version's stored body is gone. |
| `version_not_found` | 404 | a version ref or `versionId` did not match this roost's history. |
| `conflict` | 409 | the roost ID already exists on create; update or deploy on a soft-deleted roost; deploy of a version whose stored body location is missing; resync with no current version or no targets. |
| `version_url_missing` | 409 | the rollback target has no stored body location. |
| `precondition_failed` | 412 | the publish lists chunks the site does not have; `missingChunks` holds up to 20 of them. |
| `version_stale` | 412 | `expectedCurrentVersionId` did not match the current pointer when the publish committed. |
| `idempotency_key_mismatch` | 422 | an `Idempotency-Key` was reused with a different body. |
| `service_unavailable` | 503 | roost is switched off for this site. |
| `internal_error` | 500 | unexpected server error; quote the `requestId`. |
