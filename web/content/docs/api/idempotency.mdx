<Callout type="warning" title={"route-specific support"}>

the header protects only the routes listed under [which routes honor it](#which-routes-honor-it). every other route ignores it, so sending it there does not make a retry safe. notably ignored: `POST /api/roosts`, `POST /api/chunks/upload-urls`, every `/api/keys` route, and `DELETE` on webhooks and processes.

</Callout>

## header

```http
Idempotency-Key: 7c55c5de-7ec6-4c63-a1c8-94e13c56f962
```

- the key is an opaque string you generate, up to 255 characters. surrounding whitespace is trimmed.
- generate one key per logical mutation, and reuse it for every retry of that identical request.
- generate a new key when the method, URL, query string, or body changes.
- UUIDv4, ULID, and deterministic hashes such as `bulk-<sha256(row)>` all work.

---

## replay semantics

a successful (`2xx`/`3xx`) response is cached for 24 hours. a later request replays it when all of these match:

- the authenticated user
- the API-key environment (`live`, `test`, or `unknown` for session and ID-token callers)
- the `Idempotency-Key`
- the HTTP method
- the path
- the query string
- the SHA-256 of the request body

a replay returns the original status, headers, and body without running the handler again, plus:

```http
Idempotent-Replayed: true
```

the same key with a different body on the same route is refused with `422 idempotency_key_mismatch`. the same key on a different route, or a different query string, does not collide — it is simply a new request.

error responses are never cached, so a retry after a `4xx` or `5xx` runs the handler again. `text/event-stream`, `application/x-ndjson`, and chunked responses are not cached either.

the hoot send stream is the exception to watch for: it is `text/plain`, which the cache does not treat as a stream, so a completed reply is cached like any other `200`. a retry of `POST /api/hoot/conversations/{conversationId}` with the same key and body replays the recorded reply rather than asking hoot again — use a fresh key for each new message.

## which routes honor it

### required

these return `400 idempotency_key_required` when the header is missing or blank:

| area | operations |
|---|---|
| machine commands | `POST /api/sites/{siteId}/machines/{machineId}/commands` |
| machines | `DELETE /api/sites/{siteId}/machines/{machineId}`; `POST` and `DELETE .../machines/{machineId}/uninstall`; `PUT` and `DELETE .../machines/{machineId}/display-layout` |
| processes | `POST .../machines/{machineId}/processes`; `POST .../processes/{processId}/start`, `/stop`, `/restart`, `/kill`, `/schedule`; `PATCH .../processes/{processId}/launch-mode` |
| installer deployments | `POST /api/sites/{siteId}/deployments`; `DELETE .../deployments/{deploymentId}`; `POST .../deployments/{deploymentId}/retry`, `/cancel`, `/uninstall` |
| logs | `DELETE /api/sites/{siteId}/logs` |
| installer releases | `POST` and `PUT /api/installer/upload`; `POST /api/installer/{version}/set-latest` |
| hoot | `POST /api/hoot/conversations`; `POST /api/hoot/conversations/{conversationId}` |

### optional

these replay when you send the header and run normally when you do not:

| area | operations |
|---|---|
| roost | `POST /api/roosts/{roostId}/versions` (publish); `PATCH .../versions/{versionRef}`; `POST /api/roosts/{roostId}/deploy`; `POST /api/roosts/{roostId}/rollback` |
| sites | `POST /api/sites`; `PATCH` and `DELETE /api/sites/{siteId}`; `POST /api/sites/{siteId}/transfer-ownership` |
| members | `POST /api/sites/{siteId}/members`; `PATCH` and `DELETE .../members/{uid}` |
| processes | `PATCH .../processes/{processId}` |
| talons | `POST /api/sites/{siteId}/talons`; `POST .../talons/reassign` |
| webhooks | `POST /api/webhooks`; `PATCH /api/webhooks/{webhookId}`; `POST .../rotate-secret`; `POST .../deliveries/{deliveryId}/retry` |
| users | `POST /api/users/bootstrap`; `DELETE /api/users/{uid}`; `POST .../promote`, `/demote`, `/assign-sites`, `/remove-sites` |
| hoot | `PATCH` and `DELETE /api/hoot/conversations/{conversationId}` |

the `/api/cortex/*` and `/api/chat/*` hoot aliases behave like the routes they alias. the [interactive reference](/docs/api) marks the header on each operation.

## errors

| status | code | cause | what to do |
|---|---|---|---|
| 400 | `idempotency_key_required` | the route requires the header and it is missing or blank | retry the same request with a generated key |
| 400 | `idempotency_key_invalid` | the key is longer than 255 characters | generate a shorter key |
| 422 | `idempotency_key_mismatch` | the key was used on this route within 24 hours with a different body | resend the original body, or use a new key for the changed request |

all three use the standard [problem envelope](/docs/api/errors).

## retry pattern

1. build the request body.
2. generate a key and attach it.
3. if the network fails, the client times out, or the API answers `429` or a transient `5xx`, retry the identical request with the same key.
4. if you change the body or the query, generate a new key.

```bash
IDEMPOTENCY_KEY="$(uuidgen)"

curl -fsS -X POST "$OWLETTE_API_URL/api/sites/$SITE_ID/machines/$MACHINE_ID/commands" \
  -H "Authorization: Bearer $OWLETTE_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $IDEMPOTENCY_KEY" \
  -d '{"type":"capture_screenshot","params":{"monitor":"primary"},"timeout_seconds":60}'
```

for batch importers, deterministic keys mean a rerun replays the rows that already succeeded instead of repeating them:

```text
Idempotency-Key: bulk-command-<sha256(canonical-row-json)>
```

remember the 24-hour window: a rerun a day later executes again.
