## agent won't connect to cloud

**symptoms**: the machine shows offline in the dashboard, and the agent's logs show connection errors.

**check**:

1. internet connectivity on the agent machine
2. firewall rules — outbound HTTPS (port 443) must be allowed to `owlette.app`, `dev.owlette.app`, `*.googleapis.com`, `*.firebaseio.com`, and the Cloudflare R2 endpoint used for roost chunks (usually `*.r2.cloudflarestorage.com`)
3. `service.log` for specific errors — `C:\ProgramData\Owlette\logs\` on Windows, `/Library/Application Support/Owlette/logs/` on macOS, `/var/lib/owlette/logs/` on Linux
4. that `firebase.enabled` is `true` in `config.json`
5. that `firebase.site_id` matches a site that exists in Firestore

**common errors**:

| log message | cause | fix |
|-------------|-------|-----|
| "Agent not authenticated" | missing or corrupt tokens | re-pair with a new phrase — see [agent troubleshooting](/docs/agent/troubleshooting#agent-not-authenticated-error) |
| "HTTP error 403" | Firestore rules blocking access | verify the security rules are deployed |
| "Token expired" | the refresh failed | check the refresh errors in the log, and re-pair if needed |
| "Connection refused" | a firewall or proxy | allow outbound HTTPS |

## dashboard shows machine offline

**symptoms**: the agent is running but the dashboard shows it offline.

1. **check the heartbeat age** — if the machine was last seen recently, it may have intermittent connectivity
2. **check the service** — `sc query OwletteService` on Windows (should show `RUNNING`), `launchctl print system/app.owlette.agent` on macOS, `systemctl status owlette-agent` on Linux
3. **check the ConnectionManager state** in the logs — look for `BACKOFF` or `DISCONNECTED`
4. **verify the site_id** — the agent and the dashboard must be looking at the same site
5. **check Firestore directly** — Firebase Console → Firestore → `sites/{siteId}/machines/{machineId}` → check the machine document's `online`, `lastHeartbeat`, `agent_version`, and `metrics` fields

## processes not auto-restarting

1. verify `launch_mode` is `always`, or `scheduled` with the current time inside a configured schedule window
2. check whether the `relaunch_attempts` limit was reached. on Windows the reboot prompt should appear; on macOS and Linux the dashboard shows the restart pending and nothing relaunches until an admin approves or dismisses it
3. verify `exe_path` exists on the machine — a missing executable shows as **failed** (`LAUNCH_FAILED`) once the entry has launched before, or `STOPPED` if it never has, and the agent logs the failed launch and raises an `exe_missing` alert. `INACTIVE` means the launch mode is `off`
4. on macOS and Linux, check that someone is signed in at the machine's screen — managed processes launch into the signed-in user's session, and with nobody signed in the agent waits
5. check the agent's logs for launch errors, and that the service is running and its main loop is executing (look for periodic log entries)

more in [process monitoring](/docs/agent/process-monitoring).

## process won't launch after an app upgrade

**symptoms**: a managed process shows **failed** on the dashboard and in the desktop app, or the dashboard shows an executable-missing toast after software was upgraded or installed side-by-side.

1. open the dashboard toast or the activity log entry with action `exe_missing`.
2. review the suggested paths. the agent scans nearby sibling directories for executables with the same filename.
3. use the toast's **use path** action, or open the process edit dialog manually and update the path.
4. save the process. if the launch mode is `always`, the agent launches it on the next monitoring pass. if it is `scheduled`, it launches when the next matching schedule window opens.
5. if no suggestion appears, browse the machine for the new executable path and update the process manually.

## OAuth token issues

### "agent not authenticated - no refresh token found"

the encrypted token file is missing or unreadable. re-pair the agent: delete `.tokens.enc` from the data root and run `configure_site.py` with the bundled Python. the config still names the site, so the script asks `reconfigure? (y/N)` first — answer `y`, since the default cancels, or pass `--add <phrase>` with a phrase generated in the dashboard, which skips the question and needs no authorizing. otherwise authorize the phrase the script prints, from any device. either way, restart the service once pairing succeeds. the exact commands for Windows, macOS and Linux are in [agent troubleshooting](/docs/agent/troubleshooting#agent-not-authenticated-error).

### token refresh failing

check `service.log` for refresh errors. common causes:

- **machine ID mismatch** — the machine was renamed since registration
- **token revoked** — an admin revoked the token from the dashboard
- **network issue** — the agent can't reach the refresh endpoint

## deployment stuck

**symptoms**: a deployment shows "downloading" or "installing" indefinitely.

1. check the agent's logs for download and install progress
2. verify the installer URL is reachable from the agent machine (test it in a browser)
3. check whether the installation timed out (default: 40 minutes)
4. for large installers on slow connections, the download may simply be slow
5. try cancelling and re-deploying

see [deployments](/docs/dashboard/deployments#troubleshooting).

## roost sync failed

1. **R2 configuration failed** — check the web runtime logs for a missing `R2_S3_ENDPOINT`, `R2_S3_ACCESS_KEY_ID`, or `R2_S3_SECRET_ACCESS_KEY`. the endpoint should be reachable from the web app and the agents over HTTPS.
2. **chunk upload or verification failed** — retry the upload from the roost page and confirm the agent machine can reach signed R2 URLs. a publish can fail if the version references chunks that were not uploaded or were rejected after hash verification.
3. **target fanout stalled** — check `sites/{siteId}/roosts/{roostId}/target_state/{machineId}`. current target states include `pending`, `downloading`, `assembling`, `committed`, `failed`, and `cancelled`.
4. **`sync_pull` stuck or failed** — check `service.log` on the target machine for `sync_pull` errors. if no target-state document appears, confirm the machine is online and has a pending command in `sites/{siteId}/machines/{machineId}/commands/pending`.
5. **permission denied** — the configured extract root may not be writable, or may be outside the agent's allowed extract roots.

## 2FA issues

### lost authenticator

if you also have a passkey on the account, sign in with it — a passkey clears 2FA on its own, no code needed.

otherwise use one of your **backup codes** at the 2FA prompt. each code can only be used once.

### no backup codes

ask a superadmin to run **reset 2FA** on your account from the admin users page (`POST /api/users/{uid}/mfa-reset`). it removes every second factor — authenticator app, passkeys, and the backup codes — re-arms mandatory 2FA setup, and revokes the account's trusted devices, so the next sign-in starts enrollment from scratch.

two things it deliberately does **not** do: it does not revoke Firebase refresh tokens, so a session the user already holds elsewhere stays signed in until it expires on its own; and superadmins cannot reset themselves, so a locked-out superadmin needs a different superadmin to do it.

because a reset hands the account to whoever signs in next, confirm who you're talking to before running one.

### code not working

- ensure your device's clock is synchronized (TOTP is time-based)
- codes expire every 30 seconds — enter the current one
- verify you're using the correct account in your authenticator app

### "verify a factor you already have" when adding one

adding a second factor to an account that already holds one requires the current session to have cleared a 2FA challenge — the route answers `403` with `mfa_challenge_required` otherwise. verify with your existing passkey, or take the **use a code instead** link to `/verify-2fa`, then add the new factor.

### can't regenerate backup codes

regeneration needs live proof in the same request: a current 6-digit code, an unused backup code, or your passkey. being signed in is not enough — a fresh sheet of recovery codes could otherwise be used to turn 2FA off entirely. if you have none of the three, that's the superadmin reset above.

### asked to set up 2FA again

you removed your last second factor. that's allowed, but the account immediately re-arms 2FA setup, so the dashboard sends you to `/setup-2fa` to enroll a new factor — a passkey or an authenticator app — before you can use it again. trusted devices are revoked at the same time.

## hoot not responding

1. **no LLM key configured** — check hoot settings for an API key
2. **invalid API key** — verify the key is correct and has credits
3. **machine offline** — hoot checks machine status before executing tools
4. **a tool is stuck** — a turn keeps running even if you reload the page (the chat reattaches to it), so you rarely lose work. if a tool call is taking too long, use the **cancel** control on its tool card to kill it, or **stop** the whole turn from the chat.
5. **rate limited** — the API may be rate-limiting requests

some hoot tools are Windows only; on a Mac or Linux machine they refuse rather than run. see the [hoot tools reference](/docs/reference/hoot-tools).

## email alerts not working

1. verify the `RESEND_API_KEY` environment variable is set in Railway
2. check that the Resend API key is valid
3. verify `CRON_SECRET` is configured for the health check cron
4. check that the cron-job.org schedule is set: `*/5 * * * *`
5. send a test email from admin panel → email test
6. check spam and junk folders

## dashboard performance issues

### slow loading

- **cold starts** (Railway Hobby plan) — upgrade to Pro for no cold starts
- **large dataset** — many machines and processes increase Firestore reads
- **bundle size** — check the `.next/static` output during a build

### real-time updates not working

- check the browser console for Firestore listener errors
- verify the Firebase config is correct
- try a hard refresh (ctrl+shift+r)
- check whether the Firestore quota has been exceeded

## debug mode

run the agent in the foreground for detailed console output: stop the service, then run `owlette_runner.py --debug` with the bundled Python as an administrator or root. on Windows:

```cmd
net stop OwletteService
cd /d C:\ProgramData\Owlette\agent\src
C:\ProgramData\Owlette\python\python.exe owlette_runner.py --debug
```

the macOS and Linux commands, and how to hand the machine back to the service afterwards, are in [debug mode](/docs/agent/troubleshooting#debug-mode).
