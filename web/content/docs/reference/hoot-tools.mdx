hoot offers the model the same 52 tools on every machine. the tier decides whether a call needs your approval; the machine's agent decides whether it can run there. for how chats use these tools, see [hoot](/docs/dashboard/hoot).

---

## tier system

| tier | type | approval | count |
|------|------|----------|-------|
| **1** | read-only | auto-approved | 16 |
| **2** | process and machine management | auto-approved | 25 |
| **3** | privileged | in-chat approval while the site's approval gate is on (the default) | 11 |

members and chat-scoped API keys are capped at tier 1. see [approving privileged (tier-3) actions](/docs/dashboard/hoot#approving-privileged-tier-3-actions).

> **server-side tools** (`get_site_logs`, `get_system_presets`, `deploy_software`, `update_process`, `add_process`, `delete_process`, `create_talon`, `list_talons`, `set_talon_enabled`, `schedule_followup`, `cancel_followup`) run in the Next.js server process and never go through the agent's command queue. talons are site-level records and follow-ups are chat records, so neither is ever relayed to a machine.

## platforms

the tool list is not filtered by operating system. a call to a tool the machine's platform does not implement comes back as a structured refusal rather than a failure:

```json
{
  "error": "unsupported_on_platform",
  "tool": "registry_operation",
  "platform": "darwin",
  "message": "registry_operation is implemented on windows only"
}
```

**Windows only.** these 13 tools answer `unsupported_on_platform` on macOS and Linux (`WINDOWS_ONLY_TOOLS` in `agent/src/mcp_tools.py`):

`configure_gpu_tdr`, `manage_windows_update`, `suppress_setup_screens`, `manage_notifications`, `configure_power_plan`, `manage_scheduled_task`, `network_reset`, `registry_operation`, `clean_disk_space`, `get_event_logs_filtered`, `manage_windows_feature`, `run_powershell`, `execute_script`

two more paths need the Windows user-session runner and are refused off Windows with an error that starts `unsupported_on_platform: user-session execution`: `run_python`, and `run_command` or `run_powershell` with `user_session: true`.

**on macOS and Linux, differently.** these run on all three platforms, with a macOS or Linux backend that behaves differently from Windows:

| tool | macOS | Linux |
|------|-------|-------|
| `get_event_logs` | the unified log through `log show`, over the last 1 to 10 minutes | the systemd journal through `journalctl` |
| `get_service_status` | a launchd label, through `launchctl list` | a systemd unit, through `systemctl show` |
| `manage_windows_service` | `launchctl`. `startup_type` takes `auto` or `disabled` only | `systemctl`. `startup_type` takes `auto`, `manual` (disable) or `disabled` (mask) |
| `check_pending_reboot` | an OS update prepared or a security response staged; reports when the last update installed | `/run/reboot-required`, written by a package upgrade |
| `get_gpu_processes` | per-process VRAM through `nvidia-smi` (compute processes only); without it the list is empty, with a note saying why | same as macOS |
| `show_notification` | shown by the owlette app; `style` and `duration_seconds` are ignored | same as macOS |
| `capture_screenshot` | taken by the owlette app, which needs the Screen Recording grant | not available yet: a Wayland session is refused, and on X11 the owlette app does not capture |
| `run_command` | its own allow-list, see [`run_command`](#run_command) | same as macOS |
| `manage_process` | its own never-kill list, see [tier 2 blocklists](#tier-2-blocklists) | same as macOS |

on macOS and Linux the agent runs as root with no display of its own, so `show_notification` and, on macOS, `capture_screenshot` are jobs for the owlette app running in the signed-in session. when the app is not running they return `desktop_not_running`. the [platform support](/docs/reference/platform-support) page covers the rest of the agent.

### check_pending_reboot

whether the machine is waiting on a reboot, and what is asking for it. on Windows the reasons come from Windows Update, Component Based Servicing, pending file rename operations and the SCCM client; on macOS from an OS update prepared or a security response staged; on Linux from `/run/reboot-required`, which a package upgrade writes. only something already installed or prepared counts — an update that is merely available is not a pending reboot.

read-only, for incident investigations, after a suspected update, or when a machine is behaving unusually. the agent also raises a site-level alert the first time it detects a pending reboot (once, tracked with a flag file).

| parameter | type | required | description |
|-----------|------|----------|-------------|
| _(none)_ | | | |

**returns**: `pending` (bool), `reasons` (array), `last_update_installed`, `next_scheduled_update`. off Windows, `next_scheduled_update` is always null, and on Linux so is `last_update_installed`.

### schedule_followup

schedule a follow-up turn on this conversation. at the scheduled time hoot is re-opened in the same chat with `note` as the instruction, acts on it, and reports back — the way a promise to "check back in ten minutes" actually happens, since a turn ends when the assistant stops typing. **server-side**: the follow-up is a chat record (`cortex-followups/{id}`, a data-at-rest name), acted on by the cron sweep and never relayed to a machine.

| parameter | type | required | description |
|-----------|------|----------|-------------|
| `note` | string | **yes** | what the follow-up turn should do, written as a self-contained instruction to hoot's future self — the conversation is not in view when it fires. max 1000 characters |
| `delay_minutes` | number | exactly one of `delay_minutes` / `at` | fire this many minutes from now: 1 to 10080 (one minute to seven days) |
| `at` | string | exactly one of `delay_minutes` / `at` | fire at this absolute ISO 8601 timestamp with a timezone offset (e.g. `2026-01-31T14:00:00Z`). must be in the future and within seven days |
| `watch_command_id` | string | no | ID of a machine command already dispatched in this conversation. the follow-up then fires as soon as that command finishes, or at its scheduled time, whichever comes first |

**returns**: `followup_id`, `fires_at` (ISO), and `watch_command_id` when one was passed. keep `followup_id` — `cancel_followup` needs it.

pass **exactly one** of `delay_minutes` and `at`. both, or neither, is rejected with `invalid_schedule` rather than silently picking a winner. out-of-range values return `invalid_delay_minutes`, `at_in_the_past`, or `at_too_far_out`.

**early fire.** `watch_command_id` is a shortcut, not a replacement for the schedule: the scheduled time stays the backstop. the sweep resolves the watched command from the machine's `commands/completed` document and treats only the terminal statuses (`completed`, `failed`, `error`, `cancelled`) as finished; the agent's non-terminal `running` marker does not fire it. a follow-up scheduled against more than one machine — a subset of a site, or a site-wide chat — has no single command whose finish means the work is done, so the ID is ignored there and the follow-up waits for its scheduled time.

**firing.** the follow-up pass rides the once-a-minute talons cron sweep (`/api/cron/talons`). each sweep scans the 25 soonest `scheduled` follow-ups and starts at most 10 turns; a backlog drains over the following minutes. an early fire is therefore only found while the follow-up sits inside that scan window — past it, the follow-up still fires at its own scheduled time.

**tier 3 always waits for a person inside a fired follow-up.** the turn runs with `forceTier3Approval`, which overrides the site's `requireTier3Approval` setting: a site that lets an operator auto-run tier 3 while they watch has not agreed to it running while nobody does. the model may still reach for a tier-3 tool; the turn simply parks at approval-requested until the owner comes back to the chat.

**where it fires.** a follow-up fires on the machines the scheduling turn was targeting, not on whatever the chat is pointed at when it comes due — the selection may have moved since the promise was made. a site-wide follow-up stays dynamic: a machine added in the meantime is included. the target is re-validated at fire time, so machines that have left the site, gone offline or had hoot switched off are dropped; if nothing is left, the follow-up is marked `failed` with the reason on the record rather than dispatched.

**other fire-time guarantees.** site access is re-resolved on every fire and never trusted from scheduling time, so a user removed or demoted in the meantime cannot keep driving tools through a promise they left behind. the chat must still exist and still belong to the same user (`chat_deleted` / `chat_owner_mismatch`). a follow-up never supersedes a live turn: if someone is mid-conversation the document goes back to `scheduled` and the next sweep retries.

**where it is not available.** the tool needs a user chat. unattended hoot (autonomous dispatch, talon directives) runs as a system actor with no chat to re-open and no user whose access could be re-resolved, and gets `followup_unavailable`. both follow-up tools are also **withheld from the public conversations API**: that surface's `chatId` is a `chat_conversations` ID while the sweep resolves `chats/{chatId}`, so a follow-up scheduled there could never fire (it would fail closed as `chat_deleted`). withholding the tools is deliberate — better no promise than one the sweep silently breaks.

### cancel_followup

cancel a scheduled follow-up before it fires, when the thing it was going to check has already been settled in the conversation, or when the operator asks for it to be dropped. **server-side**: reaches the same store helper as `DELETE /api/hoot/followups/{followupId}`, which is what the chip above the composer calls.

| parameter | type | required | description |
|-----------|------|----------|-------------|
| `followup_id` | string | **yes** | the ID returned by `schedule_followup`. never guessed |

ownership is enforced inside the store transaction (the Admin SDK bypasses `firestore.rules`, so that is the only gate every caller passes through): only the user who scheduled a follow-up can cancel it, and only while it is still `scheduled`. failures are `followup_not_found` (404), `followup_forbidden` (403, it belongs to another user), and `followup_not_scheduled` (409, it already fired or was cancelled — a cancel that loses the race with the sweep's claim lands here). like `schedule_followup`, it is unavailable to unattended hoot and withheld from the public conversations API.

## tier 2: process and machine management tools

these run immediately, without confirmation. the owlette process controls (`restart_process`, `kill_process`, `start_process`, `set_launch_mode`) wrap existing commands. the process config tools (`update_process`, `add_process`, `delete_process`) run server-side through the same validated actions as the dashboard, and the talon tools (`create_talon`, `list_talons`, `set_talon_enabled`) run server-side through the same store as the talon editor. the rest are purpose-built, with validated parameters and a narrower blast radius than a raw shell script.

|-----------|------|----------|-------------|

### capture_screenshot

capture a screenshot of the machine's desktop and return the image for visual analysis — to diagnose display issues, verify process state, or see what is on screen.

on macOS the owlette app takes it and needs the Screen Recording grant; a Mac whose app has reported the grant missing returns `screen_recording_not_granted`, and an app that is not running returns `desktop_not_running`. on a Mac, `monitor` is off by one from Windows: `0` captures only the main display rather than all of them, and `1` captures the second display.

on Linux, screen capture is not available yet. the agent refuses a Wayland session, Ubuntu's default, with `unsupported_on_platform` rather than return a black frame, and on an X11 session the owlette app answers `unsupported_job`.

| parameter | type | required | description |
|-----------|------|----------|-------------|
| `monitor` | number | no | `0` = all monitors combined (default), `1` = primary, `2` = second, etc. |

---

### manage_process

kill, suspend or resume OS processes by name pattern. works on **any** process, not only owlette-managed ones. safer than `run_command` plus `taskkill`: validated parameters, no shell, and a built-in list of critical processes it refuses to touch (see [tier 2 blocklists](#tier-2-blocklists)).

| parameter | type | required | description |
|-----------|------|----------|-------------|
| `name_pattern` | string | **yes** | process name (with `.exe` on Windows) or glob (e.g. `chrome.exe`, `FreeFileSync*`) |
| `action` | string | **yes** | `kill`, `suspend`, or `resume` |
| `match_exact` | boolean | no | exact match (default `true`) vs glob via fnmatch |
| `force` | boolean | no | for `kill`: force immediately (default `true`), else graceful first |

### manage_windows_service

service control in one call. on Windows it has `services.msc` parity: start, stop, restart, pause/continue, set the startup type, configure failure recovery, or get full details. `set_recovery` configures auto-restart on crash (critical for unattended media installations); `get_details` returns status, startup type, binary path, dependencies and recovery config at once.

on macOS (`launchctl`) and Linux (`systemctl`) the name stays the same and the tool gains those backends, with `start`, `stop`, `restart`, `set_startup` and `get_details` only; `pause`, `continue` and `set_recovery` are refused. macOS knows only `auto` and `disabled` startup types. on Linux `manual` disables the unit and `disabled` masks it.

| `startup_type` | string | for `set_startup` | `auto`, `auto_delayed`, `manual`, `disabled` |
| `first_failure` | string | for `set_recovery` | `restart`, `run_program`, `reboot`, `none` |
| `second_failure` | string | for `set_recovery` | same options as `first_failure` |
| `subsequent_failures` | string | for `set_recovery` | action on third and later failures |

| `reboot_message` | string | no | broadcast message if the action is `reboot` |
| `run_program_path` | string | if any action is `run_program` | program to run on failure |

### create_talon

create a talon on this site — a saved automation of trigger, optional condition and outputs. see [talons](/docs/dashboard/talons) for the product-level picture. **server-side**: talons are site-level records written through the same store as the dashboard editor, never relayed to a machine.

**confirm before calling.** a talon runs unattended against real machines, so hoot is told never to call this from a vague request: it states back the exact talon it intends to create — trigger, condition, every output, the machines in scope, the cooldown — and waits for the operator to confirm.

| parameter | type | required | description |
|-----------|------|----------|-------------|
| `name` | string | **yes** | short lowercase name shown in the dashboard, 80 characters or fewer |
| `trigger` | object | **yes** | what makes the talon fire — one of the four shapes below |
| `outputs` | array | **yes** | 1 to 5 output entries, run in order |
| `description` | string | no | lowercase note about what the talon is for, 500 characters or fewer |
| `condition` | object | no | gate evaluated after the trigger fires. defaults to `{"type":"none"}` |
| `scope` | object | no | `{"machineIds":["..."]}`. omit for every machine in the site |
| `cooldownMinutes` | number | no | minimum minutes between runs, 0-1440 (default: 60) |
| `enabled` | boolean | no | whether the talon is armed as soon as it is created (default: true) |

**trigger shapes** (exactly one form):

```json
{"type": "schedule", "entries": [{"id": "e1", "days": ["mon", "wed"], "time": "09:00"}]}
{"type": "schedule", "intervalMinutes": 30}
{"type": "threshold", "metric": "cpu_percent", "operator": ">", "value": 90}
{"type": "event", "eventTypes": ["process_crash", "machine_offline"], "delayMinutes": 2}
```

- **schedule / entries**: 24-hour `HH:MM` in the site's timezone, up to 50 entries. `entries` and `intervalMinutes` are mutually exclusive.
- **schedule / intervalMinutes**: 5 to 1440 minutes, but 15 minutes minimum when the condition is a `visual_check`.
- **threshold**: metrics `cpu_percent`, `memory_percent`, `disk_percent`, `gpu_percent`, `cpu_temp`, `gpu_temp`, `network_latency`, `network_packet_loss`; operators `>`, `<`, `>=`, `<=`. threshold talons ride the existing alert pipeline: one fires when an alert rule fires and the breach matches the talon's own metric, operator and bound — so a threshold talon does nothing until a matching alert rule exists.
- **event**: `process_crash`, `machine_offline`, `process_start_failed`, `process_restarted`, `exe_missing`, and the `display_*` events. event triggers only: `delayMinutes` (0-1440) waits that long after the event before running, e.g. letting a restarted app finish booting before a `visual_check` looks at it.

**condition**: `{"type":"none"}` (default), or `{"type":"visual_check","expectation":"the lobby wall is playing the loop, not showing a desktop","monitor":0}`, which captures a fresh screenshot and asks a vision model whether the expectation holds. `expectation` is 500 characters or fewer; `monitor` is `0` for all displays combined, `1` for primary. a visual check needs a machine that can take a screenshot, which a Linux machine cannot yet (see [`capture_screenshot`](#capture_screenshot)).

**output entries**: each entry is an object keyed by `type`:

| field | applies to | description |
|-------|------------|-------------|
| `type` | all | `email`, `webhook`, `cortex`, or `command` |
| `url` | `webhook` | an HTTPS URL. private, loopback and link-local addresses are rejected (DNS-resolving SSRF check at authoring time, re-validated at send time) |
| `directive` | `cortex` | what hoot should do when the talon fires, 1000 characters or fewer |
| `commandType` | `command` | `restart_process`, `start_process`, or `stop_process` |
| `processName` | `command` | the configured process name to act on |
| `processId` | `command` | the configured process ID, when hoot already holds it |

`type: "cortex"` **is** the hoot output. the wire literal is a deliberate survivor of the cortex → hoot rename: it is persisted on every talon and every talon-run summary, and the MCP tool schema is itself a published contract. every label a person reads says `hoot`. see `web/lib/hoot/WIRE_NAMES.md` class B.

**refusals.** a `command` output takes the same privilege as issuing the command by hand — site admins only, refused with `command_output_forbidden` (403) in the tool and again in the store. a `visual_check` condition or a `cortex` output spends the talon author's own LLM key, so authoring one without a saved key returns `llm_key_required` (400). more than 20 talons on the site returns `talon_limit_reached` (409). validation rejects unknown top-level fields outright, so the model can never stamp a server-owned field onto the document; field-level failures come back as `invalid_talon` with `field_errors` rather than throwing and taking the turn down.

**returns**: `talon_id`, `name`, `enabled`, `next_run_at`.

unattended hoot cannot call this tool. authoring a talon is standing fleet policy that outlives the incident, so `create_talon` is left out of the autonomous investigator's tool list regardless of tier.

### run_python

**Windows only.** run Python code on the machine in the signed-in user's desktop session.

| parameter | type | required | description |
|-----------|------|----------|-------------|
| `code` | string | **yes** | Python code to run |

**sandboxed execution** (since v2.6.5). code from this tool runs with:

- **restricted `__builtins__`**: `eval`, `exec`, `compile`, `globals`, `locals`, `breakpoint`, `input`, `exit` and `quit` are removed. `open`, `print`, `getattr`/`setattr`, and common types and exceptions remain.
- **gated imports**: only a curated subset of the standard library can be imported: `math`, `json`, `re`, `datetime`, `time`, `random`, `collections`, `itertools`, `functools`, `operator`, `string`, `textwrap`, `decimal`, `fractions`, `statistics`, `copy`, `pprint`, `base64`, `hashlib`, `hmac`, `struct`, `io`, `csv`, `pathlib`, `typing`, `dataclasses`, `enum`, `abc`. dangerous modules — `os`, `subprocess`, `shutil`, `ctypes`, `socket`, and third-party packages like `psutil` or `mss` — raise `ImportError` with guidance to use `execute_script` or `run_command` instead.
- **no filesystem access beyond `output_dir`**: the code can `open()` files it writes into the provided `output_dir` variable, but cannot reach the rest of the filesystem without a gated import.

the model **cannot** escape this sandbox. internal first-party callers (e.g. the agent's own screenshot capture in `agent/src/session_exec.py`) pass `trusted=True`, which restores full builtins and unrestricted imports; that flag is not reachable from the tool schema the model sees.

**returns**: stdout from `print()`, plus any files written to `output_dir`.

```
  |
  +-- tier 3: pause for in-chat approval (when the per-site approval gate is on)
  |     +-- user approves: continue to the tool-name execution path
  |     +-- user denies: return "denied by user"
  |
  +-- server-side tools
  |     +-- get_site_logs / get_system_presets query Firestore on the web server
  |     +-- deploy_software creates deployment records and install commands server-side
  |     +-- update_process / add_process / delete_process call process action functions server-side
  |     +-- create_talon / list_talons / set_talon_enabled call the talon store server-side
  |     +-- schedule_followup / cancel_followup write the chat's follow-up records;
  |         the once-a-minute cron sweep fires them, with tier 3 forced to wait
  |         for approval and site access re-resolved at fire time
  |
  +-- legacy command-mapped tools
  |     +-- write existing command types such as restart_process or reboot_machine
  |     +-- the agent handles the command and writes completion state
  |
  +-- Firestore mcp_tool_call tools
        +-- create an mcp_tool_call command in Firestore
        +-- the agent receives and runs the tool, or refuses it with
        |   unsupported_on_platform on a platform without that tool
        +-- the agent writes the result to the completed queue
        +-- the turn runner polls for the result (bounded by the tool's own timeout)
```

the turn runs server-side, **detached from the browser connection**: it keeps running and its results still land in the chat if the connection drops or the page reloads, and the client reattaches to stream it. long-running shell tools (`run_command`, `run_powershell`, `execute_script`) can be **cancelled** from their tool card mid-flight: the agent kills the process tree and the card resolves to "cancelled by user". the whole turn can be **stopped** server-side from the chat.

### command allowlists

`run_command` enforces its allow-list on the **agent side**: even if a command reaches the machine through Firestore, the agent rejects it unless the first word is on the list. `run_powershell` has **no** allow-list — it accepts arbitrary PowerShell, with accountability from mandatory audit logging (site events feed and local `[MCP-AUDIT]` log). `run_python` enforces its sandbox on the agent side; the model cannot lift the import gate or restore blocked builtins.

### tier 2 blocklists

tier-2 tools carry per-tool blocklists so hoot cannot cause its own outage:

- `manage_process`: critical processes cannot be killed. on Windows that is lsass, winlogon, csrss, services, dwm, svchost and the other session processes, plus owlette's own service, host and Python processes. on macOS and Linux it is `init`, `systemd`, `systemd-logind`, `systemd-journald`, `dbus-daemon`, `sshd`, `launchd`, `loginwindow`, `WindowServer`, `SystemUIServer`, and owlette's own `owlette-desktop`, `owlette-host`, `python` and `python3`
- `registry_operation`: the SAM, SECURITY and Cryptography hives are unreachable; only an allowlist of safe key prefixes is permitted
- `manage_windows_feature`: core Windows features owlette depends on (NetFx4, WMI-\*, PowerShell\*) cannot be removed
- `create_talon`: `command` outputs are site-admin only, and webhook URLs that resolve to private, loopback or link-local addresses are rejected

agent-run tier-2 tools write a structured `[MCP-AUDIT]` log entry for each call. server-side process config tools use the process mutation audit path with actor `cortex:user_<userId>`. talon tools write `talon_mutated` rows with the same actor, `via: "cortex"`, and the originating chat ID. the follow-up tools write no mutation row of their own — the follow-up document is the record, and the `DELETE /api/hoot/followups/{followupId}` route behind the composer chip audits its own cancels as `chat_mutated` / verb `cancel_followup`.

### agent-side limits

- **subprocess timeout**: 25 seconds (the default; `execute_script` takes its own, up to 3300)
- **max output size**: 50,000 characters each for stdout and stderr
- **screenshot max size**: 10 MB
