## step 1: create the Firebase project

1. open the [Firebase Console](https://console.firebase.google.com/).
2. select **add project**.
3. name the project, for example `owlette-prod` or `owlette-dev`.
4. disable Google Analytics unless you need it.
5. finish creating the project and open **project settings**.
6. under **usage and billing**, move the project to the **Blaze** plan. Cloud Functions cannot be deployed without it, and owlette depends on them.

use a separate Firebase project for each environment. owlette itself runs one for dev and one for production, named as aliases in `.firebaserc`.

---

## step 2: create the Firestore database

1. in the Firebase Console, open **Firestore Database**.
2. select **create database**.
3. choose **start in production mode**. the repository rules are deployed in step 7.
4. pick the location closest to the operators and machines you manage.
5. select **enable**.

do not create collections by hand. owlette creates its documents through the dashboard, the API routes, the agents and trusted server code.

---

## step 3: enable authentication

1. open **Authentication**.
2. select **get started**.
3. enable these sign-in providers:
   - **email/password**
   - **Google**, if you want Google sign-in on the dashboard
4. in **Authentication → settings → authorized domains**, add every hostname that serves the dashboard: the production domain, any staging domain, and the standby origin's hostname if you run [failover](/docs/setup/web-deployment#failover-behind-a-cloudflare-load-balancer).

passkeys use Firebase custom tokens minted by the owlette server, so there is no provider to switch on for them. their relying party is fixed in code; see [what is tied to owlette.app](/docs/setup) before you rely on them on your own domain. password sign-up and password reset also need a Cloudflare Turnstile widget, which is configured in the [environment variables](/docs/setup/environment-variables), not in Firebase.

---

## step 4: enable Firebase storage

Firebase Storage holds installer binaries, screenshots, chat images and profile photos.

1. open **Storage**.
2. select **get started**.
3. start in production mode.
4. keep the default bucket unless you have a reason to use another one.

the bucket name becomes `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`. new projects use `<project-id>.firebasestorage.app`; older ones may use `<project-id>.appspot.com`. copy the exact value from the web app configuration in the next step.

---

## step 5: create a web app and copy client config

1. open **project settings → general**.
2. under **your apps**, select **add app → web**.
3. register the app, for example `owlette dashboard`.
4. copy the config values into the web deployment's environment:

```dotenv
NEXT_PUBLIC_FIREBASE_API_KEY=...
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN=your-project.firebaseapp.com
NEXT_PUBLIC_FIREBASE_PROJECT_ID=your-project-id
NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET=your-project.firebasestorage.app
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=123456789012
NEXT_PUBLIC_FIREBASE_APP_ID=1:123456789012:web:abc123
```

these values are public browser configuration. access control comes from Firebase Auth, the Firestore and Storage rules, and server-side authorization.

---

## step 6: create service account credentials

owlette's server routes use the Firebase Admin SDK for privileged work: verifying sessions, minting agent custom tokens, writing server-only collections and signing Storage uploads.

1. open **project settings → service accounts**.
2. select **generate new private key**.
3. download the JSON file.
4. copy three of its fields into separate server-side environment variables:

| JSON field | environment variable |
|------------|----------------------|
| `project_id` | `FIREBASE_PROJECT_ID` |
| `client_email` | `FIREBASE_CLIENT_EMAIL` |
| `private_key` | `FIREBASE_PRIVATE_KEY` |

```dotenv
FIREBASE_PROJECT_ID=your-project-id
FIREBASE_CLIENT_EMAIL=firebase-adminsdk-xxxxx@your-project-id.iam.gserviceaccount.com
FIREBASE_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n"
```

<Callout type="error" title={"keep the service account private"}>

never commit the downloaded JSON file or the private key. on Railway and similar hosts, wrap `FIREBASE_PRIVATE_KEY` in double quotes and keep the `\n` escape sequences; `web/lib/firebase-admin.ts` turns them back into newlines.

</Callout>

the web code reads only these three split variables; there is no single-JSON variable.

## step 7: deploy rules and indexes

install firebase-tools 15 and run these from the repository root, so `firebase.json` finds `firestore.rules`, `firestore.indexes.json` and `storage.rules`:

```bash
npm install -g firebase-tools@15
firebase login
firebase use --add
firebase deploy --only firestore:rules,firestore:indexes --project <alias>
firebase deploy --only storage --project <alias>
```

`firebase use --add` registers your project under an alias. pass `--project` on every deploy rather than trusting the active alias: owlette's own `.firebaserc` defaults to its dev project, so a deploy with no flag can land in the wrong one and still report success.

| file | purpose |
|------|---------|
| `firestore.rules` | Firestore client access rules |
| `firestore.indexes.json` | composite indexes for chat, logs, audit logs, talons, webhooks, API keys and swoop sessions |
| `storage.rules` | Firebase Storage access rules |

<Callout type="warning" title={"indexes are required"}>

do not skip `firestore:indexes`. features that query conversation history, autonomous events, logs, audit records, talon runs, webhooks or swoop sessions fail with a "requires an index" error until the composite indexes are built, and building takes a few minutes after the deploy returns.

</Callout>

see [Firestore rules](/docs/setup/firestore-rules) for how the rules are structured and how to test them.

## step 8: deploy cloud functions

`functions/` holds the Cloud Functions owlette depends on: deployment status, roost fan-out and chunk verification, upload quotas, metrics history and threshold alerts, talon event taps, webhook dispatch, the audit log, and the daily sweeps. nothing deploys them on a push.

1. create `functions/.env.<project-id>` from `functions/.env.example`. the file is gitignored and lives only on the machine you deploy from.
2. set `CORTEX_INTERNAL_SECRET` to the same value as the web app's, the three `R2_S3_*` values, `ROOST_ENV` (`prod` or `dev`), and `API_BASE_URL` to your web app's `https://<your-app>/api`. without `API_BASE_URL` the functions call `owlette.app`, or `dev.owlette.app` when the project ID contains `dev`.
3. deploy:

```bash
cd functions && npm ci && cd ..
FUNCTIONS_DISCOVERY_TIMEOUT=120 firebase deploy --only functions --project <alias>
```

the deploy builds the TypeScript first (the `predeploy` step in `firebase.json`). raise `FUNCTIONS_DISCOVERY_TIMEOUT` as shown: the CLI's 10-second default for loading the functions routinely runs out on a developer machine, and the deploy stops with `User code failed to load` before changing anything. scheduled functions get their Cloud Scheduler jobs as part of this deploy.

<Callout type="warning" title={"a missing env file fails silently"}>

a deploy without `functions/.env.<project-id>` still succeeds. the functions then run without `CORTEX_INTERNAL_SECRET`, and talons that react to display or process events, and threshold alerts, stop firing with no error anywhere. check the file exists before every functions deploy.

</Callout>

## step 9: deploy the web app with Firebase env vars

add every variable from steps 5 and 6 to the web app's environment, then deploy it. Firebase setup is not complete until the running web app has both:

- the `NEXT_PUBLIC_FIREBASE_*` client variables
- the `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL` and `FIREBASE_PRIVATE_KEY` server variables

see [environment variables](/docs/setup/environment-variables) and [web deployment](/docs/setup/web-deployment) for the rest: session and encryption secrets, Turnstile, email, rate limiting, cron, hoot, swoop and R2.

## step 10: bootstrap the first superadmin

new accounts are created as `member` with no site access. promote the first platform operator by hand after they sign in once:

1. open the deployed dashboard.
2. register or sign in with the first operator's account.
3. in the Firebase Console, open **Firestore Database → data → users →** `{uid}` for that account.
4. change `role` from `"member"` to `"superadmin"`.
5. save, then sign out and back in to refresh the dashboard session.

once a superadmin exists, use **admin panel → user management** to promote other users, and give people access to a site from that site's members.

## access model summary

owlette enforces site-scoped access in the Firestore rules and in server-side API authorization.

roles are **per site**. a person's role on one site says nothing about their role on another, and their account-level role grants nothing on any site.

| per-site role | access |
|------|--------|
| `member` | read-only on that site: view machines, capture screenshots, open live view, and watch a [swoop](/docs/dashboard/swoop) session when the site allows members to watch |
| `admin` | write access on that site: commands, configuration, deployments, roosts, talons, webhooks, membership, machine enrollment, and swoop control and settings |
| `owner` | everything `admin` can do, plus deleting the site and transferring ownership |

access is granted by a `sites/{siteId}/members/{uid}` document with `status: "active"`. account-level roles are separate:

| account role | meaning |
|------|--------|
| `member` | the default. reaches only the sites it holds member rows for |
| `admin` | a platform tier. grants **nothing** on a site without a member row |
| `superadmin` | platform admin, with implicit access to every site |
| `agent` | custom-token access to one site and one machine |

the client rules name the helpers `isSuperadmin()`, `isSiteAdmin(siteId)`, `canAccessSite(siteId)`, `isServiceAccount()` and the agent claim helpers. trusted server routes and the Admin SDK handle server-only collections and control-plane writes.

## verification checklist

- email/password login works, and Google login if you enabled it.
- a signed-in user's `users/{uid}` document exists.
- the first operator has `role: "superadmin"`.
- `firebase deploy --only firestore:rules,firestore:indexes` and `firebase deploy --only storage` completed, and every index shows **enabled** under **Firestore → indexes**.
- `firebase deploy --only functions` completed, with `functions/.env.<project-id>` in place.
- the web deployment has every `NEXT_PUBLIC_FIREBASE_*` and Firebase Admin variable.
- the dashboard can create and open a site without permission errors.
- installer upload, screenshot capture, chat image upload and profile photo upload reach Firebase Storage.

## troubleshooting

### cannot find the rules tab

create the Firestore database first. the console shows **data**, **rules**, **indexes** and **usage** only once it exists.

### permission denied in the dashboard

1. confirm the user is signed in.
2. confirm `users/{uid}` exists.
3. confirm the user has an active member row at `sites/{siteId}/members/{uid}` for the site, or is a superadmin. the older `users/{uid}.sites` array is still written, but no rule reads it.
4. confirm the rules were deployed from `firestore.rules`, to the right project.
5. try the same path and auth claims in the Firebase rules playground.

### admin features fail but the app loads

check the server-side Firebase Admin variables: `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL` and `FIREBASE_PRIVATE_KEY`. admin routes can fail while browser login works, because login only proves the `NEXT_PUBLIC_FIREBASE_*` client variables are present.

### storage upload fails

1. confirm Firebase Storage is enabled.
2. confirm `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET` matches the bucket in the Firebase Console.
3. confirm `storage.rules` was deployed with `firebase deploy --only storage`.
4. confirm the caller has the role the upload path requires.
