## why self-host?

- **data sovereignty**: app data stays in your own Firebase project, and roost content in your own Cloudflare R2 buckets
- **custom domain**: the dashboard runs on your own URL
- **full control**: change the codebase, add features, integrate it with your infrastructure
- **development**: contribute to owlette or build on top of it

## what you'll need

| requirement | purpose |
|-------------|---------|
| **Firebase project** on the Blaze plan | Authentication, Firestore, Firebase Storage, and the Cloud Functions in `functions/`, which need Blaze to deploy |
| **Cloudflare account** | R2 buckets for roost content, a Turnstile widget for sign-up and password reset, and optionally the swoop signalling worker, a TURN key and the failover load balancer |
| **web host** | Railway, Vercel or any Node.js 22 host for the Next.js app in `web/` |
| **Node.js 22.x** and npm 10 | web builds, Cloud Functions and local tooling. `firebase-admin` 14 requires `node >=22` |
| **firebase-tools 15.x** | deploying rules, indexes and functions. 13.x cannot run the functions emulator |
| **Upstash Redis** | distributed API rate limiting |
| **Resend** | alert, welcome and API-key-expiry email |
| **an HTTP scheduler** | the scheduled endpoints: offline detection, alert digests, talons, retention and more. owlette's own run on cron-job.org |
| **machines to manage** | Windows 10 or later, macOS 15 or later on Apple silicon, or Ubuntu 24.04 |

## setup sequence

1. [Firebase setup](/docs/setup/firebase): create the project, enable Authentication, Firestore and Storage, and generate service-account credentials.
2. **Cloudflare R2**: run `node scripts/provision-r2.mjs` to create the four roost buckets (`owlette-{prod,dev}-{content,manifests}`) and the content buckets' CORS rules. it reads `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_R2_API_TOKEN` from `.claude/.env.local`, and `--verify-only` checks without changing anything. then, in the Cloudflare dashboard under **R2 → manage R2 API tokens**, mint an S3 access key with object read and write on the four buckets.
3. **Cloudflare Turnstile**: add a widget covering your dashboard hostnames. without its secret, production refuses every sign-up and password reset.
4. [environment variables](/docs/setup/environment-variables): collect the Firebase client and admin values, session and encryption secrets, R2, Turnstile, Upstash, email, cron and, for swoop, its signing keys.
5. [Firestore rules](/docs/setup/firestore-rules): deploy the repository's Firestore rules and indexes and the Storage rules.
6. [Cloud Functions](/docs/setup/firebase#step-8-deploy-cloud-functions): deploy `functions/` with its own env file. talons, threshold alerts, deployment status and roost fan-out run there.
7. [web deployment](/docs/setup/web-deployment): deploy the Next.js app and attach the environment variables.
8. [scheduled endpoints](/docs/setup/web-deployment#scheduled-endpoints): register every scheduled route, in every environment.
9. [first superadmin](/docs/setup/firebase#step-10-bootstrap-the-first-superadmin): sign in once, then promote the first operator in Firestore.
10. [swoop](/docs/setup/web-deployment#the-swoop-signalling-worker), optional: deploy the signalling worker in `infra/swoop-signal` with its secrets, and set the swoop variables on the web app. swoop stays off until a site turns it on.
11. **agents**: build installers that point at your instance (below), then [install and pair](/docs/agent/installation) them.

## what is tied to owlette.app

a few values name the hosted service in code rather than in configuration. change them in your fork before you rely on the matching feature:

| what | where | effect if left alone |
|------|-------|----------------------|
| the agent's server | `get_api_base_url`, `get_project_id` and `get_web_host` in `agent/src/shared_utils.py`, with the host names in `agent/src/configure_site.py`, `agent/owlette_installer.iss` and `desktop/src/lib/environment.ts` | the agent only ever talks to `owlette.app` or `dev.owlette.app` and their Firebase projects, and ignores any other `api_base` in its `config.json`, so it never sends its tokens to a host it does not know. build your own installers after changing them |
| passkeys | `getRpId` and `getExpectedOrigins` in `web/lib/webauthn.server.ts` | in production the relying party is `owlette.app`, so passkeys fail on any other domain. authenticator-app codes work everywhere |
| R2 CORS origins | `CORS_ALLOWED_ORIGINS` in `scripts/provision-r2.mjs` | browser uploads to roost fail CORS from your domain. add it and re-run the script |
| Cloud Functions callback URL | `API_BASE_URL` in `functions/.env.<projectId>` | unset, functions call `dev.owlette.app` when the project ID contains `dev` and `owlette.app` otherwise |
| swoop signalling hostnames | `routes` in `infra/swoop-signal/wrangler.toml` | the worker deploys to `signal.owlette.app` and `signal-dev.owlette.app` |

## storage responsibilities

Firebase and R2 serve different parts of the system:

| storage service | used for |
|-----------------|----------|
| **Firestore** | sites, members, users, machines, commands, settings, audit and activity data, and agent state |
| **Firebase Storage** | installer binaries, screenshots, chat images and profile photos |
| **Cloudflare R2** | roost content chunks, immutable version bodies, signed upload and download URLs |

for the complete variable inventory, use [environment variables](/docs/setup/environment-variables). for host configuration, failover and the scheduled jobs, use [web deployment](/docs/setup/web-deployment).
