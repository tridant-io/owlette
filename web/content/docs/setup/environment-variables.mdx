the canonical list of keys lives in `scripts/env-manifest.json`: names, which deployment each key belongs on, and notes, never values. `node scripts/sync-env.mjs check` compares that list with what each deployment actually holds. this page explains what the keys do.

<Callout type="warning" title={"must match"}>

when two origins serve the same site, as a primary and a failover origin do, seven secrets must be byte-identical on both: `SESSION_SECRET`, `MFA_ENCRYPTION_KEY`, `LLM_ENCRYPTION_KEY`, `TURNSTILE_SECRET`, `SWOOP_JWT_PRIVATE_KEY`, `SWOOP_SESSION_MASTER_KEY` and `SWOOP_SIGNAL_RING_SECRET`. a mismatch fails silently, and only on the origin that differs: people are signed out, second factors stop verifying, stored LLM keys stop decrypting, or swoop sessions break.

</Callout>

## Firebase client (required)

these reach the browser. Next.js inlines every `NEXT_PUBLIC_` value into the bundle at build time, so changing one needs a rebuild.

| variable | example | source |
|----------|---------|--------|
| `NEXT_PUBLIC_FIREBASE_API_KEY` | `AIzaSy...` | Firebase console → project settings → web app |
| `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN` | `my-project.firebaseapp.com` | same |
| `NEXT_PUBLIC_FIREBASE_PROJECT_ID` | `my-project-id` | same |
| `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET` | `my-project.appspot.com` | same |
| `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID` | `123456789012` | same |
| `NEXT_PUBLIC_FIREBASE_APP_ID` | `1:123:web:abc` | same |

<Callout type="info">

these values are public by design: the Firebase client SDK runs in the browser. Firestore security rules enforce access, not the secrecy of these values.

</Callout>

`NEXT_PUBLIC_FIREBASE_APPCHECK_SITE_KEY` is optional. App Check stays off until it is set, and it is never used against the emulators.

`FIREBASE_STORAGE_BUCKET` is a server-side fallback that is read only when `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET` is unset. you do not need it.

## Firebase admin (required)

server-side only: verifying sessions, minting agent tokens and every server-mediated write. use the three separate variables, not a JSON blob.

| variable | format | source |
|----------|--------|--------|
| `FIREBASE_PROJECT_ID` | `my-project-id` | Firebase console → project settings → general |
| `FIREBASE_CLIENT_EMAIL` | `firebase-adminsdk-xxx@my-project.iam.gserviceaccount.com` | Firebase console → service accounts → generate key |
| `FIREBASE_PRIVATE_KEY` | `"-----BEGIN PRIVATE KEY-----\n..."` | same; keep the `\n` escape sequences |

<Callout type="warning">

when you set `FIREBASE_PRIVATE_KEY` on Railway, wrap the value in double quotes and keep the `\n` escapes exactly as Firebase exported them.

</Callout>

`web/lib/firebase-admin.ts` reads the three variables above. nothing reads `FIREBASE_SERVICE_ACCOUNT_KEY`; leave it unset.

## sessions and second factors (required)

| variable | format | what it does |
|----------|--------|-------------|
| `SESSION_SECRET` | 32+ character string | encrypts the iron-session HTTPOnly cookie. changing it signs everyone out |
| `MFA_ENCRYPTION_KEY` | 32+ character string | encrypts the TOTP secrets stored in Firestore. changing it locks every authenticator-app user out of their second factor |

both are must-match. generate a value:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

## bot protection (required in production)

sign-up and password reset are behind a Cloudflare Turnstile check.

| variable | what it does |
|----------|-------------|
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | the widget's site key. public, and the same on every origin |
| `TURNSTILE_SECRET` | the server-side verification secret. must-match |
| `TURNSTILE_HOSTNAMES` | comma-separated hostnames a passing check may come from, such as `owlette.app`. never include `localhost` in production |

in production, a missing `TURNSTILE_SECRET` refuses every sign-up and password reset with `403`, and an empty `TURNSTILE_HOSTNAMES` fails every check. outside production, a missing secret lets the check pass, so local development works without one.

| variable | what it does |

## Cloudflare R2 (required for roost)

the roost upload, chunk-check and version-body routes use Cloudflare R2 through its S3-compatible API, read in `web/lib/r2Client.server.ts`.

| variable | format | what it does |
|----------|--------|-------------|
| `R2_S3_ENDPOINT` | `https://<account-id>.r2.cloudflarestorage.com` | the S3-compatible endpoint, which is also where the account ID is set |
| `R2_S3_ACCESS_KEY_ID` | R2 access key ID | an R2 token with object read and write on the owlette buckets |
| `R2_S3_SECRET_ACCESS_KEY` | R2 secret access key | the matching secret |
| `ROOST_ENV` | `prod` or `dev` | picks the bucket pair. set it on every production origin |

bucket names are not variables. `bucketFor()` derives them from the roost environment:

| roost env | content bucket | manifests bucket |
|-----------|----------------|------------------|
| `prod` | `owlette-prod-content` | `owlette-prod-manifests` |
| `dev` | `owlette-dev-content` | `owlette-dev-manifests` |

without `ROOST_ENV`, the code picks `prod` when `RAILWAY_ENVIRONMENT=production` or `RAILWAY_PUBLIC_DOMAIN=owlette.app`, and `dev` otherwise. a host that is neither, such as a Vercel failover, needs `ROOST_ENV=prod` set explicitly, or it writes to the dev buckets.

the buckets stay private: uploads and downloads use presigned URLs, and version metadata URLs are derived from the manifests bucket and `R2_S3_ENDPOINT`.

`CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_R2_API_TOKEN` are inputs to `scripts/provision-r2.mjs`, not runtime variables. never set them on a deployment.

## URL configuration (required in production)

| variable | what it does |
|----------|-------------|
| `NEXT_PUBLIC_BASE_URL` | the public origin, such as `https://owlette.app`, used in email links and agent pairing links. unset, pairing links fall back to the server's own listen address and email links to `https://owlette.app` |
| `RAILWAY_PUBLIC_DOMAIN` | injected by Railway. read as a fallback origin and for roost environment detection |

`NEXT_PUBLIC_APP_URL` is a stray alias read only as one fallback for the health-check origin. use `NEXT_PUBLIC_BASE_URL` instead.

## cron (required for the scheduled endpoints)

| variable | what it does |
|----------|-------------|
| `CRON_SECRET` | authenticates every scheduled endpoint: sent as `X-Cron-Secret` to the eight `/api/cron/*` routes (`api-key-expiry`, `display-alerts`, `health-check`, `process-alerts`, `retention`, `status-ping`, `swoop-retention`, `talons`) and as `Authorization: Bearer` to `/api/hoot/escalation`. give each environment its own value. see [scheduled endpoints](/docs/setup/web-deployment#scheduled-endpoints) |

## swoop (required for remote desktop)

[swoop](/docs/dashboard/swoop) needs a signalling worker (`infra/swoop-signal`, a Cloudflare Worker you deploy yourself), an ed25519 signing key, a session master key and, for viewers behind strict routers, a Cloudflare TURN key. readers live in `web/lib/swoop/`.

| variable | required | what it does | without it |
|----------|:--------:|-------------|------------|
| `SWOOP_SIGNAL_URL` | yes | the signalling worker's origin, `https://` and no path, such as `https://signal.example.com`. the server turns it into the `wss://` room URL and adds it to the page's content security policy | every session start fails `503 swoop_not_configured`, and agents cannot fetch a session or a doorbell token |
| `SWOOP_SIGNAL_RING_SECRET` | yes | the shared secret the API sends to the worker to ring a machine's doorbell and to broadcast a kill. any string; the worker holds the same value | sessions still start, but each machine learns of a session from its polled command, 2 to 5 seconds later, and a kill falls back to a queued command |
| `SWOOP_JWT_PRIVATE_KEY` | yes | signs viewer, host and doorbell tokens (EdDSA). a PEM PKCS8 key, or the raw 32-byte ed25519 seed in base64 or base64url | every session start and lease renewal fails with `500` |
| `SWOOP_JWT_KID` | yes | the key ID stamped on every token, and the one the worker looks the key up by | as above |
| `SWOOP_JWT_PUBLIC_KEY` | yes | the public half of the signing key, sent to each machine's streamer. use base64url raw 32 bytes, the only form the worker accepts | agents cannot fetch a session bundle, so no session connects |
| `SWOOP_JWT_KID_PREVIOUS`, `SWOOP_JWT_PUBLIC_KEY_PREVIOUS` | rotation only | the outgoing key during a rotation, so tokens signed before it still verify. set both to an empty string outside a rotation | one key is active, which is the normal state |
| `SWOOP_SESSION_MASTER_KEY` | yes | the root every session's keys are derived from: the key the machine authenticates its connection details with, and each viewer's key. used as raw UTF-8 bytes, so a long random hex string works | every session start fails with `500` |
| `CLOUDFLARE_TURN_KEY_ID` | no | a Cloudflare Realtime TURN key ID | swoop offers STUN only (`stun.cloudflare.com`): fine on one network and through most routers, but two ends behind strict routers cannot connect |
| `CLOUDFLARE_TURN_KEY_API_TOKEN` | no | the bearer token that mints TURN credentials for that key, per session and per site | as above |

swoop's must-match keys are `SWOOP_JWT_PRIVATE_KEY`, `SWOOP_SESSION_MASTER_KEY` and `SWOOP_SIGNAL_RING_SECRET`: a session's start and its machine's bundle fetch can land on different origins. `SWOOP_SIGNAL_URL`, `SWOOP_JWT_KID` and `SWOOP_JWT_PUBLIC_KEY` must agree across origins too, and with the worker.

the worker holds its own copies as Wrangler secrets. it never sees the private key or the master key:

| API variable | worker secret |
|---|---|
| `SWOOP_SIGNAL_RING_SECRET` | `SWOOP_SIGNAL_RING_SECRET` |
| `SWOOP_JWT_KID`, `SWOOP_JWT_PUBLIC_KEY` | `SWOOP_JWT_KID`, `SWOOP_JWT_PUBLIC_KEY` |
| `SWOOP_JWT_KID_PREVIOUS`, `SWOOP_JWT_PUBLIC_KEY_PREVIOUS` | `SWOOP_JWT_KID_PREV`, `SWOOP_JWT_PUBLIC_KEY_PREV` (note the shorter name) |

generate a signing key pair, printed as base64url raw 32 bytes, on a machine you trust:

```bash
node -e "const c=require('crypto');const k=c.generateKeyPairSync('ed25519');console.log('private',k.privateKey.export({format:'der',type:'pkcs8'}).subarray(16).toString('base64url'));console.log('public ',k.publicKey.export({format:'der',type:'spki'}).subarray(12).toString('base64url'))"
```

**rotating the signing key**: give the worker the new key first, with the outgoing one in its `_PREV` slots, then the API, with the outgoing one in its `_PREVIOUS` slots. machines need nothing. after five minutes, the longest a host or doorbell token lives, clear both previous slots. the full runbook is in `infra/swoop-signal/README.md`.

server-side only. these connect `/api/cron/status-ping` to the hosted status page.

## never set on a deployment

the code reads these, but only for local development and tests. on a deployed origin each one is dangerous: some send every server read and write to the emulators, some switch off a security check.

- `FIREBASE_AUTH_EMULATOR_HOST`, `FIRESTORE_EMULATOR_HOST`, `NEXT_PUBLIC_USE_FIREBASE_EMULATOR` and the other `NEXT_PUBLIC_*_EMULATOR_HOST` variables
- `OWLETTE_E2E`, `E2E_DISABLE_RATE_LIMIT`
- `ALLOW_INSECURE_WEBHOOK_URLS`
- `ENABLE_CAPABILITY_ENFORCEMENT`, `ENABLE_RATE_LIMIT_ENFORCEMENT` (outage fallbacks; unset means enforced)
- `LEGACY_API_KEY_BYPASS_ENABLED`, `LEGACY_API_KEY_ALLOW_HASH_LIST`

## security notes

- **never commit** `.env.local` to git
- **use your host's variable store**, such as Railway's variables tab, which encrypts values at rest
- **`NEXT_PUBLIC_*` is public.** the prefix puts the value in every visitor's browser, so it carries only public configuration: Firebase client settings, the base URL, the Sentry DSN, the Turnstile site key and the App Check key. a secret never gets the prefix
- **rotate secrets deliberately.** know what each one breaks first: `SESSION_SECRET` signs everyone out, `CRON_SECRET` voids the unsubscribe links already sent, and a must-match key has to change on every origin at once
- **keep environments apart.** use a separate Firebase project, worker and set of secrets for development and production
